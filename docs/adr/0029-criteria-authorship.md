# ADR-0029: 審査される側が基準を書き換えたら承認を止める — 四眼原則を質問集合に掛けるのではなく

- ステータス: 承認済み
- 日付: 2026-09-12

## コンテキスト

[ADR-0022](0022-competency-question-sets.md) 決定6 はこう書いて終わっていた。

> **ただしこれは「書き換えを防ぐ」仕組みではなく「書き換えが見える」仕組みで
> ある。** ロールは階層なので、**`owner` は基準を書き換えて自分で承認できる。**
> (中略)質問集合にも四眼原則を掛けるべきかは未解決として残す

これが `P2B-16` である。そして CLAUDE.md の**不変条件14** は
「**受け入れ基準を、その基準で審査される側が書き換えられてはならない**」と
宣言している。**宣言はあるが、強制されていない。**

不変条件11 が名指しした形(「強制していない」を「強制している」と誤認させる)
そのものである。

### 四眼原則は既にあるが、この穴は塞いでいない

[ADR-0014](0014-namespace-rbac.md) 決定4 の四眼原則は
**「publish した主体は approve できない」**である。そこで残る経路を数えると:

| # | 経路 | 四眼原則は止めるか |
|---|---|---|
| 1 | 著者 P が版を書き、基準を緩め、自分で承認 | **止める**(P == approver) |
| 2 | **著者 P が版を書き、基準を緩め、同僚 C が承認** | **止めない** |
| 3 | 基準を先に定めた owner が、他人の版を承認 | 止めない(**これは正常な統制である**) |

**塞がっていないのは 2 だけ**である。しかも 2 は
「一人が全部やる」形ではないので四眼原則の考え方では捉えられない —
**問題は「審査される成果物の著者が、その合格条件を書いた」**ことにある。

そして 3 は止めてはいけない。名前空間の責任者が基準を定め、他人の成果物を
その基準で審査するのは、統制の**あるべき姿**である。

## 決定

### 1. 四眼原則を質問集合そのものには掛けない

「質問集合にも publish → submit → approve のライフサイクルを付ける」案を
採らない。

- **機構が 2 倍になる。** 状態・遷移・権限・監査をもう一組作ることになる
- **最初の改訂を誰が承認するのかが決まらない。** 基準が無い状態では
  「基準を満たす」という判定ができない
- **そして 2 の経路を塞がない。** 著者 P が改訂を出し同僚 C が承認し、
  そのあと C が版も承認すれば、条件は満たされるのに実態は同じである

### 2. `approve` が「審査される側が基準を書き換えた」ことを拒否する

不変条件14 を**強制する**。`approve` は次の条件で 422 を返す。

```
有効な質問集合の改訂の created_by == その版の created_by
  かつ
有効な質問集合の改訂の created_at >= その版の created_at
```

**時刻の境界は版の `created_at`(= publish した時刻)である。** 版の内容は
publish の時点で固定される(不変条件7)ので、著者はそこで合否を知っている。
**その後に基準を触るのが疑わしい窓**である。submit の時刻ではない —
publish から submit までの間の書き換えも同じ性質を持つ。

**基準が「緩くなった」かどうかは判定しない。** 緩めたのか締めたのかを
機械的に決めるには、改訂前後の基準で同じ版を評価して比べる必要があり、
そのうえで「緩い」の定義も要る。**測れないものを条件に入れない** —
規則は「審査される側が基準を書かない」であって、方向は問わない。

### 3. この検査は `require_two_person_approval` に従う

四眼原則が無効な名前空間ではこの検査も無効になる。

**新しいスイッチを作らない。** ADR-0014 決定4 が四眼原則を名前空間ごとの
設定にした理由は「運用者 1 人のデプロイ(postdeploy が同梱サンプルを
publish → submit → approve する経路)が動かなくなる」ことだった。
**この検査はまったく同じ制約を受ける** — 運用者 1 人なら、版を書いた人が
基準も書く。

スイッチを別に作ると、**片方だけ切って「四眼原則を有効にしたつもり」に
なれる**。1 つにまとめておけば「四眼原則が有効」の意味が 1 つで済む。

### 4. `platform-admin` もこれを飛び越えられない

不変条件12 の理由がそのまま当てはまる。管理者が飛び越えられるなら、
**四眼原則が「管理者以外への制約」に成り下がり、規制対応の文脈で意味を失う**
(ADR-0014 決定5)。実装上は既存の四眼原則の判定と同じ位置に置くので、
`platform-admin` の分岐が入る余地がない。

### 5. 逃げ道は「別の主体が基準を再確認すること」

止まったときの対処は、**別の主体が新しい改訂を出す**ことである。
内容が同じでもよい(改訂は不変で、`reason` が必須である)。

- 「基準を確認した」という**別の主体の行為が記録される**
- 元の改訂は消えない(改訂の系列は追記専用)
- 内容が同じなら、審査の結果も変わらない

**基準を消させるのではなく、基準に別の主体の署名を付けさせる。**
これが「防止」と「可視化」の間の正しい位置である — 基準を変えることは
禁じないが、**変えた人が審査もすることを禁じる**。

### 6. 事実の検出と、止めるかの判断を分ける

「著者が基準を書き換えた」という**事実の検出**は常に行い、
**止めるかどうか**だけを決定3 の設定で分岐させる。

そのため、レビュー用の口
(`POST /namespaces/{ns}/versions/{v}/questions/run`)は
**四眼原則が無効な名前空間でもこの事実を返す**。ADR-0022 決定6 の
「防止ではなく可視化」は、防止が入った後も**可視化として残す**価値がある —
四眼原則を切っている運用者にも、何が起きたかは見えるべきである。

### 7. どの改訂で通ったかは既に監査に残っている

ADR-0022 決定8 で実装済みである(`approved` の `reason` に
「質問集合の改訂 N の M 件すべてに合格」が入る)。**ここで足すものは無い。**

**確認しておく理由**は、決定2 の 422 が「承認されなかった」記録を残さない
ためである。承認が止まったことは `audit_events` に残らない(記録するのは
起きた決定だけである)。**基準の改訂自体は `questions-revised` として
残っている**ので、後から「この改訂が承認を止めた」は改訂の記録と版の
`created_at` から辿れる。

## 検討した代替案

### 「同僚 C が承認した」ことで十分とする(現状維持)

**却下。** ADR-0022 決定6 の立場である。改訂は不変で、`reason` は必須で、
減った質問は監査に出る。**見えている。**

却下理由: **見えていることと、承認者が見ることは違う。** 承認者は
「質問に全部合格した」という結果を見る。その基準が**この版のために書き換え
られた**ことは、監査証跡を別に引かなければ分からない。そして
**不変条件14 はそれを「してはならない」と宣言している** — 宣言を強制しない
ままにするのは、このリポジトリが最も避けたい形である。

### 承認者が基準の改訂を触っていたら止める(承認者側で判定する)

**却下。** 経路 1 を塞ぐが、**四眼原則が既に塞いでいる**(著者 == 承認者)。
経路 2(著者が基準を書き、別人が承認)は塞がらない。**塞ぐべき穴に効かない。**

### 基準が緩くなった改訂だけを止める

**却下(決定2)。** 締める方向の改訂は止めなくてよい、という直感は分かる。

却下理由: **緩くなったかを機械的に判定できない。** 改訂前後の基準で同じ版を
評価して比べる実装は書けるが、(a) 評価は予算付きで未評価になりうる
(ADR-0022 決定5)、(b) 「質問が減った」と「質問が緩くなった」は別物
(同じ件数でクエリを書き換えれば緩められる)、(c) 判定できなかった場合の
扱いを決めるとまた同じ問題に戻る。**測れないものを条件に入れない。**

### 版の `submitted` 時刻を境界にする

**却下(決定2)。** レビューに出した後の書き換えだけを問題にする案。

却下理由: **publish から submit までの間の書き換えを見逃す。** 版の内容は
publish で固定されるので、著者はその時点で合否を知っている。窓を狭める
理由が無い。

### 質問集合を版ごとに持たせる

**却下。** ADR-0022 決定2 が既に却下している — 版ごとにすると
**新しい版が自分の合格条件を自分で書き換えられる**。ここで蒸し返す新しい
事実は無い。

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **正当な改訂でも止まることがある。** 版の著者が、その版を publish した後に
  基準を改訂すると、その版は止まる。対処は決定5(別の主体が改訂を出す)
- **四眼原則が無効な名前空間では強制されない**(決定3)。事実は見えるが
  止まらない
- **「緩くなったか」は見ない**(決定2)。締める改訂でも止まる
- **承認が止まったこと自体は監査に残らない。** 起きた決定だけを記録する
  設計なので(決定7)

### 得られるもの

- **不変条件14 が宣言から強制になった。** 「してはならない」と書いてあるものが
  実際に止まる
- **四眼原則の穴のうち、塞ぐべき 1 つを塞いだ**(経路 2)。塞いではいけない
  経路 3(責任者が基準を定め、他人の版を審査する)は通る
- **スイッチが増えていない**(決定3)。「四眼原則が有効」の意味が 1 つで済む
- **四眼原則を切っていても事実は見える**(決定6)

### 影響を受ける他の決定

- [ADR-0022](0022-competency-question-sets.md) 決定6 — 補記を追加した
  (「防止ではなく可視化」から「特定の経路だけ防止する」へ)
- [ADR-0014](0014-namespace-rbac.md) 決定4 — `require_two_person_approval` が
  四眼原則に加えてこの検査も制御するようになった
- CLAUDE.md 不変条件14 — 宣言から強制になった
