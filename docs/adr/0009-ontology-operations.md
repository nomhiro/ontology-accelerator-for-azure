# ADR-0009: オントロジーの運用 — 決定可能性による分業と、縮められる設計

- ステータス: 承認済み
- 日付: 2026-09-01

## コンテキスト

[ADR-0006](0006-ontology-versioning-and-audit.md) は「オントロジーをどう記録するか」を決めた。しかし**記録した後どう運用し続けるか**は、どの ADR も扱っていない。この欠落は、次の問いに答えられないことで露出した。

- **「用語が増え続けたとき、誰がそれを理解し続けるのか」** — 全体を把握できる人がいなくなった時点で、オントロジーは意思決定の根拠として使えなくなる
- **「矛盾する内容が入ったとき、誰が何を根拠に判断するのか」** — 人が全部見るのか、AI が判断するのか、機械的なテストで担保するのか
- **「使われなくなった用語はどうなるのか」** — 追加しかできない仕組みは、必ず腐る

### 実装を検証して判明した事実

この ADR を書く契機は、実装の検証で見つかった具体的な欠陥である。

**1. システム自身が矛盾を作る(Critical)。** ローダは `approved/<namespace>/` の全 TTL をそれぞれの名前付きグラフへ読み込み、`tdb2:unionDefaultGraph = true` のため**既定グラフが全バージョンの和集合になる**。同一用語に矛盾する定義を持つ 2 版を公開して実測した結果:

```
公開: 1.0.0 (年間取引額が上位 20%) / 2.0.0 (年間取引額が上位 10%)
GRAPH 句なしのクエリ → 両方が返る (2 件)
載っているグラフ: urn:ontology:graph/<ns>/1.0.0, urn:ontology:graph/<ns>/2.0.0
```

ADR-0006 は「ストアに載せるバージョンを保持ポリシーで制御する(最新版 + 参照中のバージョン + 直近 N 版など)」と決定しているが、**実装が存在しない**。エージェントが `GRAPH` 句を書かなければ新旧の定義を同時に受け取る。これは「AI に正しい定義を渡す」という製品の中核目的に直接反する。

**2. 判断の道具が無い。** `rdflib` は `packages/core` の依存に入っているが**使用 0 ファイル**で、TTL は解析されずに Blob(正本)へ書かれる。`pyshacl` / SHACL / 推論 / 整合性チェックはいずれも 0 ファイル。

**3. 「なぜ」を運ぶ器が使われていない。** `audit_events` に `reason` と `diff` の列があるが、`publish` は渡していない(`namespace` / `action` / `actor` / `subject` のみ)。監査を**読み出す API も存在しない**。ADR-0006 §4 が設計したアクセスログは実装 0 行。

**4. 意味的な競合を検出しない。** `PublishRequest` は `turtle` と `version` だけで、基準バージョンを渡す口が無い。2 人が同じ版から編集して公開すると、後の版に前の変更が含まれない(lost update)。検出も警告もされない。

**5. 廃止・責任者・健全性の概念が無い。** ドキュメント全体を走査して `廃止` / `deprecation` / `所有者` / `利用状況` / `認知` はいずれも 0 件。

### 参照実装(AWS 版)も運用フェーズを扱っていない

[ADR-0008](0008-independent-implementation.md) の対象である AWS Context Ontology Accelerator を調査した(公開リポジトリのファイル一覧 1394 件、公式ドキュメント、データモデル定義)。

- 公式のライフサイクルは **Create / Induce / Upload / Fetch / Update / Validate / Delete** の 7 つ。`Update` は「メタデータの修正または再アップロード」で改訂の概念が無く、`Deprecate` が無い(引退は削除)
- データモデルの `version` は**単一の可変フィールド**。`revision` / `history` / `snapshot` / `supersede` は 0 件で、レジストリのエントリは `update_item` で書き換える
- `review` に該当する実装はすべて**ソーススキーマ(テーブル・カラム)のレビュー**。`approve` も**データソースの承認**
- ただし提案(proposal)段階では `original`(LLM の出力)と `latest`(人の編集後)の**2 枠**を保持しており、受理前のレビューは手厚い。`Validate` は受理前に整合性・品質チェックを実行する
- 公式の Best Practices は「まず induction でベースラインを生成し、それから refine する」

**結論: 提案 → レビュー → 受理までは充実しているが、受理後の進化は非対応。**つまり運用フェーズの設計は、この分野で広く未解決である。ロードマップを参照実装から写すことはできない。

## 決定

**運用フェーズを、Phase 2 の第 2 の柱として明示的に設計する。** 以下 8 点を決定とする。

### 1. 決定可能性で分業する(この ADR の中心原則)

| 問いの性質 | 誰が決めるか | 理由 |
|---|---|---|
| **形式的に決定可能**(構文、プロファイル適合、論理的整合性) | 機械が確定的に判定。ブロッキング | 健全かつ完全な決定手続きが存在する。確率的なモデルを使うのは格下げ |
| **合意済みの規約**(命名規則、必須項目、想定質問に答えられるか) | テストとして機械が実行 | 一度合意すれば人が毎回見る必要がない |
| **権限を要する判断**(この定義が自社にとって正しいか) | 人間が決める。責任者にルーティング | ボトルネックは知能ではなく説明責任。AI は責任を負えない |

**論理的矛盾を人が目で確認する設計にはしない。** 推論器の仕事である。

### 2. 既定グラフには最新の承認済み版のみを載せる

上記 Critical の対処。`unionDefaultGraph` に全バージョンを載せる現状をやめ、**既定グラフは常に単一の版**を指すようにする。旧版は名前付きグラフとして `GRAPH` 句で明示的に参照する場合にのみ見える。

併せて ADR-0006 が決定済みの**保持ポリシー**(ストアに載せる版の制御)を実装する。

### 3. オントロジーは縮められなければならない

**廃止を追加と同格の一級操作として扱う。**

- 用語単位で `owl:deprecated` を立て、後継への参照(`dcterms:isReplacedBy` 相当)を持たせる
- **IRI を削除も再利用もしない。** 廃止済みとして残す
- 廃止された用語を参照するクエリには、API 層で警告を返す

追加しかできないオントロジーは必ず腐る。この原則を ADR-0006 の「不変リビジョン」の裏側として同格に置く。

### 4. 名前空間と用語に責任者を持たせる

`created_by` / `approved_by` は「その時の行為者」であって現在の責任者ではない。**標準の責任者(owner)**を別に持ち、責任者のいない用語を健全性指標で可視化する。責任者は差分レビューのルーティング先になる(決定 1 の第 3 行)。

### 5. 健全性を測る

名前空間ごとに次を集計して提示する。測っていないものは、致命的になるまで見えない。

- 用語数
- 一定期間(既定 90 日)一度も参照されていない用語の割合
- 責任者が未設定の用語
- 一定期間再承認されていない用語
- SHACL 違反の件数
- 未射影(`projected_at IS NULL`)の版

原資料は ADR-0006 §4 のアクセスログである。**アクセスログの実装は、この指標のための前提として Phase 2 に入れる。**

### 6. 想定質問を実行可能なテストにする

「このオントロジーは『ロットのリコールで影響を受ける顧客』に答えられなければならない」を **SPARQL テストとして書き、CI で回す**。オントロジーが目的を果たしているかを主観なしに判定できる。

品質スコア型の評価は採らない(後述の代替案)。

### 7. 「なぜ」を参照時に返す

`audit_events` の `reason` と `diff` を実際に書き、**参照時に一緒に返す**。用語を引いた人やエージェントが「誰がいつ、なぜこう決めたか」を同時に得られる。列はすでに存在するので、これは最も安い施策である。

意味的差分(どのクラスが追加・削除・移動され、どの公理が変わったか)をテキスト差分ではなく構造として計算し、`diff` に格納する。

### 8. 領域をまたぐ矛盾は統合せずマッピングする

営業の「優良顧客」と経理の「優良顧客」が違うとき、**一つに統合しない**。名前空間を分けたまま、**マッピングを明示的な成果物として管理**する(SKOS の `closeMatch` / `exactMatch`、または `owl:equivalentClass`)。マッピング自体がレビュー対象になるので、意見の相違が消されずに記録される。

## 根拠

### 決定可能なものに人を使うのが最大の浪費

オントロジー運用が失敗する典型は「レビュー疲れ」である。人の判断力は有限で、それを構文エラーや論理矛盾の発見に使うと、**本来人しか判断できないこと(この定義は自社にとって正しいか)に回す余力が無くなる**。

推論器(ELK / HermiT)は充足不能クラスと矛盾を exact に検出する。SHACL は規約違反を exact に検出する。これらを CI に置けば、人が見る対象は「形式的には正しいが、業務的に妥当か分からないもの」だけに絞られる。

この理由から、**OWL 推論器を Phase 4 から Phase 2 へ前倒しする。**「最も安い正しさの担保」だからである。

### 縮められない仕組みは、時間が敵になる

不変リビジョンは「過去を消さない」ための設計であり、正しい。しかしそれだけを原則に置くと、**理解すべき対象が単調増加する**。ADR-0006 は増やす方向の原則しか持っていない。

生物医学オントロジー(GO、SNOMED CT、Uberon)は例外なく廃止のライフサイクルを持ち、IRI の削除と再利用を禁じている。これは長期運用された分野が到達した結論であり、従う理由がある。

### レビューは差分に、判断は責任者に

全体をレビューする設計は、規模とともに必ず破綻する。**差分だけを見て、その領域の責任者が判断する**形にすれば、レビュー負荷はオントロジーの大きさではなく変更の量に比例する。

責任者を持たせる理由はもう一つある。**責任者のいない用語は誰も保守しない。** 健全性指標で可視化する対象として、これが最も重要である。

### 想定質問テストが「評価」の実務的な形

オントロジーの品質評価には学術的な枠組み(OQuaRE、FAIR メトリクス、OBO Foundry Dashboard 等)が存在するが、**リリースを止める基準として使われることは稀**である。抽象度が高く、点数が下がった理由が行動に結びつかない。

一方、想定質問(Competency Questions)を SPARQL として書いておけば、失敗したときに何を直すべきかが自明である。テストが落ちるという形で運用に組み込める。

## 検討した代替案

### AI に矛盾の判断を委ねる

**却下。** 論理的矛盾は決定可能であり、推論器が健全かつ完全に判定する。ここに確率的なモデルを使うのは格下げである。

業務的な妥当性の判断については、ボトルネックが知能ではなく**説明責任**にある。「この定義でよい」と決めた主体が後から問われたときに答えられる必要があり、AI は責任を負えない。規制産業での採用可否を左右する要件(ADR-0006 のコンテキスト)と正面から衝突する。

**ただし AI を使わないという決定ではない。** 候補生成、階層内の位置の提案、差分の自然言語要約、疑わしい箇所の指摘は、いずれもレビュー負荷を実際に下げる。**「下書きと選別は AI、決定は人と機械的なテスト」**という切り分けを採る。

### 品質スコアでリリースをゲートする

**却下。** 上記のとおり、点数は行動に結びつかない。想定質問テストと SHACL という**落ちた理由が自明な形**を採る。

健全性指標(決定 5)は**可視化のためであってゲートではない**。この区別を意図的に保つ。

### 全社で単一のオントロジーを作る

**却下。** 領域ごとに意味がずれた言葉を一つに統合する試みは、合意形成のコストが規模の二乗で増える。名前空間による分離(ADR-0001 のデータセット単位の物理分離)を保ち、**マッピングで繋ぐ**(決定 8)。

### 廃止を扱わず、削除で済ませる

**却下。** AWS 版はこの方式である(引退 = 削除)。しかし削除すると、**過去にその用語を参照した判断が説明不能になる**。ADR-0006 の「3 か月前の判断はどの版に基づいていたか」に答えられなくなり、監査可能性という中核価値を失う。

### 運用の設計を Phase 3 以降に送る

**却下。** Phase 2 で承認フローとバージョニングを実装する。**そのときに廃止と責任者を設計に入れておかないと、後から入れるのは移行を伴う**(既存の用語すべてに責任者を割り当て直す作業になる)。同時に設計するほうが安い。

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **Phase 2 が重くなる。** 承認フロー・LLM 生成に加えて、廃止・責任者・健全性・想定質問テスト・推論器が入る。Phase 2 の完了条件を「AI が作れる」と「運用し続けられる」の 2 本柱として明示し、後者を落とさない
- **推論器の前倒しで Java 依存が Phase 2 に来る。** [ADR-0005](0005-reasoner-boundary.md) は「SHACL は pyshacl で完結するため Java 依存は Phase 4 まで発生しない」としていた。この判断を**変更する**。ELK(Apache-2.0)を Container Apps Job として Phase 2 で導入する
- **責任者の割り当ては人手の作業である。** 自動化できない。導入時の負担として README に明記する

### 得られるもの

- 人の判断力を、人しか判断できないことに集中できる
- オントロジーが縮む経路を持つため、時間が敵にならない
- 参照実装が扱っていない領域であり、**「初回構築のアクセラレータ」ではなく「運用できる基盤」**として位置づけられる

### 影響を受ける他の決定

- **[ADR-0005](0005-reasoner-boundary.md)**: 推論器の導入時期を Phase 4 → Phase 2 に変更する。ADR-0005 に補記を追加する
- **[ADR-0006](0006-ontology-versioning-and-audit.md)**: 「不変リビジョン」の裏側として廃止のライフサイクルを追加する。保持ポリシーの実装を Phase 2 の必須項目とする
- **[ADR-0002](0002-triple-store-as-rebuildable-projection.md)**: 既定グラフに載せる版を単一にする変更は、ローダとアセンブラの生成に影響する

### 未解決のまま残す問い

この ADR は方針を決めるものであり、次は未決である。

- 責任者の粒度(名前空間単位か、用語単位か、その両方か)
- 廃止された用語を参照するクエリへの警告を、どの層でどう返すか(SPARQL の結果に警告を混ぜられない)
- 意味的差分の計算方法(既存ツールを使うか、rdflib で自作するか)
- 定義と実データの乖離検出(SHACL 形状を定期的に実データへ当てる案があるが、Ontop 経由の連邦クエリが前提になるため Phase 3 以降)
