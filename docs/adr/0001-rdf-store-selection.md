# ADR-0001: RDF ストアの選定

- ステータス: 承認済み
- 日付: 2026-08-28

## コンテキスト

本プロジェクトの中核要件は、承認済みのビジネスオントロジーを **W3C 標準(RDF / OWL / SPARQL 1.1 / SHACL / R2RML)に忠実な形**で保存し、AI エージェントに提供することである。AWS 版では Amazon Neptune がこの役割を担っており、Neptune は RDF/SPARQL をネイティブにサポートしている。

Azure 版を設計するにあたり、まず前提として確認すべき事実がある。

**Azure にはマネージドな RDF トリプルストアが存在しない。**

- **Microsoft Fabric Graph** — グラフ機能を提供するが、モデルは **LPG(Labeled Property Graph)** であり、公式ドキュメントが RDF 非対応であることを明記している
- **Azure Cosmos DB (Gremlin API)** — 同様に LPG であり、Gremlin(Apache TinkerPop)を用いる。RDF / SPARQL には対応しない(公式明記)

したがって「マネージドサービスを使う」という選択肢が最初から存在しない。自前でトリプルストアをコンテナとして運用するか、W3C 標準路線そのものを放棄するかの二択になる。

さらに本プロジェクトには次の要件がある。

- **名前空間(テナント)ごとのデータ分離**が必要
- ストアは Azure Container Apps 上で動かす前提であり、**起動が速いことに価値がある**([ADR-0002](0002-triple-store-as-rebuildable-projection.md) の射影設計では、レプリカ起動時に毎回グラフを再構築する)
- OSS 利用者が**既存の RDF ストアを持ち込める**ようにしたい

## 決定

**既定のトリプルストアとして Apache Jena Fuseki を採用する。**

- Fuseki を Azure Container Apps 上のコンテナとして、**internal ingress のみ・読み取り専用**で運用する
- 名前空間の分離は **名前空間ごとの Fuseki データセット**で実現する
- **SPARQL 1.1 Protocol をハード境界とする**。アプリコードは Fuseki 固有の機能に依存せず、`SPARQL_ENDPOINT` 環境変数を差し替えるだけで既存の GraphDB / Stardog / Amazon Neptune 等を利用できるようにする
- Fuseki 固有の操作(データセット管理などの admin API)は `packages/core` の SPARQL クライアント層に閉じ込める
- **Oxigraph を代替候補として維持する**(下記「検討した代替案」参照)

## 根拠

### なぜ Microsoft Fabric Graph ではないのか

**Fabric Graph は RDF に対応していない**(公式ドキュメントが明記)。モデルが LPG であるため、本プロジェクトが提供したい価値の中核が成立しない。

- **OWL による推論**ができない。クラス階層、`owl:equivalentClass`、プロパティ特性(`owl:TransitiveProperty` 等)といった、オントロジーの本質にあたる意味論を表現できない
- **SPARQL が使えない**。エージェントに提供するクエリインターフェースが標準ではなくなり、「W3C 標準に忠実」という設計目標が崩れる
- **SHACL による制約検証**ができない
- **IRI による大域的な識別と語彙の再利用**ができない。既存のオントロジー(PROV-O、Dublin Core、業界標準語彙)を取り込めない
- **監査可能性**を支える名前付きグラフの概念が標準化された形で存在しない

LPG に載せるには、オントロジーを LPG へ「変換」する独自レイヤーを書くことになる。それは(a)標準からの逸脱そのものであり、(b)ラウンドトリップで意味論が失われ、(c)独自変換仕様の保守コストを恒久的に抱えることになる。**「W3C 標準に忠実」という設計目標を放棄しない限り、Fabric Graph は候補にならない。**

同じ理由で **Cosmos DB (Gremlin API)** も候補にならない。RDF 非対応は公式に明記されている。

なお、これは Fabric Graph / Cosmos DB Gremlin が劣っているという主張ではない。LPG が適した用途(高速なパストラバーサル、プロパティ中心のグラフ分析)では優れた選択肢である。**本プロジェクトの要件が RDF セマンティクスそのものである**ため適合しない、というだけである。

### なぜ Fuseki なのか

自前運用が前提になった時点で、候補は OSS のトリプルストアに絞られる。Fuseki を既定とする理由は 2 点である。

1. **名前空間分離をデータセット単位で実現できる** — Fuseki は複数データセットをホストでき、admin API でデータセットを動的に作成・削除できる。これにより、**任意 SPARQL のクエリ書き換えによるテナント分離という危険な実装を避けられる**。クエリ書き換えによる分離は、SPARQL の表現力(サブクエリ、`GRAPH` 句、`SERVICE` 句、プロパティパス)を前にすると迂回されやすく、セキュリティ境界として信頼できない。物理的にデータセットを分けるほうが検証可能である
2. **OWL / SHACL 周辺の Jena エコシステムが厚い** — `tdb2.tdbloader`(バルクロード)、Jena の推論サポート、ELK など Java 推論器との接続、SHACL 実装、RIOT によるフォーマット変換など、必要な周辺ツールが揃っている。とくに射影設計では `tdb2.tdbloader` によるバルクロード性能が起動時間に直結する

### なぜ「持ち込み可能」にするのか

Azure にマネージド RDF ストアがないという制約は、逆に言えば**ストアが差し替え可能であるべき**ことを示している。GraphDB や Stardog をすでに運用している組織、Neptune を使い続けたい組織にとって、本プロジェクトの価値は「オントロジーを AI で作り、承認し、エージェントに供給するワークフロー」の部分にある。ストアを強制する必要はない。

SPARQL 1.1 Protocol は W3C 勧告であり、実装間の互換性が実用的な水準にある。これを境界に据えることで、ストア選定の誤りが致命的にならない。

## 検討した代替案

### Microsoft Fabric Graph

**却下。** RDF 非対応(公式明記)。上記「根拠」で詳述。LPG への独自変換レイヤーを書くコストと意味論の損失が、マネージドであることの利点を大きく上回る。

### Azure Cosmos DB (Gremlin API)

**却下。** 同じく RDF 非対応(公式明記)。加えて Gremlin API はグラフの規模に対する RU 課金モデルであり、コスト予測が難しい。

### Oxigraph

**代替候補として維持。** Rust 実装の軽量なトリプルストアで、MIT / Apache-2.0 のデュアルライセンス。

- **利点**: **起動が速い**。[ADR-0002](0002-triple-store-as-rebuildable-projection.md) の射影設計ではレプリカ起動時に毎回グラフを再構築するため、起動時間の短さは直接的な利点になる。メモリフットプリントも小さく、ACA の小さいレプリカに収まりやすい
- **却下理由(既定としては)**: (a)複数データセットのホスティングと動的な管理 API が Fuseki ほど成熟しておらず、名前空間分離の実装が重くなる、(b)OWL / SHACL 周辺のエコシステムが薄い

Phase 1 のスパイクで Fuseki の再構築時間が許容できないと判明した場合、**Oxigraph への切り替えを第一の代替案とする**。射影設計により切り替えコストは低い(正本は Blob + PostgreSQL 側にあるため、ストアを入れ替えても失うものがない)。

### Virtuoso Open Source

**却下。** GPL であり、Apache-2.0 の本プロジェクトとライセンス非互換。検討対象外([`../third-party-licenses.md`](../third-party-licenses.md))。

### GraphDB / Stardog(商用ライセンス)

**既定としては却下、持ち込み対象として支援。** いずれも成熟した RDF ストアだが、商用ライセンスが必要であり、OSS として「`azd up` で誰でもデプロイできる」という要件を満たさない。ただし `SPARQL_ENDPOINT` の差し替えで利用できるようにすることで、既存利用者を排除しない。

### PostgreSQL 上に自前でトリプルテーブルを実装する

**却下。** マネージドサービスで完結する魅力はあるが、SPARQL 1.1 の完全な実装(プロパティパス、`OPTIONAL` の意味論、集約、部分グラフマッチング)を自作することになる。実装量と正しさのリスクが、得られる運用の単純さに見合わない。なお Ontop VKG は「RDB を仮想グラフとして見せる」異なるアプローチであり、これは Phase 3 で**併用**する(実データを実体化しないため、オントロジーの保存先とは役割が違う)。

### AKS + Managed Disk 上で運用する

**Phase 1 では却下、昇格パスとして案内。** Managed Disk はブロックストレージであり TDB2 の mmap とファイルロックに適合する。永続化の観点では最も素直な構成である。しかし AKS はクラスタ自体の運用コスト(コントロールプレーン、ノード、アップグレード)が発生し、「`azd up` 一発で評価できる」という要件と、月 $39〜61 のコスト目標に反する。**大規模利用者向けの昇格パスとして [`../architecture.md`](../architecture.md) で案内する。**

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **マネージドサービスの利点を失う** — バックアップ、パッチ適用、可用性、スケーリングを自分で設計する必要がある。この負担の大部分は [ADR-0002](0002-triple-store-as-rebuildable-projection.md) の射影設計で相殺する(バックアップは正本側の責務になり、ストアは失っても再構築できる)
- **Fuseki が常時 1 レプリカ稼働する** — scale-to-zero できないため、minimal 構成でも月 $10〜22 が固定費になる(詳細は [`../cost-estimate.md`](../cost-estimate.md))。ACA の idle/active 判定により最悪 8 倍に上振れするリスクがあり、Phase 1 で実測する
- **JVM のメモリ要件** — Fuseki は JVM 上で動くため、Oxigraph のような Rust 実装よりメモリフットプリントが大きい。推奨構成を 1 vCPU / 2 GiB としているのはこのためである
- **クラスタリング機構がない** — Fuseki 単体には水平スケールの仕組みがない。Phase 1 は単一レプリカとする

### 得られるもの

- **W3C 標準に忠実な実装が可能になる** — OWL 推論、SHACL 検証、SPARQL、既存語彙の再利用、名前付きグラフによるバージョン固定がすべて標準の枠内で成立する
- **ストア選定の可逆性** — SPARQL 1.1 Protocol を境界にしたことで、本 ADR の判断が誤りだった場合の修正コストが低い。Oxigraph への切り替え、あるいは利用者による持ち込みが、アプリコードの変更なしに可能である
- **テナント分離が検証可能** — データセット単位の物理分離であり、クエリ書き換えのような「抜け道を探す攻撃者との競争」にならない

### 影響を受ける他の決定

- [ADR-0002](0002-triple-store-as-rebuildable-projection.md) — Fuseki を選んだことで、TDB2 の mmap 要件が Azure Files 上での運用リスクとなり、射影設計を採る動機になった
- [ADR-0005](0005-reasoner-boundary.md) — Jena エコシステム(Java)を前提にしたことで、OWL 推論器の選択肢が広がった
