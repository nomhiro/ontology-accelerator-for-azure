# ADR-0044: レビュー画面は「計算できなかった」を「変更が無い」と同じ見た目にしない

- ステータス: 承認済み
- 日付: 2026-09-13

## コンテキスト

`P2A-03`(Web でのレビュー・承認フロー)と `P2A-04`(グラフ可視化)は、
バックログで**「見た目と操作の設計(人の好み)。ADR で決めるより実物を見て
決めるほうが早い」**として後回しにされていた。

その判断は半分正しい。配色・余白・コンポーネントの選び方は好みである。

**しかし好みではない部分がある。** この製品のレビュー画面は、
**人が「承認する」と決める場所**である。API が既に知っている事実を画面が
落とすと、**落としたことは画面に出ない**。

このリポジトリは同じ形の判断を何度も積んできた。

| どこ | 何を拒んだか |
|---|---|
| [ADR-0016](0016-semantic-diff.md) 決定5 | 空白ノードが多すぎたら差分を**計算せず「計算できなかった」と返す** |
| [ADR-0034](0034-construct-describe.md) 決定4 | RDF を切り詰めない(**封筒が無い**ので切り詰めたと名乗れない) |
| [ADR-0037](0037-deprecated-target-metric.md) | 廃止の件数と**「調べられなかった」件数は 2 つで 1 組** |
| [ADR-0039](0039-ask-row-count.md) | 束縛が無い結果に**行数 0 を作らない** |
| [ADR-0043](0043-ontology-proposal.md) 決定4 | **何回目で通ったか**を記録する |

**API がこれだけ丁寧に区別してきたものを、画面が最後に潰す**ことがありうる。
それがこの ADR の主題である。

### 決めるべきこと

1. **API が「分からない」と言ったとき、画面は何を見せるか**
2. **どの型を使うか**(生成された型は gitignore されている)
3. **承認できないとき、何を見せるか**
4. **差分の何を最も目立たせるか**
5. **グラフをどこから引くか。全部描けないときどうするか**
6. **判断をどこに置くか**(テストできる形にするため)
7. **認証をどうするか**

## 決定

### 1. 「計算できなかった」には専用の見た目を与える。空の差分と区別する

**これがこの ADR の中心である。**

[ADR-0016](0016-semantic-diff.md) 決定5 は、空白ノードが
`MAX_BLANK_NODES` を超えたら差分を**計算せず**、そう返すと決めた
(rdflib の正規化が空白ノード 1,000 個で 42 秒かかるため)。

画面が「追加 0 / 削除 0 / 変更 0」と表示したら、**レビュアは「変更が無い」と
読む**。実際には「**測っていない**」である。承認の判断が逆になる。

だから API の応答を 3 状態として扱う。

| API の応答 | 画面 |
|---|---|
| 差分が計算できた(変更あり) | 追加・削除・変更を出す |
| 差分が計算できた(変更なし) | **「変更はありません」と明記する** |
| **差分が計算できなかった** | **警告色の帯 + 理由 + 「承認の判断材料が揃っていない」** |

**3 番目のとき、承認ボタンは出すが警告を消さない。** 止めないのは、
計算できないことがレビュアの責任ではないからである
(ADR-0016 が「計算しない」を選んだのは性能上の判断であり、
その代償を承認の停止にすると、**大きなオントロジーは永久に承認できない**)。

### 2. Web は生成された型を使う。CI が生成して不整合を検出する

`openapi.json` と `apps/web/src/api/schema.ts` は **gitignore されている**
(生成物である)。したがって今の CI の web ジョブ(`pnpm build`)では、
**生成物を import した瞬間に型検査が落ちる**。

[ADR-0004](0004-schema-first-api.md) は手書きの型を明確に却下し、
受け入れるコストとして**「生成漏れによる不整合を CI で検出する仕組みが
必要」**と書いていた。**その仕組みは作られていなかった。** ここで作る。

- web ジョブに `uv` と生成ステップ(`just gen-api` 相当)を足す
- **`web` の paths-filter に API の経路を足す**

2 番目が重要である。今の `web` フィルタは `apps/web/**` だけなので、
**API を変えて Web の型が壊れても web ジョブが動かない**。生成元が変わったら
生成先を検査しなければ、検出の仕組みとして意味がない。

### 3. 承認できない理由を出す。無効なボタンだけにしない

四眼原則(不変条件12、[ADR-0014](0014-namespace-rbac.md) 決定5)により、
**自分が publish した版は自分では承認できない**。`platform-admin` でも
飛び越えられない。

無効化したボタンだけを出すと、レビュアは**壊れていると思う**。理由を書く。

| 状況 | 見せるもの |
|---|---|
| 自分が publish した版(四眼原則) | 「**あなたが公開した版です。** 別の主体が承認します」 |
| `in-review` ではない | 現在の状態と、次に可能な操作 |
| ロールが足りない | 必要なロール名 |

**「押せない」ことと「押してよいか分からない」ことを区別する。**

### 4. 差分で最も目立たせるのは「消えた用語」である

不変条件8(オントロジーは縮められなければならない)と
[ADR-0017](0017-deprecation-lifecycle.md) 決定2 により、
**現行版にあった用語を消した版は `approve` が 422 で拒否する**。

つまり**消えた用語は承認を止める**。レビュアが最初に見るべきものである。
追加された用語より上に、警告色で置く。

**`approve` が止めるのに画面でも目立たせるのは重複ではない。** 422 は
「押した後」に分かる。押す前に分かるほうがよい。

### 5. グラフは SPARQL で引く。`draft` は描けないと言う

**Turtle をブラウザで解析しない。** 理由が 3 つある。

1. **この製品の提供する口を使うべきである。** SPARQL エンドポイントは
   エージェントに提供しているものそのもので、画面が同じ口を使えば
   **画面が動くことがその口の検証になる**
2. パーサの依存(`n3` など)が増えない
3. **`draft` はストアに無い**([ADR-0010](0010-approval-and-projection.md)
   決定1)。SPARQL で引けば**引けないことが分かる**

3 番目は欠点ではなく**設計の可視化**である。生成された候補(`P2A-02`)は
`draft` なので、**グラフを描けない**。空のグラフを出すのではなく
「**`draft` は射影されていないため描けません。`submit` すると
名前付きグラフに載ります**」と言う。

**上限を超えたら「全部は描いていない」と言う**(`GRAPH_MAX_NODES`)。
ADR-0034 決定4 の「封筒が無いものを切り詰めない」の画面版である。
グラフには封筒があるので**切り詰めてよい。ただし黙ってはいけない。**

### 6. 判断は純粋関数に置く。コンポーネントは薄くする

**見た目は検証できないが、判断は検証できる。**

ブラウザを持たないので、描画結果は確かめられない。しかし

- 差分の 3 状態の判定(決定1)
- 承認できるか、できないなら理由(決定3)
- LLM 生成かどうかの判定(決定7)
- SPARQL の束縛からグラフ要素への変換と打ち切り(決定5)

は**すべて純粋関数**にできる。`vitest` を入れてここをテストする。

**コンポーネントは純粋関数の結果を並べるだけにする。** 判断が
コンポーネントの中の三項演算子に散ると、テストできなくなる。

### 7. LLM が生成した候補であることを最上部に出す

[ADR-0043](0043-ontology-proposal.md) 決定10 は、生成の出自
(モデル・デプロイ・API バージョン・**試行回数**)を
`audit_events.reason` に書くと決めた。

**レビュー画面はそれを最上部に出す。** 「人間のレビューを経ていない候補で
ある」という文字列が監査に入っているのだから、レビュアが最初に見るべき
ものである。

**試行回数も出す。** 1 回で通った候補と 3 回目でやっと通った候補は別物で、
後者は**モデルがこのスキーマを扱いかねている**信号である(決定4)。

### 8. 人が操作する経路では `reason` を必須にする

`submit` / `approve` / `reject` の `reason` は API では任意である
(`reject` だけ必須)。**自動投入(`postdeploy`)を壊さないため**に任意に
した(`P2B-08`)。

**画面では必須にする。** バックログが「人が操作する経路(Web UI、`P2A-03`)
では必ず書かせる」と約束していた分である。空の監査は説明にならない。

### 9. 認証は当面トークンの貼り付けにする。MSAL は `P2A-20`

`AUTH_MODE=disabled`(ローカル)ではトークンが要らない。デプロイ環境では
必要になる。

**MSAL を入れない。** 理由は ADR-0042 決定5 と同じ形である —
**SPA のリダイレクト URI はアプリ登録の変更を伴い、デプロイ窓なしに
検証できない**。「書いたが動かしていない認証」を残さない。

代わりに `az account get-access-token` で得たトークンを貼る口を置く。

- **メモリにしか持たない。** `localStorage` に書かない(XSS で持ち出される)
- 貼らずに 401 が返ったら、**理由と対処をその場に出す**

`P2A-20` として記録する。

## 検討した代替案

### 差分が計算できなかったことを小さな注記で済ませる

**却下(決定1)。** 画面が散らからない。

却下理由: **注記は読まれない。** 「追加 0 / 削除 0」という数字のほうが
目に入る。**数字を出さないか、警告と同じ強さで出すかの二択**であり、
数字を出して注記を添えるのは最も悪い(読み手が数字を信じる)。

### 生成された型をコミットする

**却下(決定2)。** CI に生成ステップを足さずに済む。

却下理由: ADR-0004 が**「生成物を手で編集しない」を規約にした**のは、
一度手が入ると再生成が破壊的になるためである。コミットすると
**手で直す誘惑が生まれる**(コンフリクトを手で解決するのは「手で編集」で
ある)。CI で生成すれば、**生成物は常に生成物のままになる。**

### Web の型を手書きする

**却下(決定2)。** ADR-0004 が既に却下している。Phase 2 の構造
(リビジョン・差分・承認状態・SHACL の結果)で手書きの型は必ず乖離する。

### グラフのために Turtle をブラウザで解析する

**却下(決定5)。** `draft` も描けるようになる。

却下理由: **`draft` が描けることは利点ではない。** `draft` がストアに
無いことは ADR-0010 決定1 の設計であり、**画面がそれを回避すると、
「エージェントから見えない」という性質が画面では成り立たない**ことになる。
レビュアが見たグラフとエージェントが見るグラフが違う状態を作る。

依存が増えることも理由だが、こちらは副次的である。

### グラフの上限を超えたら描画をやめる

**却下(決定5)。** 中途半端なグラフを見せない。

却下理由: **グラフには封筒がある。** 「1,000 ノードのうち 200 を描いて
います」と画面に書ける。RDF の切り詰めを拒んだ(ADR-0034 決定4)のは
**Turtle に「一部である」と書く場所が無い**からで、画面にはある。

### MSAL を入れてしまう

**却下(決定9)。** デプロイ環境でそのまま使える。

却下理由: **アプリ登録に SPA のリダイレクト URI を足す必要があり、
デプロイ窓なしに検証できない**。ADR-0042 決定5 で azd の
`containerapp-job` 対応を「確認できないから依存しない」とした判断と
同じである。**動かしていない認証は、動くと書いてはいけない。**

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **web ジョブが重くなる**(決定2)。`uv` と Python のセットアップが入る
- **`web` フィルタが API の変更でも動く**(決定2)。API だけを変えた push で
  web ジョブが走る — **それが目的である**
- **デプロイ環境ではトークンを貼る必要がある**(決定9)。`P2A-20` まで
- **グラフは `draft` を描けない**(決定5)。設計どおりだが、生成した候補を
  そのまま可視化したい要求には応えられない
- **描画は検証できていない**(決定6)。ブラウザを持たないので、
  純粋関数と型検査・ビルドまでしか確かめていない。**「動作を確認した」と
  書かない**
- **`reason` が必須になる**(決定8)。API より厳しいので、画面から
  操作するときだけ手間が増える

### 得られるもの

- **「測っていない」が画面で消えない**(決定1)。API が積んだ区別が
  最後まで残る
- **API と Web の型の不整合が CI で出る**(決定2)。ADR-0004 が求めていた
  仕組みができた
- **承認できない理由が分かる**(決定3)
- **消えた用語が最初に目に入る**(決定4)。`approve` の 422 を押す前に知る
- **画面が SPARQL の口を使う**(決定5)。画面が動くことがその口の検証になる
- **判断がテストされている**(決定6)

### 影響を受ける他の決定

- [ADR-0004](0004-schema-first-api.md) — 「生成漏れによる不整合を CI で
  検出する仕組みが必要」を実装した
- [ADR-0016](0016-semantic-diff.md) 決定5 — 「計算できなかった」の**提示
  形式**が決まった(同 ADR の未解決事項だった)
- [ADR-0010](0010-approval-and-projection.md) 決定1 — `draft` が射影され
  ないことが、画面の制約として現れる
- [ADR-0043](0043-ontology-proposal.md) 決定10 — 出自の**見せ方**が決まった
- [ADR-0014](0014-namespace-rbac.md) 決定5 — 四眼原則の**説明のしかた**が
  決まった
