# ADR-0030: マッピングの先の生死を両側から見せる — 読めない名前空間の状態を推測しない

- ステータス: 承認済み
- 日付: 2026-09-12

## コンテキスト

[ADR-0023](0023-cross-domain-mappings.md) が受け入れたコストにこう書いた。

> **マッピングの先が廃止されても気づけない。**
> [ADR-0017](0017-deprecation-lifecycle.md) の廃止検査は名前空間ごとの TTL を
> 見るので、PostgreSQL のマッピングは視界に入らない。相手の名前空間の TTL を
> 読む必要があり、権限の設計(A の分析者が B の用語の状態を知ってよいか)も
> 絡む。**`P2B-18` として記録する**

これが `P2B-18` である。放置すると何が起きるか。

1. 経理が `finance:PremiumCustomer` を廃止し、後継 `finance:KeyAccount` を
   定める(正しい縮め方。ADR-0009 決定3)
2. 営業の `sales:GoldCustomer → finance:PremiumCustomer`(`closeMatch`)は
   **そのまま残る**
3. エージェントが `term_mappings` でそれを読み、**廃止された用語を根拠に
   回答を作る**

ADR-0017 が `sparql_query` に廃止警告を付けた([ADR-0017](0017-deprecation-lifecycle.md)
決定3)のと同じ問題が、マッピングの経路では塞がれていない。

### 権限が本当の論点である

`sales` の分析者に `finance:PremiumCustomer` の生死を教えてよいか。

- 教えないと、営業は死んだ用語を指したままになる(上の 3)
- 教えると、**`finance` を読む権限が無い主体に `finance` の内容が 1 ビット
  漏れる**。IRI を当て推量で並べて `declare` すれば、
  「その IRI が `finance` に存在するか」を探る道具になりうる

不変条件11 は「権限の既定は拒否。暗黙のフォールバックを作らない」と言う。

## 決定

### 1. 相手の名前空間を読む権限が無ければ、状態を「調べていない」として返す

`data-analyst` を相手の名前空間に持っていなければ、
**`unknown` + 理由「権限が無いので調べていない」**を返す。
**`active`(生きている)とは言わない。**

これは不変条件11 の素直な適用である。**そして「調べられなかった」を
「問題なし」と書かないという、このリポジトリが繰り返している判断でもある**
([ADR-0021](0021-owl-reasoning-in-ci.md) 決定1 /
[ADR-0025](0025-result-limit-enforcement.md) 決定3 / ADR-0026 決定5 /
[ADR-0027](0027-revision-lineage.md) 決定5 と**同じ原則の 8 例目**)。

**「領域をまたいで対応を張るなら、相手の語彙の生死も追えるべきである。」**
追えないなら、追えないと表示する。権限を足すのは運用の正当な手順であり、
システムが勝手に覗く理由にはならない。

### 2. 状態は 4 つ。`active` と `absent` と `unknown` を混ぜない

| 状態 | 意味 |
|---|---|
| `deprecated` | 相手の現行版に `owl:deprecated true` があった。**`successor` も返す** |
| `active` | 相手の現行版に IRI があり、廃止されていなかった |
| `absent` | 相手の現行版に**その IRI が無かった**。マッピングが何も指していない |
| `unknown` | **調べていない / 調べられなかった。** `note` に理由が入る |

**`absent` を `active` に丸めない。** 「何も指していないマッピング」は
「廃止された先を指すマッピング」と同じくらい直すべきものである。
そして **`unknown` に丸めても駄目である** — 調べた結果として「無い」と
分かったことと、調べていないことは違う。

`unknown` の理由は次のいずれかで、**必ず区別して返す**。

| `note` | いつ |
|---|---|
| 外部語彙 | どの名前空間の `base_iri` にも属さない(SKOS、schema.org など) |
| 権限が無い | 決定1 |
| 承認済みの版が無い | 相手の名前空間にまだ承認済み版が無い |
| 正本を読めなかった | Blob へ到達できない / TTL を解析できない |
| 上限 | 1 回の応答で読む名前空間の数の上限に達した(決定4) |

**外部語彙を `absent` にしない。** SKOS の用語はこのシステムのどの名前空間にも
無いが、それは「存在しない」ではなく「**このシステムの管理外である**」。
ADR-0023 決定6 が「ターゲット用語の実在は検査しない」と決めた主用途がそれで
ある。

### 3. 宣言のときには検査しない。読むときに返す

`PUT /namespaces/{ns}/mappings` は**これまでどおり何も検査しない**
(ADR-0023 決定6)。

理由もそのままである。検査を入れると**宣言が Blob の可用性に依存する** —
正本への書き込みを射影や別の名前空間の可用性に依存させるのは、
不変条件2・3 が禁じている向きである。そして外部語彙へのマッピングは
そもそも検査できない。

**廃止は宣言の後に起きる。** 宣言時に検査しても、この ADR が防ごうとしている
事象(後から廃止される)には効かない。

### 4. 1 回の応答で読む名前空間の数に上限を置き、超えたことを返す

`MAX_TARGET_NAMESPACES = 10`。

マッピングは外部語彙も含めて任意の IRI を指せるので、**対象の名前空間の数に
上界が無い**。1 回の一覧で 50 個の名前空間の TTL を Blob から読んで rdflib で
解析すると、一覧そのものが使えなくなる。

上限に達した分は `unknown` + 理由「上限」で返す。**黙って `active` にしない。**
[ADR-0016](0016-semantic-diff.md) 決定5(空白ノードの上限)と同じ形である。

**名前空間ごとに 1 回だけ読む。** 同じ名前空間を指すマッピングが 100 件あっても
TTL の読み込みと解析は 1 回である(件数ではなく**対象の名前空間の数**が
コストを決める)。

### 5. 廃止する側にも見せる。そちらは権限の問題が無い

`M` が用語を廃止するとき、**`M` の側に「他の名前空間がこの用語を指している」
と報告する**。`term_mappings` は PostgreSQL にあるので Blob も推論器も要らず、
**`M` 自身のデータに対する `incoming` の情報**なので権限の論点が生じない
(`GET /namespaces/M/mappings?direction=incoming` が既に同じものを見せている)。

`ProblemKind.MAPPED_BY_OTHERS` として廃止検査の報告に加える。
**`GET .../versions/{v}/deprecation` と `approve` の両方に出る。**

### 6. しかし `approve` はブロックしない

**他の名前空間のデータが自分の承認を止められてはいけない。**

ADR-0017 決定2 は「生きている用語が廃止された用語を参照」を報告のみに留めた。
ここはもっと強い理由がある — **ブロックすると `N` が `M` を人質に取れる。**
`N` が `M` の用語へマッピングを張るだけで、`M` はその用語を廃止できなくなる。
`M` は `N` の行を消せない(決定3 により逆向きの書き込み口が無い)ので、
**`M` には従う手段が無い。**

ADR-0017 決定2 の規則(「ブロックが妥当なのは、規則が一義的で**かつ従う正当な
手段が常にある**ときだけ」)にそのまま反する。

### 7. 廃止された先を指すことは異常ではない

ADR-0017 決定2 が「生きている用語が廃止された用語を参照」をブロックしない
理由に**「旧→新のマッピングはどちらも書けなければならない」**を挙げている。

つまり **`deprecated` を指すマッピングは正当にありうる。** 旧用語を指す
マッピングを保持したまま、後継を指す新しいマッピングを足すのが正しい移行で
ある。だから `target_status` は**警告ではなく事実として**返す。

エージェント向けには MCP のツール説明で扱いを明示する
(**「廃止された用語を根拠に回答するなら、廃止されていることと後継を必ず
添える」**)。ADR-0017 決定3 の `deprecation_warnings` と同じ扱いである。

## 検討した代替案

### 権限に関わらず生死を返す

**却下(決定1)。** 「その IRI は廃止されている」は、呼び出し側が自分で名前を
挙げた用語についての 1 ビットにすぎない、という論法は成り立つ余地がある。

却下理由: **`active` と `absent` を区別すると存在の oracle になる。**
IRI を当て推量で `declare` して読み返せば、相手の語彙に何があるかを 1 件ずつ
探れる。区別を捨てて「廃止か否か」だけにすれば oracle は狭まるが、
今度は決定2 が禁じた丸め(`absent` を `active` に混ぜる)になる。
**権限で切るのが、どちらも犠牲にしない唯一の線である。**

### 廃止された先を指すマッピングを自動で取り消す

**却下。** 死んだ参照が消えるので一覧が綺麗になる。

却下理由: **ADR-0023 決定3 の「相手の名前空間に相手が宣言していない主張を
作らない」の裏返しを、こちらが行うことになる。** マッピングは `N` の
`owner` が `reason` 付きで宣言した成果物である。`M` の都合で消すのは、
`N` の宣言を `M` が書き換えることと同じである。そして決定7 のとおり、
旧用語を指すマッピングは正当にありうる。

### 廃止された先を指すマッピングの宣言を拒否する

**却下(決定3)。** 新しい死んだ参照が増えない。

却下理由: 3 つある。(a) 宣言が Blob と他の名前空間の可用性に依存する
(不変条件2・3)、(b) 外部語彙には効かない、(c) **そして肝心の事象(宣言の
後に廃止される)には効かない。**

### `M` の `approve` をブロックする

**却下(決定6)。** 死んだ参照が作られない。

却下理由: **`N` が `M` を人質に取れる。** `M` には従う手段が無い
(ADR-0017 決定2 の規則に反する)。

### 健全性指標に「廃止された先を指すマッピングの数」を足す

**却下(今は)。** [ADR-0020](0020-health-metrics.md) の枠組みには素直に入る。

却下理由: **健全性指標が他の名前空間の Blob の可用性に依存する。**
ADR-0020 は指標が測れなかったときに `None` を返す形を持っているので
表現はできるが、**指標を 1 つ足すために health の依存を増やす**判断は
要求が出てから行う(`P2B-21` として記録)。決定5 の報告が、廃止する側には
既に届いている。

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **相手の名前空間を読めない主体には生死が分からない**(決定1)。運用で
  `data-analyst` を付与する必要がある
- **一覧が Blob を読む。** 対象の名前空間の数だけ読み込みと解析が走る
  (上限 10。決定4)。マッピングの件数には比例しない
- **外部語彙の生死は永久に `unknown` である**(決定2)。SKOS や schema.org の
  廃止は追えない
- **`M` の承認は止まらない**(決定6)。死んだ参照は残りうる
- **健全性指標には出ない**(`P2B-21`)

### 得られるもの

- **「廃止された用語を根拠に回答する」経路が塞がった。** ADR-0017 決定3 が
  `sparql_query` に対して行ったことを、マッピングの経路でも行った
- **両側から見える**(決定1・5)。指している側は状態を、指されている側は
  依存を見る
- **読めないものを推測しない**(決定1・2)。`unknown` の理由を区別して返す
- **人質を作らない**(決定6)

### 影響を受ける他の決定

- [ADR-0023](0023-cross-domain-mappings.md) — 受け入れるコストに挙げていた
  「マッピングの先が廃止されても気づけない」に決着を付けた。決定6
  (実在を検査しない)は**そのまま維持**している(決定3)
- [ADR-0017](0017-deprecation-lifecycle.md) 決定2・3 — 報告の種類を 1 つ
  足した(`MAPPED_BY_OTHERS`)。ブロックしない理由は同決定の規則から導いた
- [ADR-0020](0020-health-metrics.md) — 指標は足していない(`P2B-21`)
