# ADR-0005: 推論器の境界 — SHACL 検証と OWL 推論の分離、ELK を既定に

- ステータス: 承認済み
- 日付: 2026-08-28

## コンテキスト

オントロジーを扱うシステムには、性質の異なる 2 つの「論理的な処理」がある。この 2 つはしばしば混同されるが、要求される道具も実行タイミングも異なる。

**(1) SHACL による制約検証(validation)**
- 「このオントロジーやデータは、定めた形を満たしているか」を検査する
- 閉世界的な検査であり、**結果は真偽と違反箇所のリスト**である
- オントロジーの**承認フローの中で同期的に実行したい**。専門家がレビューする画面で「この提案は制約に違反しています」と即座に示す必要がある

**(2) OWL による推論(reasoning / inference)**
- クラス階層の含意、`owl:equivalentClass`、プロパティ特性(推移性・逆関係)などから、**明示されていない事実を導出する**
- 開世界仮説に基づく
- 計算量が理論的に高く、**実行時間が予測しづらい**

この 2 つを実装する際、Python エコシステムには重大な制約がある。**実用的な OWL 推論器は Java 実装に集中している**(HermiT、ELK、Pellet 系)。一方 SHACL には純 Python 実装(pyshacl)が存在する。

さらにライセンス上の論点がある。

- **HermiT は LGPL-3.0** である。本プロジェクトは Apache-2.0 で配布する
- **owlready2**(Python の OWL ライブラリ)は **LGPL-3.0** であり、かつ**改変版 HermiT を同梱している**

Java への依存をいつ導入するかは、プロジェクトの複雑さに直接影響する。Java ランタイムをコンテナに入れる、Maven / Gradle のビルドを CI に追加する、といったコストが発生する。

## 決定

**SHACL 検証と OWL 推論を、実装・実行形態・導入時期のすべてで分離する。**

| | SHACL 検証 | OWL 推論 |
|---|---|---|
| 実装 | **pyshacl(純 Python)** | **ELK reasoner(Java, Apache-2.0)を既定** |
| 実行形態 | Core API 内で**同期実行** | **ACA Job で非同期実行**(別プロセス・別コンテナ) |
| 導入 Phase | **Phase 2** | **Phase 4** |
| ランタイム | Python のみ | Java |

具体的な決定事項:

1. **SHACL 検証は pyshacl で完結させる。** これにより **Java 依存は Phase 4 まで発生しない**
2. **OWL 推論の既定は ELK(Apache-2.0)** とする
3. OWL 推論は **ACA Job(`reasoner-job`)として非同期に実行**する。Core API の同期パスに入れない。HTTP API も持たせない
4. **HermiT(LGPL-3.0)は配布物に同梱しない。** 利用したい場合の**任意有効化オプション**として、コンテナビルド時に利用者側が取得する方式とする。実行は ACA Job の**別プロセス**とする
5. **owlready2 は採用しない**

## 根拠

### Java 依存を Phase 4 まで遅らせられる

これが本決定の最も実利的な効果である。

pyshacl が純 Python であるおかげで、Phase 2 の核心機能(LLM によるオントロジー生成 → SHACL 検証 → 専門家のレビュー → 承認)を、**Java ランタイムなしで完成させられる**。

- コンテナイメージに JRE を入れる必要がない(イメージサイズ、脆弱性の管理対象)
- CI に Java のビルドステップを追加する必要がない
- ローカル開発の前提ツールに JDK が加わらない
- コントリビューターの環境構築が単純なままである

Phase 1 と Phase 2 を Python だけで完走できることは、**プロジェクトが動き出すまでの摩擦**を大きく減らす。

なお Fuseki コンテナは Java(Jena)で動くが、これは**公式イメージをそのまま使う**ため、本プロジェクトが Java のビルドを持つ話とは別である。

### 承認フローに必要なのは検証であって推論ではない

専門家がオントロジーの提案をレビューする画面で必要なのは「この提案は形式的に妥当か」であり、これは SHACL の担当である。「このクラス階層からこういう含意が導かれる」という OWL 推論は、あると価値があるが**承認の必須条件ではない**。

したがって、実行時間が予測しづらい OWL 推論を同期パスに入れる理由がない。**同期的に必要なものと、非同期でよいものを分ける**ことで、API の応答時間の予測可能性を保てる。

### OWL 推論を ACA Job にする理由

1. **実行時間が予測しづらい。** OWL DL の推論は理論的に高い計算量を持つ。同期の HTTP リクエストに載せると、タイムアウトの設計が困難になる
2. **リソースを分離できる。** 推論のために大きなメモリを要求するジョブが、API のレプリカと同じリソースを食い合わない
3. **失敗を隔離できる。** 推論器の OOM やハングが API の可用性に影響しない
4. **LGPL 対応に都合がよい**(次項)

### LGPL コンポーネントを別プロセスに閉じ込める

**HermiT は LGPL-3.0** である。LGPL は、ライブラリとしてリンクする場合に「利用者がライブラリを差し替えられること」を保証する義務を課す。この義務の解釈は静的リンク・動的リンク・同一プロセスでの利用などで議論があり、**コンテナイメージを配布する形態では判断が難しい領域**に入る。

本プロジェクトの方針は、この議論に入らないことである。

- **配布物に同梱しない。** リポジトリにもコンテナイメージにも含めない。したがって本プロジェクトの配布に LGPL の義務は生じない
- 利用したい利用者は、**自身のコンテナビルド時に取得する**(任意有効化)
- 実行は **ACA Job の別プロセス**として行う。同一プロセス内でリンクしない構成は、LGPL の観点で最も安全である
- この方針は [NOTICE](../../NOTICE) および [`../third-party-licenses.md`](../third-party-licenses.md) に明記する

**ELK は Apache-2.0** であり、この問題がない。だから既定にする。

### ELK を既定にする実務上の理由

ライセンス以外にも ELK を既定とする理由がある。ELK は **OWL 2 EL プロファイル**に特化した推論器であり、その範囲では**多項式時間で動作する**。ビジネスオントロジー(クラス階層、部分・全体関係、ドメイン・レンジ制約)の大部分は EL プロファイルに収まる。

つまり、**表現力を少し諦めることで、実行時間の予測可能性を得る**という交換である。これは本プロジェクトの用途に合っている。EL を超える表現力(否定、選言、基数制約の複雑な組み合わせ)が必要な利用者には、HermiT を任意有効化する道を残す。

### owlready2 を採用しない理由

owlready2 は Python から OWL を扱う優れたライブラリだが、**改変版 HermiT を同梱する LGPL-3.0 のパッケージ**である。これを Apache-2.0 の本体に依存関係として取り込むと、**コンテナイメージを配布する時点で LGPL の順守義務が絡む**。

「Python だけで OWL 推論ができる」という利点は魅力的だが、それを得るために配布物のライセンス条件を複雑化させる判断はしない。**rdflib(BSD-3-Clause)+ pyshacl(Apache-2.0)+ 別プロセスの Java 推論器**の組み合わせで代替する。

## 検討した代替案

### owlready2 で Python 側に推論を統合する

**却下。** Java 依存を完全に排除でき、Phase 4 の実装量も減る、という強い利点があった。却下理由は上記の通り LGPL-3.0 のライセンス条件である。改変版 HermiT を同梱するパッケージに依存すると、Apache-2.0 の配布物としての単純さが失われる。

**この却下はライセンス上の判断であり、技術的な優劣ではない。** 将来 owlready2 のライセンス状況が変わる、あるいは同等の Apache-2.0 互換ライブラリが登場した場合、この判断は見直す価値がある。

### HermiT を既定の推論器にする

**却下。** HermiT は OWL 2 DL の完全な推論をサポートし、表現力では ELK を上回る。

却下理由:
- **LGPL-3.0 であり、配布物に同梱できない。** 既定にするなら同梱が必要になり、Apache-2.0 の配布物としてのライセンス整理が複雑になる
- **実行時間が予測しづらい。** OWL 2 DL の完全推論は最悪ケースの計算量が高く、ビジネスオントロジーの規模でも実行時間が跳ねる可能性がある

**任意有効化のオプションとしては残す。** EL を超える表現力が必要な利用者の要求を否定しない。

### SHACL 検証も Java(Jena SHACL)で実装する

**却下。** Fuseki と同じ Jena エコシステムを使うため、SHACL の実装が推論器と同じランタイムに揃うという一貫性の利点がある。

却下理由: **Java 依存が Phase 2 に前倒しになる。** 本決定の最大の効果(Phase 1・2 を Python だけで完走できる)が失われる。pyshacl は SHACL Core および SHACL-SPARQL に対応しており、承認フローに必要な機能を満たす。一貫性のために摩擦を先払いする理由がない。

### OWL 推論を同期 API として提供する(推論サービスコンテナ)

**却下。** 推論結果を即座に得られるため、レビュー画面での体験は良くなる。

却下理由:
- **実行時間の予測が困難で、タイムアウト設計が破綻する。** 「たまに 5 分かかる」処理を同期 API に載せられない
- 常時稼働するコンテナが 1 つ増え、コストが上がる(月 $10〜22 相当)。Phase 4 の機能のために固定費を払うことになる
- 推論は承認の必須条件ではない(上記「根拠」参照)

### OWL 推論を実装しない

**却下(スコープからの除外ではなく延期)。** Phase 3 までは実際に実装しないため、実質的にこの案と同じ状態が続く。しかし OWL を使うと宣言しておきながら推論を一切提供しないのは、**W3C 標準忠実路線の看板に対して不誠実**である。導出された含意をエージェントに提供できることは、単なる語彙集との差別化にあたる。Phase 4 で実装する。

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **Phase 4 で Java のビルドと運用が持ち込まれる。** `containers/reasoner/` の Java ビルド、CI へのステップ追加、JRE を含むイメージの脆弱性管理が発生する。**先送りしただけであり、消えたわけではない**
- **既定の推論能力が OWL 2 EL に限られる。** EL を超える表現力を使ったオントロジーでは、期待した含意が導出されない。この制約を利用者に説明するドキュメントが必要になる
- **推論結果が非同期に遅れて現れる。** 「承認した直後に推論結果を見たい」という要求には応えられない。ジョブの完了通知と結果の反映を UI で設計する必要がある
- **HermiT を任意有効化する経路の保守。** 利用者がビルド時に取得する手順を文書化し、それが壊れていないことを確認する負担が残る。ただし配布物に含まれないため、CI で常時検証する対象ではない
- **2 つの論理処理系を持つことになる。** pyshacl と ELK で、制約と含意という異なる関心を扱う。利用者から見て「どちらがどこまでを担当するのか」が分かりにくくなる恐れがあり、ドキュメントでの説明が必要

### 得られるもの

- **Phase 1 と Phase 2 を Python だけで完走できる。** プロジェクトが動き出すまでの摩擦が大きく減る。これが本決定の主目的である
- **配布物が Apache-2.0 で完全に閉じる。** LGPL コンポーネントを含まないため、利用者がライセンスを気にせず再配布できる
- **API の応答時間が予測可能である。** 実行時間の読めない処理が同期パスに入らない
- **障害が隔離される。** 推論器の OOM やハングが API の可用性に影響しない
- **既定構成での推論時間が予測可能である**(ELK / OWL 2 EL による多項式時間)

### 影響を受ける他の決定

- [ADR-0001](0001-rdf-store-selection.md) — Jena エコシステム(Java)を採用したことで、ELK との接続が容易になっている
- [`../third-party-licenses.md`](../third-party-licenses.md) — HermiT と owlready2 の扱いは本 ADR の決定を反映している
- [NOTICE](../../NOTICE) — HermiT を同梱しない方針を明記する

## 補記: 推論器の導入時期を Phase 2 へ前倒し (2026-09-01)

本 ADR は「SHACL 検証は pyshacl で完結するため Java 依存は Phase 4 まで発生しない」としていた。
**この判断を変更する。** OWL 推論器 (ELK, Apache-2.0) の導入を **Phase 4 → Phase 2** に前倒しする。

理由は [ADR-0009](0009-ontology-operations.md) に記録した「決定可能性による分業」である。
論理的整合性は形式的に決定可能であり、推論器は健全かつ完全に判定する。これを CI に置けば
人がレビューする対象が「形式的には正しいが業務的な妥当性が不明なもの」だけに絞られる。
**最も安い正しさの担保**であり、承認フローを実装する Phase 2 と同時に入れるのが筋が通る。

SHACL を pyshacl で扱う判断（純 Python で完結する範囲は Java を持ち込まない）は変更しない。
HermiT (LGPL-3.0) を同梱せず、ELK を既定とする判断も変更しない。
