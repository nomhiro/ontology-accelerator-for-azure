# ADR-0002: トリプルストアを再構築可能な射影として扱う

- ステータス: 承認済み
- 日付: 2026-08-28

## コンテキスト

[ADR-0001](0001-rdf-store-selection.md) により、既定のトリプルストアは Azure Container Apps 上で動く Apache Jena Fuseki(TDB2)となった。ここで永続化の問題に直面する。

**Azure Container Apps の永続ストレージは Azure Files のみである。** 公式ドキュメントが NetApp Files および Blob のマウント不可を明記している。

一方、**TDB2 は mmap とファイルロックに依存する**。ネットワークファイルシステム上での mmap の挙動とロックの正しさは、TDB2 側で保証されていない。SMB 経由でのメモリマップドファイルの一貫性は、実装依存かつ環境依存であり、「動いているように見えるが破損する条件がある」という最悪の形の不確実性を持ち込む。

当初案は「単一レプリカ固定 + Azure Files + 夜間ダンプ」であった。この案には次の問題があった。

- **最大リスクを運用で押さえ込む形になっている。** 「レプリカを 1 つに固定すればロック競合は起きない」「毎晩ダンプを取れば壊れても戻せる」という設計は、根本原因(ネットワーク FS 上での TDB2 の安全性が未保証)に触れていない
- 夜間ダンプはデータ損失の窓を最大 24 時間残す
- Azure Files Premium は最小 100 GiB からのプロビジョニングであり、**月 $19** が固定費として乗る
- Phase 1 のスパイクが「Azure Files で TDB2 は壊れないか」になる。**これが不合格だった場合、設計をやり直すことになる**。検証結果に設計全体が賭けられている状態は望ましくない

同時に、次の事実に着目した。ACA には **replica-scoped ephemeral storage(EmptyDir)** がある。これはレプリカの生存期間中は永続し、**コンテナの再起動をまたいで保持される**。容量は 1 vCPU で 4 GiB、1 vCPU 超で 8 GiB である。オントロジー(スキーマレベルの語彙とその関係)は、実データと違って規模が小さい。この容量で十分である。

## 決定

**トリプルストアを「正本」ではなく「いつでも作り直せる派生物(射影)」として扱う。** 検索インデックスと同じ位置づけである。

具体的には次のとおり。

1. **正本(system of record)を Blob + PostgreSQL に置く**
   - 承認済みオントロジーを**バージョン付き TTL** として Blob Storage に保存する
   - メタデータ・承認履歴・R2RML マッピングを PostgreSQL に保存する(詳細は [ADR-0003](0003-postgresql-as-system-of-record.md))

2. **ストアのデータは EmptyDir に置き、起動時に再構築する**
   - Fuseki コンテナの **entrypoint** が起動時に Blob から最新スナップショットを取得し、`tdb2.tdbloader` で EmptyDir にロードしてから Fuseki を起動する(当初は init コンテナで行っていた。変更理由は後述の「補記」を参照)
   - ロード完了後に Fuseki 本体を起動する
   - **startup probe** により、ロードが完了するまでトラフィックを流さない

3. **書き込みの順序を「正本 → 射影」に固定する**
   - Core API が正本(Blob + PostgreSQL)に書いた**後で**、Fuseki へ射影する
   - **SPARQL Update / Graph Store Protocol による直接書き込みは Core API のみが行う。** エージェント・Web・外部クライアントには読み取りのみを提供する

4. **Bicep パラメータ `graphPersistence` で切り替え可能にする**
   - `ephemeral`(既定)— EmptyDir + 起動時再構築
   - `azureFiles` — 「ストア自体を正本にしたい」利用者向けのオプトイン
   - 大規模利用者には **AKS + Managed Disk** への昇格パスを案内する

## 根拠

### 永続化リスクが設計上消える

「失っても再構築できる」ものについては、永続化の正しさを問う必要がない。ネットワーク FS 上での TDB2 の安全性という**検証も保証もできない前提が、設計から取り除かれる**。EmptyDir はレプリカローカルのディスク相当であり、mmap とファイルロックが素直に動く領域である。

これは運用による緩和ではなく、**リスクの除去**である。

### Phase 1 のスパイクが安全になる

| | 当初案 | 本決定 |
|---|---|---|
| スパイクの問い | 「Azure Files で TDB2 は壊れないか」 | 「再構築にどれくらいかかるか、射影ループは正しく回るか」 |
| 不合格時の帰結 | **設計をやり直す** | パラメータ調整、あるいは Oxigraph への切り替え(切り替えコストは低い) |
| 検証コスト | 破損条件を探す長期試験が必要 | 時間計測。安価・短時間 |

**設計全体を賭けた検証を、局所的なチューニングの検証に変えられる。** これが本決定の最も大きな効果である。

### コストが下がる

Azure Files Premium の最小 100 GiB × $0.192/GiB/月 = **月 $19 が不要になる**([`../cost-estimate.md`](../cost-estimate.md))。これは見積り上の不確実性を含まない、確実な削減である。

### 将来の読み取り水平スケールへの道が開ける

各レプリカが自分のコピーを持つ構成であるため、原理的には読み取りを水平にスケールできる。ただし**現時点では単一レプリカ運用とする**(後述のトレードオフ参照)。

### セキュリティ対策と同じ方向を向く

「Fuseki への書き込み口は Core API のみ」という制約は、データ保全のための制約であると同時に、SPARQL の攻撃面対策そのものでもある。エージェントに SPARQL Update を提供しないことは[攻撃面の縮小](../../SECURITY.md)であり、射影設計の前提と一致する。**2 つの要求が同じ制約に収束している**ことは、この設計の妥当性を裏付けている。

### グラフに巨大な実データを載せない前提が支えている

この設計が成立するのは、**トリプルストアに載るのがオントロジー(スキーマレベルの語彙と関係)であり、実データではない**ためである。実データは Ontop VKG による仮想グラフとして扱い、実体化しない(Phase 3)。EmptyDir の 4〜8 GiB で足りるのはこの前提のおかげであり、逆にこの前提が崩れる(実データをグラフに載せる)なら本決定は再検討が必要になる。

## 検討した代替案

### Azure Files + 単一レプリカ固定 + 夜間ダンプ(当初案)

**却下。** 上記「コンテキスト」で詳述。根本原因に触れず運用で押さえ込む設計であり、最大 24 時間のデータ損失窓、月 $19 の固定費、そして Phase 1 スパイクに設計全体を賭ける構造を持つ。

なお `graphPersistence: azureFiles` として**オプトインの選択肢としては残す**。「ストア自体を正本にしたい」「射影ループを運用したくない」という利用者の判断を否定しない。ただし既定にはしない。

### AKS + Managed Disk

**Phase 1 では却下、昇格パスとして案内。** Managed Disk はブロックストレージであり、TDB2 の要件に素直に適合する。永続化の観点では最も正統な構成である。

却下理由は運用コストである。AKS はクラスタのコントロールプレーン、ノードプール、アップグレードサイクルの管理が発生し、「`azd up` 一発で評価できる」という要件と月 $39〜61 のコスト目標に反する。大規模利用者にとっては合理的な選択なので、[`../architecture.md`](../architecture.md) で昇格パスとして案内する。

### 常に Blob から全体を再ロードし、EmptyDir も使わない(インメモリ)

**却下。** Jena のインメモリデータセットを使えば、ディスクの議論が完全に消える。しかし(a)ヒープに全グラフを載せるためメモリ要件が跳ね上がり ACA の小さいレプリカに収まらない、(b)TDB2 のバルクロードとインデックスの利点(大きなグラフでのクエリ性能)を失う。EmptyDir を使えばディスクの利点を保ちながら永続化リスクも避けられるため、あえてインメモリにする理由がない。

### Fuseki を正本とし、Blob へ定期バックアップする

**却下。** これは当初案の一般形である。ストアを正本とすると、(a)ストアの永続化の正しさが不可欠になり、(b)承認履歴・RBAC・R2RML マッピングといったリレーショナルなメタデータをどこに置くかという問題が別途残る。[ADR-0003](0003-postgresql-as-system-of-record.md) の通り、正本は PostgreSQL + Blob に置くほうが要件に適合する。

### SPARQL Update を公開し、ストアへの直接書き込みを許す

**却下。** 射影設計と両立しない。ストアへ直接書かれた内容はレプリカ再作成時に失われるため、「書けたのに消えた」という最悪のユーザー体験を生む。加えて SPARQL Update の公開は攻撃面を大きく広げる([SECURITY.md](../../SECURITY.md))。書き込み口を Core API に一本化することで、両方の問題が同時に解消する。

## 結果(トレードオフ・影響)

### 受け入れる制約

- **Fuseki に直接書き込まれた内容は失われる。** これは設計上の制約であり、バグではない。SPARQL Update を一切公開しないことで封じる(設計原則 4)。この制約は [SECURITY.md](../../SECURITY.md) と [`../architecture.md`](../architecture.md) に明記する
- **レプリカ起動時に再構築時間がかかる。** startup probe でトラフィックを止めるため、デプロイやスケールイベントのたびに空白時間が生じる。**この所要時間の実測が Phase 1 の必須スパイク**である。許容できない場合は Oxigraph(起動が速い)への切り替えを検討する
- **複数レプリカにすると複製間が乖離する。** 内部 ingress のロードバランスにより、射影の書き込みが 1 レプリカにしか届かないためである。**Phase 1 は単一レプリカとする。** 将来複数レプリカにするには変更伝播の仕組みが別途必要になる(オントロジー公開時にリビジョンの再起動をトリガする等)。承認は低頻度な操作なので、この方式は許容できると判断する
- **射影ループの実装が必要になる。** 「正本に書く → ストアへ射影」の一貫性(片方だけ成功した場合の扱い、リトライ、冪等性)を Core API で設計・実装する責任が生じる。これは当初案には存在しなかったコストである
- **EmptyDir の容量上限(1 vCPU で 4 GiB、超で 8 GiB)がグラフ規模の上限になる。** オントロジー規模では十分だが、実データをグラフに載せる用途では足りない。その用途は Ontop VKG(実データを実体化しない)で扱う
- **`azureFiles`(温存モード)では `DELETE /namespaces/{name}` が共有ボリューム上の TDB2 を即座に削除する(実測)。** Fuseki 6.2.0 の `DELETE /$/datasets/<name>` は `/fuseki/databases/<name>` 自体を削除する。この構成を選ぶ利用者は「ストアが正本」という前提で運用しているため、Blob に無い更新をストア側だけに持っていた場合はそれが失われる。ブランチ全体レビュー C-1 の対応(Blob に公開済み版が残っていれば 409 で削除を拒否する)により大部分は閉じるが、「Blob に反映していないストア側の更新を持っている」ケースはこの温存モードの前提そのものであり、閉じられない。この構成を選ぶ利用者は名前空間の削除を慎重に行うこと

### 得られるもの

- **永続化リスクが消滅する。** ローカルディスク相当であり、失っても再構築できる
- **Azure Files Premium の月 $19 が不要になる**(既定構成)
- **Phase 1 のスパイクが安価・低リスクになる。** 不合格でも設計やり直しにならない
- **ストア選定の可逆性がさらに高まる。** 正本がストアの外にあるため、ストアを入れ替えても失うものがない。[ADR-0001](0001-rdf-store-selection.md) の判断の修正コストが下がる
- **バックアップの責務が正本側に集約される。** Blob のバージョニングと PostgreSQL のバックアップという、マネージドサービスの機能で完結する
- **バージョン固定参照が自然に実装できる。** バージョンごとに別の名前付きグラフへ射影する構成が素直に成立する([ADR-0006](0006-ontology-versioning-and-audit.md))

### 影響を受ける他の決定

- [ADR-0003](0003-postgresql-as-system-of-record.md) — 本決定の前提として、正本を PostgreSQL + Blob に置く判断が必要になる
- [ADR-0006](0006-ontology-versioning-and-audit.md) — 不変リビジョンを Blob に保存する設計は、本決定の射影モデルと一体である
- [SECURITY.md](../../SECURITY.md) — 書き込み口を Core API に限定する制約が、SPARQL 攻撃面対策の前提になる

## 補記: init コンテナから entrypoint への変更 (2026-08-28)

実サブスクリプションへの `azd up` で判明した問題により、再構築を行う場所を
**ACA の init コンテナから Fuseki コンテナの entrypoint へ移した**。

### 問題

azd は provision → deploy の順に実行し、deploy が差し替えるのは各コンテナアプリの
**メインコンテナのイメージだけ**である。init コンテナのイメージは Bicep 経由でしか
更新されないため、次の順序問題が起きていた。

1. `azd provision` 実行時点ではイメージがまだ存在せず、init にはプレースホルダが入る
2. `azd deploy` がメインコンテナだけを新しいイメージに差し替える
3. init は古い(あるいはプレースホルダの)イメージのまま残り、コードとタグが乖離する

結果として **`azd up` 一回では正しく動かず**、利用者が `azd provision` をもう一度
実行して初めて配線が揃うという状態だった。実測でも init が
`azd-deploy-1787918225`、メインが `azd-deploy-1787919880` という乖離を確認している。

OSS として配布する以上、初回の `azd up` が一発で通らないのは受け入れがたい。

### 決定

再構築を entrypoint (`containers/fuseki/entrypoint.sh`) で行う。同一イメージ内の
処理になるため、**コードとイメージタグは構造的に常に一致する**。この問題は設定で
回避するのではなく、発生し得ない形に変えた。

- Startup プローブ (failureThreshold 30 × periodSeconds 10 = 最大 5 分) が
  再構築の完了までトラフィックを流さない
- 再構築に失敗したら entrypoint が異常終了する。空のグラフを黙って配らない
- `docker compose` でも同じ流れになり、ローカルと Container Apps の差が縮んだ

### 併せて入れたガード

`graphPersistence=azureFiles` は「ストア自体を正本にしたい」利用者向けの構成であり、
そこで毎回 Blob から作り直すとストア側の更新を失う。`PRESERVE_EXISTING_TDB` を
追加し、既存の TDB2 があるときは再構築せずそのまま使うようにした。Bicep は
`azureFiles` のときだけ `true` を渡す(既定の `ephemeral` では毎回作り直す)。

### トレードオフ

- init コンテナによる「ロードと配信の関心の分離」は失われた。ただし本設計では
  ロードは起動処理の一部であり、分離の利得は上記の不整合リスクに見合わない
- レプリカが再作成されるたびに再構築が走る。オントロジー規模では数秒で終わるため
  許容する。大規模化した場合は `azureFiles` か AKS + Managed Disk へ移る
