# ADR-0036: JSON-LD は同じ URL で返し、`@context` は埋め込む — 解決できない URL を名乗らない

- ステータス: 承認済み
- 日付: 2026-09-12

## コンテキスト

[ADR-0026](0026-provenance-export.md) は監査証跡を PROV-O の Turtle として
書き出すと決め、代替案として JSON-LD を挙げて**却下**した。

> JSON-LD で返す(**`@context` の公開先**という新しい問題が生まれる。`P2A-17`)

`P2A-17` はこの保留の解決である。

### JSON-LD に価値がある理由

Turtle は RDF ツールには最良だが、**JSON しか読まないクライアントには読めない**。
このリポジトリの API の利用者には AI エージェントと運用者のスクリプトが含まれ、
どちらも JSON を前提に組まれることが多い。

JSON-LD なら**同じ 1 つの文書**が、

- JSON パーサ(`jq`・標準ライブラリ)からは普通の JSON に見え、
- RDF ツールからは PROV-O のグラフに見える。

「標準に写すために情報を落とす」(ADR-0026 決定4)の逆で、**表現を足すだけで
両方に届く**。

### 保留されていた問題: `@context` をどこに置くか

JSON-LD の語彙の意味は `@context` が与える。**外部の URL を指す**のが一般的な
形だが、この製品ではどの置き場所も成り立たない。

| 置き場所 | なぜ成り立たないか |
|---|---|
| この API(`GET /context/provenance.jsonld`) | **認証が要る。** JSON-LD プロセッサは Bearer トークンを持たないので取得できない。無認証で配れば「この API には無認証の口がある」という別の問題を作る |
| この API(デプロイごとの URL) | **URL がデプロイごとに違う。** 書き出した文書を第三者に渡した時点で壊れる。`production` プロファイルは内部 ingress なので最初から解決できない |
| リポジトリの raw URL | **文書の意味がリポジトリの可用性に依存する。** 移転・改名・ブランチの削除で過去の書き出しが読めなくなる |
| 恒久的な URL を別に用意する | OSS の利用者ごとにドメインを持たせることになる。`azd up` 一発という前提を壊す |

**どれも「解決できる URL を名乗っているのに解決できない」形である。** それは
このリポジトリが繰り返し避けてきた誤り(測っていないことを主張する)の一種で、
しかも**壊れていることが受け取った側にしか分からない**。

## 決定

### 1. JSON-LD は同じ URL の内容交渉で返す。新しいエンドポイントを作らない

`GET /namespaces/{ns}/provenance` に `Accept: application/ld+json` を付けると、
**同じグラフ**が JSON-LD で返る。

**ADR-0026 決定1 が却下した内容交渉とは別物である。** あちらが却下したのは
`/audit`(JSON のページ)と RDF の交渉で、理由は

> JSON には `cursor` が要るが RDF では意味が薄く、**同じ URL が表現によって
> 違うパラメータを取る**形になる

だった。**同じグラフの 2 つの直列化はパラメータが同じ**なので、この理由が
当たらない。`/audit` と `/provenance` の境界は変えない。

### 2. `@context` は文書に埋め込む。外部に公開しない

これが**コンテキストの置き場所という問題を消す方法**である。置き場所を選ぶの
ではなく、置き場所を要らなくする。

JSON-LD 1.1 はインラインの `@context` を正規の形として認めている。埋め込めば
**文書が自己完結する** — 認証も、デプロイごとの URL も、リポジトリの可用性も
関係なくなる。書き出した文書をメールで送っても意味が保たれる。

### 3. 用語の別名(term alias)を作らない。接頭辞だけにする

キーは `ont:action` / `prov:generated` のままにする。`"action"` のような
短い別名は作らない。

**別名は 2 つ目の語彙である。** Turtle の述語名と JSON のキー名を同期させ
続けることになり、片方だけ足したときに**表現によって名前が違う**状態になる
([ADR-0027](0027-revision-lineage.md) の受け入れるコスト「名前が 2 つに
なる」と同じ形)。別名が買うのは見やすさだけで、**情報は 1 つも増えない。**

副作用として、対応表を持たないので**述語を足しても JSON-LD 側の変更が要らない**
(接頭辞で圧縮されるだけである)。表に追いつかないことで壊れる余地が無い。

### 4. rdflib の既定の接頭辞表を出さない

`Graph.serialize(format="json-ld")` にコンテキストを渡さないと、rdflib は
**自身の既定の名前空間束縛をすべて** `@context` に書き出す。実測で 30 件で、
Brick(建物)・GeoSPARQL(地理)・SOSA(センサー)・ODRL(権利)など
**その文書に一切現れない語彙**が並ぶ。

「この文書はそれらについて何か言っている」と読める余地を作らない。明示した
コンテキスト(決定3 の接頭辞だけ)を渡す。

### 5. 内容交渉は足すだけにする。既定は Turtle、406 は返さない

| `Accept` | 返すもの |
|---|---|
| ヘッダ無し / 空 / `*/*` | **Turtle**(既定) |
| `application/ld+json` | JSON-LD |
| `application/json` | **Turtle** |
| `application/ld+json;q=0` | **Turtle**(明示的な拒否) |
| `text/turtle, application/ld+json`(同じ品質値) | **Turtle** |
| 解釈できない `q` | **Turtle** |
| `application/xml` など | **Turtle**(406 にしない) |

3 つとも「既存のクライアントの振る舞いを変えない」向きである。

- **`application/json` で切り替えない。** 既定で `Accept: application/json` を
  送る HTTP クライアントは多い。そこで JSON-LD に切り替えると、**いまこの口を
  Turtle として使っているクライアントが黙って壊れる**
- **406 を返さない。** いまは `Accept` を完全に無視している。406 にすると、
  狭い `Accept` を送っている既存クライアントが動かなくなる。内容交渉を足す
  変更が既存の利用を壊してはいけない
- **`q=0` を尊重する。** 部分文字列一致で判定すると
  `Accept: application/ld+json;q=0`(= この型は受け付けない)に JSON-LD を
  返す。**明示的な拒否を肯定として読む**のは最も悪い誤読である

### 6. 2 つの直列化は同じグラフから出す。構造で保証する

`provenance_graph()` / `mapping_graph()` が `rdflib.Graph` を返し、Turtle と
JSON-LD はどちらもその戻り値を直列化する。

**経路ごとにトリプルを組み立ててはいけない。** 片方だけ直したときに
**表現によって内容が違う**という静かな不整合になり、どちらが正しいのかを
判定する手段が無くなる。

**同型であることをテストで固定する**(`rdflib.compare.isomorphic`)。
これがこの決定の実効部分である。

### 7. 形は常に `@graph` の配列にする

rdflib は主語が 1 つのときだけ平らなノードオブジェクトを返す。そのまま返すと
**イベントが 0 件の書き出しだけ形が変わる**(束のノードしか無いため)。

形が入力で変わる契約はクライアントに分岐を強いる。空のグラフでは
`"@graph": []` にする — 「ノードが 1 つある」と「ノードが無い」を同じ形で表す。

### 8. RDF を返すすべての口に同じ規則を適用する

`/namespaces/{ns}/provenance`(ADR-0026)と
`/namespaces/{ns}/mappings/export`([ADR-0031](0031-mapping-export.md))の
両方で交渉する。

**片方だけにすると説明のつかない差になる。** 「なぜマッピングは JSON-LD で
取れないのか」に技術的な答えが無い(どちらも同じ `Graph` である)。

## 検討した代替案

### 別のエンドポイントを作る(`/provenance.jsonld`)

**却下(決定1)。** `Accept` の解釈が要らず、URL を見れば形が分かる。

却下理由: **絞り込みのパラメータを 3 か所で同期させることになる。**
ADR-0026 決定1 は 2 つの表現でさえ「別のモジュールに分けると片方だけ更新
されて表現によって見える範囲が変わる」と警告し、同じモジュールに置く判断を
した。3 つ目を別の URL で足すのはその逆である。

### `@context` を API から配る

**却下(決定2)。** コンテキストが 1 か所にまとまり、応答が小さくなる。

却下理由: **認証が要る URL は JSON-LD プロセッサから解決できない。**
無認証にすれば解決できるが、「認証が要る API に無認証の口が 1 つある」という
状態を作る。そして URL はデプロイごとに違うので、文書を外に渡した時点で壊れる。

### `@context` をリポジトリの raw URL で配る

**却下(決定2)。** デプロイに依存しない恒久 URL に見える。

却下理由: **恒久ではない。** 移転・改名・ブランチの削除で過去の書き出しが
読めなくなる。文書の意味が GitHub の可用性に依存するのも筋が悪い。

### `/audit` の JSON を JSON-LD にする

**却下。** 新しい口を増やさずに JSON クライアントへ PROV-O が届く。

却下理由: **既存の契約を壊す。** `events` / `next_cursor` は JSON-LD の語彙
ではなく、JSON-LD にするなら形を変えるしかない。そしてパラメータが違う
(ADR-0026 決定1)。

### 用語の別名を定義して JSON を読みやすくする

**却下(決定3)。** `"action": "published"` のように短いキーになる。

却下理由: **2 つ目の語彙を作る。** Turtle の述語名と同期させ続ける義務が
生まれ、情報は 1 つも増えない。

### 解釈できない `Accept` に 406 を返す

**却下(決定5)。** HTTP としては正しい。

却下理由: **いまは `Accept` を無視している。** 406 に変えると、狭い `Accept`
を送っている既存クライアントが動かなくなる。内容交渉を**足す**変更が既存の
利用を壊してはいけない。

### JSON-LD をやめて Turtle だけにする

**却下。** 表現が 1 つなら同期の問題が起きない。

却下理由: 同期の問題は決定6(同じグラフから出す)で構造的に消えている。
そのうえで、**JSON しか読まないクライアントに PROV-O が届かない**という
ADR-0026 が残した穴が埋まらない。

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **コンテキストが応答ごとに繰り返される**(決定2)。1 応答あたり数百バイト。
  リモートコンテキストならキャッシュできるが、**解決できないコンテキストは
  キャッシュもできない**
- **`urn:` の IRI は dereferenceable でないままである**(`P2A-07` の未解決)。
  コンテキストの埋め込みが解くのは「語彙の意味をどこで引くか」であって
  「主体や版の詳細をどこで引くか」ではない
- **JSON-LD は `@graph` の配列である**(決定7)。単一のオブジェクトを期待する
  JSON クライアントは `@graph` を辿る必要がある。**平らにはできない** —
  1 つの書き出しに束・行為・主体・版という複数の主語が出る
- **`Accept` の解析を自前で持つ**(決定5)。RFC 9110 の完全な実装ではなく、
  見るのは `application/ld+json` と `text/turtle` の 2 つだけである。
  `Accept-Charset` や `Accept-Language` は見ない
- **`application/json` では JSON-LD にならない**(決定5)。JSON クライアントは
  **`application/ld+json` を明示しなければならない**。README に書く
- **キーに接頭辞が付く**(決定3)。`jq '.["@graph"][0]["ont:action"]'` のように
  なり、素の JSON としては読みにくい。**別名を作らない判断の代償である**

### 得られるもの

- **ADR-0026 が保留した JSON-LD が、新しい問題を作らずに入った。**
  「`@context` をどこで公開するか」は**公開しないことで消えた**
- **JSON しか読まないクライアントに PROV-O が届く。** 同じ 1 つの文書が
  両方の世界で読める
- **2 つの直列化が食い違えない**(決定6)。同型であることをテストが固定して
  いるので、片方だけ直す変更は落ちる
- **マッピングの書き出しも同じ規則で読める**(決定8)

### 影響を受ける他の決定

- [ADR-0026](0026-provenance-export.md) 決定1 — 補記を追加した(却下したのは
  `/audit` と RDF の交渉であり、**同じグラフの直列化の交渉ではない**)
- [ADR-0031](0031-mapping-export.md) 決定2 — マッピングの書き出しも
  `Accept` で JSON-LD になる(決定8)
- [ADR-0017](0017-deprecation-lifecycle.md) 決定3 の「エージェントはヘッダを
  見ない」は**変わらない**。ここで `Accept` を要求するのは**クライアントが
  形を選ぶため**であり、**安全に関わる情報をヘッダに載せているのではない**。
  切り詰めの旗は引き続き RDF の中にある(ADR-0026 決定5)
