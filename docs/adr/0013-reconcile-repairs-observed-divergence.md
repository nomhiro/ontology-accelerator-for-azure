# ADR-0013: reconcile は観測された乖離を修復する

- 状態: 採用
- 日付: 2026-09-09
- 関連: [ADR-0002](0002-triple-store-as-rebuildable-projection.md)（射影であり正本ではない）、[ADR-0010 補記1](0010-approval-and-projection.md)（グラフ単位の突き合わせ）、バックログ `P1-25` / `P1-17` / `P1-19`

## コンテキスト

`reconcile` には現在 2 つの回収経路がある。

1. **バージョン単位の回収**: `VersionRepository.unprojected()`（`projected_at IS NULL` かつ `draft` でない）を射影し直す。`publish` / `submit` / `approve` の途中で射影が失敗した場合を回収する（不変条件3）
2. **グラフ単位の突き合わせ**（ADR-0010 補記1）: ストアに実際にあるグラフと正本が求めるグラフを比較し、**残留**（`reject` の削除失敗など）を削除し、**欠落**を `missing_graphs` として報告する

問題は 2 の欠落側で、**報告するだけで修復していない**。Blob には TTL があるので技術的には再射影できる。主な発生源はローダによる名前空間のスキップで、その場合データセットは存在するが空になり、**エージェントから見ると「データが無い」と区別がつかない**。

`P1-19` の実装時に、修復を入れるには先に決めるべきことが 3 つあると判断して `P1-25` に分離した。この ADR でそれを決める。

### 論点 1: `projected_at` が非 NULL の版を再射影してよいか

経路 1 の対象は `projected_at IS NULL` に限られている。欠落した版はすでに一度射影に成功しているので `projected_at` は非 NULL であり、経路 1 では拾えない。この境界を広げてよいかが論点だった。

### 論点 2: `SUPERSEDED_RETAIN` との関係

ローダは既定（`SUPERSEDED_RETAIN=0`）で `superseded` の版を読み込まない。reconcile が `superseded` を再射影すると、**再構築のたびにローダの保持ポリシーを即座に打ち消す**。

### 論点 3: 自動修復が根本原因を隠さないか

ローダがスキップした本当の理由（マニフェストの欠落・破損、Blob へ到達できない、`GRAPH_IRI_BASE` の食い違い）に運用者が気づかなくなる恐れがある。

### 論点 4（起草中に判明）: 既定グラフの欠落は今の突き合わせでは見えない

`SparqlStore.list_graphs` は**名前付きグラフしか返さない**（クエリが `GRAPH ?g { ?s ?p ?o }` であるため）。ところが**エージェントが読むのは既定グラフ**である（`GRAPH` 句を書かないクエリ。ADR-0010 決定6）。つまり「名前付きグラフは揃っているのに既定グラフが空」という状態は、**最も害が大きいのに現在の検出に一切映らない**。

なお `approve` は名前付きグラフと既定グラフの**両方が成功したときだけ** `mark_projected` する。したがって承認処理中の部分失敗は経路 1 が回収する。ここで問題にしているのは、**一度成功した後にストア側の状態が失われた**場合である。

## 決定

### 1. `projected_at` は書き込み経路の知識であり、ストアの現在の状態ではない

`projected_at` が非 NULL であることは「**書き込み経路が知る限り、この行の現在の状態に対応する射影は完了している**」を意味する。これは**ストアが今その内容を保持しているという主張ではない**。

[ADR-0002](0002-triple-store-as-rebuildable-projection.md) によりストアはいつでも作り直される派生物なので、**PostgreSQL 側の列からストアの現在の状態を主張することは原理的にできない**。「ストアは今それを持っているか」に答えられるのはストア自身だけである。

### 2. `unprojected()` の境界は広げない。修復は観測されたストアの状態を根拠にする

**証拠が 2 種類あり、修復の仕組みは 1 つである**という構造にする。

| 経路 | 証拠 | 意味 |
|---|---|---|
| バージョン単位（既存） | `projected_at IS NULL` | 書き込み経路が完了していない |
| グラフ単位（この ADR） | `list_graphs` に無い / 既定グラフが空 | 一度完了した後にストアの状態が失われた |

修復そのものは既存の `_project_named_graph` / `_project_default_graph` を両経路が共用する。**判断（何を直すか）は 2 箇所だが、実装（どう直すか）は 1 箇所**にする。

### 3. 修復の対象は `in-review` と `approved` に限る。`superseded` の在否は不問とする

reconcile は `superseded` の欠落を**報告もせず修復もしない**。逆に、`superseded` のグラフが存在していても**残留として削除しない**。

**`superseded` がストアに載るかどうかを決めるのはローダだけである。** reconcile はその決定に関与しない。

### 4. 既定グラフの空も検出・修復する

名前空間に `approved` の版があるのに既定グラフが空なら、欠落として報告し修復する。判定は `ASK { ?s ?p ?o }` 相当のクエリで行う（`list_graphs` とは別に確認する必要がある。論点 4）。

**内容の食い違い（既定グラフに別の版が載っている）は検出しない。** 検出には内容の比較が必要で、Phase 1 の範囲を超える（未解決事項に置く）。

### 5. 修復しても報告を消さない

`missing_graphs`（何が欠けていたか）はそのまま残し、修復できたものを `graphs_repaired` として**別に**報告する。**修復が成功したことを理由に欠落の記録を消してはならない。**

運用者にとって `graphs_repaired` が空でないことは「上流に問題がある」という信号であり、成功報告ではない。

### 6. 背景での自動自己修復は導入しない

修復は運用者が `POST /admin/reconcile` を叩いたときにだけ起きる。定期実行するループやフックは作らない。

## 根拠

### 論点 1 への答え: 境界を広げるのではなく、正しい証拠を使う

「`projected_at` が非 NULL の版を再射影してよいか」という問いの立て方自体が、`projected_at` に 2 つの意味を混同させていた。決定 1 でこれを分離すると、問いは「**ストアが持っていないと観測された版を直してよいか**」に変わり、答えは自明に「よい」になる。ストアは再構築可能な派生物であり、正本から作り直すことが設計そのものだからである（ADR-0002）。

境界を広げる案（`unprojected()` に非 NULL も含める）を採らないのは、それが**毎回すべての版を無条件に再射影する**ことになり、証拠に基づかない動作になるためである。

### 論点 2 への答え: 決定の所有者を 1 つに保つ

`superseded` の在否について reconcile とローダが両方意見を持つと、必ず食い違う。ローダは `SUPERSEDED_RETAIN`（Fuseki コンテナの環境変数）を見て決めるが、**reconcile（Core API）はこの値を知らない**。

reconcile 側にも同じ設定を持たせる案は、**同一の決定を 2 箇所で設定する**ことになり設定のドリフトを生む。`P1-22` で「判断が二箇所に存在すると、片方だけ直して食い違う」という同じ問題を一度解いている。

したがって `superseded` は reconcile の契約外とし、その在否はローダの再構築時の判断に委ねる。運用者が `SUPERSEDED_RETAIN` を変えたなら、反映させる手段は再構築である。

### 論点 3 への答え: reconcile は運用者が叩くものであり、報告は消さない

論点 3 の懸念は「静かに自己修復して原因が見えなくなる」ことだった。しかし **reconcile は背景で回っていない**（決定 6 で今後も回さない）。運用者が明示的に叩いたときにだけ動くので、「勝手に直った」という状況は起きない。

その上で決定 5 により、修復した事実は必ず報告に残る。さらに reconcile は最後にマニフェストを PostgreSQL から再生成するので、**ローダのスキップ原因がマニフェストの欠落・破損であればその原因自体も直る**。

一方、原因が別（Blob へ到達できない、`GRAPH_IRI_BASE` の食い違い、ローダのクラッシュ）なら、**修復は毎回症状だけを消し続ける**。だからこそ `graphs_repaired` が空でないことを異常の信号として扱う必要がある。README と API のドキュメントにこの読み方を書く。

### 論点 4 への答え: エージェントが読む場所を検出対象から外してはいけない

既定グラフは「`GRAPH` 句を書かないクエリが単一の承認済み現行版を返す」という中心的な性質（ADR-0010 決定6、`P1-C1` の Critical）を担う場所である。名前付きグラフだけを見る検出は、**最も重要な読み取り経路を検査していない**。

`list_graphs` を既定グラフも返すように変える案は採らない。SPARQL には「既定グラフ」を名前で列挙する仕組みが無く、`list_graphs` の契約（名前付きグラフの IRI を返す）を曖昧にする。別の確認として実装する。

## 検討した代替案

### 欠落を検出したら `projected_at` を NULL に戻し、既存の `unprojected()` に拾わせる

最も実装が小さい。`reset_projected` の既存の意味（「射影をやり直す必要がある」）にも沿う。

**却下する理由**: (a) 修復が次回の reconcile 実行までずれる（同一実行内で直すにはループの順序を組み替える必要があり、「射影ループを先に置く」という残留誤検出防止の順序と衝突する）、(b) 観測（ストアに無い）を正本の列に書き戻すことになり、決定 1 で分離した 2 つの意味を再び混ぜる。**証拠は証拠のまま使い、正本の列に混ぜない。**

### 報告のみで修復しない（現状維持）

`P1-19` の現状。運用者は報告を見て再構築を促せばよい、という立場。

**却下する理由**: reconcile は「正本を基準にストアの状態を揃える」と名乗っている。**揃えられる乖離を揃えないのは契約違反である。** 特に原因がマニフェストなら reconcile 自身が原因を直せるのに、症状を直さないのは不合理。

### reconcile に `SUPERSEDED_RETAIN` を持たせる

reconcile がローダと同じ保持ポリシーを適用できるようになる。

**却下する理由**: 同一の決定を 2 箇所で設定することになる（上記「論点 2 への答え」）。将来ローダが件数指定の保持ポリシーを実装したら（ADR-0010 の未解決事項）、その実装も 2 箇所に増える。

### 背景で定期的に自己修復する

ストアの乖離が自動的に閉じるので運用が楽になる。

**却下する理由**: 論点 3 の懸念が現実になる。加えて、不変条件3（射影の失敗は正本への書き込みを失敗させない）は「**失敗を握り潰す代わりに、回収の責任を運用者が起動する経路に置く**」という設計であり、背景で静かに直すのはこの設計と噛み合わない。

### 既定グラフの内容の食い違いまで検出する

既定グラフに別の版が載っている状態も検出する。

**却下する理由（Phase 1 では）**: 内容の比較が必要で、トリプル数の一致は等価性を保証しない。正しくやるには正規化（c14n）が必要で Phase 1 の範囲を超える。未解決事項に置く。

## 結果（トレードオフ・影響）

### 得られるもの

- **ローダのスキップから自力で回復できる。** データセットが空になった名前空間を、運用者が reconcile を叩くだけで（マニフェストの再生成と合わせて）復旧できる
- **エージェントが読む既定グラフが検査対象に入る。** 「`GRAPH` 句なしのクエリが何も返さない」という最も分かりにくい障害が検出できる
- **`projected_at` の意味が確定する。** 「書き込み経路の知識」であり「ストアの現在の状態」ではない。この区別が曖昧なままだと、今後も「どちらの列を信じるか」という問いが再発する
- **決定の所有者が 1 つになる。** `superseded` の在否はローダ、常に在るべき版は reconcile

### 受け入れるコスト

- **reconcile が Blob を読む回数が増える。** 欠落 1 件あたり 1 回の `get_version`。対象は `in-review` + `approved` に限られるので名前空間あたり数件で収まる
- **`superseded` の欠落は誰も直さない。** `SUPERSEDED_RETAIN` を 0 以外にしている運用者は、欠落したら再構築が必要。報告もされない
- **既定グラフの内容の食い違いは検出できない。** 空かどうかだけを見る
- **修復が上流の問題を隠しうる。** 決定 5（報告を消さない）と運用手順の記述で緩和するが、構造的には残る

### 影響を受ける他の決定

- **[ADR-0002](0002-triple-store-as-rebuildable-projection.md)**: 「再構築可能な射影」という性質を、`reconcile` が**部分的な再構築**としても使えるようにする。全体の再構築（ローダ）と増分の修復（reconcile）の 2 段になる
- **[ADR-0010 補記1](0010-approval-and-projection.md)**: 欠落側を「報告のみ」としていた判断をこの ADR が上書きする。補記1 には「復旧は `P1-25` に分離」と書いてあり、その分離の結論がこれである
- `ReconcileReport` に `graphs_repaired` が加わる

### 未解決のまま残す問い

- 既定グラフの**内容**の食い違い（別の版が載っている）の検出。正規化を伴う比較が必要
- `superseded` の保持ポリシーを reconcile 側にも反映させる必要が出た場合の設計（ローダと設定を共有する仕組み）
- 修復の回数が多いことを異常として能動的に知らせる仕組み（健全性指標 `P2B-06` の対象）

## 補記: 退役を乖離の一種として扱う (2026-09-12、`P2B-19`)

[ADR-0032](0032-namespace-retirement.md) で名前空間の退役が入った。
`reconcile` は退役した名前空間について**射影せず、残っているグラフを消す**。

**これはこの ADR の「観測された乖離を直す」そのものである。** 正本が
「1 版も載せない」(マニフェストの `skip:retired`)と言っているのにストアに
載っているなら、それは乖離である。

**必要になった理由は `retire` が `projected_at` を `NULL` に戻すからである**
(ADR-0032 決定3。`unretire` したときに拾えるようにするため)。
何もしないと `unprojected()` が全版を返し、**`reconcile` が即座に射影を
戻してしまう**。

報告に 2 つ足した。**黙って飛ばさない** — 報告に出ないと、運用者は
「reconcile を回したのに射影が戻らない」を故障として調べ始める。

| 欄 | 意味 |
|---|---|
| `retired_namespaces` | 退役しているので射影しなかった名前空間 |
| `retired_graphs_removed` | 退役した名前空間に残っていたので消したグラフ |
