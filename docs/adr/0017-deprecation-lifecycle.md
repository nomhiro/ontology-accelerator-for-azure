# ADR-0017: 廃止のライフサイクル

- 状態: 採用
- 日付: 2026-09-10
- 関連: [ADR-0009](0009-ontology-operations.md) 決定3（オントロジーは縮められなければならない）・決定1（決定可能性による分業）・未解決事項「廃止された用語を参照するクエリへの警告」、[ADR-0006](0006-ontology-versioning-and-audit.md)（不変リビジョン）、[ADR-0016](0016-semantic-diff.md) 決定6（削除のブロックを `P2B-03` に送った）、[ADR-0001](0001-rdf-store-selection.md)（SPARQL 1.1 Protocol をハード境界にする）、バックログ `P2B-03`

## コンテキスト

[ADR-0009](0009-ontology-operations.md) 決定3 は「オントロジーは縮められなければならない」と決め、3 つを要求した。

1. 用語単位で `owl:deprecated` を立て、後継への参照を持たせる
2. **IRI を削除も再利用もしない。** 廃止済みとして残す
3. 廃止された用語を参照するクエリには、API 層で警告を返す

現状はどれも実装されていない。ただし [ADR-0016](0016-semantic-diff.md)（`P2B-09`）が **IRI の削除を観測可能にした**。同 ADR 決定6 は削除のブロックを意図的にこの ADR へ送った — **廃止の経路が無い状態で削除をブロックすると、縮める正当な手段が 1 つも無くなる**からである。その順序の依存がここで解ける。

同 ADR-0009 は未解決事項に「廃止された用語を参照するクエリへの警告を、どの層でどう返すか（**SPARQL の結果に警告を混ぜられない**）」を残していた。

決めるべきことは 4 つある。

1. **廃止の情報をどこに持つか**（TTL か PostgreSQL か）
2. **何を形式的に検証し、どれをブロックするか**
3. **廃止された用語を参照するクエリへの警告を、どこにどう載せるか**
4. **IRI の削除をいつからブロックするか**

## 決定

### 1. 廃止は TTL に書く。PostgreSQL に別のテーブルを作らない

`owl:deprecated true` と後継への参照（`dcterms:isReplacedBy`）は**オントロジーの内容そのもの**である。「この用語はもう使うな、代わりにこれを使え」は定義に関する主張であり、W3C の語彙がそれを表現するために存在する。

**責任者（[ADR-0015](0015-term-owners.md)）を TTL に書かなかったのと逆の判断であり、理由も逆である。** 責任者は**現在の状態**で、変わるたびに新しい版を公開することになるので TTL には置けなかった。廃止は**定義の一部**であり、廃止した事実が版に固定されるのは正しい（不変条件7）。

副産物として、廃止は SPARQL でそのまま引ける。専用の API を作らずに `?s owl:deprecated true` で問い合わせられる。

### 2. 形式的に検証する。ブロックするのは 2 つだけ

[ADR-0009](0009-ontology-operations.md) 決定1 は「形式的に決定可能なものは機械が確定的に判定する」と決めた。**ただし決定可能であることは、ブロックすべきであることを意味しない。** ブロックが妥当なのは、規則が一義的で、**かつ従う正当な手段が常にある**ときである。

| 検査 | 決定可能 | 扱い |
|---|---|---|
| **IRI の削除**（現行版にあった用語が消えた） | はい | **ブロック**（422） |
| **廃止された用語に後継も理由も無い** | はい | **ブロック**（422） |
| 生きている用語が廃止された用語を参照している | はい | **報告のみ** |

**IRI の削除をブロックする理由**は決定3 そのものである。従う手段は「削除せず `owl:deprecated` を立てる」で常にある。

**後継も理由も無い廃止をブロックする理由**は、それが利用者に何も伝えないからである。「この用語は使うな」だけでは、利用者は代わりに何を使えばよいか分からない。**後継が無いこと自体は正当**（間違って作った用語、統合されずに消える概念）なので、後継（`dcterms:isReplacedBy`）**または**理由（`rdfs:comment` / `skos:historyNote`）のどちらかを要求する。両方を要求はしない。

**生きている用語からの参照をブロックしない理由**は、**SHACL の形状やマッピングが廃止された用語を正当に参照する**からである。旧データを検証する形状、旧→新のマッピング（`dcterms:replaces`）はどちらも書けなければならない。ブロックすると移行のための記述が禁止される。**報告に留める**（下記の警告と、`validate` の報告に出す）。

なお `dcterms:replaces` と `rdfs:seeAlso` による参照は**歴史的参照**として最初から問題として数えない。これらは「昔これがあった」を記録するための述語であり、参照しているのが目的である。

### 3. クエリの警告は **SPARQL の結果の外**に載せる。層ごとに置き場所が違う

**SPARQL Results JSON を書き換えない。** [ADR-0001](0001-rdf-store-selection.md) は「SPARQL 1.1 Protocol をハード境界にし、`SPARQL_ENDPOINT` を差し替えられる」ことを設計原則にした。結果の JSON に独自のキーを混ぜると、標準の形を期待するクライアントとの互換が崩れ、ストアを差し替えたときに挙動が変わる。

| 層 | 置き場所 | 理由 |
|---|---|---|
| **Core API** (`POST /namespaces/{ns}/sparql`) | **HTTP レスポンスヘッダ** `X-Ontology-Deprecated-Terms` | 本文は標準の SPARQL Results JSON のまま。ヘッダは無視しても壊れない |
| **MCP** (`sparql_query`) | **ツール結果の本文**（`deprecation_warnings` キー） | ツール結果の形は**この製品が定義するもの**で、SPARQL の protocol ではない。**エージェントはヘッダを見ない** — 見えなければ廃止された用語を自信を持って使う |

**MCP だけ本文に載せるのが、この決定の要点である。** 「AI エージェントに正しいコンテキストを渡す」ことがこの製品の目的なので、エージェント経路で警告が届かないなら警告を作る意味がない。一方で Core API の SPARQL 応答は標準であり続けなければならない。**同じ情報を、層ごとに違う場所に置く。**

`SELECT` の結果に現れた IRI のうち廃止されているものを列挙する。判定にはデータセットへの追加のクエリ 1 本（`?s owl:deprecated true`）を使う。

### 4. 削除のブロックは、廃止の経路と同時に入れる

[ADR-0016](0016-semantic-diff.md) 決定6 が送った判断をここで実行する。**同じ変更で「削除を禁じる」と「廃止できる」を入れる。** 順序を逆にすると、縮める手段が無い状態で削除だけが禁止される期間ができる。

基準は「その承認によって `superseded` になる版」である（ADR-0016 決定2 と同じ）。**最初の承認では基準が無いのでブロックしない。**

**検査は状態遷移より前に置く**（SHACL 検証と同じ理由。承認後の検査は意味が無い）。差分の計算（ADR-0016 は状態遷移の後に置いた）とは扱いが違う — あちらはブロックしないので前に置く理由が無かった。

## 検討した代替案

### 廃止を PostgreSQL のテーブルで管理する

責任者（`term_owners`）と同じ形にできる。**却下**: 決定1 の理由。廃止は定義の一部であり、版に固定されるべきである。テーブルに置くと、過去の版を参照したときに「その時点で廃止されていたか」が失われる（テーブルは現在の状態しか持たない）。

### 廃止された用語を既定グラフから外す

エージェントが廃止された用語を見なくなる。**却下**: 「廃止済みとして残す」（決定3）に反する。廃止された用語を**引けなくする**と、過去のデータを解釈できなくなる。廃止は「もう使うな」であって「無かったことにする」ではない。SNOMED CT や GO が IRI を残し続けるのはこのためである。

### 生きている用語から廃止された用語への参照もブロックする

一貫性は高い。**却下**: 決定2 の理由。SHACL の形状とマッピングが正当に参照する。ブロックすると移行のための記述が書けなくなる。

### 後継の指定を必須にする（理由では代替させない）

利用者に必ず移行先を示せる。**却下**: 後継が存在しない廃止は正当にある（間違って作った用語、統合されずに消える概念）。必須にすると、存在しない後継を捏造させることになる。

### 警告を SPARQL Results JSON に追加のキーとして混ぜる

すべての経路で同じ形になり実装も 1 つで済む。**却下**: [ADR-0001](0001-rdf-store-selection.md) の「SPARQL 1.1 Protocol をハード境界にする」に反する。標準の形を期待するクライアントが壊れ、ストアを差し替えたときの挙動が変わる。**MCP のツール結果は SPARQL の protocol ではない**ので、そちらだけ本文に載せるのは矛盾しない。

### 警告を出さない（`owl:deprecated` を引くのは利用者の責任とする）

追加のクエリが不要で速い。**却下**: 「AI エージェントに正しいコンテキストを渡す」がこの製品の目的である。エージェントは廃止されていることを自分で確認しない。**黙って古い定義を使わせるのは、この製品が存在する理由に反する。**

### 削除のブロックを `P2B-09` の時点で入れる

早く規律が効く。**却下（`P2B-09` の時点で判断済み）**: 廃止の経路が無い状態で削除を禁じると、縮める正当な手段が 1 つも無くなる。ADR-0009 決定3 の目的そのものに反する。

## 結果（トレードオフ・影響）

### 得られるもの

- **オントロジーが縮められるようになる。** ADR-0009 決定3 の 3 項目すべてが動く
- **IRI の削除が実際に禁止される。** [ADR-0016](0016-semantic-diff.md) が観測可能にしたものを強制に変える
- **エージェントが廃止された用語を黙って使わなくなる。** MCP の結果に警告が載る
- 廃止は SPARQL でそのまま引ける（`?s owl:deprecated true`）

### 受け入れるコスト

- **SPARQL の応答に追加のクエリ 1 本が乗る。** 廃止された用語の集合を引くため。結果は小さいが往復が 1 回増える
- **Core API の利用者はヘッダを見ないと警告に気づかない。** 標準の SPARQL Results JSON を保つための代償である
- **既存の承認フローが 1 つ厳しくなる。** 用語を削除した版は承認できなくなる。`P2B-09` の時点では通っていた（そのときのテストを更新した）
- **廃止された用語への参照は報告に留まる。** 「気づけるが止まらない」状態が残る
- **廃止の取り消しは検査しない。** 誤った廃止を戻す経路を塞がないため

### 影響を受ける他の決定

- **[ADR-0009](0009-ontology-operations.md) 決定3**: 実装される。未解決事項「廃止された用語を参照するクエリへの警告」を閉じる（**層ごとに置き場所を変える**）
- **[ADR-0016](0016-semantic-diff.md) 決定6**: 「削除はブロックしない」を**この ADR が上書きする**。差分は依然として報告のみだが、承認は削除を拒否する
- **[ADR-0010](0010-approval-and-projection.md)**: `approve` の検査が 1 つ増える。**状態遷移より前**に置く

### 未解決のまま残す問い

- **名前空間をまたぐ参照。** 別の名前空間で廃止された用語を参照している場合は検出しない（そのデータセットを引かないため）
- **廃止された用語の責任者**（[ADR-0015](0015-term-owners.md) の未解決事項）。残すか外すかは決めていない
- **廃止の警告の粒度。** 「結果に現れた」だけを見ており、クエリ本文に書かれた廃止済み IRI（結果が空でも警告に値する）は検出しない
- **推移的な後継の解決。** `A → B → C` と廃止が連鎖したとき、`A` の利用者に `C` を示すべきかどうか

---

## 補記: 報告の種類を 1 つ足した (2026-09-12、`P2B-18`)

[ADR-0030](0030-mapping-target-lifecycle.md) 決定5 で
`ProblemKind.MAPPED_BY_OTHERS` を足した。**廃止する用語へ他の名前空間から
マッピングが張られている**ことを、廃止する側に報告する。

**ブロックしない。** 決定2 の規則(「ブロックが妥当なのは、規則が一義的で
**かつ従う正当な手段が常にある**ときだけ」)がそのまま効く — ブロックすると
**マッピングを張るだけで相手の廃止を封じられる**。張られた側は相手の行を
消せない(ADR-0023 決定3 により逆向きの書き込み口が無い)ので、
**従う手段が無い。**

決定3(`sparql_query` に廃止警告を付ける)と同じ穴が**マッピングの経路**に
開いていたことも、ADR-0030 で塞いだ。`term_mappings` の各件に終点の生死が
付き、廃止済みなら後継も返る。
