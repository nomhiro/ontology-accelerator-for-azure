# ADR-0006: オントロジーのバージョニングと監査 — 不変リビジョンと PROV-O

- ステータス: 承認済み
- 日付: 2026-08-28

## コンテキスト

このカテゴリの製品が解決する問題は、「AI エージェントに正しい社内知識を渡す」だけではない。**その知識がなぜ正しいと言えるのかを後から説明できること**にある。AWS 版の訴求も「説明可能・監査可能な意思決定」である。

当初の設計案には、この要素が明確に不足していた。オントロジーを生成し、承認し、Fuseki に載せてエージェントに提供する流れは描けていたが、次の問いに答えられなかった。

- **「3 か月前にエージェントが下したこの判断は、どの版のオントロジーに基づいていたのか」**
- **「この用語定義は誰が提案し、誰が承認したのか。なぜその定義になったのか」**
- **「オントロジーを更新したら、既に動いているエージェントの挙動が変わってしまうのではないか」**
- **「監査を受けたとき、AI に渡した文脈の履歴を提示できるか」**

これらは規制産業(金融、医療、製造)での採用可否を左右する要件である。また、オントロジーの更新がエージェントの挙動を予告なく変えてしまう構造は、**運用上の信頼を損なう**。

一方で本プロジェクトは「W3C 標準に忠実」を掲げている。監査の表現に独自のスキーマを発明すると、その看板と整合しない。

## 決定

**バージョニングと監査を、後付けの機能ではなく中核機能として設計する。** 実装は Phase 2。

### 1. オントロジーを不変リビジョンとして保存する

- **識別子は コンテンツハッシュ + semver** の組み合わせとする
- 承認されたオントロジーは Blob Storage に**バージョン付き TTL** として保存する([ADR-0003](0003-postgresql-as-system-of-record.md))
- **リビジョンは一度作られたら変更されない。** 修正は新しいリビジョンの作成として表現する

### 2. バージョンごとに別の名前付きグラフへ射影する

- Fuseki へ射影する際、**バージョンごとに異なる名前付きグラフ**に載せる
- **エージェントはバージョンを固定して参照できる。** オントロジーが更新されても、明示的に切り替えない限り挙動が変わらない

### 3. 監査証跡を PostgreSQL に記録し、PROV-O で表現する

記録する内容:

| 項目 | 内容 |
|---|---|
| 誰が提案したか | 提案者(人間 / LLM のどちらか、およびモデル識別子) |
| 誰が承認したか | 承認者(Entra ID の主体) |
| いつ | 提案時刻、承認時刻 |
| 差分 | 前リビジョンからの diff |
| 理由 | 提案の根拠、承認・却下のコメント |

表現には **W3C PROV-O** を用いる。`prov:Entity`(リビジョン)、`prov:Activity`(提案・承認)、`prov:Agent`(人間・LLM)、`prov:wasDerivedFrom`(リビジョン間の派生)といった標準語彙に対応させる。

### 4. コンテキストのアクセスログを記録する

エージェントへ提供したコンテキストについて、**どのバージョンの何を返したか**を記録する。

> **実装した([ADR-0018](0018-context-access-log.md)、2026-09-10、`P2B-05`)。** 「コンテキスト」は SPARQL の経路に限ると決めた。イベント(`access_events`)と用語ごとの集約(`term_access`)に分け、**集約はイベントより長生きする**(保持期間を過ぎたイベントを消しても「最後にいつ参照されたか」は残らなければならない)。

## 根拠

### 不変リビジョンが説明可能性の土台になる

「あの時点でのオントロジー」を再現できなければ、過去の判断を説明できない。可変なグラフを更新していく設計では、この再現が原理的に不可能である。

**不変リビジョン + コンテンツハッシュ**であれば、
- ハッシュが一致すれば内容が同一であることが保証される
- 「エージェントがバージョン `1.4.0`(ハッシュ `a1b2...`)を参照した」という記録が、内容の証明になる
- 改変の検出ができる

### semver を併用する理由

コンテンツハッシュだけでは、**変更の性質**が人間に伝わらない。オントロジーの変更には明確に異なる影響度がある。

- **破壊的変更**(クラスの削除、プロパティのドメイン変更)— 既存のクエリが壊れる
- **後方互換な追加**(新しいクラスの追加)— 既存のクエリは動き続ける
- **修正**(ラベルや注釈の訂正)— 意味論に影響しない

semver はこの区別を利用者に伝える確立された語彙である。ハッシュが「同一性」を、semver が「互換性の意図」を担う。

### バージョン固定参照が運用上の信頼を作る

エージェントが常に最新版を参照する設計では、**オントロジーの承認がエージェントの挙動を予告なく変える**。承認する専門家は、自分の承認が本番のエージェントに即座に影響することを恐れて、承認をためらうようになる。

バージョン固定ができれば、
- オントロジーの改善と、エージェントへの適用が分離される
- 新バージョンを検証環境のエージェントで試してから本番に適用できる
- 問題が起きたら参照バージョンを戻せる

これは**ソフトウェアの依存関係管理と同じ構造**である。オントロジーをエージェントの「依存関係」として扱う。

### 名前付きグラフによる実装が標準の枠内で成立する

バージョンごとに別の名前付きグラフに載せる方式は、RDF の標準的な機能(named graph)で実現できる。独自の仕組みを持ち込まない。

- SPARQL の `FROM` / `GRAPH` 句でバージョンを指定できる
- 複数バージョンを同一ストアに共存させられる
- [ADR-0002](0002-triple-store-as-rebuildable-projection.md) の射影設計と整合する(どのバージョンを射影するかを Core API が制御する)

### PROV-O を使う理由

監査証跡のスキーマを自分で発明する必要はない。W3C **PROV-O** は「あるものが、誰によって、何から、どのように生成されたか」を記述するための勧告であり、まさにこの用途のために作られている。

- **W3C 忠実路線と整合する。** 監査だけ独自スキーマ、という不整合を避けられる
- **相互運用性がある。** PROV-O を理解する外部ツールがそのまま使える
- **語彙設計の議論を省略できる。** 「提案者」と「承認者」をどうモデル化するかという設計判断が、標準に委ねられる
- オントロジーを扱う製品が、**自身のメタデータも標準語彙で表現している**ことは、設計の一貫性の表明になる

なお、**PROV-O で表現すること**と、**PostgreSQL に保存すること**は矛盾しない。PROV-O は表現の語彙であり、保存媒体を指定しない。トランザクション、外部キー制約、時系列検索が必要なため保存先は PostgreSQL とし([ADR-0003](0003-postgresql-as-system-of-record.md))、PROV-O 準拠の RDF として出力・公開できるようにする。

### アクセスログが監査の最後のピースになる

オントロジーの履歴が完全でも、「そのオントロジーからエージェントに実際に何が渡ったか」が分からなければ、判断の説明は完結しない。どのバージョンの何を返したかを記録することで、**「AI がこう答えた理由」を文脈まで遡って提示できる**。

## 検討した代替案

### Git でオントロジーをバージョン管理する

**却下(ただし発想は取り入れる)。** TTL はテキストであり、Git で管理すれば履歴・差分・ブランチが無料で得られる。開発者にとって馴染みのあるモデルでもある。

却下理由:
- **承認フローが Git のワークフローに縛られる。** オントロジーをレビューするのはビジネスの専門家であり、必ずしも Git を使える人ではない。Web UI で承認する体験と Git の整合を取るには、Git 操作をアプリから代行することになり、複雑さが増す
- **RBAC が二重管理になる。** 名前空間 × ロールの権限を PostgreSQL で管理する一方で、Git リポジトリの権限を別途管理することになる
- **テキスト差分は RDF の差分ではない。** TTL のテキスト diff は、トリプルの並び替えやプレフィックスの変更でノイズだらけになる。意味のある差分にはグラフレベルの diff が必要である

なお「不変リビジョン + コンテンツハッシュ + 派生関係」という発想自体は Git のモデルから来ている。**モデルは借り、実装は借りない**という判断である。

### 可変グラフを更新し、変更ログのみを記録する

**却下。** 実装が最も単純で、ストアの容量も節約できる。

却下理由: **過去の状態を再現できない。** 変更ログから逆再生して復元する方式は理論上可能だが、(a)復元の正しさを保証するのが難しく、(b)「あの時点のオントロジー」の取得が高コストな操作になり、(c)エージェントによるバージョン固定参照が実現できない。監査可能性を中核機能に据える方針と両立しない。

### RDF の標準的なバージョニング語彙(`owl:versionIRI` など)のみに頼る

**却下(併用はする)。** `owl:versionIRI` と `owl:versionInfo` はオントロジー自身にバージョンを記述する標準的な方法である。

却下理由: これらは**オントロジー文書の自己申告**であり、承認履歴・提案者・差分・理由といった**プロセスのメタデータ**を表現しない。またコンテンツハッシュによる同一性保証も提供しない。`owl:versionIRI` は**リビジョンの識別子として併用する**が、監査証跡の仕組みとしては不足である。

### 監査証跡を独自の JSON スキーマで設計する

**却下。** 実装は速い。しかし W3C 標準忠実路線を掲げるプロジェクトが、自身のメタデータには独自スキーマを使うのは一貫性を欠く。PROV-O を採用する追加コストは、語彙を学ぶ時間だけであり、それは設計判断を標準に委ねられる利益で相殺される。

### すべてのバージョンを常に Fuseki に載せる

**却下(保持ポリシーで制御する)。** すべてのリビジョンを名前付きグラフとして常時ストアに置けば、任意のバージョンにいつでもクエリできる。

却下理由: **EmptyDir の容量上限(1 vCPU で 4 GiB、超で 8 GiB)を圧迫し、起動時の再構築時間が単調増加する**([ADR-0002](0002-triple-store-as-rebuildable-projection.md))。リビジョンは蓄積し続けるため、この設計は時間とともに劣化する。

代わりに、**ストアに載せるバージョンを保持ポリシーで制御する**(最新版 + 参照中のバージョン + 直近 N 版など)。正本は Blob にあるため、ストアに載っていないバージョンも必要になれば射影し直せる。

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **実装量が増える。** リビジョン管理、グラフレベルの diff、承認フローの状態機械、PROV-O へのマッピング、アクセスログ。**Phase 2 の作業量の相当部分をこれが占める**
- **グラフ差分の実装が必要になる。** 意味のある diff にはトリプル集合の比較(かつ blank node の扱いを考慮した比較)が必要で、テキスト diff より手間がかかる
- **ストレージが単調増加する。** 不変リビジョンを保持するため、Blob の容量が増え続ける。Blob のライフサイクル管理(古いリビジョンを Cool / Archive 階層へ)で緩和する
- **保持ポリシーという新しい設計判断が生じる。** どのバージョンをストアに載せておくか、載っていないバージョンへのクエリをどう扱うか(オンデマンド射影か、エラーか)を決める必要がある
- **PROV-O の語彙を学ぶ必要がある。** コントリビューターにとっての学習コストになる。ドキュメントでのマッピング説明が必要
- **アクセスログの量が多くなる可能性がある。** エージェントの呼び出し頻度に比例するため、保持期間とサンプリングの設計が必要になる

### 得られるもの

- **規制産業での採用可能性が開ける。** 監査に対して履歴を提示できる
- **オントロジーの改善とエージェントへの適用が分離される。** 承認が本番に即座に影響しないため、専門家が安心して承認できる。**これは運用上の信頼に直結する**
- **問題発生時にバージョンを戻せる。** オントロジーの変更が原因のエージェント挙動の劣化を、参照バージョンの切り戻しで即座に止められる
- **AI の出力に対する説明責任を果たせる。** 「なぜそう答えたか」を、参照したオントロジーのバージョンとその承認履歴まで遡って示せる
- **設計の一貫性。** オントロジーを扱う製品が、自身のメタデータも W3C 標準語彙で表現している

### 影響を受ける他の決定

- [ADR-0002](0002-triple-store-as-rebuildable-projection.md) — バージョンごとの名前付きグラフへの射影は、射影設計と一体である。保持ポリシーは EmptyDir の容量制約から要求される
- [ADR-0003](0003-postgresql-as-system-of-record.md) — 不変リビジョンを Blob に、監査証跡を PostgreSQL に置く配置は本 ADR の要件から導かれている

## 補記: 廃止のライフサイクルと保持ポリシーの実装 (2026-09-01)

本 ADR は「オントロジーを不変リビジョンとして保存する」という**増やす方向の原則**を定めた。
[ADR-0009](0009-ontology-operations.md) はその裏側として **「オントロジーは縮められなければならない」**
を同格の原則として追加する。用語単位の `owl:deprecated` と後継への参照を持たせ、
IRI の削除と再利用を禁じる。追加しかできないオントロジーは必ず腐るためである。

また本 ADR は「ストアに載せるバージョンを保持ポリシーで制御する(最新版 + 参照中のバージョン +
直近 N 版など)」と決定したが、**実装が存在しなかった**。ローダが全 TTL を各名前付きグラフへ
読み込み、`tdb2:unionDefaultGraph = true` のため既定グラフが全バージョンの和集合になり、
`GRAPH` 句なしのクエリで新旧の定義が同時に返る状態になっていた(2026-09-01 に実測)。

保持ポリシーの実装と「既定グラフは常に単一の版を指す」ことを **Phase 2 の必須項目**とする。
バックログの `P1-C1`(欠陥修正) および `P2B-02`(保持ポリシー) を参照。

> **保持ポリシーを実装した([ADR-0019](0019-retention-policy.md)、2026-09-10、`P2B-02`)。** 判断は正本側(Python)で行い、マニフェストの `projection` で運ぶ。`SUPERSEDED_RETAIN` は**個数**として効くようになった(以前は名前が「N 版保持」なのに実装は真偽値だった)。**「参照中のバージョン」は保持の対象にしていない** — アクセスログが `GRAPH` 句で明示された版を解決できないため(ADR-0018 未解決事項)。

## 補記 2: 監査証跡の読み出し (2026-09-10、`P2B-08` / `P2B-11`)

決定3 は「監査証跡を PostgreSQL に記録する」と決めたが、**読み出す口を決めていなかった**。実装して 2 段構えになった。

| 口 | 粒度 | 用途 | 権限 |
|---|---|---|---|
| `GET /namespaces/{ns}/versions/{v}/decisions` | 1 つの版。**起きた順** | エージェントが答えの根拠を示す(MCP の `version_decisions`) | `data-analyst` |
| `GET /namespaces/{ns}/audit` | 名前空間全体。**新しい順**・絞り込み・ページング | 運用者が「先週何が起きたか」「この人が何をしたか」を追う | `data-analyst` |

### 並び順とページングの鍵は `id` である。`occurred_at` ではない

`occurred_at` の既定値は `now()` で、**PostgreSQL の `now()` はトランザクション開始時刻**を返す。同一トランザクション内で記録した複数のイベントは**同じ値になる**。時刻を鍵にページングすると、境界にある同時刻の複数件を取りこぼすか二重に返す。`id` は追記専用のテーブル([ADR-0011](0011-database-privilege-separation.md) 決定2 で `DELETE` を剥奪している)の単調増加する主キーなので、**全順序で安定**している。

**offset ではなく keyset(cursor)にする。** 照会している最中に新しいイベントが追記されるのは普通に起こる。降順の offset ページングだと、新しい行が先頭に入るたびに窓が 1 件ずれ、**既読のページの末尾を取りこぼす**。`id < cursor` で辿れば、追記は必ず大きい `id` を持つので既読のページは動かない。

### 集約した口に、より強い権限を要求しない

名前空間全体の照会も `data-analyst` である。版単位の `decisions` が既に `data-analyst` で読めるため、**版を列挙すれば同じ情報を集められる**。足し合わせれば見えるものを集約したときだけ隠すのは見せかけの制限であり、「守られている」という誤解を作るぶん、制限が無いより悪い。

### 期間は半開区間 `[since, until)`。日時はタイムゾーン必須

境界を両側とも含めると、期間を並べて集計したときに二重に数える。タイムゾーンの無い日時を素朴に UTC と解釈しないのは、**監査の照会で 9 時間ずれた結果を返すのは「何も返らない」よりたちが悪い**からである(誤った結論の根拠になる)。

### 未解決のまま残す問い

- **名前空間をまたぐ照会**(「この人が全名前空間で何をしたか」)。権限判定が名前空間単位では収まらないため、`platform-admin` に限るか、見える名前空間だけを合成するかを決めていない
- **アクセスログ**(決定4)は未実装のままである(`P2B-05`)。この口が返すのは「オントロジーに何が起きたか」で、「エージェントに何を返したか」は含まない

## 補記 3: PROV-O での書き出しと、名前を挙げた語彙のうち出さないもの (2026-09-12、`P2A-07`)

[ADR-0026](0026-provenance-export.md) で決定3 の後半(「PROV-O 準拠の RDF として出力・公開できるようにする」)を実装した。`GET /namespaces/{ns}/provenance` が `text/turtle` を返す。権限は `/audit` と同じ `data-analyst` である(同じ情報を別の語彙で出すだけなので、ここだけ厳しくすると補記 2 の「見せかけの制限」になる)。

**決定3 が名前を挙げた `prov:wasDerivedFrom` は出さない。** この ADR を書いた時点の想定と、実装した記録の内容が食い違っていた。

`audit_events` には**「どの版から編集したか」が無い**。`publish` は `base_version` を受け取るが、lost update の検出にだけ使って保存していない(`P1-13`)。[ADR-0016](0016-semantic-diff.md) 決定2 が差分の基準を「この承認によって `superseded` になる版」と決めたのは**実務上の基準**であって、著者が実際に何から編集したかではない。

つまりこのシステムが知っているのは**承認の順序**だけである。「2.0.0 は 1.0.0 の次に承認された」は記録されているが、「2.0.0 は 1.0.0 から派生した」は記録されていない。承認の順序から `prov:wasDerivedFrom` を出せば、**測っていないことを標準語彙で主張する**ことになる。しかも**相互運用性があるぶん害が大きい** — 外部の PROV ツールは派生の系譜として表示し、誰も疑わない。「相互運用性がある」という上の根拠は、嘘を書いたときの害も同じだけ大きくする。

同じ理由で、決定3 が括弧で書いた「`prov:Agent`(**人間・LLM**)」の区別も出さない。`audit_events.actor` は Entra のオブジェクト ID だけで、人間かサービスプリンシパルかを持っていない。`prov:SoftwareAgent` と書けば外部ツールは「自動生成」と読む — **四眼原則を記録する監査証跡で、人間の承認を自動化された行為として見せるのは最悪の誤りである。**

果たすために必要なものは分離した。

| 何が要るか | バックログ |
|---|---|
| `base_version` を保存する(そうすれば `prov:wasDerivedFrom` を出せる) | `P2A-15` |
| 主体が人間か機械かを記録する(トークンの `idtyp` クレーム等) | `P2A-16` |
| JSON-LD 表現(`@context` の公開先の設計が要る) | `P2A-17` |
