# ADR-0015: 用語単位の責任者

- 状態: 採用
- 日付: 2026-09-09
- 関連: [ADR-0009](0009-ontology-operations.md) 決定4・決定5（責任者と健全性指標）、[ADR-0014](0014-namespace-rbac.md)（名前空間 RBAC。名前空間単位の責任者はここで決まっている）、[ADR-0002](0002-triple-store-as-rebuildable-projection.md)（ストアは再構築可能な射影）、バックログ `P2B-04`

## コンテキスト

[ADR-0009](0009-ontology-operations.md) 決定4 は「名前空間と用語に責任者を持たせる」と決めたが、**粒度（名前空間単位か、用語単位か、その両方か）を未解決のまま残した**。

そのうち名前空間単位は [ADR-0014](0014-namespace-rbac.md) で決着している。`namespace_roles` の `owner` ロールがその名前空間の責任者である。ADR-0014 は「権限（何ができるか）と責任者（誰が説明責任を負うか）は別の概念」と述べ、用語単位をこの ADR に送った。

残っているのは用語単位である。ADR-0009 が用語単位の責任者を要求する理由は 2 つある。

- **差分レビューのルーティング先になる**（決定1 の「レビューは差分に、判断は責任者に」）。オントロジーが大きくなると、名前空間の `owner` 全員に投げるのでは誰も見ない
- **責任者のいない用語を健全性指標で可視化する**（決定5）。ADR-0009 は「責任者のいない用語は誰も保守しない。健全性指標で可視化する対象として、これが最も重要である」と述べている

決めるべきことは 5 つある。

1. **1 つの用語に責任者は何人か**
2. **責任者がいない用語への問い合わせをどこへ回すか**（フォールバックを作るか）
3. **どの IRI に責任者を置けるか**（その名前空間が発行した IRI に限るか）
4. **責任者として書ける主体に制約を付けるか**（その名前空間のロールを持っている必要があるか、用語が実在する必要があるか）
5. **誰が責任者を付け替えられるか**

## 決定

### 1. 1 つの用語に責任者は 1 人

`term_owners`（`namespace`, `term_iri`, `principal_id`, `assigned_by`, `assigned_at`）。`(namespace, term_iri)` を一意にする。付け替えは置き換えであり、重複エラーにする理由がない（[ADR-0014](0014-namespace-rbac.md) 決定1 の付与と同じ形）。

**複数人を許さないのは、説明責任が分散するとその意味を失うためである。** 「この用語の定義について答えるべき人」を尋ねたときに 3 人返ってくるなら、誰も答えない。手が足りないときは用語を分けて別々の責任者を置くか、名前空間の `owner` に回る（決定2）。

`principal_id` は Entra の**オブジェクト ID**である（ADR-0014 決定1 と同じ規則。UPN や表示名は変わりうる）。

### 2. 責任者がいない用語は名前空間の `owner` に回す。**ルーティングにはフォールバックを作る**

問い合わせ先の解決は次の順に落ちる。

1. その用語の `term_owners` の主体
2. 無ければ、その名前空間で `owner` ロールを持つ主体（[ADR-0014](0014-namespace-rbac.md)）
3. それも無ければ「解決できない」を明示的に返す

**[ADR-0014](0014-namespace-rbac.md) 決定6 は「権限に暗黙のフォールバックを作らない」と決めた。これはそれに反しない。** 安全側の向きが逆だからである。

| | 無いときの安全側 | 理由 |
|---|---|---|
| **権限** | **拒否**する | 「付与が無ければ全員に許可」は「強制していない」を「強制している」と誤認させる |
| **ルーティング** | **上位に回す** | 「責任者が無ければ誰にも届かない」ほうが危険。届かない問い合わせは放置されるだけで、放置されたことも分からない |

**ただし暗黙にはしない。** 解決結果には「用語の責任者そのものか、名前空間の `owner` への代替か」を必ず含める。代替で解決したことが見えなければ、`P2B-06` の健全性指標が「責任者が未設定の用語」を数えられない。

### 3. 用語 IRI は絶対 IRI であればよい。`base_iri` 配下に限らない

**限定しない理由は [ADR-0009](0009-ontology-operations.md) 決定8（領域をまたぐ矛盾は統合せずマッピングする）である。** 自分の名前空間から外部語彙への `skos:closeMatch` を張るとき、そのマッピングの妥当性について説明責任を負うのは**張った側**である。外部 IRI に責任者を置けなければ、マッピングの責任者を記録できない。

検証するのは「絶対 IRI であること」（スキームがあり、空白や制御文字を含まない）だけである。**用語 IRI は名前空間名とは違い、データセット名・Blob パス・グラフ IRI の組み立てには使わない**（不変条件5 の対象ではない）。ただし将来 SPARQL に埋め込むなら、そこでエスケープする責任は埋め込む側にある。

### 4. 責任者の実在も、用語の実在も検査しない

**用語が実在するかを検査しない。** ストアは再構築可能な射影であって正本ではない（[ADR-0002](0002-triple-store-as-rebuildable-projection.md)）。用語の存在を確かめるにはストアに問い合わせるしかなく、それは**正本への書き込みを射影の可用性に依存させる**（不変条件2・3 が禁じている向き）。加えて、まだ承認されていない版で定義される用語に、先に責任者を決めておくことは自然に起こる。

**責任者がその名前空間のロールを持っているかも検査しない。** 退職して RBAC から外れた人が責任者のまま残っている状態は**起こる**。それは書き込みを拒否して防ぐものではなく、`P2B-06` の健全性指標が可視化するものである。拒否すると、付与の順序（責任者を決めてからロールを付ける）が動かなくなる。

### 5. 責任者の付け替えは `maintainer`。読み取りは `data-analyst`

| 操作 | 必要なロール |
|---|---|
| 責任者の一覧・解決 | `data-analyst` |
| 責任者の付与・取り消し | `maintainer` |

**読み取りを `data-analyst` に開くのは意図的である。** [ADR-0014](0014-namespace-rbac.md) は `namespace_roles` の一覧に `owner` を要求した（「誰がどの権限を持っているか」は管理する立場の人が知るべき情報だから）。責任者は逆で、**「この用語について誰に聞けばよいか」を知ることが主目的**である。分析者が引けなければ存在する意味がない。

付け替えを `maintainer` にしたのは、責任の割り当てが名前空間のキュレーションの一部だからである。`owner` を要求すると付け替えが滞る。一方 `data-steward`（提案する人）に許すと、自分の提案の責任者を自分で他人にできてしまう。

## 検討した代替案

### 責任者を用語単位ではなく「用語のグループ」単位にする

領域（サブドメイン）ごとに責任者を置く形。**却下**: グループの定義という新しい語彙が必要になり、オントロジー側（SKOS の概念スキーム等）と二重管理になる。用語単位で置けるなら、グループ単位は「同じ責任者を複数の用語に付ける」で表現できる。**同じ役割の仕組みを 2 つ持たない**（`P2A-05` で SHACL と想定質問の役割を分けたときと同じ判断）。

### 責任者をオントロジー自身（TTL）に書く

`dcterms:creator` や `prov:wasAttributedTo` として RDF に持たせる案。**却下**: 責任者は**現在の状態**であり、オントロジーは**不変リビジョン**である（不変条件7）。責任者が変わるたびに新しい版を公開することになり、意味的な変更が無いのに版が増える。ADR-0009 決定4 が「`created_by` / `approved_by` は行為者であって現在の責任者ではない」と言うのと同じ理由が、TTL への埋め込みにも当てはまる。

### 名前空間単位の責任者を `namespace_roles` とは別に持つ

責任者と権限を完全に分離する形。**却下**: 名前空間単位では両者がほぼ一致し、2 つの一覧を同期させる手間だけが残る。ADR-0014 が既に `owner` を「その名前空間を管理する立場」と定義しており、そこに説明責任も乗せてよい。**用語単位こそが、権限では表現できない粒度である。**

### 責任者を複数人にする（バックアップのため）

不在時に止まらない。**却下**: 決定1 の理由（説明責任の分散）。バックアップは決定2 のフォールバック（名前空間の `owner`）が担う。フォールバックは「代替で解決した」ことが見えるので、**主たる責任者が不在であることが記録に残る**。複数人にすると、その事実が消える。

### 責任者に指定できる主体をその名前空間のロール保持者に限る

無意味な責任者を防げる。**却下**: 決定4 の理由。加えて、この制約は「ロールを外した瞬間に責任者が消える」か「ロールを外せなくなる」のどちらかを招く。どちらも運用を壊す。

## 結果（トレードオフ・影響）

### 得られるもの

- **差分レビューのルーティング先が決まる。** `P2B-09`（意味的差分）が「この差分を誰に見せるか」を答えられるようになる
- **`P2B-06` の健全性指標が「責任者が未設定の用語」を数えられる。** ADR-0009 決定5 の 6 項目のうち 1 つが原資料を得る
- **エージェントの答えに「誰に確認すべきか」を添えられる道が開く。** この ADR は API までで、MCP への露出は `P2B-11` と合わせて設計する

### 受け入れるコスト

- **責任者が実在するかを保証しない。** 退職者が責任者のまま残る状態は起こる。可視化は `P2B-06` に依存する
- **用語 IRI のタイプミスを検出できない。** 実在を検査しないため、存在しない IRI に責任者を置ける。これも健全性指標側（ストアの用語一覧との突き合わせ）で拾う
- **責任者を割り当てる UI が無い。** `P2A-03`（Web のレビュー画面）まで API 直叩きになる
- **用語数が多い名前空間では付与が手作業になる。** 一括付与の口はこの ADR では作らない（必要になってから作る）

### 影響を受ける他の決定

- **[ADR-0009](0009-ontology-operations.md)**: 未解決事項「責任者の粒度」を閉じる。**名前空間単位は `namespace_roles` の `owner`、用語単位は `term_owners`** である
- **[ADR-0014](0014-namespace-rbac.md)**: 未解決事項「用語単位の責任者」を閉じる。決定6（権限に暗黙のフォールバックを作らない）との関係を決定2 で明示した

### 未解決のまま残す問い

- **責任者への通知経路。** 「誰に回すか」は決まるが、実際に届ける手段（メール・Teams・Issue）は決めていない
- **用語の一括付与と、責任者ごとの用語一覧の逆引き。** 逆引き（`GET /principals/{id}/terms`）は名前空間をまたぐ読み取りになるため、権限判定が名前空間単位では収まらない
- **廃止された用語の責任者。** 廃止（`P2B-03`）した用語の責任者を残すか外すかは、廃止のライフサイクルを実装するときに決める

## 補記: 差分レビューのルーティング先を実装した (2026-09-12、`P2B-13`)

「得られるもの」に挙げていた

> **差分レビューのルーティング先が決まる。** `P2B-09`(意味的差分)が
> 「この差分を誰に見せるか」を答えられるようになる

を実装した([ADR-0040](0040-term-owner-not-an-approval-gate.md) 決定2)。
`GET /namespaces/{ns}/versions/{v}/diff` の応答に `owners` が入る。

**決定2 のフォールバックをそのまま使う。** `source` が `term-owner` /
`namespace-owners` / `unresolved` のどれかを必ず言う — 代替で解決したことを
隠さない。

**責任者は承認の条件ではない**(ADR-0040 決定1)。決定5 で `maintainer` が
責任者を付け替えられるようにしているので、条件にすると**責任者の付与が
承認権限の付与になる**(ADR-0014 のロール階層を回避する経路ができる)。
不変条件13 が「混ぜるな」と言っているのはこの形である。

**まとめて解決する口を足した**(決定5)。`resolve_many` はクエリ 2 回で、
用語数に依らない。`resolve`(1 件)はそれに委譲する — **規則を 2 か所に
書かない**ため。

未解決のまま残した「責任者への通知経路」はまだ未解決である。`owners` は
**問い合わせ先を返すだけ**で、届けはしない。
