# ADR-0016: 意味的差分の計算

- 状態: 採用
- 日付: 2026-09-10
- 関連: [ADR-0009](0009-ontology-operations.md) 決定7（「なぜ」を参照時に返す）・決定3（オントロジーは縮められなければならない）・未解決事項「意味的差分の計算方法」、[ADR-0006](0006-ontology-versioning-and-audit.md)（不変リビジョン・監査証跡）、[ADR-0010](0010-approval-and-projection.md)（承認と射影）、バックログ `P2B-09`

## コンテキスト

[ADR-0009](0009-ontology-operations.md) 決定7 は「なぜそう決めたか」を参照時に返すと決め、`P2B-08` が `reason` を記録・読み出せるようにした。しかし **`diff` は常に `null` のまま**である。同 ADR は未解決事項に「意味的差分の計算方法（既存ツールを使うか、rdflib で自作するか）」を残していた。

差分が必要な理由は 2 つある。

- **レビューは差分に対して行う**（決定1 の「レビューは差分に、判断は責任者に」）。全体をレビューする設計は規模とともに必ず破綻する
- **オントロジーは縮められなければならない**（決定3）。**IRI を削除も再利用もしない**という規律が守られているかは、差分を見なければ分からない

**テキスト差分では答えにならない。** 同じ内容の TTL が、接頭辞・トリプルの順序・空白ノードのラベルの違いだけでバイト列として別物になる。「意味的」差分とは、少なくともこれらの違いを差分として報告しないことを意味する。

決めるべきことは 5 つある。

1. **正規化を何で行うか**（既存ツールか自作か）
2. **何を基準に比較するか**（どの版との差分か）
3. **どの粒度で報告するか**（トリプル単位か用語単位か）
4. **差分が計算できないときどうするか**
5. **差分は承認をブロックするか**

## 決定

### 1. 正規化は rdflib の `graph_diff` に任せる。自作しない

**実測で必要な性質を満たすことを確認した**（rdflib 7.6.0）。

| 違い | 差分として報告されるか |
|---|---|
| 接頭辞の違い（`ex:` と `e2:`） | されない（正しい） |
| トリプルの順序 | されない（正しい） |
| **空白ノードのラベル**（`sh:property [ sh:path ex:name ; sh:minCount 1 ]` の記述順を入れ替え） | **されない（正しい）** |
| 実際の内容の変更 | される |

自作しない理由は、空白ノードの正規化が RDF Dataset Canonicalization の問題そのものであり、**微妙に間違えても静かに間違う**ためである。rdflib は BSD-3-Clause で既に依存に入っており（`docs/third-party-licenses.md`）、追加の依存も発生しない。

### 2. 基準は「その承認によって `superseded` になる版」である

差分の意味は「**この承認によって現行の定義がどう変わるか**」である。したがって基準は、承認時点で `approved` だった版（`approve` が自動で `superseded` にする版。[ADR-0010](0010-approval-and-projection.md) 決定3）である。

**publish 時ではなく approve 時に計算する。** `draft` は数週間放置されうるので、publish 時点の「現行」は承認時点の「現行」と違う。publish 時に計算した差分を保存すると、**承認の記録に、その承認とは無関係な基準の差分が残る**。

基準が無い場合（最初の承認）は差分を `null` にする。「何も無かったところに全部追加された」という差分は情報量が無い。

レビューのために任意の 2 版を比べる口は別に用意する（`GET /namespaces/{ns}/versions/{v}/diff?base=<版>`）。**保存された差分は決定についての事実、その場の差分は決定するための道具**であり、役割が違う。

### 3. 用語単位を主、トリプル単位を従とする

レビュアが見たいのは「どの用語が増え、減り、変わったか」である。トリプルの列挙はその根拠として添える。

| 分類 | 意味 |
|---|---|
| `added` | 新しい版で初めて主語として現れた IRI |
| `removed` | 旧版にあり、新しい版では**主語として一切現れない** IRI |
| `deprecated` | 新しい版で `owl:deprecated true` を得た IRI |
| `modified` | 両方にあり、記述が変わった IRI |

**`deprecated` を `removed` と分けるのがこの分類の要点である。** ADR-0009 決定3 は「廃止を追加と同格に扱い、IRI を削除も再利用もしない」と決めた。**廃止は正しい縮め方、削除は規律違反**であり、同じ「減った」に混ぜてはいけない。

### 4. 用語単位の `added` / `removed` は正規化なしで求める。**差分の最も重要な部分が最も安い**

`added` と `removed` は「IRI が主語として現れるか」だけで決まる。**空白ノードの同一性に一切依存しない**ので、正規化せずに集合演算で厳密に求まる（O(トリプル数)）。

これが重要なのは、正規化のコストが**空白ノードの数だけ**で決まり、しかも急激に伸びるからである（実測）。

**2 グラフの差分の所要時間**（`graph_diff`。条件を揃えて測定）:

| 空白ノード数 | トリプル総数 | 差分の所要 |
|---|---|---|
| 100 | 1,000 | 0.14 秒 |
| 200 | 1,400 | 0.71 秒 |
| **300** | 1,800 | **2.0〜4.5 秒** |
| 400 | 2,200 | 5.9 秒 |
| 500 | 2,600 | 8.0 秒 |
| 800 | 3,800 | 25.6 秒 |
| 1,000 | 4,600 | 42.1 秒 |

**トリプル総数はほとんど効かない**（空白ノードを 300 に固定して総数を 1,200 → 7,200 に増やして 2.00 → 2.27 秒）。おおよそ空白ノード数の 2.5〜3 乗である。SHACL の property shape は 1 つずつ空白ノードを作るので、実用規模のオントロジーで数千に達しうる。

**`rdflib.compare.graph_diff` は引数を内部で `to_canonical_graph` に通す**（rdflib 7.6.0 の実装を読んで確認。実測でも `to_isomorphic` を外から挟んでも所要時間は変わらない）。したがって呼び出し側で正規化を明示する必要はない。

### 5. 空白ノードが上限を超えたら、トリプル単位の差分は計算しない。**「差分が無い」と混同させない**

**上限は 1 グラフあたり空白ノード 300 個**とする（実測で 2 グラフの差分に 2〜4.5 秒。オントロジーの解析を 5 MB ≒ 5 秒で上限としているのと同程度の予算に合わせた）。

超えた場合、差分の `triple_status` を `skipped-too-many-blank-nodes` にし、**理由と実際の個数を添える**。`modified` の一覧も同時に `null` になる（トリプル単位の比較が要るため）。`added` と `removed` は決定4 のとおり常に厳密に返る。

**空の差分を返さない。** 「変更なし」と「計算できなかった」を混同すると、規律違反（IRI の削除）を見落とす。これは `P2A-05` で「検証できなかった」を違反として扱わないと決めたのと同じ形の判断である。

### 6. 差分は承認をブロックしない。報告するだけである

IRI の削除は ADR-0009 決定3 に反し、決定1 の基準（形式的に決定可能なものはブロッキング）に照らせばブロック対象に見える。**それでもここではブロックしない。**

**理由は順序である。** 廃止の仕組み（`owl:deprecated` + 後継への参照）は `P2B-03` で実装する。**それが無い状態で削除をブロックすると、オントロジーを縮める正当な手段が 1 つも無くなる。** 「縮められなければならない」という決定3 の目的そのものに反する。

削除のブロックは `P2B-03` が廃止の経路を用意した後に、`P2B-03` の一部として入れる。

### 7. 監査に保存するのは要約である。**厳密な差分は正本から再計算できる**

`audit_events.diff` には JSON の**要約**（件数と、用語 IRI の一覧を上限つきで）を保存する。全トリプルは保存しない。

**そうしてよい根拠は不変条件7（オントロジーは不変リビジョン）である。** 版は Blob に不変で残るので、**任意の 2 版の厳密な差分はいつでも再計算できる**。監査行に全トリプルを積むと、行が非有界に育ち、監査そのものが読めなくなる。

用語 IRI の一覧は各分類 50 件までとし、切り捨てたことを `truncated` で明示する。**黙って切らない。**

## 検討した代替案

### テキスト差分（`difflib`）で済ませる

実装は 10 行で終わる。**却下**: 接頭辞の変更だけで全行が差分になり、レビューの役に立たない。「意味的差分」という要求に対して答えになっていない。

### 正規化を自作する（トリプルの空白ノードを構造的な署名で置き換える）

用語ごとの部分グラフだけを正規化すれば、空白ノードの島が小さい実用ケースでは線形に近くなる。**却下（ただし将来の選択肢として残す）**: RDF Dataset Canonicalization の再実装であり、**空白ノードが循環する場合や複数の用語から共有される場合に静かに間違う**。今回の上限（決定5）で実用範囲は覆えており、覆えないケースは「計算できなかった」と正直に報告するほうが、間違った差分を返すより良い。上限が実際に問題になったら、そのときに島ごとの正規化を検討する。

### 上限を超えたら近似的な差分を返す（空白ノードを 1 つの記号に置き換えて比較する）

「たぶん変わっていない」が分かる。**却下**: 監査の文脈で近似は毒である。「変更なし」と表示された差分が実は変更を含んでいた、という状態を作ってはいけない。**判定できないことを判定できないと言う**のが、この製品が繰り返し選んでいる側である。

### publish 時に差分を計算して保存する

レビューに出す前から差分が見える。**却下**: 決定2 の理由。`draft` は放置されうるので、publish 時点の「現行」は承認時点の「現行」と違う。承認の記録には、その承認の基準に対する差分だけが載るべきである。なお**レビュー時に差分を見る要求は満たされている** — その場で計算する口を別に用意した。

### 全トリプルを `audit_events.diff` に保存する

再計算が不要になる。**却下**: 決定7 の理由。監査行が非有界に育つ。版は不変で Blob に残るので、再計算はいつでもできる。

### 差分の計算に失敗したら承認を失敗させる

差分が必ず記録される。**却下**: 差分は説明のための記述的なメタデータであって、承認の前提条件ではない（決定6 でブロックしないと決めた）。Blob への到達不能で承認が止まるのは、不変条件3（射影の失敗は正本への書き込みを失敗させない）と同じ向きの誤りである。失敗したら `diff` は `null` のまま残し、ログに出す。

## 結果（トレードオフ・影響）

### 得られるもの

- **`P2B-08` が用意した `diff` 列が埋まる。** 「なぜそう決めたか」に「何が変わったか」が伴う
- **IRI の削除が見えるようになる。** ADR-0009 決定3 の規律が守られているかを機械的に確認できる。しかも**この部分は空白ノードの数に関係なく常に厳密**である
- **廃止と削除が区別される。** 正しい縮め方と規律違反を混ぜない
- レビュー時に任意の 2 版を比べられる（`P2A-03` の承認画面の前提）

### 受け入れるコスト

- **空白ノードが 300 個を超える版では、トリプル単位の差分と `modified` の一覧が得られない。** SHACL を多用する大きなオントロジーで起こりうる。`added` / `removed` は得られる
- **`approve` が遅くなる。** 基準の版の TTL を Blob から取得し、2 つのグラフを正規化する。上限まで使うと 2〜4.5 秒。SHACL 検証と同様に `asyncio.to_thread` へ出してイベントループは塞がないが、スレッドを占有する
- **`modified` は「変わった」ことしか言わない。** どう変わったか（制約が厳しくなったのか緩んだのか）の分類はしない。それは形式的に決定可能な範囲を超える
- **保存される差分は要約である。** 厳密な差分が必要なら再計算する

### 影響を受ける他の決定

- **[ADR-0009](0009-ontology-operations.md)**: 未解決事項「意味的差分の計算方法」を閉じる。**rdflib の正規化を使い、用語単位の層を自作する**
- **[ADR-0009](0009-ontology-operations.md) 決定3**: 「IRI を削除も再利用もしない」が観測可能になる。**強制は `P2B-03`**（廃止の経路が先に必要）
- **[ADR-0010](0010-approval-and-projection.md)**: `approve` の処理に差分の計算が加わる。**状態遷移より前ではなく、記録の直前に置く**（差分は承認の可否に影響しないので、SHACL 検証と違って前段に置く理由が無い）

### 未解決のまま残す問い

- **`modified` の中身の分類。** 「制約が厳しくなった」（既存データを壊しうる）と「緩んだ」を区別できると価値が高いが、形式的な定義が難しい
- **空白ノードの島ごとの正規化。** 上限が実際に問題になったときの選択肢
- **差分の提示形式。** JSON の要約は機械向けである。人が読む形（`P2A-03` の画面）は Web 側の設計
- **推論を挟んだ差分。** OWL 推論（`P2B-01`）後のグラフで比較すると「含意が変わったか」が分かるが、推論器の導入が前提になる
