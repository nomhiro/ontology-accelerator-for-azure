# ADR-0008: AWS 版をフォークせず、独立実装とする

- ステータス: 承認済み
- 日付: 2026-08-28

## コンテキスト

本プロジェクトは、AWS が 2026 年 7 月に GA した [Context Ontology Accelerator](https://github.com/aws/context-ontology-accelerator) の Azure 版を作るものである。

AWS 版の状況を確認した結果:

- **ライセンスは Apache-2.0**(著作権表示: Amazon.com, Inc.、GitHub API で確認済)
- 商用利用・改変・再配布・派生物の作成すべてが許諾されている
- **したがって、フォークすることすら法的には問題ない**

AWS 版の技術構成は次の通りである。

| 領域 | AWS 版の採用技術 |
|---|---|
| グラフストア | Amazon Neptune |
| 検索 | OpenSearch Serverless |
| LLM | Amazon Bedrock |
| IaC | AWS CDK |
| API 定義 | Smithy |
| 仮想グラフ | Ontop VKG |
| Web UI | Cloudscape Design System |

このうち **Ontop VKG 以外はすべて AWS 固有**である。ワークフロー(Scan → Model → Serve)と概念(名前空間 RBAC、承認フロー、MCP 経由の提供)は移植可能だが、実装の土台は共有できない。

ここで判断が必要になる。**フォークして Azure 向けに書き換えるか、参考にした新規実装とするか。**

## 決定

**フォークせず、アーキテクチャと概念を参考にした Azure ネイティブな独立実装とする。**

- AWS 版の**コード・設定・ドキュメント本文・サンプルオントロジー・プロンプト文を一切コピーしない**
- 参考にするのは**アーキテクチャと概念**に限る(Scan → Model → Serve のワークフロー、名前空間 RBAC の考え方、MCP による提供、オントロジーを AI が起案し人間が承認するという中心的な発想)
- README・NOTICE に **AWS 版との関係(独立実装であり、フォークではないこと)** と、**AWS 版が Apache-2.0 であること**を明記する
- README・NOTICE に **Amazon Web Services および Microsoft と非提携・非承認・非スポンサーである旨**を明記する
- **将来もし一部でもコピーする場合は、対象ファイルを台帳管理し NOTICE に追記する運用にする**

**この決定はライセンス上の制約によるものではなく、技術的判断である。**

## 根拠

### AWS 固有技術への深い結合を持ち込まないため

フォークした場合、置き換えの対象は次のようになる。

| AWS 版 | Azure 版での置き換え | 置き換えの深さ |
|---|---|---|
| AWS CDK | Bicep + azd | **IaC は全面書き換え。** 言語もモデルも異なる |
| Neptune | Fuseki on ACA(+ 射影設計) | **永続化設計の根本から異なる**([ADR-0002](0002-triple-store-as-rebuildable-projection.md)) |
| Smithy | FastAPI / Pydantic | **API 契約の仕組みごと変更**([ADR-0004](0004-api-contract-strategy.md)) |
| Bedrock | Microsoft Foundry | SDK・認証・モデル可用性が異なる |
| OpenSearch Serverless | Azure AI Search | API・課金モデルが異なる |
| Cognito/IAM | Entra ID + Managed Identity | 認証フローの設計が異なる |
| Cloudscape | Fluent UI | UI コンポーネントを全面差し替え |
| Step Functions | ACA Jobs | オーケストレーションのモデルが異なる |

**残るものがほとんどない。** フォークの利点は「既存のコードを土台にできる」ことだが、その土台のほぼ全部を置き換えるなら、利点は失われる。

さらに悪いことに、フォークは**元の構造の痕跡を残す**。CDK 前提のディレクトリ構成、Smithy 生成物を前提としたコードの形、Neptune の特性(常時可用な永続ストア)を暗黙に仮定したロジック。これらは「動いているから触らない」まま残り、Azure の文脈では不自然な設計として固定化する。

とくに **[ADR-0002](0002-triple-store-as-rebuildable-projection.md) の射影設計は、Neptune 前提の設計からは出てこない。** Neptune はマネージドな永続ストアであり、「ストアを失っても再構築できるようにする」動機がない。Azure の制約(ACA の永続ストレージが Azure Files のみ、TDB2 は mmap 依存)から出発したからこそ、この設計に到達した。**フォークから始めていたら、Neptune の前提を引きずったまま Azure Files で無理を通す設計になっていた可能性が高い。**

### Azure の制約から出発するほうが良い設計になる

上記の射影設計はその一例である。他にも、

- **AI Search を Phase 3 まで未デプロイにする**という判断は、Azure AI Search の課金モデル(Basic で月 $97 の固定費)から出てきた。OpenSearch Serverless の課金モデルとは異なる制約である
- **Purview に依存しない**判断([ADR-0007](0007-no-purview-dependency.md))は、Glue Data Catalog と Purview の位置づけの違いから出てきた
- **Java 依存を Phase 4 まで遅らせる**判断([ADR-0005](0005-reasoner-boundary.md))は、Phase 構成をゼロから設計できたから成立した

移植ではなく設計として取り組むことで、これらの判断が可能になった。

### OSS としての説明責任

本プロジェクトを OSS として公開する以上、「これは何なのか」を明確に説明する責任がある。フォークであれば「AWS 版の Azure 移植」と説明でき、それも明快な立場である。しかし実態が「ほぼ全面書き換えたフォーク」だと、利用者は AWS 版との差分を把握しづらい。**独立実装として、参考にした点と異なる点を明示する**ほうが誠実である。

## 検討した代替案

### AWS 版をフォークして Azure 向けに書き換える

**却下。** 上記「根拠」で詳述。要約すると、(a)置き換え対象が構成のほぼ全体に及ぶためフォークの利点が失われる、(b)元の構造の痕跡が Azure の文脈で不自然な設計として固定化する、(c)Neptune 前提から出発すると射影設計に到達しない。

**ただし、この選択には明確な利点があった**(後述のトレードオフ参照)。とくに Apache-2.0 §3 の特許許諾を受けられる点は、独立実装では得られない。

### AWS 版のドキュメントとプロンプトのみを流用し、コードは新規に書く

**却下。** サンプルオントロジーやプロンプト文は、AWS 固有技術に依存しない部分である。流用すれば実装量が減る。

却下理由: **これは著作権上の義務を発生させる。** ドキュメント本文、サンプルオントロジー、プロンプト文はいずれも著作物であり、コピーすれば Apache-2.0 §4 の義務(ライセンス全文の同梱、著作権表示の保持、変更点の明示、NOTICE の内容の継承)が生じる。

義務そのものは軽い(NOTICE への記載で足りる)が、問題は**境界の管理**である。「どのファイルが由来を持つか」を台帳で管理し続ける運用は、プロジェクトが成長するほど破綻しやすい。将来「このファイルは AWS 版由来だったか」が分からなくなれば、ライセンス順守の主張が曖昧になる。

**一切コピーしないという明快な境界を選ぶ**ほうが、長期的な運用コストが低い。ただし将来コピーする判断をする場合は、台帳管理と NOTICE への追記を運用として明記する(決定事項に含めた)。

### AWS 版に Azure サポートを追加する Pull Request を送る

**却下。** upstream に貢献するほうがコミュニティ全体には望ましい、という見方はできる。

却下理由:
- AWS が自社製品のアクセラレータに、競合クラウドのサポートを受け入れる可能性は低い
- 受け入れられたとしても、マルチクラウド対応のための抽象化層が両方の設計を制約する。Azure 固有の制約(ACA の永続ストレージ)から出発した設計([ADR-0002](0002-triple-store-as-rebuildable-projection.md))は、Neptune と共通の抽象に収めるのが困難である
- リリースサイクルと方針決定が AWS 側に依存する

## 結果(トレードオフ・影響)

### 受け入れるコスト

#### 1. 特許許諾を受けられない(最も明確なトレードオフ)

**Apache-2.0 §3 は、「その成果物の利用者」に対する明示的な特許ライセンスを与える。** 具体的には、各 Contributor が自身の Contribution に必然的に含まれる特許クレームについて、永続的・世界的・無償・取消不能なライセンスを付与する。

フォークすれば、本プロジェクトと利用者はこの特許許諾の対象となる。**独立実装を選ぶと、この許諾を受けられない。** 理論上、AWS 版に関連する特許が存在した場合、フォークした場合には保護されたが独立実装では保護されない、という状況が生じ得る。

**これは独立実装を選ぶことによる明確な不利益である。**

実務上のリスクは低いと判断している。理由は、(a)本プロジェクトが使う技術要素は W3C 標準(RDF/OWL/SPARQL/SHACL/R2RML)と既存 OSS(Jena、Ontop、ELK)であり、いずれも長く公知の技術である、(b)アーキテクチャレベルの発想(データカタログからオントロジーを生成し、人間が承認し、グラフストアに載せ、エージェントに提供する)は個別の実装技術ではない。

しかし**リスクがゼロだと主張するものではない。** これは意識した上での選択であり、その事実をここに記録する。もし将来この判断が問題となる可能性が高まった場合(たとえば関連特許の存在が判明した場合)、フォークへの切り替えを再検討する余地がある。

#### 2. 商標を使えない(Apache-2.0 §6 で明確に除外される)

**Apache-2.0 §6 は商標権を許諾しない。** ライセンスが明示的に除外している事項である(成果物の出自を記述するための合理的・慣習的な使用と、NOTICE ファイルの内容の複製を除く)。

これはフォークを選んだ場合でも同じであり、独立実装固有の不利益ではない。ただし本プロジェクトには次の実務的な影響がある。

- **"AWS" / "Amazon" をプロジェクト名・ブランディングに使えない。** 「AWS Context Ontology Accelerator の Azure 版」のような名乗り方は、Amazon の商標を製品名として使うことになるため避ける
- **README に非提携である旨を明記する必要がある。** 「本プロジェクトは Amazon Web Services および Microsoft とは提携・承認・スポンサー関係にありません。AWS, Amazon, Azure, Microsoft は各社の商標です。」を掲載する
- **"Azure" も同じ論点を持つ**(R8)。OSS 名の先頭に "Azure" を置くのは Microsoft の商標ガイドライン上グレーである。現在の表示名 `Ontology Accelerator for Azure` は**暫定**であり、公開時に変更する可能性がある。ディレクトリ名(`azure-ontology-accelerator`)は当面維持するが、これも再考の余地がある

つまり、**参照元と参照先の両社の商標を、製品名として使えない**という制約下で名前を決める必要がある。これは本プロジェクト固有の面倒さであり、解決を先送りしている論点である。

#### 3. 実装量が増える

AWS 版のコードを土台にできないため、すべてを新規に書く。Phase 1〜4 のロードマップ全体がこのコストを織り込んでいる。

#### 4. AWS 版の改善を自動的に取り込めない

upstream の修正や機能追加を `git merge` で取り込むことができない。AWS 版の設計上の改善を参考にする場合は、都度読んで判断し、自分で実装することになる。

### 得られるもの

- **Azure の制約から出発した設計ができる。** [ADR-0002](0002-triple-store-as-rebuildable-projection.md) の射影設計はその最大の成果である
- **AWS 固有技術への結合を持ち込まない。** CDK / Smithy / Neptune の前提が残らない
- **著作権上の義務が発生しない。** アーキテクチャや概念は著作権の保護対象ではないため、コピーしない限り Apache-2.0 §4 の義務は生じない。台帳管理の運用負担がない
- **設計判断を自分で選べる。** Smithy を採用しない([ADR-0004](0004-api-contract-strategy.md))、Purview に依存しない([ADR-0007](0007-no-purview-dependency.md))、Java 依存を遅らせる([ADR-0005](0005-reasoner-boundary.md))といった判断が、upstream の構造に縛られずに可能である
- **AWS 版へのリスペクトを明示できる。** 独立実装であることを明記しつつ、参考にしたことと AWS 版が Apache-2.0 であることを README・NOTICE で示す。「黙って真似た」形にしない

### 運用として守ること

1. **AWS 版のコード・設定・ドキュメント本文・サンプルオントロジー・プロンプト文をコピーしない。** Pull Request のレビューで、他プロジェクト由来の成果物の持ち込みがないか確認する([CONTRIBUTING.md](../../CONTRIBUTING.md))
2. **将来コピーする判断をした場合は、対象ファイルを台帳管理し、NOTICE に追記する**
3. **README・NOTICE の非提携表記を維持する**
4. **プロジェクト名の最終決定時に、両社の商標ガイドラインを再確認する**(R8)

### 影響を受ける他の決定

本 ADR は、以下の ADR が AWS 版と異なる選択をしている理由の土台である。

- [ADR-0001](0001-rdf-store-selection.md) — Neptune ではなく Fuseki(Azure にマネージド RDF ストアがないため)
- [ADR-0002](0002-triple-store-as-rebuildable-projection.md) — Neptune 前提では出てこない射影設計
- [ADR-0004](0004-api-contract-strategy.md) — Smithy 不採用
- [ADR-0007](0007-no-purview-dependency.md) — Glue に対応する Purview を必須依存にしない
