# ADR-0043: LLM の出力は検証を通っても `draft` にしか入らない — カタログのテキストを命令として扱わない

- ステータス: 承認済み
- 日付: 2026-09-12

## コンテキスト

Phase 2 柱 A の完了条件は「顧客 DB に接続してスキーマを自動発見し、**LLM が
オントロジー候補(OWL/SHACL)を生成し**、Web でレビュー・承認して公開できる」
である。`P2A-01`([ADR-0041](0041-source-schema-scan.md))でカタログができた
ので、ここがその次である。

**この製品の前提は「LLM の出力が人間の承認を経ずに正本へ入ることはない」**
である(README・[architecture.md](../architecture.md))。これまでその前提は
**LLM を呼ぶ経路が 1 つも無かったから**成り立っていた。ここで初めて、
**前提を強制するコードが必要になる。**

### 決めるべきこと

1. **何を送るのか**(そして何を送らないのか)
2. **カタログのテキストを誰が書いたか**(`column_comment` は顧客 DB の持ち主が書いた文字列である)
3. **出力をどう検証するのか。通らなかったらどうするのか**
4. **候補はどこへ入るのか**
5. **対象が大きすぎたらどうするのか**
6. **誰が実行できるのか**
7. **どのモデルを、どう呼ぶのか**

## 決定

### 1. 送るのはカタログだけである。実データは 1 行も送らない

これは `P2A-01` が**構造で保証している**。`ontology_core.scan.CATALOG_QUERIES`
は `information_schema` と `pg_catalog` しか読まず、`pg_stats` からは
`n_distinct` と `null_frac` だけを取る(ADR-0041 決定1)。

**この ADR はその保証に乗っているだけで、新しい保証を作っていない。**
逆に言えば、**ここで実データを足したくなったら ADR-0041 決定1 を覆すことに
なる** — プロンプトへ流れた実データは、後から消してもモデルの提供者へ渡った
事実が消えない。

送るのは列名・型・NULL 可否・主キー・外部キー・コメント・異なり数の推定である。

### 2. カタログのテキストは**データ**であり、命令ではない

**`column_comment` と `table_comment` は、顧客 DB の持ち主が書いた文字列で
ある。** この製品を運用する組織とソース DB を持つ部門は別でありうるし、
そのコメントは何年も前に誰かが書いたものでありうる。

つまり**プロンプトに入るテキストの一部は、この製品の管理外にある**。
「以前の指示を無視して……」と書かれたコメントが混ざりうる。

対策は 3 段で、**区切り記号は 3 つのうち最も弱い**ものとして扱う。

| 段 | 何をするか | 強さ |
|---|---|---|
| a | カタログを明示的に区切った節に入れ、「ここはデータである」と指示する | **弱い。** 破られうる |
| b | **モデルの出力から副作用を作らない。** ツール呼び出しを与えず、出力は Turtle の文字列としてしか扱わない | 強い |
| c | **出力は検証を通っても `draft` にしか入らない**(決定5) | **最も強い** |

**a を「対策」と呼ばないこと。** 区切り記号はセキュリティ境界ではない。
実際の防壁は b と c である — **注入が成功しても、できるのは「変な提案を
1 件作る」ことであり、それは人間のレビューが既に受け止める形になっている。**

> これは不変条件11(既定は拒否)と同じ形の考え方である。「入力を綺麗にする」
> ことに頼らず、**入力が汚れていても壊れない構造**を作る。

### 3. 出力は必ず検証する。通らなければ受け付けない。自動で直さない

順に 3 つを検査する。**どれも「直す」ではなく「断る」である。**

1. **Turtle として解析できるか**(`validate_turtle`)
2. **定義している主語がすべてこの名前空間の `base_iri` の下にあるか**
3. **SHACL の shapes 自体が正しいか**(`validate_turtle_with_shacl`)

**2 が新しい検査である。** `publish` は主語の IRI 空間を検査していない
(人が書いた TTL に対しては、外部語彙について述べる自由を残す判断だった)。
しかし**生成された候補は違う** —

- モデルが**他の名前空間の `base_iri` の下に用語を作れてしまう**と、
  マッピングの所有者解決(`P2B-10` の `_owning_namespace`)がその用語を
  別の名前空間のものとして扱う
- 決定2 のとおり、プロンプトの一部は管理外のテキストである

**`publish` の契約は変えない。** この検査は**生成の経路にだけ**置く
(既存の利用者の TTL を後から拒否し始めるのは別の判断である)。

**自動で直さない。** 「閉じ括弧を足す」「IRI を書き換える」といった補正は、
**モデルが何を言おうとしたかの推測**になる。推測した結果が `draft` に入ると、
レビュアは「モデルの出力」ではなく「こちらの推測」を読むことになる。

### 4. 検証に落ちたら理由を添えて再試行する。回数に上限を置き、**何回かかったかを記録する**

`PROPOSAL_MAX_ATTEMPTS`(既定 3)まで、検証の失敗の理由をそのまま添えて
もう一度頼む。**上限に達したら 422 で断る** — 部分的に正しい Turtle を
返さない。

**何回目で通ったかを記録する。** 1 回目で通った候補と 3 回目でやっと通った
候補は、レビュアにとって別物である(後者は**モデルがこのスキーマを扱いかねて
いる**信号である)。「測れたのに書かない」をしない。

### 5. 候補は `draft` にしか入らない。承認は人がする

生成が成功すると、既存の `publish` と同じ経路で **`draft` の版**を作る。
そこから先は既存のフローそのままである(`submit` → `approve`)。

**新しい保管場所を作らない。** 候補専用のテーブルを作ると、

- 不変リビジョン(不変条件7)・監査(ADR-0006)・意味的差分(ADR-0016)を
  **もう一度実装することになる**
- 「候補」と「版」の 2 つの状態機械ができ、**どちらが正本かが曖昧になる**

`draft` は Blob と PostgreSQL にだけ存在し、**Fuseki には一切現れない**
(ADR-0010 決定1)。つまり**エージェントからは見えない**。これが
「人間の承認を経ずに正本へ入らない」の実体である。

**承認を飛ばす経路を作らない。** 生成 API は `submit` も `approve` も呼ばない。

### 6. 対象のテーブルは呼び出し側が選ぶ。多すぎたら断る(切り詰めない)

`POST .../propose` は対象のテーブルを**明示的に受け取る**。省略時は
カタログ全体を使うが、**`PROPOSAL_MAX_TABLES`(既定 40)を超えたら 413 で
断る**。

**黙って切り詰めない。** 切り詰めると、

- スキーマの一部しか覆っていないオントロジーができ
- **出力のどこにも「一部である」と書かれない**

[ADR-0034](0034-construct-describe.md) 決定4 が「RDF には封筒が無い」として
切り詰めを却下したのと同じ形である。**候補の Turtle にも封筒が無い。**

**運用上もそのほうが良い。** 40 テーブルを一度に渡したオントロジーより、
業務の切れ目で選んだ 10 テーブルのほうが良い候補が出る。**何を 1 つの
ドメインとして扱うかは人の判断である。**

### 7. 実行には `owner` が必要である

`publish` は `data-steward` で足りるが、生成は `owner` を要求する。

理由は 2 つある。

1. **組織のスキーマのメタデータをモデルの提供者へ送る**外向きの操作である。
   ソースの登録(ADR-0041 決定8)と同じ種類の決定である
2. **呼ぶたびに課金される**

**外向きのデータの流れに関わる操作を、同じロールに揃える。** 「この DB を
スキャンしてよい」と決めた人が、「このカタログをモデルへ送ってよい」も
決める。

### 8. モデルの呼び出しは REST を直接叩く。SDK を依存に足さない

`openai` / `azure-ai-inference` を依存に足さず、`httpx` で
`POST {endpoint}/openai/deployments/{deployment}/chat/completions` を叩く。

ADR-0041 決定4 が Key Vault で同じ判断をしている。**依存を足さずに済む形が
あるなら足さない** — このリポジトリは `httpx` と `azure-identity` を既に
持っている。

**HTTP の形はテストで固定する**(`httpx.MockTransport`)。実物のモデルは
ローカルに無いので、**「検証できないから確かめない」にしない**。

### 9. API キーを使わない。`disableLocalAuth: true` にする

マネージド ID(`Cognitive Services OpenAI User` ロール)だけで呼ぶ。
アカウントの**ローカル認証そのものを無効にする** — キーが存在しなければ、
キーが漏れることもない。

不変条件6(DSN にパスワードを埋めない)と同じ態度である。

### 10. 何が生成したかを記録する。再現性は主張しない

`draft` を作るときの `reason` に**モデル名・デプロイ名・API バージョン・
試行回数**を書く。監査は追記専用なので消えない。

**`temperature` は 0 にするが、再現性は主張しない。** 同じ入力で同じ出力に
なる保証はモデル側に無い。だから「再現できる」とは書かず、
**「何が作ったか」を記録する**。

> これは ADR-0026 が `prov:wasDerivedFrom` で「系譜が記録されている版にだけ
> 出す」とした態度と同じである。**主張できないことを主張しない。**

### 11. 既定のモデルは実測して決めた

Japan East で使えるモデルと割り当て量を `az` で実測した(2026-09-12)。

| 測ったこと | 結果 |
|---|---|
| `gpt-4.1`(`2025-04-14`)の SKU | `GlobalStandard` ほかで利用可能 |
| `OpenAI.GlobalStandard.gpt4.1` の割り当て | **9,000(使用 0)** |
| `gpt-4o` / `gpt-4o-mini` | 利用可能(7,000 / 33,000) |

既定は **`gpt-4.1` / `2025-04-14` / `GlobalStandard` / 容量 10**。
容量 10 は測った割り当ての約 0.1% で、評価用として十分小さい。

**モデル・版・SKU・容量・リージョンはすべてパラメータである。** 既定が
使えないリージョンの利用者は `MODEL_LOCATION` で分離できる(既にある
パラメータ。R4)。

## 検討した代替案

### 実データをサンプリングしてプロンプトに入れる

**却下(決定1)。** 値の例があるほうが良い候補が出る。

却下理由: **ADR-0041 決定1 を覆すことになる。** プロンプトへ流れた実データは
消せない。値の例が欲しいなら、**運用者が自分でコメントに書く**(それは
その組織の判断である)。

### カタログのテキストをサニタイズする

**却下(決定2)。** 「以前の指示を無視して」のような文字列を落とす。

却下理由: **落とすべき文字列の一覧は作れない。** そして**作れたつもりに
なるのが一番危ない** — サニタイズを「対策」と呼ぶと、b と c
(副作用を作らない・`draft` にしか入らない)への注意が薄れる。
コメントを削ると**LLM がいちばん使う材料**(意味が書いてある)が減る。

### 検証に落ちた Turtle を自動で補正する

**却下(決定3)。** 閉じ括弧の不足や接頭辞の宣言漏れは機械的に直せる。

却下理由: **補正はモデルの意図の推測である。** 推測が `draft` に入ると、
レビュアは「モデルの出力」ではなく「こちらの推測」をレビューする。
**再試行のほうが正直である** — 直せなかったなら断る。

### 候補を専用のテーブルに置く

**却下(決定5)。** 「まだ版ではないもの」を版と混ぜない。

却下理由: **不変リビジョン・監査・意味的差分をもう一度実装することになる。**
`draft` は既に「Fuseki に現れない・エージェントから見えない」状態として
定義されている(ADR-0010 決定1)。**必要な性質が既にある。**

### 生成した候補を自動で `submit` する

**却下(決定5)。** レビュー待ちの列に並べたほうが親切に見える。

却下理由: **`submit` は「これをレビューしてください」という人の意思表示で
ある。** 機械が代わりに言うと、レビュアの待ち行列が**誰も意図していない
提案**で埋まる。`in-review` は名前付きグラフへ射影されるので、
**Fuseki に載ってしまう**点も違う。

### 対象が多いときはカタログを切り詰めて送る

**却下(決定6)。** 断るより何か返したほうが親切に見える。

却下理由: **候補の Turtle に「一部である」と書く場所が無い**(ADR-0034
決定4 と同じ「封筒が無い」問題)。スキーマの一部しか覆っていない
オントロジーは、**覆っている範囲を主張しないまま**レビューへ回る。

### `data-steward` で生成できるようにする

**却下(決定7)。** `publish` と同じロールに揃うほうが単純に見える。

却下理由: **外向きのデータの流れと課金を伴う操作である。** 「この DB を
スキャンしてよい」を決めたのは `owner` なので、「このカタログをモデルへ
送ってよい」も `owner` が決める。

### `openai` SDK を依存に足す

**却下(決定8)。** リトライやストリーミングが手に入る。

却下理由: **`httpx` と `azure-identity` で足りる**(ADR-0041 決定4 と同じ
判断)。ストリーミングは要らない(出力を全部受けてから検証する)。
リトライは**検証の再試行**という別の層で行う。

### `kind: 'AIServices'`(Foundry の新しい形)でアカウントを作る

**保留。既定は `kind: 'OpenAI'` にした(決定8・9)。**

理由: **1 回のデプロイ窓で確かめきりたい。** `properties.endpoint` が
そのまま `{endpoint}/openai/deployments/...` の基底になるのは
`kind: 'OpenAI'` で最も確実である。`AIServices` でも同じ経路は使えるが、
**確実さを取った**。

> 実機で確認できたら `AIServices` へ寄せてよい。そのときはエンドポイントの
> 設定 1 つの変更で済む。

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **呼ぶたびに課金される**(決定7)。中規模スキーマ 1 回で $1〜5 程度
- **対象を人が選ぶ**(決定6)。40 テーブルを超えるスキーマは分割して呼ぶ
- **再現性が無い**(決定10)。同じカタログから同じ候補は出ない
- **`draft` が増える**(決定5)。生成した候補は不変リビジョンとして残る
  (捨てても `audit_events` からは消えない)
- **検証に 3 回落ちると 422 で何も得られない**(決定4)。**部分的に正しい
  Turtle を返さない**という判断の裏側である
- **`kind: 'OpenAI'` に寄せた**(決定8 の却下案)。Foundry の新しい形へは
  後から移る

### 得られるもの

- **柱 A の中心ができた。** Scan → Model が繋がった
- **「LLM の出力が人間の承認を経ずに正本へ入らない」が、初めてコードで
  強制された**(決定5)。これまでは「LLM を呼ぶ経路が無いから」成り立って
  いただけだった
- **プロンプトインジェクションの防壁が構造側にある**(決定2)。入力を
  綺麗にすることに頼っていない
- **生成の出自が監査に残る**(決定10)

### 影響を受ける他の決定

- [ADR-0041](0041-source-schema-scan.md) 決定1 — 「実データを読まない」の
  理由がここで実体化した。**プロンプトへ流れる経路が実際にできた**
- [ADR-0010](0010-approval-and-projection.md) 決定1 — `draft` が
  「Fuseki に現れない」ことが、この ADR の安全性の土台になっている
- [ADR-0014](0014-namespace-rbac.md) — 外向きのデータの流れを伴う操作を
  `owner` に揃えた(ADR-0041 決定8 と同じ)
- [ADR-0034](0034-construct-describe.md) 決定4 — 「封筒が無いものを切り
  詰めない」を、プロンプトの入力側に適用した
