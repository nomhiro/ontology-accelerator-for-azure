# ADR-0024: 名前空間の削除と公開の競合を行ロックで閉じる

- ステータス: 承認済み
- 日付: 2026-09-11

## コンテキスト

Phase 1 から残っている既知の競合状態(`P2B-12`)。

`DELETE /namespaces/{name}` の順序は次である。

1. 名前空間名の検証 / `owner` の権限
2. PostgreSQL に名前空間があるか
3. **Blob に `.ttl` が 1 件でも残っていれば 409**
4. PostgreSQL の行を削除 → commit
5. データセットを削除(失敗しても `reconcile` が回収)

手順 3 が **PostgreSQL の版数ではなく Blob 本体**を見るのには理由がある。
`containers/fuseki/load-snapshot.sh` は **PostgreSQL を一切見ず Blob だけを見て**
名前空間ごとの TDB2 を再構築する。Blob を残したまま PostgreSQL の行だけ消すと、
レプリカ再作成(デプロイ・スケールイベント)で**削除したはずのオントロジーが
復活し、認証済みの呼び出し元に返る**。手順 3 はこれを防ぐために入っている。

一方 `publish` の順序は不変条件2(Blob → PostgreSQL → Fuseki)に従う。

1. 名前空間があるか
2. 内容ハッシュによる冪等判定 / `base_version` の検査 / TTL の構文検証
3. **Blob に `.ttl` を書く**
4. PostgreSQL に版を書く → commit
5. 射影

### 手順 3 と 4 の間に publish が入ると、Blob だけが残る

| 時刻 | DELETE | PUBLISH |
|---|---|---|
| t1 | Blob を確認 → **空** | |
| t2 | | **Blob に `.ttl` を書く** |
| t3 | | PostgreSQL に版を書く |
| t4 | PostgreSQL の名前空間を削除 → commit | |

結果は **Blob に TTL があり、PostgreSQL には何も無い**状態である。ローダは
Blob だけを見るので、**次のレプリカ再作成で名前空間が復活する。** 手順 3 が
防ごうとしていた失敗そのものが、並行実行下で成立してしまう。

t3 と t4 が逆順でも同じである。その場合 publish の版行の挿入が外部キー違反で
失敗するが、**t2 の Blob 書き込みは既に終わっている**ので孤児 Blob は残る。

現状の検出手段は `POST /admin/reconcile` の `orphan_blobs` だけで、**削除は
しない**(オントロジーは不変リビジョン。[ADR-0006](0006-ontology-versioning-and-audit.md))。
つまり「復活する名前空間」が運用者の手作業まで放置される。

## 決定

### 1. 名前空間の行を `SELECT ... FOR UPDATE` でロックする

**Blob に `.ttl` を書く経路と、名前空間を削除する経路が、同じ行ロックを取る。**

- `publish`: 名前空間の存在確認を `get_locked` に変える(**Blob 書き込みより前**)
- `DELETE /namespaces/{name}`: 存在確認を `get_locked` に変える(**Blob の検査より前**)

ロックは `session.commit()` まで保持される。

| 先にロックを取った側 | 起きること |
|---|---|
| DELETE | Blob は空 → 行を削除 → commit。PUBLISH はロック解放後に**行が無い**ので 404。**Blob には何も書かれない** |
| PUBLISH | Blob と PostgreSQL に書いて commit。DELETE はロック解放後に**その TTL を見る**ので 409 |

**どちらの順序でも、Blob と PostgreSQL が食い違った状態にならない。**

### 2. 「後から検査し直す」では閉じられない

削除の commit の直前に Blob をもう一度見る案は、**publish が Blob を書く前に
DELETE が commit してしまう順序**を防げない。その場合 publish の版行は外部キー
違反で入らないが、**Blob は残る**。

**検査の回数を増やしても窓は閉じない。** 排他が必要である。この理由を明記して
おくのは、将来「もう一度確認すれば済むのでは」と考える人が必ず現れるからである。

### 3. ロックを取るのは Blob に `.ttl` を書く経路だけ

`approve` は `.ttl` を書かないが、`_refresh_manifest` が `_state.json` を書く。
ここでロックを取らないのは、**`_state.json` は名前空間を復活させないから**である
(ローダは `.ttl` だけを読み込む)。承認を名前空間の行ロックで直列化する代償の
方が大きい。

**残るのは孤児 `_state.json` である。** `reconcile` の `orphan_blobs` は
`list_versions()`(`.ttl` だけを返す)を使うので**これは検出できない**。害は
「Blob に、誰も読まないファイルが 1 つ残る」に留まる。`P2B-20` として記録する。

### 4. 公開済みオントロジーを含む名前空間の削除は、別の決定として切り離す

現在の 409 のメッセージは「公開済みオントロジーを含む名前空間の削除は
Phase 2(監査経路)で対応します」と書いている。**この約束の中身はこの ADR では
決めない。** 不変条件7(公開済みの版を書き換えない。削除もしない)との関係を
決める必要があり、競合の修正とは別の作業である。

選択肢を書き出しておく(`P2B-19`)。

1. **恒久的に拒否する。** 名前空間は消すものではなく廃止するもの、とする
   (不変条件8 の「縮めるときは廃止する」と揃う)
2. **正本を残し、射影だけ止める(退役)。** マニフェストに「退役」を書いて
   ローダにスキップさせる。**不変条件7 を守れる**が、マニフェストのスキーマ
   (現在 2)、ローダとその shell テスト、`reconcile`、名前空間一覧の絞り込みに
   波及する
3. **理由付きで Blob も消す。** 不変条件7 に正面から反する

**2 が筋が通っている**が、この ADR の範囲ではない。

## 検討した代替案

### 削除の commit 直前に Blob を再検査する

**却下。** 決定2 の通り窓が閉じない。**「1 回では足りないなら 2 回」という直感が
効かない形の問題である**ことを記録しておく。

### アドバイザリロック(`pg_advisory_xact_lock`)を使う

**却下。** 名前空間の行という**自然な排他対象がある**のに、名前をハッシュした
人工のロック空間を持ち込む理由が無い。行ロックなら「その名前空間が存在すること」と
「排他」が 1 回の `SELECT` で同時に得られる。

アドバイザリロックが要るのは「まだ存在しない対象を排他したい」場合(名前空間の
**作成**の競合など)で、そこは一意制約が既に守っている。

### トランザクションの分離レベルを `SERIALIZABLE` に上げる

**却下。** この 1 つの競合のために、**すべての経路が直列化失敗の再試行を
扱わなければならなくなる**。影響範囲が釣り合わない。

### Blob 側に「削除中」のマーカーを置く

**却下。** Blob は正本であり、排他制御の状態を置く場所ではない。加えて状態を
2 か所に持つと、**マーカーを残したまま失敗したときの回復**がもう 1 つの問題に
なる(それを直すために `reconcile` に新しい責務が増える)。

### 削除を非同期ジョブにする

**却下。** ジョブなら「Blob の検査 → 削除」を他の書き込みと調停できる、という
案。しかし調停の仕組みは結局必要で、**ジョブキューという新しい依存を足した上で
同じ排他の問題を解く**ことになる。

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **同じ名前空間への同時 publish が直列化される。** ロックは TTL の構文検証
  (実測で約 1.0 秒/MB、上限 5MB で約 5 秒)と Blob の書き込みを含む区間で
  保持される。**PostgreSQL の行ロックを外部 I/O をまたいで保持する**形であり
  一般には避けたいが、publish は低頻度の操作で、代替は「バグを残す」である。
  名前空間が違えば互いに影響しない
- **孤児 `_state.json` は残りうる**(決定3、`P2B-20`)
- **SQLite では効かない。** SQLAlchemy は SQLite に `FOR UPDATE` を出さない。
  テストも本番も PostgreSQL なので実害は無いが、「ローカルだけ SQLite」に
  戻すならこの決定は成立しない
- **ロック待ちのタイムアウトを設定していない。** publish が長く詰まると
  削除が待たされる。PostgreSQL の既定では待ち続ける

### 得られるもの

- **削除した名前空間が復活しない。** C-1 の Blob 検査が本来守ろうとしていた
  性質が、並行実行下でも成立する
- **`orphan_blobs` の主要な発生源が 1 つ減る**([ADR-0013](0013-reconcile-repairs-observed-divergence.md))
- **副産物として、同じ名前空間への同時 publish の版番号の競合が消える。**
  自動採番は `latest_for` を読んで次の版を決めるので、直列化されていなければ
  2 つの publish が同じ版番号を計算しうる。現状は `(namespace, version)` の
  一意制約で片方が `IntegrityError` になり、**内容ハッシュが一致しない場合は
  回復せず呼び出し元に伝播する**(コード中のコメントがその経路を明示している)

### 影響を受ける他の決定

- **不変条件2**(Blob → PostgreSQL → Fuseki)— 順序は変えていない。
  **その順序が並行実行下で崩れることを防いだ**
- [ADR-0013](0013-reconcile-repairs-observed-divergence.md) — `orphan_blobs` の
  発生源が減る。検出の仕組み自体は変えない
- [ADR-0006](0006-ontology-versioning-and-audit.md) / 不変条件7 — 公開済み
  オントロジーを含む名前空間の削除は未決のまま(決定4、`P2B-19`)
