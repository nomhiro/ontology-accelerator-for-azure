# ADR-0019: 保持ポリシーは正本側で決め、マニフェストで運ぶ

- 状態: 採用
- 日付: 2026-09-10
- 関連: [ADR-0006](0006-ontology-versioning-and-audit.md)（保持ポリシーを決定したが実装が無かった）、[ADR-0009](0009-ontology-operations.md) 決定2（既定グラフには最新の承認済み版のみ）、[ADR-0010](0010-approval-and-projection.md) 決定5・決定7（射影は状態で決める / マニフェスト）、[ADR-0013](0013-reconcile-repairs-observed-divergence.md)（観測された乖離を修復する）、[ADR-0002](0002-triple-store-as-rebuildable-projection.md)（ストアは再構築可能な射影）、バックログ `P2B-02`

## コンテキスト

[ADR-0006](0006-ontology-versioning-and-audit.md) は「ストアに載せるバージョンを保持ポリシーで制御する（最新版 + 参照中のバージョン + 直近 N 版など）」と決定したが、同 ADR の補記が「**実装が存在しなかった**」と記録している。`P1-C1` の欠陥修正で「既定グラフは常に単一の版」は入ったが、**保持ポリシーそのものは無い。**

実装を読んで、2 つの具体的な問題が分かった。

### 問題1: `SUPERSEDED_RETAIN` は名前が「N 版保持」なのに、実装は真偽値である

ローダの `projection_targets`（`containers/fuseki/lib/validate.sh`）は次のようになっている。

```sh
superseded)
    if [ "${retain}" = "0" ]; then
        printf 'skip:superseded-retain-0'
    else
        printf 'named'        # ← 個数を見ていない
    fi
```

**`SUPERSEDED_RETAIN=2` と書いた運用者は「直近 2 版を残す」と読むが、実際には全部載る。** エラーにならず、静かに期待と違う結果になる。このリポジトリが繰り返し避けている形である。

### 問題2: 「ストアに載せるか」の決定が、ローダと API で食い違いうる

`approve` は前の版を `superseded` にするが、**その名前付きグラフをストアから外さない**。一方ローダは再構築時に（既定では）`superseded` を読み込まない。したがって**ストアの内容が「再構築したかどうか」で変わる。**

`reconcile` はこの食い違いを避けるため、`superseded` の在否を**どちらも不問**にしている（コメントに「ストアに載せるかの決定をローダ 1 箇所に保つ」と書いてある）。判断の重複を避けた点は正しいが、結果として**保持ポリシーを誰も強制していない**。

決めるべきことは 4 つある。

1. **保持ポリシーをどこで決めるか**（ローダか、正本側か）
2. **`SUPERSEDED_RETAIN` の意味をどうするか**
3. **「直近 N 版」の順序を何で決めるか**
4. **ポリシーの外に出た版をストアから外すのは誰か**

## 決定

### 1. 保持ポリシーは**正本側（Python）で決め、マニフェストに載せて運ぶ**

マニフェストの各版に `projection` を持たせる。値はローダが今使っている語彙そのままにする。

```json
{
  "schema": 2,
  "namespace": "retail-core",
  "current": "2.0.0",
  "retain_superseded": 1,
  "versions": [
    { "version": "2.0.0", "status": "approved",   "projection": "named default" },
    { "version": "1.5.0", "status": "superseded", "projection": "named" },
    { "version": "1.0.0", "status": "superseded", "projection": "skip:superseded-beyond-retain" }
  ]
}
```

**ローダは判断しない。** マニフェストの `projection` をそのまま解釈する。

これは既存のコメント「**判断が二箇所に存在すると、片方だけ直して食い違う**」（`validate.sh`）を素直に適用したものである。`reconcile` が `superseded` の在否を不問にしたのは、その原則を守るために**判断を持たない側に降りた**結果だった。**判断を 1 箇所に集めれば、降りる必要が無くなる。**

正本側に置く理由は 3 つある。

- **ポリシーの入力が正本にしかない。** 「直近 N 版」の順序は `approved_at`（PostgreSQL）で決まる。マニフェストには載っていない
- **`reconcile` が強制できるようになる。** ポリシーを知っているのは Python 側なので、そこに決定があれば残留の削除も欠落の修復も同じ場所で判断できる
- **テストできる。** シェル + `jq` より Python の純粋関数のほうが、境界（N=0、N が版数以上、`approved_at` が NULL）を網羅しやすい

### 2. `SUPERSEDED_RETAIN` は**個数**にする。既定は 0

`superseded` の版のうち**直近 N 版だけ**を名前付きグラフに載せる。`0` は「載せない」（現在の既定と同じ挙動）。

**名前を変えない。** `SUPERSEDED_RETAIN` は既にローダとその ADR・テストから参照されている（ID は変えないという規律と同じ理由）。**名前が示していた意味に実装を合わせる**方向で直す。

**既定を 0 のままにするのは、[ADR-0010](0010-approval-and-projection.md) が保持ポリシーの既定値を未決として残しているため**である。この ADR は「N を正しく効かせる」ことを決めるが、「N をいくつにすべきか」は決めない。0 は「増やす方向の変更だけが必要」という安全側である。

### 3. 「直近 N 版」の順序は `approved_at` の降順で決める

**バージョン文字列で並べない。** `validate_version` は英字と記号を広く許すので（`1.0.0-rc1`、`2026-09` 等）、文字列順は「直近」を意味しない。

`superseded` の版は**かつて `approved` だった**ので `approved_at` を持つ。「直近」は「**最後に現行だった**」であり、それは `approved_at` が大きいものである。

**`approved_at` が NULL の版は最も古いものとして扱う。** 本来ありえない（`superseded` は `approved` を経る）が、データの移行や手作業で起こりうる。NULL を「新しい」と解釈すると、**古い版が残って新しい版が落ちる**という最も分かりにくい壊れ方になる。

### 4. ポリシーの外に出た版は `reconcile` が外す。`approve` は外さない

**`SUPERSEDED_RETAIN` は API 側の設定にする。** マニフェストを作るのは API なので、ポリシーの値を知る必要があるのは API だけである。**ローダの環境変数は後方互換のためだけに残る**（`projection` を持たない古いマニフェストに落ちたときのみ効く）。値を 2 箇所に置くと食い違うので、Bicep から注入するのは API だけにする。

| 誰が | 何をするか |
|---|---|
| `approve` | 前の版を `superseded` にし、**マニフェストを更新する**。名前付きグラフはそのまま |
| `reconcile` | マニフェストの `projection` と**ストアの実際の状態**を突き合わせ、`skip:` の版の名前付きグラフを削除する |
| ローダ（再構築時） | マニフェストの `projection` に従って読み込む。`skip:` は読み込まない |

**`approve` が外さない理由は不変条件3 である。** 承認は正本への書き込みであり、その成否を射影の操作（グラフの削除）に依存させてはいけない。削除に失敗したときに承認まで巻き戻すのは間違いだし、握り潰すなら結局 `reconcile` が回収することになる。**回収する仕組みがあるなら、最初からそこに任せる。**

**これは [ADR-0013](0013-reconcile-repairs-observed-divergence.md) が決めた形そのものである。** 同 ADR は「`projected_at` は書き込み経路の知識であり、ストアの現在の状態ではない」「ストアに問い合わせて観測された乖離を修復する」と決めた。保持ポリシーの逸脱も**観測された乖離**の一種であり、同じ経路で扱う。

`reconcile` の報告に `retention_removed`（ポリシーの外に出たので削除した）を加える。**既存の `graphs_removed`（正本に無い残留）とは分ける** — 前者は「正本にあるが載せない版」、後者は「正本に無い版」で、運用者が読むべき意味が違う。

## 検討した代替案

### ローダ側にポリシーを実装する（`SUPERSEDED_RETAIN` を jq で数える）

変更が `validate.sh` に収まり、マニフェストの形を変えなくて済む。**却下**: 決定1 の理由。(1) 順序を決める `approved_at` がマニフェストに無い（載せれば済むが、そのとき既にマニフェストの形は変わっている） (2) `reconcile` が強制できないままになる（判断がシェル側にあるので Python から参照できない） (3) 境界のテストがシェル + jq になり、網羅が難しい。

### マニフェストに `approved_at` を載せ、判断はローダに残す

順序の問題は解ける。**却下**: `reconcile` が強制できない問題が残る。加えて**判断が 2 箇所（ローダと、将来ポリシーを読む何か）に増える方向**である。マニフェストは「ローダのための射影」（ADR-0010 決定7）なので、**判断済みの結果を運ぶほうが役割に合う。**

### `approve` の時点で名前付きグラフを削除する

ストアの状態が即座に正しくなる。**却下**: 決定4 の理由。不変条件3 に反する向きである。削除の失敗を握り潰すなら結局 `reconcile` が必要になり、**同じことを 2 箇所で行う**ことになる。

### `SUPERSEDED_RETAIN` を真偽値のまま、名前を `SUPERSEDED_LOAD_ALL` に変える

実装を変えずに名前を実態に合わせられる。**却下**: ADR-0006 が決めた保持ポリシー（「直近 N 版」）を実装しないことになる。`P2B-02` はまさにそれを実装するタスクである。なお `SUPERSEDED_RETAIN` は**現時点では Bicep から注入されていない**（ローダの既定値 0 だけが効いている）ので、名前を変えても壊れる既存のデプロイは無い。それでも変えないのは、ADR とスクリプトから参照されている ID を動かさないという規律（`CLAUDE.md`）と、**名前が示していた意味に実装を合わせるほうが正しい直し方**だからである。

### 「参照中のバージョン」も保持の対象にする（ADR-0006 の原文）

ADR-0006 は「最新版 + **参照中のバージョン** + 直近 N 版」と書いている。**却下（この ADR では扱わない）**: `P2B-05` のアクセスログは `default_graph_version` と `used_graph_clause` を記録するが、**`GRAPH` 句で明示された版が何かは記録していない**（[ADR-0018](0018-context-access-log.md) 決定7・未解決事項）。参照中の版を知るにはクエリの解析器が必要である。**分からないものを推測して保持の判断に使わない。** アクセスログが版を解決できるようになったら、そのときに足す。

### マニフェストのスキーマを上げず、`projection` を任意フィールドとして足す

古いローダが新しいマニフェストを読んでも壊れない。**却下（半分採る）**: スキーマは `2` に上げる（何が変わったかを版で示せないと、後から読む人が困る）。ただし**ローダは `projection` が無いマニフェストでも動く** — 古いマニフェストが残っている窓（デプロイの入れ替え中、`reconcile` を回す前）があるため、従来の状態ベースの判断に落ちて**そのことを警告としてログに出す**。黙って落ちない。

## 結果（トレードオフ・影響）

### 得られるもの

- **`SUPERSEDED_RETAIN` が名前どおりに効く。** 「2 と書いたのに全部載る」が終わる
- **保持ポリシーが強制される。** `reconcile` がポリシーの外に出た版を外すので、**ストアの内容が「再構築したかどうか」で変わらなくなる**
- **判断が 1 箇所になる。** `reconcile` が `superseded` の在否を不問にする必要が無くなる（判断を持たない側に降りなくてよい）
- ポリシーの境界（N=0、N が版数以上、`approved_at` が NULL）が Python の純粋関数としてテストできる

### 受け入れるコスト

- **マニフェストのスキーマが 2 になる。** 古いローダは `projection` を無視して従来の判断に落ちる（警告を出す）。**`reconcile` を 1 回回せば全名前空間のマニフェストが更新される**
- **`SUPERSEDED_RETAIN` を 0 以外にしていた既存のデプロイは挙動が変わる。** 「全部載る」から「直近 N 版だけ」になる。**これは修正である**が、載っていた版が消えるという意味では破壊的でもある。README に明記する
- **`reconcile` が削除を行う。** これまで `superseded` の在否を不問にしていたので、初回の `reconcile` でポリシーの外の版がまとめて消える。**報告に出るので黙っては消えない**
- **「参照中のバージョン」は保持の対象にならない。** ADR-0006 の原文の 3 要素のうち 1 つが未実装のまま残る

### 影響を受ける他の決定

- **[ADR-0006](0006-ontology-versioning-and-audit.md)**: 保持ポリシーが実装される（「参照中のバージョン」を除く）
- **[ADR-0010](0010-approval-and-projection.md) 決定7**: マニフェストのスキーマが 2 になり、**判断済みの `projection` を運ぶ**。決定5（射影は状態で決める）は「状態 + 保持ポリシー」に拡張される
- **[ADR-0013](0013-reconcile-repairs-observed-divergence.md)**: 保持ポリシーの逸脱を「観測された乖離」の一種として扱う。`ReconcileReport` に `retention_removed` が加わる
- **[ADR-0009](0009-ontology-operations.md) 決定2**: 「併せて保持ポリシーを実装する」が実行される

### 未解決のまま残す問い

- **`SUPERSEDED_RETAIN` の既定値をいくつにすべきか**（[ADR-0010](0010-approval-and-projection.md) が未決として残したまま。この ADR は「N が正しく効く」ことだけを決めた）
- **「参照中のバージョン」の保持**（アクセスログが `GRAPH` 句の版を解決できるようになってから）
- **保持ポリシーを名前空間ごとに変えられるようにするか**（今はデプロイ全体で 1 つ）
- **`rejected` / `draft` の扱い**（マニフェストに載らないので保持ポリシーの対象外。[ADR-0010](0010-approval-and-projection.md) の未解決事項のまま）
