# ADR-0027: 何から編集したかを記録する — 「分からない」を「派生していない」と書かない

- ステータス: 承認済み
- 日付: 2026-09-12

## コンテキスト

[ADR-0026](0026-provenance-export.md) 決定2 は `prov:wasDerivedFrom` を
**出さない**と決めた。理由は、そもそも記録していないからである。

`publish` は `base_version` を受け取るが、**lost update の検出にだけ使って
捨てている**(`P1-13`)。検査が通れば「編集の基準は当時の最新版だった」と
分かっているのに、その事実をどこにも書いていない。

[ADR-0016](0016-semantic-diff.md) 決定2 が差分の基準に選んだ「この承認によって
`superseded` になる版」は**実務上の基準**であって、著者が実際に何から編集したか
ではない。承認の順序は派生ではない — 1.0.0 が承認される前に書かれた 2.0.0 も
ありうる。

`P2A-15` はこの穴を埋める。

### 3 つの状態がある

素直に「`base_version` を列に保存する」だけでは足りない。**NULL に 2 つの
意味が同居する。**

| 状況 | いま分かること |
|---|---|
| `base_version` を渡して publish した | **その版から編集した** |
| 名前空間の**最初の版**だった | **この名前空間に先行する版は無かった**(測った事実) |
| `base_version` を渡さず publish した(既存の全行を含む) | **分からない** |

3 つ目を 2 つ目と同じ NULL にすると、**「宣言されなかった」が「派生していない」
として読める。** このリポジトリが繰り返し避けてきた形である。

## 決定

### 1. 列を 2 つ足す。`edited_from` と `edited_from_recorded`

```
edited_from          VARCHAR(64) NULL   -- 編集の基準にした版
edited_from_recorded BOOLEAN NOT NULL DEFAULT false
```

| `edited_from_recorded` | `edited_from` | 意味 |
|---|---|---|
| `false` | `NULL` | **分からない**(宣言されなかった)。**既存の全行がこれ** |
| `true` | `NULL` | この名前空間に先行する版が無かった(最初の版) |
| `true` | `'1.0.0'` | 1.0.0 から編集した |

**旗を別の列にする。** 1 つの nullable 列で 3 状態は表せない。文字列の
番兵(`''` や `'-'`)で表す案は、**バージョン文字列として妥当な値と区別が
つかなくなる**ので採らない(`_VERSION_PATTERN` は英数字 1 文字を許す)。

**既定は `false`(分からない)である。** マイグレーションは backfill しない
(決定4)。安全側の向きは「知らないことにする」であり、**既定を `true` に
すると既存の全行が「先行する版は無かった」と主張し始める。**

### 2. `base_version` を渡さなかった最初の版は「先行版なし」として記録する

`publish` の時点で名前空間に版が 1 つも無ければ(`latest is None`)、
**この名前空間内に先行する版は存在しない**。これは推測ではなく測った事実
なので `edited_from_recorded = true`、`edited_from = NULL` で記録する。

**「先行する版が無い」は「どこからも来ていない」ではない。** 著者が別の場所で
書いたファイルを投入した場合も最初の版になる。記録しているのは
**この名前空間の改訂の系譜における根である**ことだけで、ADR-0026 決定2 の
「測っていないことを主張しない」に反しない。この意味は列のコメントと
`OntologyVersion` の docstring に書く。

### 3. 名前は `edited_from`。`base_version` を使い回さない

**API の中に既に `base_version` があり、意味が違う。**

| どこ | `base_version` の意味 |
|---|---|
| `POST .../publish` のリクエスト | **lost update を検出するための基準**。編集の元にした版 |
| `GET .../versions/{v}/diff` の応答 | **差分を取る相手**。既定はこの版を承認したときに `superseded` になる版 |
| `GET .../versions/{v}/deprecation` の応答 | 同上 |

保存した事実に `base_version` という名前を付けると、**応答の中で同じ語が
「系譜の親」と「比較の相手」の 2 つの意味を持つ**。ADR-0026 決定7 で
「版のグラフ IRI を版そのものに流用しない」と決めたのと同じ話である —
**名前の共有は概念の同一視として読まれる。**

リクエストの `base_version` は名前を変えない。あちらは**検査の基準**という
役割の名前であって、保存する事実の名前ではない(そして既存のクライアントの
契約である)。

### 4. マイグレーションは backfill しない

既存の行の `edited_from_recorded` は `false` のままにする。

**推測して埋められる余地はある** — 版の `id` の順に並べて直前の版を親とすれば、
それらしい系譜が作れる。**やってはいけない。** それは ADR-0026 決定2 が
拒否したもの(承認の順序を派生として出す)を、**API の手前ではなく正本に
書き込む**形である。正本に書いた嘘は後から区別できない。

`0004_access_log` / `0005_competency_question_sets` / `0006_term_mappings` と
同じ判断である。

### 5. PROV-O には「記録されているか」も出す

`ontology_core.prov` は版の実体に次を出す。

```turtle
<urn:ontology:revision/retail-core/2.0.0> a prov:Entity ;
    ont:version "2.0.0" ;
    ont:editedFromRecorded true ;
    prov:wasDerivedFrom <urn:ontology:revision/retail-core/1.0.0> .
```

**`ont:editedFromRecorded` を真偽どちらでも出す。** これが無いと、
`prov:wasDerivedFrom` が無いことが「根である」とも「記録していない」とも
読める。**RDF は「無い」と「記録していない」を区別できない**
([ADR-0025](0025-result-limit-enforcement.md) 決定3 / ADR-0026 決定5 と
同じ原則の 7 例目)。

**版の行が引けなかったときは `ont:editedFromRecorded` も出さない。**
`audit_events` には名前空間への外部キーが無いので、名前空間を削除して同名で
作り直すと**版の行が無い監査イベント**が残りうる。そのとき `false` を出すと
「行を見て、記録されていなかった」と読める — 実際には**行を見られなかった**。
3 段目の「分からない」であり、`false` と混ぜない。

### 6. 書き出しで引く版は、監査イベントが参照しているものだけにする

名前空間の全版を引かない。`ontology_core.prov.referenced_versions()` が
**書き出しに含まれる監査イベントから対象の版を抜き出し**、ルータはその集合
だけを `IN` で引く。

**対象の解析規則を 1 か所に閉じるため**でもある。`<名前空間>@<バージョン>`
の読み方が `prov.py` とルータの両方にあると、片方だけ直したときに
「実体は出るが系譜が出ない」という静かな不整合になる。

## 検討した代替案

### `audit_events` に `base_version` を足す

**却下。** 監査は追記専用で、`published` のイベントは既にある。そこに 1 列
足すのは自然に見える。

却下理由: **`prov:wasDerivedFrom` は実体と実体の関係であり、行為の属性では
ない。** 監査行に置くと、書き出しのときに「行為 → その行為の対象の版 →
親の版」という 2 段の読み替えが必要になる。そして**版の属性を版の行以外から
引く**形は、`GET .../versions/{v}` が系譜を返せないことも意味する。

### 単一の nullable 列にして、NULL を「根または不明」とする

**却下(決定1)。** 列が 1 本で済む。

却下理由: **この ADR が直している問題そのものである。** 「分からない」と
「根である」を同じ値にすると、PROV-O にも同じ曖昧さがそのまま出る。

### `base_version` を必須にする

**却下。** 最も情報が集まる。

却下理由: 既存のクライアントの契約を壊す。そして**最初の版には渡せる値が
無い**ので、結局「渡さなかった」場合の意味を決めなければならない。
必須化はこの ADR の問題を解かずにクライアントを壊す。

### 既存の行を版の順序から backfill する

**却下(決定4)。** 系譜が一気に埋まって見栄えが良い。

却下理由: **承認の順序は派生ではない。** ADR-0026 決定2 が API の手前で
拒否したことを、正本に書き込む形になる。正本に書いた推測は、後から事実と
区別できない。

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **列が 2 本増える。** 1 本の nullable 列では 3 状態を表せない
- **既存の版には系譜が無い**(決定4)。`edited_from_recorded = false` のまま
  で、`prov:wasDerivedFrom` は出ない
- **`base_version` を渡さないクライアントには系譜が付かない。** 最初の版を
  除いて `false` になる。README で渡すことを勧める
- **`edited_from` に外部キーを張らない。** 書き込み時に「当時の最新版」と
  一致することを検査しているので実在は保証されるが、**制約としては表現して
  いない**。版の行は個別には削除されないので(不変条件7、名前空間の削除は
  CASCADE で全版が消える)、宙に浮く参照は生まれない
- **名前が 2 つになる**(決定3)。リクエストは `base_version`、保存と応答は
  `edited_from`

### 得られるもの

- **ADR-0006 決定3 が名前を挙げた `prov:wasDerivedFrom` を、測った事実として
  出せる**([ADR-0026](0026-provenance-export.md) 決定2 が保留していた部分)
- **「分からない」が読み取れる**(決定5)。無言の欠落ではなく
  `ont:editedFromRecorded false` として出る
- **`GET .../versions/{v}` が系譜を返す。** PROV-O を経由しなくても読める

### 影響を受ける他の決定

- [ADR-0026](0026-provenance-export.md) 決定2 — 補記を追加した
  (`prov:wasDerivedFrom` を出す条件)
- [ADR-0006](0006-ontology-versioning-and-audit.md) 決定3 — 補記 3 の表を
  更新した
- [ADR-0016](0016-semantic-diff.md) 決定2 — 差分の基準(`superseded` になる版)
  と系譜の親(`edited_from`)は**別物**であることが、決定3 で名前の上でも
  区別された
