# ADR-0035: 主体が人間かサービスプリンシパルかを記録する — 「設定していない」を「人間だった」と書かない

- ステータス: 承認済み
- 日付: 2026-09-12

## コンテキスト

[ADR-0026](0026-provenance-export.md) 決定3 は主体を `prov:Agent` のままにし、
`prov:Person` / `prov:SoftwareAgent` に**分けない**と決めた。理由は、そもそも
記録していないからである。

> `audit_events.actor` は Entra のオブジェクト ID だけで、人間かサービス
> プリンシパルかを区別していない。**区別できないものを区別して出さない。**
> `prov:SoftwareAgent` と書けば外部ツールは「これは自動生成だ」と読む。
> 人間の承認を自動化された行為として見せるのは、四眼原則を記録する監査証跡
> としては最悪の誤りである。

`P2A-16` はこの穴を埋める。**書き出しの時点で Entra へ問い合わせてはいけない**
ので(監査の書き出しが Entra の可用性に依存する。不変条件3 と同じ向きの判断)、
**記録の時点で保存する**。

### 既存の実装は既に推測していた

`Principal.is_service_principal` は既に存在し、こう導出されていた。

```python
is_app = claims.get("idtyp") == "app" or "oid" not in claims
```

**この値はどこからも読まれていない**(`grep` で確認。定義と代入の 2 箇所だけ)。
つまり書き出しには影響していなかったが、**読み始める前に直す必要がある。**

`idtyp` は**任意クレーム**である。Entra の文書は次を明記している。

- 「既定ではアプリ専用トークンにのみ発行される」
- 「アクセストークンに影響する任意クレームと同じく、**リソース側**(この API の
  アプリ登録)が設定しなければならない。アクセストークンはリソースが所有する」

つまり**設定していないテナントでは、サービスプリンシパルのトークンにも
`idtyp` が付かない。** そのとき `"oid" not in claims` が最後の砦になるが、

- アプリ専用トークンにも `oid`(サービスプリンシパルのオブジェクト ID)は**付く**
- Entra の文書は「アプリ専用のシナリオでは `oid` はサービスプリンシパルの
  オブジェクト ID」と書いている

ので、この砦は**成り立たない**。結果として現在の式は、`idtyp` を設定して
いないテナントのサービスプリンシパルを `is_service_principal = False` と
判定する — **ADR-0026 決定3 が「最悪の誤り」と呼んだものの逆向き**、すなわち
自動化された行為を人間の行為として見せる形である。

### 3 つの状態がある。真偽値では表せない

| トークンの状態 | 分かること |
|---|---|
| `idtyp == "app"` | **サービスプリンシパルである** |
| `idtyp == "user"` | **人間である** |
| `idtyp` が無い | **分からない**(ユーザートークンなのか、任意クレームが未設定なのか区別できない) |

3 つ目が本質である。文書上、`idtyp` をユーザートークンにも発行させる
`include_user_token` という追加プロパティがあるが、**それが v2.0 の
アクセストークンに効くことは文書から確定できない**(`additionalProperties` の
表は「v1.0 固有の任意クレーム」節の下にある)。実機で確かめるには課金される
デプロイが必要である(`P2A-09` 実機確認と同じ制約)。

**したがって設計は「`user` が一度も現れなくても正しい」ものでなければならない。**
真偽値にすると、この 3 つ目が `False` に潰れて 1 つ目と 2 つ目の区別に化ける。

## 決定

### 1. `Principal.is_service_principal` を捨て、3 値の `actor_type` にする

```python
class ActorType(StrEnum):
    USER = "user"
    SERVICE_PRINCIPAL = "service-principal"
    UNKNOWN = "unknown"
```

| `idtyp` | `actor_type` |
|---|---|
| `"app"` | `service-principal` |
| `"user"` | `user` |
| 無い / それ以外(`device` 等) | **`unknown`** |

**`oid` の有無から推測しない**(コンテキストの通り成り立たない)。

**派生プロパティとして `is_service_principal` を残さない。** 真偽値は
`unknown` を「サービスプリンシパルではない」に畳む — それが直したい誤りその
ものである。読んでいる箇所が無いので、消すのに移行期間も要らない。

**`AUTH_MODE=disabled` の `Principal.local_dev()` も `unknown` にする。**
検証したトークンが存在しないので、人間だと名乗る根拠が無い。副作用として
**ローカル開発の書き出しが「`idtyp` 未設定のテナント」と同じ見た目になる** —
運用者が設定漏れの状態を手元で見られる。

### 2. Entra の語彙(`idtyp`)を監査の列に持ち込まない

`device` を `unknown` に畳んで生の値を捨てる。ADR-0026 決定4 が
`ont:action` に**生の文字列も必ず書く**と決めたのと逆だが、対象が違う。

- `action` は**このリポジトリの語彙**である。対応表が追いつかないことがある
  ので、生の値を残す
- `idtyp` は**Entra の語彙**である。監査証跡が答えたい問いは
  「**この行為に人間が説明責任を負うか**」であって「トークンの種別は何か」
  ではない。3 値はその問いへの意図的な射影である

`audit_events` は `AUTH_MODE=disabled` でも、将来 Entra 以外の検証器を
足したときにも同じ意味を持たなければならない。そこに Entra 固有の語彙を
入れると、意味が発行者ごとに変わる。

### 3. `audit_events.actor_type` を 1 本足す。旗は足さない

nullable の `String(32)`。**`NULL` は「この機能より前に書かれた行」である。**

| 列の値 | 意味 |
|---|---|
| `NULL` | **問うていない**(この機能より前の既存の全行) |
| `'unknown'` | **問うて、分からなかった**(`idtyp` が無かった) |
| `'user'` / `'service-principal'` | 記録した |

[ADR-0027](0027-revision-lineage.md) 決定1 は 3 状態を表すために列を 2 本
(`edited_from` と `edited_from_recorded`)足した。**ここでは 1 本で足りる。**
あちらの `edited_from` は「親の版」という値の列で、`NULL` に「親が無い」と
「記録していない」が同居した。こちらは**最初から列挙型**なので、`unknown`
という明示的な値を語彙の中に持てる。`NULL` はもう 1 つだけ別の意味
(問うていない)を運べばよい。

### 4. 種別は**行為ごと**に記録し、主体のクラスは**矛盾しないときだけ**出す

`ont:actorType` は `prov:Activity` に付ける。`prov:Person` /
`prov:SoftwareAgent` は `prov:Agent` に付けるが、**その書き出しに含まれる
その主体のすべての行為が一致しているときだけ**にする。

**主体の IRI は行為ごとではなく主体ごとである。** 同じオブジェクト ID が、
`idtyp` を設定する前の行為では `unknown`、設定した後の行為では `user` として
記録されうる。種別を主体に付けると、1 つの IRI に複数の値がぶら下がり
**「この主体は user でも unknown でもある」**と読める。

| その主体の行為の記録 | 出力 |
|---|---|
| すべて `user` | `prov:Agent`, **`prov:Person`** |
| すべて `service-principal` | `prov:Agent`, **`prov:SoftwareAgent`** |
| `unknown` を含む / 食い違う / `NULL` を含む | `prov:Agent` **のみ** |

行為ごとの記録は**測った事実**であり、主体のクラスは**主体についての主張**
である。主張には一致が要る。食い違いをどちらかに丸めると、「測っていない
ことを標準語彙で主張する」形になる(ADR-0026 決定2 と同じ論点)。

なお `prov:Person` / `prov:SoftwareAgent` と**併せて `prov:Agent` も出す**。
下位クラスの推論をしない相手にも主体として読める(ADR-0026 決定4 と同じ形)。

### 5. `NULL` のときは `ont:actorType` を出さない

ADR-0027 決定5 と同じ規則である。`'unknown'` を出すと「問うて、分からな
かった」と読めるが、実際には**問うていない**。

| 列の値 | `ont:actorType` |
|---|---|
| `NULL` | **出さない** |
| `'unknown'` | `"unknown"` |
| `'user'` / `'service-principal'` | その値 |

### 6. `AuditRepository.record` は `actor_type` を**必須**にする

サービス層(`ProjectionService` の各メソッド)とルータには
`actor_type: ActorType = ActorType.UNKNOWN` の既定値を置くが、
**正本の表に書く関数だけは既定値を持たない。**

`P2B-20` の教訓(「**署名の狭さが強制である**」)を、ここでは 1 箇所に
効かせる。書き込みの直前で必ず決めさせれば、新しい行為を足すときに
「種別をどうするか」を考えずに済むことがない。

**全層で必須にはしない。** 既定値 `unknown` は**安全な向き**である —
渡し忘れた呼び出しは情報を落とすだけで、**偽の主張はしない**(決定5 により
`'unknown'` として区別可能に出る)。全層を必須にすると 260 箇所以上の
テストを機械的に書き換えることになり、その差分は「安全側の既定値」より
壊れやすい。

### 7. `idtyp` を任意クレームとして**設定する手順を製品に持つ**

`scripts/setup-app-role.py` に `optionalClaims` の合成を足す。
**設定しなければこの機能は永久に `unknown` を記録する。**

`optionalClaims` は `appRoles` と同じ Microsoft Graph の**複合プロパティ**で、
部分更新すると既存の定義が丸ごと消える(`P1-09` の罠1 と同じ)。
合成は `ontology_core.auth.optional_claims.merge_optional_claim` という
純粋関数に置き、**既存の任意クレームを 1 件も落とさない**ことをテストで
固定する。`--skip-optional-claims` で降りられるようにする(アプリ登録の
書き込み権限が無い運用者のため)。

## 検討した代替案

### `oid` の有無で判定し続ける

**却下(決定1)。** いま動いている(ように見える)。

却下理由: アプリ専用トークンにも `oid` は付く。**成り立たない推測**であり、
成り立たない向きが「自動化を人間として見せる」側である。

### `is_service_principal` を派生プロパティとして残す

**却下(決定1)。** 既存の利用箇所を壊さない。

却下理由: **利用箇所が無い。** そして真偽値は `unknown` を
「サービスプリンシパルではない」に畳むので、残せば誤りを温存する出口を
用意することになる。

### 書き出しの時点で Entra のディレクトリに問い合わせる

**却下。** 既存の行にも種別が付き、backfill できる。

却下理由: **監査証跡の書き出しが Entra の可用性に依存する。** 不変条件3 が
守っている向き(射影の可用性が正本を止めない)と同じ判断である。監査は
インシデントの最中に読むものであり、そのとき外部依存が増えているのは最悪で
ある。加えて、オブジェクト ID は再利用されないとはいえ**削除された主体は
引けない**ので、古い行ほど埋まらない。

### 既存の行を `unknown` で backfill する

**却下(決定3)。** `NULL` を扱う分岐が消える。

却下理由: 「問うていない」を「問うて、分からなかった」に書き換えることに
なる。ADR-0027 決定4 が却下した backfill と同じ形である。

### 主体のクラスを「最後に記録された種別」で決める

**却下(決定4)。** 1 つの値に決まるので出力が単純になる。

却下理由: **並び順に依存する主張になる。** RDF は順序を持たないので、
「最後」は書き出しの実装の都合であって事実ではない。食い違いがあるなら、
それは「分からない」である。

### `device` を `unknown` と別の値にする

**却下(決定2)。** トークンの種別が完全に残る。

却下理由: 答えたい問いは「人間が説明責任を負うか」である。デバイス
トークンはそれを立証しない。語彙を Entra に合わせると、監査の列の意味が
発行者ごとに変わる。

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **テナント側の設定が必要である**(決定7)。アプリ登録に `idtyp` の任意
  クレームを足さないと、記録は `unknown` のままになる。`setup-app-role.py`
  が面倒を見るが、**アプリ登録の書き込み権限が必要**である
- **`user` が本当に出るかを実機で確かめていない**(コンテキスト)。
  `include_user_token` が v2.0 のアクセストークンに効くかは文書から確定
  できない。**効かなければ人間は永久に `unknown` である** — 設計はその場合も
  正しいが、`prov:Person` は出ない。`P2A-18` として実機確認を記録する
- **既存の監査行には種別が無い**(決定3)。`NULL` のまま `ont:actorType` も
  `prov:Person` も出ない
- **主体のクラスが書き出しの範囲に依存する**(決定4)。期間で切った書き出しと
  全件の書き出しで、同じ主体が `prov:Person` を持つかどうかが変わりうる。
  行為ごとの `ont:actorType` は変わらない
- **`Principal` の公開フィールドが 1 つ消える**(決定1)。このリポジトリの
  外で `is_service_principal` を読んでいるコードは壊れる。v0.1.0 未リリース
  なので移行措置は置かない
- **サービス層の既定値は渡し忘れを黙って通す**(決定6)。`unknown` として
  記録されるので偽の主張にはならないが、**情報は落ちる**。既存の記録経路
  すべてについて、種別が実際に届くことをルータ越しのテストで固定する

### 得られるもの

- **ADR-0006 決定3 が名前を挙げた `prov:Person` / `prov:SoftwareAgent` を、
  測った事実として出せる**(ADR-0026 決定3 が保留していた部分)
- **`idtyp` の設定漏れが読み取れる。** 無言の欠落ではなく
  `ont:actorType "unknown"` として出る
- **成り立たない推測が 1 つ消える。** `"oid" not in claims` は、この
  リポジトリに残っていた「測っていないことを主張する」実装だった

### 影響を受ける他の決定

- [ADR-0026](0026-provenance-export.md) 決定3 — 補記を追加した(条件付きで
  `prov:Person` / `prov:SoftwareAgent` を出す)
- [ADR-0006](0006-ontology-versioning-and-audit.md) 決定3 — 補記 3 の表を
  更新した
- [ADR-0014](0014-namespace-rbac.md) 決定1 — 主体の識別子(`oid`)の選択は
  変えない。**識別子と種別は別の列**である
