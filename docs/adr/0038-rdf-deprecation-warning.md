# ADR-0038: `CONSTRUCT` / `DESCRIBE` の結果にも廃止済み用語を警告する — グラフは 1 回しか解析しない

- ステータス: 承認済み
- 日付: 2026-09-12

## コンテキスト

[ADR-0017](0017-deprecation-lifecycle.md) 決定3 は「**エージェントが廃止された
用語を根拠に回答を作る**」ことを塞いだ。結果に廃止済み用語が現れたら、
Core API は応答ヘッダで、MCP は**本文で**警告する(エージェントはヘッダを
見ないため。層で分けた)。

[ADR-0034](0034-construct-describe.md)(`P2A-14`)が `CONSTRUCT` / `DESCRIBE` を
通したとき、**この警告は付けなかった**。

> **廃止済み用語のヘッダは付けない。** `deprecated_iris_in_results` は
> SPARQL Results JSON の形を前提にしている。RDF の結果に対して同じ警告を
> 出す設計は別途必要なので、**出せないものを出したふりをしない**
> (`P2B-23` として記録する)

`P2B-23` はこの穴を埋める。

### 穴の形

**同じデータが、クエリの形を変えるだけで警告なしに取れる。**

| クエリ | 廃止済み用語の警告 |
|---|---|
| `SELECT ?s WHERE { ?s a owl:Class }` | **出る** |
| `CONSTRUCT { ?s ?p ?o } WHERE { ?s a owl:Class ; ?p ?o }` | **出ない** |

ADR-0017 決定3 が塞いだ穴が、**別の入口で開いたままだった。** しかも
`CONSTRUCT` は「自分のストアへ読み込む」用途(ADR-0031 決定1 と同じ動機)で
使われるので、**廃止済み用語がそのまま利用者のストアへ複製される。**

### 切り詰めとは問題の形が違う

ADR-0034 決定4 は**切り詰めを拒否して 413 にした**。理由は
「**RDF には封筒が無い**」— 切り詰めたことを書く場所が RDF の中に無く、
ヘッダに書いてもエージェントは見ないので、**不完全なグラフが完全なものとして
届く**。

**廃止の警告はこれと違う。**

| | 切り詰め | 廃止の警告 |
|---|---|---|
| グラフ自体 | **不完全になる** | **完全で正しい** |
| 見落としたときの帰結 | 「N 件で全部」と誤って結論する | 廃止済み用語を使ってしまう(グラフは正しい) |
| RDF の中に書けるか | 書けない(トリプルを足すと利用者のグラフを汚す) | 同じく書けない |
| ヘッダで足りるか | **足りない**(不完全さが伝わらないまま届く) | **足りる**(Core API の層では) |

切り詰めを 413 にしたのは「**ヘッダでは足りないから**」であって「ヘッダが
悪いから」ではない。廃止の警告はヘッダで足りる — そして MCP の層で本文に
載せ替える経路は既にある(ADR-0017 決定3)。

## 決定

### 1. `SELECT` と同じヘッダを使う。同じ形で並べる

`X-Ontology-Deprecated-Terms` に IRI をカンマで並べる。**クエリの形によって
警告の受け取り方が変わってはいけない。**

MCP 側も同じヘッダを読み、`deprecation_warnings` として本文に載せる
(ADR-0017 決定3 の層分けをそのまま適用する)。**MCP の RDF の経路は
早期 return しているので、そこに載せ忘れると警告は届かない。**

### 2. 警告を RDF の中に入れない

ADR-0034 決定4 と同じ理由である。

> トリプルを足せば**利用者のグラフにこちらが作った主張を混ぜる**ことになります

切り詰めのためにそれを拒んだのに、警告のために混ぜるのは一貫しない。
`ont:deprecatedTermsInResult` のようなトリプルを足すと、利用者が
`CONSTRUCT` の結果を自分のストアへ読み込んだ時点で**この API が作った
メタデータが利用者のオントロジーの一部になる。**

### 3. グラフは 1 回しか解析しない。`RdfResult` が IRI の集合を持つ

`load_construct_result` は上限の検査のために既にグラフを解析している。
その場で IRI(主語・述語・目的語)を集めて `RdfResult.iris` に入れる。

**解析を足さない。** この経路は既に

1. 上限の検査(`load_construct_result`)
2. アクセスログの用語(`terms_in_graph`)

で**2 回解析していた**。ここに廃止の検査を足すと 3 回になる。rdflib の解析は
CPU バウンドで、そのためにわざわざ別スレッドへ逃がしている(ADR-0034)。
**同じ本文を 3 回解析するのは、上限を 50,000 トリプルにしている API では
無視できない。**

そこでアクセスログ側も同じ集合から求める。`terms_in_graph(turtle, base_iri=…)`
は `terms_with_prefix(iris, base_iri=…)` に置き換える — **解析しない純粋な
絞り込み**になる。`base_iri` が空なら何も返さない規則はそのまま保つ
(空の接頭辞で全 IRI を数えないため)。

### 4. 主語・述語・目的語のすべてを見る

`terms_in_graph` と同じ判断である(ADR-0034 決定7)。

**`SELECT` 側より網羅的になる。** `deprecated_iris_in_results` は束縛のセルで
`type == "uri"` のものだけを見るので、**述語は拾えない**(`SELECT ?s ?o` の
結果に述語は現れない)。廃止された property を使ったクエリは、`SELECT` では
警告が出ないが `CONSTRUCT` では出る。

**これは良い方向の差である**(警告は多いほうが安全側)。ただし
「同じ意図のクエリで警告の数が変わる」ことは受け入れるコストに書く。

### 5. リテラルは IRI として扱わない

`URIRef` のノードだけを見る。文字列が偶然一致しても警告しない
(`deprecated_iris_in_results` と同じ判断)。

### 6. `base_iri` で絞らない

廃止済み用語の集合(`deprecated_terms_in_dataset`)は**そのデータセットに
対する SPARQL で求めている**ので、そこに入るのは呼び出し元が既に読める
用語だけである。`base_iri` で絞ると、**そのデータセットに取り込んだ外部語彙の
廃止を警告できなくなる。**

取り込んだ語彙の廃止は利用者にとって同じだけ重要で、かつ**新しい情報の漏れは
無い**(呼び出し元は同じデータセットに `SELECT` を投げれば読める)。

### 7. 413 のときは警告しない

上限を超えたら本文はグラフではない(エラーの detail である)。
**返していないものを警告しない** — ADR-0025 決定3 が「廃止の検査は切り詰めた
後の結果に対して行う」と決めたのと同じ理屈である。

## 検討した代替案

### 警告のトリプルを結果のグラフに足す

**却下(決定2)。** エージェントは RDF を読むので、RDF の中にあれば必ず届く。

却下理由: **利用者のグラフにこちらが作った主張を混ぜる。** ADR-0034 決定4 が
切り詰めのために拒んだのと同じ理由である。`CONSTRUCT` の結果は自分のストアへ
読み込む用途があるので、混ぜたトリプルは**利用者のオントロジーの一部として
永続する。**

### RDF の経路だけ別のヘッダ名にする

**却下(決定1)。** `SELECT` の警告と区別できる。

却下理由: **区別する理由が無い。** 「廃止済み用語が結果に現れた」という事実は
クエリの形に依らない。名前を分けると MCP 側が 2 つ読まなければならず、
片方を読み忘れたときに**警告が静かに消える**。

### `deprecated_iris_in_results` を RDF も受け取れるように広げる

**却下。** 呼び出し側の分岐が 1 つ減る。

却下理由: **入力の形が根本的に違う**(JSON の束縛 vs 解析済みのグラフ)。
1 つの関数にすると「どちらの形も受ける `Any`」になり、**型で守れるものが
減る**。そして RDF 側は**既に解析済みのグラフを持っている**ので、文字列を
渡し直すと決定3 が避けた再解析に戻る。

### アクセスログ用の `terms_in_graph` をそのまま残す

**却下(決定3)。** 変更が小さい。

却下理由: `RdfResult.iris` を足した時点で、**同じ本文をもう 1 回解析する
理由が無くなる。** 残せば「なぜここだけ再解析するのか」に答えが無い。

### 413 のときも「上限を超えた結果に廃止があった」と警告する

**却下(決定7)。** 情報が増える。

却下理由: **返していない結果について警告することになる。** 受け取った側には
対応するトリプルが無い。ADR-0025 決定3 と同じ判断である。

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **`SELECT` と `CONSTRUCT` で警告の数が変わる**(決定4)。RDF 側は述語も
  見るので、廃止された property を使うクエリは `CONSTRUCT` でだけ警告が出る。
  **多いほうが安全側**だが、同じ意図のクエリで数が違うのは説明が要る
- **`RdfResult` が IRI の集合を持つ**(決定3)。50,000 トリプルの結果なら
  最大 150,000 個のノードを走査して集合に入れる。**解析そのものより軽い**
  (解析は既に行っている)が、メモリは増える
- **`terms_in_graph` が無くなる**(決定3)。`terms_with_prefix` に置き換えた。
  外部から呼んでいるコードは壊れる(v0.1.0 未リリースなので移行措置は置かない)
- **ヘッダは Core API の層でしか届かない**(決定1)。素の HTTP クライアントで
  `CONSTRUCT` を叩く利用者は、**ヘッダを見なければ警告に気づかない**。
  これは `SELECT` と同じ性質であり、エージェントのための層(MCP)では本文に
  載せてある
- **廃止済み用語の取得が 1 クエリ増える**(`CONSTRUCT` の経路にも
  `deprecated_terms_in_dataset` が入る)。`SELECT` の経路では既に払っている
  コストである

### 得られるもの

- **ADR-0017 決定3 が塞いだ穴が、別の入口でも閉じる。** クエリの形を変えれば
  警告なしに廃止済み用語が取れる状態が終わる
- **解析が 3 回ではなく 1 回になる**(決定3)。廃止の検査を足しながら、
  むしろ既存の経路が速くなった
- **`SELECT` では出なかった述語の廃止も警告できる**(決定4)

### 影響を受ける他の決定

- [ADR-0017](0017-deprecation-lifecycle.md) 決定3 — 補記を追加した
  (RDF の結果にも同じヘッダで警告する)
- [ADR-0034](0034-construct-describe.md) — 補記を追加した(未解決だった
  廃止の警告を埋めた)。決定4(413 で断る)は**変えていない** — 切り詰めと
  警告は問題の形が違う(コンテキストの表)
- [ADR-0025](0025-result-limit-enforcement.md) 決定3 — 「返していないものを
  警告しない」を RDF の経路にも適用した(決定7)
