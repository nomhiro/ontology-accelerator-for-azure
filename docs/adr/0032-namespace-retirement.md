# ADR-0032: 名前空間は削除ではなく退役させる — 正本を残し、射影と増設を止める

- ステータス: 承認済み
- 日付: 2026-09-12

## コンテキスト

`DELETE /namespaces/{name}` は、Blob に公開済み TTL が 1 件でも残っていれば
409 を返す。そのメッセージが**約束をしている**。

> 公開済みオントロジーを含む名前空間の削除は Phase 2(監査経路)で対応します

[ADR-0024](0024-namespace-delete-locking.md) 決定4 はこの約束の中身を決めず、
選択肢を 3 つ書いて `P2B-19` に送った。

1. 恒久的に拒否する
2. **正本を残し、射影だけ止める(退役)**
3. 理由付きで Blob も消す

同決定は「**2 が筋が通っている**」と書いている。これがその実装である。

### なぜ 1 でも 3 でもないか

**3 は不変条件7(公開済みの版を書き換えない。削除もしない)に正面から反する。**
そして [ADR-0006](0006-ontology-versioning-and-audit.md) の中核価値
「誰が承認した定義に基づく答えかを説明できること」は、**その名前空間が
使われなくなった後こそ効く** — 過去の回答の根拠を辿るために監査証跡が要る。

**1 は約束を破る。** 409 のメッセージが「Phase 2 で対応します」と書いてある。
恒久的に拒否するなら、まずメッセージを直さなければならない。そして
**「もう使わない名前空間」が一覧に残り続け、射影の資源も消費し続ける**。

### `P2B-C1` が設計に影響した

この作業のためにローダを読んでいて、**マニフェストの `schema` の食い違いで
ローダが全名前空間をスキップしていた**ことが見つかった(`P2B-C1`)。

そこから得た規則が退役の設計を決めた。

> **安全に関わる指示を新しい schema にだけ載せてはいけない。**
> 古いローダが無視すると事故になる。

退役は**古いローダが既に従う欄**で表現する(決定2)。

## 決定

### 1. 退役は名前空間の状態であって、削除ではない

`namespaces` に 3 列足す。

```
retired_at     TIMESTAMPTZ NULL   -- NULL なら現役
retired_by     VARCHAR(255) NULL
retired_reason TEXT NULL
```

**`retired_at` が NULL かどうかが唯一の判定である。** 「状態」の列
(`status`)にしない — 名前空間の状態は他に無く、1 つの真偽のために
文字列の状態機械を作ると、値の追加に伴う移行が毎回要る。

`POST /namespaces/{ns}/retire`(`owner`、`reason` 必須)で退役し、
`POST /namespaces/{ns}/unretire`(同じ)で戻せる。**どちらも監査に残る**
(`action="retired"` / `"unretired"`)。

**戻せるようにする。** 正本は無傷なので、戻すのは列を消すだけである。
戻せないと、**誤って退役させた運用者に DB を直接触る以外の回復手段が無い**。
退役は削除ではないのだから、不可逆にする理由が無い。

### 2. 射影の停止は、古いローダが既に従う欄で表現する

退役した名前空間のマニフェストは

- `current` を `null` にする
- **各版の `projection` を `skip:retired` にする**
- 併せて `retired: true` を載せる(**観測のためだけ**)

**`schema` は上げない。** `projection` は schema 2 のローダが**そのまま
従う**欄で、`skip:*` は「読み込まない。理由をログに出す」として既に
実装されている(`projection_targets` / `build_namespace_tdb`)。
つまり**ローダを 1 行も変えずに退役が効く。**

`retired: true` は人とログのためであり、**これが無視されても安全は崩れない**。
`P2B-C1` の規則をそのまま適用した形である。

### 3. 退役したら、そのときに射影を止める。次の再構築を待たない

`retire` は同じトランザクションの後で

1. マニフェストを更新する(決定2)
2. **ストアからその名前空間のデータセットを消す**
3. 全版の `projected_at` を `NULL` にする

3 が要るのは、**`unretire` したときに `reconcile` が拾えるようにする**ため
である。`projected_at` は「書き込み経路の知識」であって「ストアの現在の
状態」ではない(不変条件10)ので、射影を止めたなら NULL に戻すのが正しい。

**2 が失敗しても退役は失敗させない**(不変条件3)。射影の失敗は正本への
書き込みを失敗させない。マニフェストが既に `skip:retired` なので、
**次の再構築で必ず止まる**。

### 4. `reconcile` は退役した名前空間を再射影しない。残骸は消す

決定3 で `projected_at` を NULL にするので、**何もしないと `reconcile` が
即座に再射影してしまう**。

`reconcile` は退役した名前空間について
**「射影しない」+「ストアに残っている名前付きグラフを消す」**を行う。
これは [ADR-0013](0013-reconcile-repairs-observed-divergence.md) の
「観測された乖離を直す」そのものである — 正本が「射影しない」と言っている
のにストアに載っているなら、乖離である。

### 5. 退役が止めるのは「内容を増やすこと」と「射影を通じて提供すること」

| 経路 | 退役中 | 理由 |
|---|---|---|
| `publish` / `submit` / `approve` / `reject` | **409** | 内容を増やす |
| `POST .../sparql` | **409** | 射影を通じた提供。**0 行を静かに返さない** |
| `POST .../questions`(改訂) | **409** | 作れない版の受け入れ基準である |
| `PUT .../mappings`(宣言) | **409** | 退役した領域からの新しい主張になる |
| `DELETE .../mappings`(取り消し) | 通す | 片付け |
| ロール付与・剥奪 / 用語の責任者 | 通す | **ガバナンスの片付けはできるべき** |
| 版の一覧・決定記録・監査・PROV-O・健全性・差分 | 通す | **これを残すために退役している** |
| `unretire` | 通す | — |

**SPARQL を 409 にするのが重要である。** データセットを消した後に
クエリを通すと**0 行が静かに返る**。「この名前空間は退役しています」と
言わなければ、エージェントは「該当なし」と読んで回答を作る。
[ADR-0025](0025-result-limit-enforcement.md) 決定3 以来ずっと避けている形で
ある。

### 6. `DELETE` の 409 は残す。メッセージを退役へ向ける

`DELETE /namespaces/{name}` は**公開済み TTL があれば引き続き 409** である。
不変条件7 は変わっていない。

ただしメッセージを変える。「Phase 2 で対応します」ではなく
**「`POST /namespaces/{ns}/retire` を使ってください」**と言う。
**約束を果たした形で閉じる。**

**公開済み TTL が無い名前空間の `DELETE` はこれまでどおり通る。** 作って
すぐ消す(実験、名前の付け間違い)経路を塞ぐ理由が無い。

### 7. 一覧から隠さない

`GET /namespaces` は退役した名前空間も返し、`retired_at` / `retired_by` /
`retired_reason` を添える。

**隠すと `unretire` できない。** そして「消えたように見えるが正本は残って
いる」状態は、この ADR が避けたいものそのものである。絞り込みが必要になれば
クエリパラメータを足す(要求が出てから)。

## 検討した代替案

### 恒久的に拒否する(ADR-0024 決定4 の選択肢 1)

**却下(コンテキスト)。** 409 のメッセージを直せば筋は通るが、
**使われない名前空間が一覧と射影に残り続ける**。

### Blob も消す(選択肢 3)

**却下。** 不変条件7 に正面から反する。過去の回答の根拠を辿れなくなる。

### `.ttl` を別の接頭辞へ移してローダの視界から外す

**却下。** ローダを 1 行も変えずに済み、**古いローダにも確実に効く**
(決定2 より強い保証)。

却下理由: **移動は copy + delete であり、原子的ではない。** 途中で落ちると
正本を失う。そして `ontology_versions.blob_path` を書き換えることになり、
不変リビジョンの行に手を入れる(不変条件7 の周辺を侵す)。
決定2 の `skip:retired` は**データを 1 バイトも動かさずに同じ効果**を得る。

### マニフェストの `schema` を 3 に上げて `retired` を必須にする

**却下(決定2)。** 形式としては素直である。

却下理由: **`P2B-C1` で踏んだ罠そのものである。** 古いローダは未知の schema を
拒否して**名前空間を丸ごとスキップ**する — 退役の場合それは偶然「安全」に
見えるが、逆向きの変更(退役の解除)では**解除が効かない**。そして schema を
上げるとローダの入れ替えと API の入れ替えの順序に依存関係が生まれる。

### 退役を不可逆にする

**却下(決定1)。** 「退役」という言葉の強さには合う。

却下理由: **正本が無傷なのに回復手段が無いのは不合理である。** 誤操作の
回復に DB を直接触らせるのは、運用手順として最悪である。監査には両方の
行為が残るので、可逆であることが説明責任を弱めない。

### 退役中も SPARQL を通す(0 行を返す)

**却下(決定5)。** 実装は何もしなくてよい。

却下理由: **エージェントが「該当なし」と読む。** 退役した名前空間への
クエリが 0 行を返すのと、本当に該当が無いのは別の事実である。
このリポジトリが最も繰り返し避けている混同である。

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **列が 3 つ増える**(決定1)
- **`unretire` の直後はストアが空である**(決定3・4)。`reconcile` を回すか、
  次のレプリカ再作成を待つ。**そのことを応答で伝える**
- **退役した名前空間の名前は再利用できない**(行が残るので)。これは意図した
  振る舞いである — 同名で作り直せると、監査証跡が別のオントロジーの記録と
  混ざる
- **退役中に通る書き込みがある**(決定5)。ロール・責任者・マッピングの
  取り消しは通る
- **一覧に残り続ける**(決定7)

### 得られるもの

- **ADR-0024 決定4 の約束を果たした。** 409 のメッセージが指す先が実在する
- **不変条件7 を守ったまま「もう使わない」を表現できる**
- **ローダを変えずに射影が止まる**(決定2)。`P2B-C1` の教訓を適用した
- **退役した名前空間への問い合わせが 0 行ではなく 409 になる**(決定5)
- **戻せる**(決定1)

### 影響を受ける他の決定

- [ADR-0024](0024-namespace-delete-locking.md) 決定4 — 選択肢 2 を実装した
- [ADR-0013](0013-reconcile-repairs-observed-divergence.md) — `reconcile` が
  退役を乖離の一種として扱うようになった(決定4)
- [ADR-0019](0019-retention-policy.md) — マニフェストの `projection` が
  退役の表現にも使われる(決定2)。`schema` は上げていない
- [ADR-0010](0010-approval-and-projection.md) 決定7 — マニフェストに
  `retired` を足した(観測のためだけ)
