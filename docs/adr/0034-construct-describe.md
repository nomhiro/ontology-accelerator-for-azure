# ADR-0034: `CONSTRUCT` / `DESCRIBE` を通す — 切り詰めた RDF は「切り詰めた」と言えない

- ステータス: 承認済み
- 日付: 2026-09-12

## コンテキスト

[ADR-0025](0025-result-limit-enforcement.md) 決定8 は `CONSTRUCT` / `DESCRIBE` を
ガードで **400 で断る**ことにし、対応そのものを `P2A-14` へ分離した。
断った理由は「実装していないから」ではない — **通すと 502 になっていた**。

`FusekiStore.query` は `Accept: application/sparql-results+json` を送るが、
Fuseki はクエリの形に従って Turtle を返すため JSON の解析に失敗し、
**`SparqlStoreError`(502)になる**(実測)。ガードが通したクエリが 502 で
落ちる状態は、エージェントに「サーバが壊れている」と誤解させる。

### 実測して原因の所在を訂正した

この作業で**もう一度測って、原因の所在が違っていたことが分かった。**

```
Accept=text/turtle                     -> 200 text/turtle  len=254
Accept=application/sparql-results+json -> 200 text/turtle  len=254
Accept=*/*                             -> 200 text/turtle  len=254
```

**Fuseki は `CONSTRUCT` に対して `Accept` に関わらず Turtle を返す。**
つまり 502 の原因は「`Accept` が食い違っていたこと」ではなく、
**`query` が `_send_json`(`response.json()`)を通っていたこと**である。

この訂正は決定2 の形を変えない(別のメソッドにするのが正しい)が、
**理由が変わる** — `Accept` を直せば済む話ではなかった。`Accept` を
正しく送ることは**プロトコルとしての正しさ**であり、持ち込みストア
(ADR-0001 設計原則3)が `Accept` を尊重する実装かもしれないから続ける。
**Fuseki だけを見て「不要」と結論しない。**

同 ADR は対応に 3 つの設計が要ると書いた。

1. `FusekiStore.query` の内容交渉(クエリの形に応じて `Accept` を変える)
   — **これは実際には必要条件ではなかった**(上記の実測)。要ったのは
   **JSON として解析しない経路**である
2. 戻り値の型(いまは `dict`。RDF を返すなら別の型か表現が要る)
3. **トリプル数の上限**(行数の上限とは別の量である)

## 決定

### 1. クエリの形を判定する関数を 1 つ置き、ガードとルータの両方がそれを使う

`ontology_core.sparql.guards.query_form(query) -> QueryForm`
(`SELECT` / `ASK` / `CONSTRUCT` / `DESCRIBE` / `UNKNOWN`)。

**判定を 2 か所に置かない。** ガードが「通す」と決めた形とルータが
「こう扱う」と決めた形が食い違うと、**ガードを通ったクエリが別の経路で
落ちる**(ADR-0025 決定8 が直したのと同じ形の不具合になる)。

`UNKNOWN` は**通さない**。知らない形を推測して扱わない
(`skip:unknown-status-*` と同じ方針)。

### 2. 戻り値の型は増やす。`query` の契約は変えない

`SparqlStore` に **`construct(sparql, *, dataset) -> str`**(Turtle)を足す。
`query` は `dict` を返す契約のままにする。

**不変条件4(ストアの失敗は必ず `SparqlStoreError`)と、ADR-0025 が
「`query` が `dict` を返す契約を変えない」として却下したストリーミングの
判断を、どちらも維持する。**

**抽象メソッドとして足す。** 既定実装を置いて例外を投げる形にすると、
持ち込みストア(ADR-0001 の設計原則3)で**黙って 500 になる**。
抽象にすれば、実装し忘れはインスタンス化の時点で分かる。

**実装は `_send`(生のテキスト)を使う。`_send_json` ではない。**
コンテキストの実測のとおり、502 の原因は `response.json()` であって
`Accept` ではなかった。それでも `Accept: text/turtle` を送るのは
**プロトコルとしての正しさ**であり、持ち込みストアが `Accept` を尊重する
かもしれないからである(`test_sparql_client.py` がヘッダを固定している)。

### 3. 同じエンドポイントで返す。URL を分けない

`POST /namespaces/{ns}/sparql` が、クエリの形に応じて
`application/sparql-results+json` か `text/turtle` を返す。

**[ADR-0026](0026-provenance-export.md) / [ADR-0031](0031-mapping-export.md) が
別の URL を選んだのとは事情が違う。** あちらは**同じデータの 2 つの表現**で、
表現ごとに取るパラメータが違った。ここは**1 つの操作で、結果の型がクエリに
よって決まる** — それが SPARQL 1.1 Protocol の振る舞いであり、ADR-0001 は
そのプロトコルをハード境界にすると決めている。

URL を分けると、**クライアントがクエリを送る前に形を判定しなければならない**。
標準の SPARQL クライアントはそういう作りになっていない。

### 4. トリプル数の上限を超えたら**切り詰めずに 413 で断る**

`SPARQL_MAX_TRIPLES`(既定 50,000)。超えたら **413 Payload Too Large** で、
実際のトリプル数と上限を添えて断る。

**ADR-0025 決定5 は行数について「エラーにしない」と決めた。ここは意図的に
違う判断をする。** 理由は 1 つで十分に強い。

> **RDF には封筒が無い。**

`SELECT` の結果は JSON の封筒(`head` / `results`)で、そこに
「切り詰めた」という情報を載せる場所がある(ADR-0025 決定4 はヘッダに、
MCP は本文に載せた)。**Turtle にはその場所が無い。** トリプルを足せば
**利用者のグラフにこちらが作った主張を混ぜる**ことになる。

ヘッダに載せる手はあるが、**[ADR-0017](0017-deprecation-lifecycle.md) 決定3 が
「エージェントはヘッダを見ない」と結論している**。つまり
**切り詰めた RDF は、切り詰めたと言えないまま完全な RDF として届く。**

MCP の経路だけは本文に旗を立てられるが、**Core API と MCP で同じクエリの
振る舞いが変わる**のは避ける(ADR-0017 決定3 は同じ情報の**置き場所**を
層で分けたのであって、振る舞いを分けたのではない)。

**413 は行動可能である。** 断る理由と実数を返すので、エージェントは
条件を足して問い直せる。

### 5. 上限の検査には解析が要る。その費用を認める

トリプル数を数えるには Turtle を rdflib で解析する必要がある。
**安く済む方法は無い**(バイト数はトリプル数の代理にならない)。

ADR-0025 が既に受け入れている未解決事項と同じである。

> **ストアの応答全体は一度メモリに載る**(上限は API のメモリを守らない。
> 時間の上限が事実上の防波堤)

ここでも `arq:queryTimeout`(10 秒 / 30 秒)が事実上の防波堤である。
**新しい未解決を作ったのではなく、既にある未解決が 1 つの経路に増えた。**

解析は CPU バウンドなので `asyncio.to_thread` に逃がす(SHACL 検証・
意味的差分と同じ扱い)。

### 6. 応答は解析し直した Turtle にする

ストアが返した本文をそのまま転送せず、rdflib で解析して再直列化する。

- 上限の検査のためにどうせ解析する(決定5)
- **形が 1 つに決まる。** 持ち込みストアが Turtle の書き方を変えても、
  この API の応答は同じ書き方になる
- **空白ノードのラベルは保たれない。** `CONSTRUCT` の空白ノードのラベルは
  そもそも安定していないので、失うものが無い

### 7. アクセスログにトリプル数の列を足す

`access_events.returned_triple_count`(NULL 可)を足し、
`returned_row_count` を **NULL 可に変える**。

| クエリの形 | `returned_row_count` | `returned_triple_count` |
|---|---|---|
| `SELECT` | 行数 | `NULL` |
| `CONSTRUCT` / `DESCRIBE` | **`NULL`**(行の概念が無い) | トリプル数 |

**`0` を書かない。** 「0 行返した」と「行という概念が無い」は違う。
[ADR-0025](0025-result-limit-enforcement.md) 決定3 の
`total_rows=None`(「数えていない」)と同じ区別である。

**`ASK` は既存の振る舞い(`0`)を変えない。** あれも同じ混同だが、
この作業で意味を変えると既存の記録の読み方が変わる。`P2B-22` として記録する。

**返した用語(`returned_term_count`)はグラフからも数える。** 主語・述語・
目的語のうち、その名前空間の `base_iri` で始まる IRI を数える。
`SELECT` の結果より**むしろ正確**である(束縛に現れない IRI も拾える)。

### 8. MCP は本文で Turtle を渡す

`sparql_query` は `CONSTRUCT` / `DESCRIBE` のとき
`{"form": "construct", "turtle": "...", "triple_count": n}` を返す。

**`head` / `results` を偽造しない。** 空の `results` を付けると、
エージェントは「0 行だった」と読む。**形が違うことを形で伝える。**

ツール説明に**「`turtle` が来たら RDF として読むこと。`results` は無い」**と
書く。エージェントはヘッダも ADR も読まないので、ツール説明に書かなければ
届かない(ADR-0017 決定3)。

## 検討した代替案

### 上限を超えたら切り詰めて旗を立てる(ADR-0025 決定5 と揃える)

**却下(決定4)。** 一貫性は魅力的で、しかも **RDF は単調なので、トリプルを
落としても偽になる主張は生まれない**(部分集合はより少ないことを言うだけ)。

却下理由 2 つ。

1. **旗を立てる場所が無い**(決定4)。ヘッダはエージェントに届かず、
   トリプルを足すのは利用者のグラフへの混入である
2. **空白ノードの構造が割れる。** `owl:Restriction` から `owl:onProperty` が
   落ちた断片は、偽ではないが**無意味**であり、素朴な消費者を誤解させる。
   主語単位で切る実装は書けるが、空白ノードの連鎖を辿る必要があり
   (空白ノードの扱いで既に痛い目を見ている。ADR-0016 決定5)、
   **正しく切るコストが切らないコストを上回る**

### `CONSTRUCT` / `DESCRIBE` 専用の URL を作る

**却下(決定3)。** 応答の型が URL で決まるので型生成が素直になる。

却下理由: **クライアントがクエリを送る前に形を判定しなければならない。**
標準の SPARQL クライアントはそういう作りになっていない。ADR-0001 が
SPARQL 1.1 Protocol をハード境界にすると決めた以上、プロトコルの振る舞いに
合わせる。

### `query` の戻り値を `dict | str` に広げる

**却下(決定2)。** メソッドが増えない。

却下理由: **呼び出し側が毎回型を判定することになる。** `list_graphs` /
`has_default_graph_content` のような内部利用も含めて全箇所である。
ADR-0025 が「`dict` を返す契約」を根拠にストリーミングを却下しているので、
その契約は維持する。

### ストアの応答をそのまま転送する(解析しない)

**却下(決定5・6)。** 速い。

却下理由: **トリプル数を数えられない。** 数えないなら上限も無く、
「RDF を返す経路には上限が無い」という `SPARQL_MAX_RESULTS` 導入前と同じ
状態に戻る(ADR-0025 が直した問題の再来)。

### バイト数で上限をかける(解析しない)

**却下。** 安く、メモリも守れる。

却下理由: **バイト数はトリプル数の代理にならない。** 接頭辞の使い方と
IRI の長さで 10 倍変わる。上限の目的は「エージェントが digest する量」を
抑えることなので、量の単位を間違えると効かない(`fuseki:queryLimit` が
効いていなかったのと同じ「持っているだけの設定」になる)。

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **応答全体を解析する**(決定5)。CPU とメモリを使う。
  `arq:queryTimeout` が事実上の防波堤で、**ADR-0025 が既に受け入れている
  未解決と同じもの**である
- **上限を超えると結果が得られない**(決定4)。ADR-0025 の行数とは振る舞いが
  違う。理由は「RDF には封筒が無い」
- **空白ノードのラベルが保たれない**(決定6)
- **`ASK` の `returned_row_count` は `0` のまま**(決定7、`P2B-22`)
- **`DESCRIBE` の結果はストアの実装に依存する。** SPARQL 1.1 は
  `DESCRIBE` の返す内容を規定していない(Jena は CBD 相当)。持ち込みストアで
  内容が変わる

### 得られるもの

- **ADR-0025 決定8 が約束した `P2A-14` を果たした。** ガードのメッセージが
  指す先が実在する
- **クエリの形の判定が 1 か所になった**(決定1)。ガードとルータが食い違わない
- **RDF を返す経路にも上限がある**(決定4)。「持っているだけの設定」を作らない
- **行とトリプルを混ぜない**(決定7)

### 影響を受ける他の決定

- [ADR-0025](0025-result-limit-enforcement.md) 決定8 — ガードの拒否を外した。
  決定5(エラーにしない)とは**意図的に違う判断**をしている(決定4)
- [ADR-0001](0001-rdf-store-selection.md) 設計原則3 — 抽象に
  `construct` が増えた。持ち込みストアは 1 メソッド実装が増える
- [ADR-0018](0018-context-access-log.md) — アクセスログに列が 1 つ増え、
  `returned_row_count` が NULL 可になった(決定7)
- [ADR-0017](0017-deprecation-lifecycle.md) 決定3 — 「エージェントはヘッダを
  見ない」が決定4 の根拠になった

## 補記: 廃止済み用語の警告を足した (2026-09-12、`P2B-23`)

この ADR は廃止済み用語の警告を付けずに残していた
(`deprecated_iris_in_results` が SPARQL Results JSON の形を前提にしていた)。
[ADR-0038](0038-rdf-deprecation-warning.md) が埋めた。

**決定4(上限を超えたら 413 で断る)は変えていない。** 切り詰めと廃止の警告は
問題の形が違う。

| | 切り詰め | 廃止の警告 |
|---|---|---|
| グラフ自体 | **不完全になる** | **完全で正しい** |
| RDF の中に書けるか | 書けない | 同じく書けない |
| ヘッダで足りるか | **足りない** | **足りる** |

切り詰めを 413 にしたのは「**ヘッダでは足りないから**」であって「ヘッダが
悪いから」ではない。廃止の警告はグラフが正しいうえでの助言なので、ヘッダで
足りる(エージェント向けには MCP が本文へ載せ替える)。

**決定7 の周辺が速くなった。** この経路は上限の検査とアクセスログの用語で
**同じ本文を 2 回解析していた**。`RdfResult.iris` が IRI の集合を持つように
したので、廃止の検査を足しながら**解析は 1 回になった**
(`terms_in_graph` は `terms_with_prefix` に置き換えた)。

**413 のときは廃止を引きもしない**(ADR-0038 決定7)。返していないものを
警告しない。
