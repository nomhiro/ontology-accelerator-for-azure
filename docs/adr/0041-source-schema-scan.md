# ADR-0041: ソース DB のスキャンはメタデータだけを読む — 実データを 1 行も取らない

- ステータス: 承認済み
- 日付: 2026-09-12

## コンテキスト

Phase 2 柱 A の完了条件は「顧客 DB に接続してスキーマを自動発見し、LLM が
オントロジー候補を生成し、Web でレビュー・承認して公開できる」である。
`P2A-01` はその入口 — `scan-job` がソース DB のスキーマと統計を抽出し、
PostgreSQL のカタログへ蓄積する([architecture.md](../architecture.md))。

**このカタログは `P2A-02`(LLM によるオントロジー候補生成)の入力になる。**
そこが設計の中心である。

### 決めるべきこと

1. **何を読み、何を読まないか**
2. **顧客 DB の資格情報をどう持つか**(不変条件6 は DSN にパスワードを埋めることを禁じている)
3. **どこへ接続できるか**(任意のホストへ接続できる口は新しい攻撃面である)
4. **カタログの形**(上書きするのか、観測として積むのか)
5. **どう走らせるか**
6. **どの DB に対応するか**

## 決定

### 1. 実データを 1 行も読まない。メタデータだけを読む

`information_schema` と `pg_catalog` だけを読む。**ユーザーテーブルに対して
`SELECT` を発行しない。**

統計は**カタログ自身が持つ推定値**から取る。

| 欲しいもの | どこから |
|---|---|
| 列・型・NULL 可・既定値 | `information_schema.columns`(**SQL 標準**なので移植しやすい) |
| テーブルの一覧・種別・コメント | `pg_catalog.pg_class` / `pg_namespace` / `obj_description` |
| 行数の推定 | `pg_catalog.pg_class.reltuples` |
| `ANALYZE` が走ったか | `pg_catalog.pg_stat_all_tables.last_analyze` / `last_autoanalyze` |
| 列のコメント | `pg_catalog.pg_attribute` / `col_description` |
| 列の異なり数・NULL 率 | `pg_catalog.pg_stats.n_distinct` / `.null_frac`(**この 2 列だけ**) |
| 主キー・外部キー | `pg_catalog.pg_constraint`(`conkey` / `confkey` を `unnest ... WITH ORDINALITY` で展開) |

**制約は `information_schema` から取らない。** `key_column_usage` と
`constraint_column_usage` を結合すると、**複合外部キーで列の対応が曖昧になる**
(参照先の列に順序が付かない)。`pg_constraint` の配列を順序付きで展開すれば
**複合キーでも正確**である。移植性より正確さを採る — 曖昧な対応は
「この列がこの列を参照している」という**誤った事実**になる。

**行をサンプリングしない。** 理由は 1 つで十分に強い。

> **サンプリングした実データは、このカタログを経て LLM のプロンプトへ流れる。**

`P2A-02` の入力はこのカタログである。顧客の実データが一度そこへ入れば、後から
消しても**モデルの提供者へ渡った事実は消えない**。これは ADR-0001 と
アーキテクチャが掲げる「**実データを実体化しない**」(Ontop VKG)と同じ向きの
判断である。

**`pg_stats` を丸ごと取らない。** `most_common_vals` / `histogram_bounds` /
`most_common_elems` には**実データの値がそのまま入る**。列を選んで取るのでは
なく、**`n_distinct` と `null_frac` だけを `SELECT` する**。

### 2. 統計の「無い」と「0」を区別する。比率を件数に化けさせない

**実測して分かった 2 つの区別がある。** どちらも「測っていないものを数として
書かない」という同じ判断に落ちる。

#### `reltuples` の `-1` は「まだ分析されていない」

| 観測 | 記録 |
|---|---|
| `reltuples = -1` | `estimated_rows = NULL`(**分析されていない**) |
| `reltuples = 0` かつ `ANALYZE` の記録なし | `estimated_rows = NULL`(同上) |
| `reltuples = 0` かつ `ANALYZE` の記録あり | `estimated_rows = 0`(**測った 0**) |

`reltuples = 0` は「0 行」とも「まだ分析されていない」とも読める(PostgreSQL 14
より前は未分析でも `0` だった)。**`pg_stat_all_tables.last_analyze` /
`last_autoanalyze` を併せて読む**ことで、この曖昧さが消える。実測では
この製品自身のテーブルのほとんどが `reltuples = -1`(未分析)だった。

#### `pg_stats.n_distinct` の負の値は**比率**である

PostgreSQL は `n_distinct` に

- **`>= 0`**: 異なり数の推定値(絶対数)
- **`< 0`**: **行数に対する比率**(`-1` なら全行が異なる、`-0.5` なら半分)

を入れる。実測で `alembic_version.version_num` が `-1` だった。

**絶対数に換算しない。** 換算するには行数の推定が必要で、その行数が
`NULL`(未分析)のときに**存在しない数を作る**ことになる。だから列を 2 つ
持つ。

| 観測 | 記録 |
|---|---|
| `n_distinct >= 0` | `distinct_estimate = その値`、`distinct_ratio = NULL` |
| `n_distinct < 0` | `distinct_estimate = NULL`、`distinct_ratio = -その値` |
| `pg_stats` に行が無い | 両方 `NULL` |

**片方だけを読むクライアントが誤読しないことが要点である。** `-1` を件数と
して読めば「異なり数は -1 件」という無意味な値になる。

### 3. 発行する SQL を allowlist にし、テストで固定する

決定1 は「そういう方針である」だけでは守れない。**発行するクエリの集合を
モジュールの定数として持ち、それ以外を発行できない形にする。**

`ontology_core.scan.CATALOG_QUERIES` に固定の SQL を置き、スキャンは
その値しか実行しない。テストは

- 定数のどの SQL も `information_schema` / `pg_catalog` 以外を参照しないこと
- どの SQL にも `most_common` / `histogram` が現れないこと

を機械的に検査する。**「読まないと決めた」を「読めない」に近づける。**

### 4. 資格情報をカタログに保存しない。API で受け取らない

`scan_sources` が持つのは**接続の行き先**と**秘密の在り処**だけである。

| 列 | 例 |
|---|---|
| `host` / `port` / `database` | `db.example.internal` / `5432` / `sales` |
| `auth_mode` | `entra`(既定)/ `key-vault-secret` |
| `secret_name` | Key Vault の秘密名(`key-vault-secret` のときだけ) |
| `username` | Entra でもユーザー名は要る |

**パスワードをこの API に POST させない。** リクエストで秘密を受け取ると、
**ログ・監査・例外メッセージ・リクエストの再送**に載る経路が一斉に生まれる。
運用者が Key Vault に自分で入れ、**名前だけを登録する**。

不変条件6 をそのまま適用する — 接続のたびに秘密を解決して
`connect_args["password"]` に渡し、DSN には埋めない。

### 5. 接続先をホストの allowlist で絞る。既定は空

`SCAN_ALLOWED_HOSTS`(カンマ区切り)に無いホストへは接続しない。
**既定は空で、そのときスキャンは使えない。**

任意のホストへ接続できる口は、認証済みの主体に**内部ネットワークの到達性を
調べる手段**を与える(接続の成否だけで十分な情報になる)。SPARQL の
`SERVICE` 句を既定で禁止したのと同じ判断である。

**「設定が無ければ拒否」にする**(不変条件11)。「設定が無ければどこへでも」は
このリポジトリが最も避けたい形である。

### 6. カタログは観測の記録である。上書きしない

`scan_runs` が 1 回のスキャン、`scan_tables` / `scan_columns` が
**そのときの観測**を持つ。前回の行を書き換えない。

**スキーマは変わる。** 上書きすると「列が消えたこと」が分からなくなる。
オントロジーを不変リビジョンとして扱う(不変条件7)のと同じ理由で、その素材も
積む。

**追記専用にしてよい理由**は、スキャンが**運用者の操作で起きる**ことである。
`access_events`(エージェントの稼働に比例して無限に伸びる。[ADR-0018](0018-context-access-log.md)
決定2 で保持期間を与えた)とは性質が違い、`audit_events`([ADR-0011](0011-database-privilege-separation.md)
決定2 で `DELETE` を剥奪した)と同じ側である。

### 7. 途中で落ちたスキャンを「完了した観測」と混ぜない

`scan_runs` は先に `running` で書き、最後に `succeeded` へ変える。
失敗したら `failed` と理由を書く。

**読み手は `succeeded` の run だけを使う。** 途中で落ちた run は `running` の
まま残り、**「完了していない観測」として区別できる**。`projected_at IS NULL` が
未射影を表すのと同じ形である(不変条件10)。

**半端なカタログを「テーブルが少ない DB」として読ませない。**

### 8. スキャンのソースは名前空間に属する

登録と実行は `owner`、閲覧は `data-analyst`。

**権限のモデルを 1 つに保つ。** ソースを全体で 1 つの一覧にすると、
「誰がどの顧客 DB へ接続できるか」が名前空間の境界の外に出る。名前空間名は
セキュリティ境界である(不変条件5)ので、そこに寄せる。

カタログは最終的に**その名前空間のオントロジー候補**になるので、所属としても
自然である。

### 9. PostgreSQL から始める。読み手はインターフェースにする

`information_schema` は SQL 標準なので多くが移植できるが、**統計は方言**である
(`pg_class.reltuples` / `pg_stats` は PostgreSQL 固有)。

**対応していない driver は明示的に拒否する。** 黙って空のカタログを作ると、
「テーブルが 1 件も無い DB」として読まれる。

### 10. API から同期で起動する。ACA Job はこの ADR では作らない

メタデータのクエリは**テーブル数に依らず定数回**(カタログのビューを 1 回ずつ
引く)なので、同期で完了する。

**ACA Job の Bicep は課金なしに検証できない。** 書くだけ書いて「動くはず」と
記録するのは、このリポジトリが避けている形である。`P2A-19` として記録し、
デプロイ窓が取れたときに実機で確かめる。

## 検討した代替案

### 行をサンプリングして値の例をカタログに入れる

**却下(決定1)。** LLM がオントロジーを推測する材料が増え、精度が上がりうる。

却下理由: **顧客の実データが LLM のプロンプトへ流れる。** 一度渡れば消せない。
「実データを実体化しない」という製品の前提と正面から衝突する。値の例が
どうしても必要になったなら、**それは別の ADR で、匿名化と同意の設計と一緒に
決める**。

### `pg_stats` を `SELECT *` で取る

**却下(決定1)。** クエリが 1 つで済む。

却下理由: **`most_common_vals` は実データである。** 列名を挙げて取らないと、
方針を書いただけで実データを取り込むことになる。

### 発行する SQL をコード中に散らす

**却下(決定3)。** 普通の書き方である。

却下理由: **「読まないと決めた」を機械的に検査できない。** 定数にまとめれば、
「`information_schema` / `pg_catalog` 以外を参照していないか」をテストで
確かめられる。方針は検査できる形で置く。

### パスワードを登録 API で受け取って Key Vault へ書く

**却下(決定4)。** 運用者の手順が 1 つ減る。

却下理由: **秘密が API を通る。** ログ・監査・例外・再送の経路に載る。そして
**API に Key Vault への書き込み権限が必要になる** — 読み取りだけで済んでいた
権限が広がる。

### 接続先を絞らない

**却下(決定5)。** 設定が要らず、すぐ使える。

却下理由: **認証済みの主体に内部ネットワークの到達性調査を与える。**
SPARQL の `SERVICE` を既定で禁止したのと同じ理由である。既定で使えないのは
不便だが、**「設定が無ければどこへでも」は不変条件11 が禁じている形**である。

### スキャンごとにカタログを上書きする

**却下(決定6)。** 行数が増えず、読み出しが単純になる。

却下理由: **「列が消えたこと」が分からなくなる。** オントロジーを縮めるときに
必要なのは「前はあった」という記録である(不変条件8 と同じ動機)。

### 途中で落ちたスキャンの行を消す

**却下(決定7)。** カタログに半端な観測が残らない。

却下理由: **失敗したことが分からなくなる。** どこまで読めたかは診断の材料で
ある。`running` のまま残す形なら、読み手は `succeeded` で絞るだけでよい。

### スキャンのソースを名前空間に属させない

**却下(決定8)。** 1 つの顧客 DB を複数の名前空間から使える。

却下理由: **「誰がどの顧客 DB へ接続できるか」が名前空間の境界の外に出る。**
新しい権限の層を作ることになり、不変条件5 と 11 の適用範囲が曖昧になる。
同じ DB を複数の名前空間から使いたいなら、**それぞれに登録する**(ホストの
allowlist が共通の歯止めになる)。

### ACA Job を今書く

**却下(決定10)。** アーキテクチャ図と揃う。

却下理由: **課金なしに検証できない。** `az bicep build` が通ることは
「デプロイできる」ではない(`azd provision` の冪等性で何度も踏んでいる)。
**同期の API で先に中身を確かめる。**

### カタログを MCP のツールとして出す

**却下。** エージェントがソース DB のスキーマを直接引ければ、オントロジーが
無くても質問に答えられる場面がある。

却下理由が 2 つある。

**1. カタログは誰の承認も経ていない。** この製品の前提は「**LLM の出力が
人間の承認を経ずに正本へ入ることはない**」であり、エージェントに出すのは
`approved` の版だけである(ADR-0010)。カタログは*観測*であって、レビューも
承認も受けていない。MCP に出すと、**審査を通っていない語彙がエージェントの
文脈に入る経路ができる** — 承認フロー全体が任意のものになる。

**2. 表と列の名前それ自体が機微である。** 「どの DB にどんな表があるか」は、
多くの組織で外に出してよい情報ではない。カタログは `data-analyst` で読めるが、
それは**名前空間の境界の内側**での話である。MCP は境界の外にいる
エージェントに向いた口である。

**カタログの読み手は `P2A-02` である。** サーバ側でオントロジー候補を生成し、
**人間が承認した結果**がエージェントに届く。運用者が中身を確かめる必要が
あるときは Core API の `GET .../catalog` を使う(名前空間の権限が効く)。

この判断を書いているのは、**書かないと「まだ出していないだけ」に見える**
ためである。

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **統計が推定値である**(決定2)。`reltuples` は `ANALYZE` が走った時点の値で
  あり、`n_distinct` の負の値は比率である。**どちらも「無い」と「0」を区別して
  記録する**ので、読み手は `NULL` を扱わなければならない
- **値の例が無い**(決定1)。列名と型だけで意味を推測することになり、
  `P2A-02` の精度はその範囲に制限される。**これは意図した制約である**
- **既定ではスキャンが使えない**(決定5)。`SCAN_ALLOWED_HOSTS` を設定する
  までは 403 で断る
- **運用者が Key Vault に秘密を入れる手順が要る**(決定4)。API だけでは
  完結しない
- **カタログが積み上がる**(決定6)。スキャンの回数に比例する。運用者の操作で
  しか増えないので追記専用にするが、**保持ポリシーは決めていない**
- **PostgreSQL 以外はまだ読めない**(決定9)。拒否されることで分かる
- **ACA Job が無い**(決定10)。定期実行はできない。`P2A-19`

### 得られるもの

- **柱 A の入口ができる。** `P2A-02` が使う材料の形が決まった
- **「実データを取らない」が検査できる形で置かれた**(決定3)。方針が
  コメントではなくテストになった
- **接続先の攻撃面が既定で閉じている**(決定5)

### 実装して測って分かったこと

**この機能のテストの中心を「自分自身の PostgreSQL を実際にスキャンする」に
置いた**。フェイクの `dict` では `information_schema` の書き方も
`reltuples = -1` も `pg_stats` の中身も再現できないためである。そこで
2 件の不具合が見つかった。**どちらもフェイクに対しては緑になる種類である。**

1. **`pg_class.relkind` と `pg_constraint.contype` は asyncpg から `bytes` で
   返る。** PostgreSQL の `"char"` は 1 バイトの内部型でテキストではない。
   `str(b"r")` は `"b'r'"` になるので、テーブルの種別が対応表から静かに外れ、
   **主キーと外部キーが「1 件も無い」ことになっていた。** 後者が悪い —
   この ADR が何度も避けている「**読めなかったことが、無かったことになる**」
   そのものである。SQL 側で `::text` に寄せ、読み手でも `bytes` を受けられる
   ようにした
2. **`create_async_engine(..., poolclass=None)` はプールを無効にしない**
   (`None` は「既定のプールを使う」の意味)。`NullPool` を明示しないまま
   「プールしない」とコメントしていた。**顧客 DB への接続がプロセスに
   残り続ける**

どちらも CLAUDE.md の「既知の罠」に記録した。**1 が見つかったのは、テストが
「実データが入ったテーブルをスキャンして、主キーと外部キーが読めること」を
実物に対して確かめていたからである** — 検査を「発行する SQL の形」だけに
留めていたら通り過ぎていた。

### 影響を受ける他の決定

- [ADR-0007](0007-no-purview-dependency.md) — Purview からの取り込みは
  この ADR の範囲外。カタログの形は Purview に依存しない
- [ADR-0018](0018-context-access-log.md) 決定2 — 保持期間を与えた
  `access_events` と違い、`scan_*` は追記専用でよい(増える理由が違う。決定6)
- [ADR-0011](0011-database-privilege-separation.md) 決定2 — `scan_*` も
  追記専用の側に置く
