# ADR-0045: Web の認証は MSAL の認可コードフロー(PKCE)にする — localhost の登録にデプロイ窓は要らなかった

- ステータス: 承認済み
- 日付: 2026-09-13

## コンテキスト

[ADR-0044](0044-review-ui.md) 決定9 は、Web の認証を**トークンの貼り付け**に
した。理由はこう書いてあった。

> **MSAL を入れない。** 理由は ADR-0042 決定5 と同じ形である —
> **SPA のリダイレクト URI はアプリ登録の変更を伴い、デプロイ窓なしに
> 検証できない**。「書いたが動かしていない認証」を残さない。

**この理由は部分的に誤っていた。** `P2A-20` に着手して測り直したところ、
**「登録」と「デプロイ済みオリジンの検証」を混同していた**ことが分かった。

| 何を | デプロイ窓が必要か |
|---|---|
| `http://localhost:5173` を SPA のリダイレクト URI として登録する | **不要**(Graph への PATCH だけ。課金なし) |
| デプロイ済み Static Web Apps のオリジンを登録する | **必要**(ホスト名が provision 後にしか分からない) |
| 対話的なサインインの往復を確かめる | **人がブラウザで認証する必要がある**(デプロイ窓とは別の話) |

1 番目が不要だと分かったので、**貼り付けをやめて MSAL を入れられる。**

### 測ったこと(Entra の文書)

| 事実 | 出典 |
|---|---|
| **HTTP は localhost だけ例外**で、`http://localhost` は有効 | [reply-url#supported-schemes](https://learn.microsoft.com/entra/identity-platform/reply-url#supported-schemes) |
| **localhost ではポートが照合で無視される。** ポートだけ違う URI を複数登録してはいけない(**サーバが任意に 1 つ選ぶ**) | 同上 |
| **`spa` 型で登録しないと認可コードフローが CORS で失敗する** | [v2-oauth2-auth-code-flow](https://learn.microsoft.com/entra/identity-platform/v2-oauth2-auth-code-flow#redirect-uris-for-single-page-apps-spas) |
| `spa` 型のリダイレクト URI は**非 SPA のフローで使えない**(`Origin` ヘッダが無いと Entra が拒否する) | 同上 |

### 決めるべきこと

1. **どのフローを使うか**
2. **リダイレクト URI を誰がどう登録するか**
3. **クライアントのアプリ登録を分けるか**
4. **どのスコープを要求するか**
5. **トークンをどこに置くか**(ADR-0044 決定9 は「メモリのみ」と決めていた)
6. **貼り付けを残すか**
7. **設定が無いときどうするか**
8. **何を検証できて、何を検証できないか**

## 決定

### 1. 認可コードフロー + PKCE を使う。暗黙フローを使わない

`@azure/msal-browser` 5.x(MIT)の既定である。**暗黙フローを却下する理由**は

- トークンが **URL フラグメントに載る**(ブラウザの履歴・プロキシのログに残る)
- **リフレッシュトークンが得られない**
- `spa` 型は暗黙フローと後方互換だが、**互換であることは推奨ではない**

### 2. リダイレクト方式を使う。ポップアップを使わない

**ポップアップのブロックは静かな失敗である。** ブロックされたとき、
利用者に見えるのは「何も起きない」だけで、理由が分からない。

代償として `handleRedirectPromise` の扱いが増え、**サインインでページが
離れる**(入力途中の理由が消える)。**それでもリダイレクトを採る** —
このリポジトリは繰り返し「静かな失敗」を拒んできた。

> 副作用: レビュー画面で理由を書いている途中にトークンが切れると、
> サインインのリダイレクトで理由が消える。**`acquireTokenSilent` を先に
> 試す**ので通常は起きないが、起きうることを README に書く。

### 3. リダイレクト URI は `spa` 型で登録する。`web` 型では動かない

文書が明示している — **`web` 型のまま認可コードフローを使うと CORS で
失敗する**。`spa` 型が PKCE と CORS を有効にする。

`setup-app-role.py` が `spa.redirectUris` を更新する。**`appRoles` と
`optionalClaims` と同じ複合プロパティの罠がある**(部分更新すると既存が
丸ごと消える。`P1-09` の罠1)ので、**完全な配列を送る**。

### 4. localhost は 1 つだけ登録する

文書が明示している — **localhost ではポートが照合で無視される**ため、
`http://localhost:5173` を登録すれば `http://localhost:4173`
(`vite preview`)でも通る。そして

> Do not register multiple localhost redirect URIs where only the port
> differs. The login server picks one arbitrarily.

**ポートだけ違う URI を足してはいけない。** 足すと、どの登録の型
(`spa` / `web` / `native`)が使われるかが不定になる。

**この事実をテストで固定する** — スクリプトが localhost を 2 つ登録しようと
したら落ちるようにする。

### 5. クライアントのアプリ登録を分けない。API と同じものを使う

理想は「クライアント用」と「リソース用」を分ける形である。**分けない。**

理由は 2 つ。

1. **このリポジトリは既に同じ形で動いている。** `postdeploy` と
   `check-platform-admin.py` は Azure CLI(preAuthorizedApplications に
   登録済み)で `api://<appId>/.default` のトークンを取っている
2. **アプリ登録を 2 つにすると、`setup-app-role.py` が作るものが増える** —
   新しいアプリ登録の作成、`preAuthorizedApplications` の配線、
   **そのどれもがテナントへの書き込みである**

**受け入れるコスト**: クライアントとリソースが同じなので、
`aud` はこのアプリの ID になり、**「誰がこのトークンを使うのか」が
アプリ登録の構造からは読めない**。`idtyp`(ADR-0035)と `roles` で
主体は分かるので、実務上は足りる。

### 6. スコープは `api://<clientId>/user_impersonation` にする

アプリが公開しているスコープがこれ 1 つである(実測。
`az ad app show --query "api.oauth2PermissionScopes[].value"`)。

`.default` も使える(`postdeploy` はそれを使っている)。**`user_impersonation`
を既定にするのは、公開しているスコープを明示的に要求するほうが読めるから**で
ある。`VITE_API_SCOPE` で差し替えられる。

### 7. トークンは `sessionStorage` に置く。`localStorage` には置かない

**ADR-0044 決定9 の「メモリにしか持たない」を撤回する。**

理由: **リダイレクト方式はページの遷移をまたぐ**(サインインで一度
`login.microsoftonline.com` へ出て戻る)。メモリだけでは**戻ってきた時点で
PKCE の verifier が消えており、フローが成立しない**。

| 置き場所 | 生存範囲 | 採否 |
|---|---|---|
| メモリのみ | ページの再読み込みで消える | **リダイレクト方式では成立しない** |
| `sessionStorage` | そのタブを閉じるまで | **採用** |
| `localStorage` | 明示的に消すまで(**タブ・再起動をまたぐ**) | 却下 |

**`localStorage` を却下する理由は XSS である。** 持ち出されたトークンが
再起動後も有効なのは、被害の範囲が違う。

**既定に頼らず明示する。** `msal-browser` の既定は `sessionStorage` だが、
**既定は変わりうる**。`cacheLocation: "sessionStorage"` と
`storeAuthStateInCookie: false` を書く。

### 8. 貼り付けの口を削除する

ADR-0044 決定9 で置いた「トークンを貼る」入力を消す。

**2 つの経路を残さない。** 残すと、**MSAL が動かないときに貼り付けへ
逃げる**運用が生まれ、「サインインが壊れている」ことに誰も気づかない。
貼り付けは**回避路であり、回避路は問題を隠す**。

### 9. 設定が無ければ MSAL を初期化しない

`VITE_ENTRA_CLIENT_ID` が空なら、**認証の仕組みを一切作らない**。
`AUTH_MODE=disabled`(ローカル開発)でトークンを送らずに動く形をそのまま
残す。

**半端に初期化しない。** 設定が無いのに MSAL を作ると、サインインの
ボタンが出て、押すと `AADSTS900971: No reply address provided` のような
**設定の誤りに見えないエラー**になる。

画面には「認証は設定されていません(`AUTH_MODE=disabled` 用)」と出す。

### 10. 検証できないものを「確認した」と書かない

| 何を | 検証したか |
|---|---|
| リダイレクト URI が `spa` 型で登録される | **した**(Graph に PATCH して読み戻した) |
| localhost を 2 つ登録しようとしたら止まる | **した**(テスト) |
| 設定の組み立て・スコープ・エラーの訳し分け | **した**(テスト) |
| 型検査・ビルド | **した** |
| **対話的なサインインの往復** | **していない**(人がブラウザで認証する必要がある) |
| **デプロイ済みオリジンでの動作** | **していない**(`P2A-21`) |

**5 番目を自分で確かめてはいけない。** 資格情報の入力は行わない。
README に「1 コマンドで試せる手順」を書き、**運用者が確かめる**形にする。

## 検討した代替案

### 貼り付けのまま据え置く(ADR-0044 決定9 を維持する)

**却下(決定8)。** 変更が要らない。

却下理由: **据え置いた理由そのものが誤っていた**(localhost の登録に
デプロイ窓は要らない)。誤った前提で置いた回避路を残すと、
**前提が誤っていたことも残る**。

### ポップアップ方式にする

**却下(決定2)。** 画面の状態が消えない。

却下理由: **ポップアップのブロックが静かな失敗になる**。利用者に見えるのは
「押しても何も起きない」だけである。

### クライアント用のアプリ登録を別に作る

**却下(決定5)。** 識別子の設計としては正しい。

却下理由: **テナントへの書き込みが増える**(アプリ登録の作成、
`preAuthorizedApplications` の配線)。このリポジトリは既に API のアプリ登録
1 つで動いており、**分ける利益が、増える自動化の検証コストを上回らない**。
分けたくなったら `setup-app-role.py` に足せる。

### `localStorage` にトークンを置く

**却下(決定7)。** 再読み込みでサインインが残る。

却下理由: **XSS で持ち出されたトークンが再起動後も有効になる。**
`sessionStorage` なら被害はそのタブの寿命に限られる。

### `http://localhost:5173` と `http://localhost:4173` の両方を登録する

**却下(決定4)。** `vite preview` でも試せる。

却下理由: **文書が明示的に禁じている** — localhost はポートが無視されるので、
ポートだけ違う登録は**サーバが任意に 1 つを選ぶ**。1 つ登録すれば両方で
通る。

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **トークンが `sessionStorage` に載る**(決定7)。ADR-0044 の「メモリのみ」
  より弱い。**リダイレクト方式がページ遷移をまたぐため避けられない**
- **サインインでページが離れる**(決定2)。入力途中の理由が消えうる
- **`aud` がこのアプリの ID になる**(決定5)。クライアントとリソースが
  同じアプリ登録である
- **対話的な往復を検証していない**(決定10)。運用者が 1 回試す必要がある
- **デプロイ済みオリジンは未登録**(決定10)。`P2A-21` として記録する
- **`@azure/msal-browser` が依存に増えた**(MIT。`docs/third-party-licenses.md`
  に追記)

### 得られるもの

- **貼り付けが消えた**(決定8)。回避路が無い
- **デプロイ窓を待たずに前に進んだ。** 「検証できない」と書いた理由を
  測り直したら、**半分は検証できた**
- **`spa` 型・localhost のポート無視・複数登録の禁止**が文書の実測として
  記録された(決定3・4)
- **設定が無ければ何も作らない**(決定9)。設定の誤りが認証の失敗に化けない

### 実装して測って分かったこと

**`.default` と `user_impersonation` は同じトークンを生む**(実測。2026-09-13)。

```
.default:            aud=<appId> scp=user_impersonation roles=[platform-admin] idtyp=user
user_impersonation:  aud=<appId> scp=user_impersonation roles=[platform-admin] idtyp=user
```

このアプリ登録が公開しているスコープが `user_impersonation` 1 つだけなので、
`.default` がそれに解決される。**どちらでも API は受け入れる** —
デプロイ窓(2026-09-13)で API が受け入れたトークンと同じ形である。

つまり決定6 は**読みやすさの選択**であって、動作の違いではない。

**MSAL の型と自前の型を合わせる必要があった。** `MsalLike` を狭く作ったら
実物の `PublicClientApplication` を渡せなかった(`scopes` が
`readonly string[]` では MSAL の可変 `string[]` に合わず、`AccountLike` に
`environment` / `tenantId` / `localAccountId` が無いと `logoutRedirect` に
渡せない)。**キャストで潰さず、実物の形に合わせた** — キャストで潰すと、
偽物だけが通るテストになる。
