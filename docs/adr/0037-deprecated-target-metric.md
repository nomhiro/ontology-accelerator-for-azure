# ADR-0037: 廃止された先を指すマッピングを指標に出す — 調べられなかった分を同じ欄に混ぜない

- ステータス: 承認済み
- 日付: 2026-09-12

## コンテキスト

[ADR-0030](0030-mapping-target-lifecycle.md) は「健全性指標に足す」を代替案として
**却下**した。理由は

> **指標が他の名前空間の Blob の可用性に依存する**(`P2B-21` として記録)

だった。`P2B-21` はこの保留の解決である。

### 却下の理由は、既に答えのある形だった

[ADR-0020](0020-health-metrics.md) 決定3 は**まさにこの問題**に答えている。

> 各項目は `int` か `null` で返す。`null` は「測れなかった」であり、
> **`0` とは違う**。加えて `unavailable` に「どの項目がなぜ測れなかったか」を
> 並べる。
>
> **部分的に測れたことを「全部測れなかった」にもしない。**

Blob の可用性に依存する項目は既にある(`term_count` / `shacl_violation_count`)。
依存すること自体は障害ではない。

### 本当に新しい問題は「呼び出し元によって値が変わる」ことである

ADR-0030 決定1 は、相手の名前空間に `data-analyst` が無ければ `unknown` を返す
と決めた(`active` とは言わない)。したがって**マッピングの先の生死は、
呼び出し元の権限に依存する。**

`ns` に `data-analyst` を持つ 2 人が、他の名前空間への権限が違えば
**違う数を見る。** 健全性指標は普通「測る対象の性質」として読まれるので、
呼び出し元に依存する数はこの API に無かった種類のものである。

**ただしこれは新しい依存ではない。** `GET /namespaces/{ns}/mappings` は既に
呼び出し元の権限に依存して `target_status` を返している(ADR-0030 決定1)。
指標はその集約である。

## 決定

### 1. 項目を 2 つ足す。片方だけ足さない

```
"mappings_to_deprecated_count": 2,
"mappings_unknown_target_count": 5,
```

**廃止の数だけ出してはいけない。** `2` だけを見せると「残りのマッピングは
健全である」と読める。実際には 5 件が**調べられていない**。

これは ADR-0020 決定3 の `null` と同じ判断を、**項目の中の粒度**で行うもので
ある。あちらは「項目が測れたか」で、こちらは「マッピング 1 件ごとに調べられた
か」である。粒度が細かいぶん、**測れた分を返しつつ測れなかった分を数えられる。**

### 2. この 2 項目は `null` にならない。全部か無かにしない

ADR-0020 決定3 は「測れなかった項目は `null`」と決めたが、**この 2 項目は
`null` にならない。** 調べられなかったマッピングは
`mappings_unknown_target_count` に入るからである。

| 調べられなかった理由(ADR-0030 の 5 種) | どこに出るか |
|---|---|
| 外部語彙(このシステムの名前空間でない) | `unknown` |
| 相手の名前空間を読む権限が無い | `unknown` |
| 相手にまだ承認済みの版が無い | `unknown` |
| 対象の名前空間の数が上限に達した | `unknown` |
| 相手の正本を読めなかった(Blob の障害) | `unknown` |

**最後の行が却下の理由だったものである。** Blob の障害は項目を `null` に
するのではなく、その分を `unknown` として数える。ADR-0030 が一覧で既にこの形を
採っているので、**指標だけ別の形にしない** — 一覧が「2 件廃止・5 件不明」と
言っているのに指標が `null` と言うのは、同じ事実の 2 つの報告が食い違うことで
ある。

`null` になりえない項目を `int | None` で宣言すると、**到達しない分岐**を
作ることになる(そこにコメントを書くと、動かない振る舞いを説明する嘘になる)。
だから `int` で宣言する。

### 3. 自分が張ったマッピング(`outgoing`)だけを数える

`incoming`(他の名前空間が自分の用語を指しているもの)は数えない。

**それは相手の問題である。** 自分の用語を廃止したことを相手に伝える経路は
ADR-0030 決定7 が別に持っている(`MAPPED_BY_OTHERS` を**廃止する側**の
`approve` に報告する)。指標に混ぜると、**自分では直せないものが自分の健全性の
数字を悪くする。** 行動に結びつかない数字は指標として害である
(ADR-0020 が「健全性の総合スコア」を却下した理由と同じ)。

### 4. 指標のために権限ゲートを外さない

**サービス自身の権限で全名前空間を読んで「客観的な数」を出してはいけない。**
呼び出し元に依存しない数にはなるが、ADR-0030 決定1 が守っている
**存在の oracle** が開く。

> `active` と `absent` を区別するので、権限で切らないと存在の oracle になる。
> IRI を当て推量で `declare` して読み返せば相手の語彙を 1 件ずつ探れてしまう。

指標の数からも同じことができる。自分が張ったマッピングは自分で選べるので、
**1 件ずつ張って数の増減を見れば相手の語彙を探れる。** 集約しても oracle は
閉じない。

**逆に、呼び出し元の権限で数える限り新しい情報は 1 つも増えない。**
その呼び出し元は `GET /namespaces/{ns}/mappings` で同じ生死を 1 件ずつ
読めるからである。だから ADR-0020 決定4(`data-analyst` が読める)を変えずに
足せる。

### 5. `HealthService.measure` が `principal` を受ける

権限に依存する項目が入ったので、サービスは「誰として測るか」を知らなければ
ならない。**呼び出し元の権限をそのまま使う**(決定4)。

これは署名の変更として目に見える形にしておく価値がある — **指標が呼び出し元に
依存することが型に現れる。**

## 検討した代替案

### 廃止の件数だけを出す

**却下(決定1)。** 応答が 1 項目増えるだけで済む。

却下理由: **「残りは健全」と読める。** ADR-0030 が `unknown` を必ず返すと
決めた理由(省略すると「載っていないものは問題なし」と読まれる)が、
集約したときにも同じだけ当てはまる。

### 1 件でも調べられなければ項目を `null` にする

**却下(決定2)。** 「客観的な数か、測れなかったか」の 2 択になり、
呼び出し元に依存する数を公開しなくて済む。

却下理由: **ADR-0020 決定3 が却下した「全部か無か」である。** 10 個の名前空間を
指していて 1 つが外部語彙なら、それだけで指標が消える。実運用では
**ほぼ常に `null`** になり、項目を足した意味が無い。そして一覧
(ADR-0030)が「2 件廃止」と言っているのに指標が `null` と言うのは、
同じ事実の 2 つの報告が食い違うことである。

### サービスの権限で全名前空間を読んで客観的な数を出す

**却下(決定4)。** 呼び出し元に依存しない数になる。

却下理由: **存在の oracle が開く**(ADR-0030 決定1)。自分が張ったマッピングは
自分で選べるので、1 件ずつ張って数の増減を見れば相手の語彙を探れる。
集約は oracle を閉じない。

### `incoming` も数える

**却下(決定3)。** 「自分の用語を指しているマッピングが廃止に巻き込まれて
いないか」も見える。

却下理由: **自分では直せない。** 相手のマッピングを自分で取り消すのは
ADR-0023 決定3 の裏返し(相手が宣言していない主張を相手の名前空間に作る/
消す)であり、ADR-0030 決定7 が既に却下している。行動に結びつかない数字を
健全性の欄に置かない。

### 廃止された先を指すマッピングを一覧で返す(IRI 付き)

**却下(将来の選択肢として残す)。** どれを直すべきかが直接分かる。

却下理由: ADR-0020 決定4 が用語 IRI の一覧を `include_terms=true` の
オプトインにしたのと同じ扱いが必要になり、この ADR の範囲が広がる。
そして**既に `GET /namespaces/{ns}/mappings` が一覧を返している** —
指標は「見るべきかどうか」を教えるもので、「どれを見るか」は一覧の仕事である。

### 指標を計算するときだけ `MAX_TARGET_NAMESPACES` を上げる

**却下。** 上限に達して `unknown` になる分が減る。

却下理由: ADR-0030 決定4 の上限は**上界が無いものに上限を置く**ためのもので、
指標でも同じ理由が当てはまる(マッピングは任意の IRI を指せる)。
経路ごとに上限が違うと、**一覧と指標で `unknown` の件数が食い違う。**

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **指標が呼び出し元に依存する**(決定4)。他の名前空間への権限が違う 2 人は
  違う数を見る。`mappings_unknown_target_count` がそれを見せるが、
  **「この数字は誰が見た数字か」を意識しなければならない**
- **Blob の読み込みが増える**(最大 `MAX_TARGET_NAMESPACES` = 10 件の TTL)。
  ADR-0020 は既に 1 件の TTL の解析コスト(実測 約 1.0 秒/MB)を受け入れて
  いるが、**最大で 11 倍になりうる**。オンデマンドの運用者向けの口なので
  許容する。上限は ADR-0030 決定4 のものをそのまま使う(決定と同じ理由で、
  経路ごとに変えない)
- **`incoming` は見えない**(決定3)。「自分の用語を廃止したら誰が困るか」は
  指標では分からない。それは廃止する側の `approve` で報告される
  (ADR-0030 決定7)
- **どのマッピングが廃止を指しているかは指標では分からない**。件数だけである。
  一覧(`GET /namespaces/{ns}/mappings`)で引く
- **`HealthService.measure` の署名が変わる**(決定5)。`principal` が必須に
  なった

### 得られるもの

- **ADR-0030 が受け入れたコスト「気づくのは一覧を見たときだけ」が埋まる。**
  健全性指標を見る運用の中で気づける
- **調べられなかった分が数として見える**(決定1)。一覧を 1 件ずつ読まなくても
  「どれくらい調べられていないか」が分かる
- **一覧と指標が同じ形で報告する**(決定2)。同じ事実の 2 つの報告が食い違わない

### 影響を受ける他の決定

- [ADR-0030](0030-mapping-target-lifecycle.md) — 代替案「健全性指標に足す」に
  補記を追加した(却下の理由は ADR-0020 決定3 が既に答えていた)
- [ADR-0020](0020-health-metrics.md) 決定3 — **この 2 項目は `null` に
  ならない**(決定2)。決定3 の規則の例外ではなく、**同じ規則をより細かい
  粒度で適用した結果**である
- [ADR-0020](0020-health-metrics.md) 決定4 — `data-analyst` が読めることは
  変えない(決定4 の通り、新しい情報は増えない)
