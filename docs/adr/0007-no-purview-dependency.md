# ADR-0007: Microsoft Purview に依存しない

- ステータス: 承認済み
- 日付: 2026-08-28

## コンテキスト

AWS 版の Context Ontology Accelerator は **AWS Glue Data Catalog** をデータカタログとして利用している。Scan フェーズでソースのスキーマ・メタデータを取得する際の入力源であり、AWS 環境では自然な選択である。

Azure における対応物は **Microsoft Purview**(Data Map)である。Purview は Apache Atlas 2.2 互換の API を提供し、データソースのスキャン、リネージ、用語集(glossary)、分類といった機能を持つ。「Azure 版を作る」という観点では、Glue → Purview と対応させるのが素直に見える。

しかし、両者には利用形態の面で重要な違いがある。

- **AWS Glue Data Catalog** は多くの AWS データ利用パターンにおいて実質的に前提となる基盤であり、多くの環境で既に存在する
- **Microsoft Purview** は独立した製品として導入・有効化する対象であり、**Capacity Unit (CU) 課金が発生する**。Azure サブスクリプションがあれば自動的に使えるものではない

本プロジェクトは **OSS として、誰でも `azd up` で評価できる**ことを設計目標としている。月額の見積りも $39〜61(minimal)という水準を提示している([`../cost-estimate.md`](../cost-estimate.md))。

ここで判断が必要になる。**Purview を必須の依存にするか、しないか。**

## 決定

**Microsoft Purview に依存しない。**

- **カタログの正本は自前の PostgreSQL に持つ**([ADR-0003](0003-postgresql-as-system-of-record.md))。`scan-job` がソース DB のスキーマ・統計を直接抽出し、Blob の文書を取り込んで、PostgreSQL のカタログへ蓄積する
- **Purview は「任意のソースコネクタ」として Phase 3 で対応する。** 既に Purview を運用している組織が、Data Map(Atlas 2.2 API)からメタデータを取り込めるようにする
- Purview が存在しない環境でも、**機能が一切欠けないこと**を保証する
- 承認済み用語を **Purview の用語集へ公開する双方向連携は将来スコープ**とする(現時点では実装しない)

## 根拠

### CU 課金が評価の障壁になる

本プロジェクトの価値は、まず試してもらえないと伝わらない。Purview を必須にすると、`azd up` の前提に「Purview アカウントを作成し、CU 課金を受け入れる」が加わる。これは次の問題を生む。

- **月額見積りが崩れる。** $39〜61 という水準を提示できなくなり、「評価に気軽に試せる OSS」という位置づけが失われる
- **個人や小規模チームが試せなくなる。** OSS の初期の採用者はこの層である
- **`azd down --purge` でコストが止まる**という保証が複雑になる

### Purview が提供する価値は、本プロジェクトの中核ではない

Purview の主な価値はエンタープライズ全体のデータガバナンス(横断的なカタログ、リネージ、分類、コンプライアンス)である。本プロジェクトが必要とするのは、Scan フェーズにおける「ソースのスキーマと統計」であり、これは**ソース DB から直接取得できる**。

`information_schema` の照会、テーブルの行数・カーディナリティ・NULL 率といった統計の取得は、Purview を経由しなくても実装できる。**間に製品を挟むことで得られるのは、Purview を既に運用している組織における重複作業の削減**であり、それは必須依存にする理由ではなく、コネクタを用意する理由である。

### 依存しないことで、Purview 利用組織も損をしない

「依存しない」は「連携しない」ではない。Purview を運用している組織にとっては、既にスキャン済みのメタデータを再利用できるほうがよい。これは**任意のソースコネクタ**として Phase 3 で提供する。

この構造(自前のカタログを正本とし、外部カタログは入力源の 1 つ)であれば、
- Purview がある組織は取り込みを使える
- ない組織は直接スキャンを使える
- **どちらでも機能は同じ**

必須依存にした場合、後者が使えなくなるだけで、前者に追加の利益はない。**非対称な選択である。**

### SPARQL_ENDPOINT の思想と同じ構造

これは [ADR-0001](0001-rdf-store-selection.md) で `SPARQL_ENDPOINT` を差し替え可能にした判断と同じ構造である。**既存の投資を持ち込めるようにするが、それを前提にはしない。** 外部システムとの結合点を「任意の入力源」として設計することで、利用者の環境の多様性を許容する。

### 双方向連携を将来スコープにする理由

「承認済みのビジネス用語を Purview の用語集へ公開する」機能は、Purview を運用している組織にとって明確な価値がある。オントロジーの承認フローが、そのまま企業のデータガバナンス基盤に反映される形になる。

しかし現時点では実装しない。理由は、
- **Phase 1〜3 の中核機能が完成していない段階で、外部製品への書き込み連携を作るのは順序が逆**である
- 用語集のスキーマとオントロジー(OWL クラス・プロパティ)のマッピングには設計判断が必要で、実際の利用者の要求を聞いてから決めたほうがよい
- 書き込み連携は、失敗時の扱い(片方だけ更新された状態)の設計を要求する

**要求が実際に出てきた時点で設計する**(YAGNI、設計原則 6)。

## 検討した代替案

### Purview を必須の依存とする(AWS 版の Glue に素直に対応させる)

**却下。** AWS 版との構成上の対応が明快になり、エンタープライズ向けの訴求も強くなる。

却下理由: 上記「根拠」で詳述。CU 課金が評価の障壁になり、月額見積りと「気軽に試せる OSS」という位置づけが崩れる。加えて、Purview が提供する価値は本プロジェクトの中核機能ではない。

**AWS 版と同じ構成にすることそれ自体に価値はない**、という判断でもある。本プロジェクトは AWS 版の移植ではなく、Azure ネイティブな独立実装である([ADR-0008](0008-independent-implementation.md))。対応表を埋めることより、Azure の文脈で妥当な選択をすることを優先する。

### Purview を既定で有効にし、無効化オプションを提供する

**却下。** 「エンタープライズ向けの既定」として Purview を有効にし、コストを気にする利用者はオプトアウトする、という構成。

却下理由:
- **既定でコストが発生する OSS は、評価してもらえない。** `azd up` を実行した利用者が、意図せず CU 課金を発生させる構造は避けるべきである
- 有効・無効の両方の経路をテストする負担が生じる。しかも無効側(Purview なし)が実質的に主要な経路であるため、**主要経路が「オプション扱い」になるという歪みが生まれる**
- 既定は「最小のコストで動く構成」であるべきである(設計原則 5 の `minimal`)

### 独自のカタログを持たず、Purview を唯一のカタログとする

**却下。** カタログの二重管理を避けられ、実装量も減る。

却下理由:
- Purview 必須になるという上記の問題に加え、
- **[ADR-0003](0003-postgresql-as-system-of-record.md) の正本設計と衝突する。** カタログはオントロジー生成の入力であり、承認履歴や名前空間 RBAC と関連付けて扱う。これを外部製品に置くと、参照整合性を保てない
- 外部製品の可用性とスキーマ変更に、本プロジェクトの中核機能が影響を受ける

### Azure Data Catalog(旧世代)や他社カタログ製品に対応する

**却下。** Azure Data Catalog は Purview に置き換えられており、新規採用の対象ではない。他社製品(Collibra、Alation 等)への対応は、要求が出てから検討する。**カタログを「任意のソースコネクタ」として設計しておく**ことで、将来の追加は既存の構造の上に載る。

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **スキーマ抽出を自前で実装する必要がある。** `scan-job` が各種 DB(PostgreSQL、SQL Server、MySQL 等)のスキーマと統計を抽出するコードを持つ。DB ごとの方言への対応が発生し、対応 DB を増やすたびに実装が必要になる。Purview に依存すれば、この部分は Purview のコネクタ群に任せられた
- **Purview が持つ横断的な機能を利用できない。** リネージ、分類、コンプライアンススキャンといった機能は、本プロジェクトの範囲外になる。これらを求める利用者は Purview を別途運用し、コネクタ経由で連携することになる
- **カタログが二重に存在する状態が生じる**(Purview 利用組織において)。同じテーブルのメタデータが Purview と本プロジェクトの PostgreSQL の両方にある。取り込み時点のスナップショットであり、Purview 側の更新が自動反映されるわけではないことを、ドキュメントで明示する必要がある
- **エンタープライズ向けの訴求が一段弱くなる。** 「Purview と統合済み」と言えるほうが、大企業の評価では有利に働く場面がある

### 得られるもの

- **`azd up` の前提が増えない。** Azure サブスクリプションだけで評価できる
- **月額見積り $39〜61(minimal)を維持できる。** CU 課金という予測しづらい変動要因が入らない
- **Purview のない環境でも機能が欠けない。** OSS の利用者層を狭めない
- **Purview 利用組織も損をしない。** Phase 3 のコネクタで既存のメタデータを取り込める
- **外部製品の可用性・スキーマ変更に中核機能が影響されない。** 依存が薄いことは保守性の利点である
- **カタログの正本を自前に持つことで、承認履歴・RBAC との参照整合性が保てる**([ADR-0003](0003-postgresql-as-system-of-record.md))

### 将来この決定を見直す条件

- Purview の課金モデルが変わり、小規模利用が実質無料になった場合
- 利用者から用語集への双方向連携の要求が具体的に出てきた場合(将来スコープの実装を検討する)
- 自前のスキーマ抽出の DB 方言対応が保守しきれない規模になった場合(Purview のコネクタ群に任せる価値が上がる)

### 影響を受ける他の決定

- [ADR-0003](0003-postgresql-as-system-of-record.md) — カタログの正本を PostgreSQL に置く判断は本 ADR の前提である
- [ADR-0001](0001-rdf-store-selection.md) — 「既存の投資を持ち込めるようにするが、前提にはしない」という同じ設計思想を共有している
