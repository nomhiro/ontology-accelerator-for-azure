# ADR-0012: MCP から Core API への認証

- 状態: 採用
- 日付: 2026-09-06
- 関連: [ADR-0006](0006-ontology-versioning-and-audit.md)（監査可能性）、[ADR-0010](0010-approval-and-projection.md)、バックログ `P1-12` / `P2A-06`

## コンテキスト

MCP サーバはツールの実処理を**すべて Core API に委譲する**設計である（`packages/mcp-server/src/ontology_mcp/server.py` の冒頭コメント）。ストアを直接叩かないのは、名前空間ごとの認可判定と「どのバージョンの何をエージェントへ返したか」の監査記録を Core API の一箇所に集めるためである（ADR-0006）。

**しかし現状、MCP は Core API を認証ヘッダなしで呼んでいる。** その結果:

- `AUTH_MODE=disabled` のローカル開発では動く
- **`AUTH_MODE=entra` のデプロイ環境では、MCP のツール呼び出しがすべて 401 になる**（`GET /namespaces` がトークン無しで 401 を返すことは Azure 実機で確認済み）
- `tools/list` は MCP サーバ自身が返すため成功する。**ツール一覧は見えるのに呼ぶと失敗する**ので、外からは「MCP は動いている」ように見える

MCP サーバ自身にも受信トークンの検証が無い。つまり Core API へ引き継ぐべき呼び出し元の識別子が、そもそも存在していない。

### なぜ「後で足す」で済まないのか

エージェント経路が使えないことは、この製品の価値そのものの欠落である（Phase 1 の完了条件が「AI エージェントが MCP 経由で参照できる」）。加えて **README がこれを「Phase 1 で動作するもの」に挙げていた**ため、記述が実態と食い違っていた。このリポジトリが繰り返し戦っている「静かに間違う」型の問題である。

## 決定

### 1. MCP と Core API は同一のオーディエンス（同一アプリ登録）を共有する

MCP サーバに独立したアプリ登録を作らない。エージェントは **Core API 向けのトークン**（`api://<appId>/.default`）を取得し、それを MCP へ提示する。

### 2. MCP は受信した Bearer トークンを自分で検証する

Core API と同じ `EntraVerifier`（同じテナント・同じオーディエンス）で署名・`iss`・`aud`・`exp` を検証する。**ヘッダが存在することを識別子の主張として扱わない。** MCP SDK の `Context.headers` の docstring 自身が「Headers are client-supplied input - never treat one as an identity assertion」と警告している。

境界で検証するのは、クエリのガード（`ensure_agent_safe_query`）を MCP 側にも置いているのと同じ理由である。Core API 側の検証が権威であり、MCP 側は二重だが、明らかに不正な入力を境界で落とす方が安全側に倒れる。

### 3. 検証を通ったトークンを、そのまま `Authorization` ヘッダとして Core API へ転送する

トークン交換（OBO）を行わない。**転送するのは `Authorization` ヘッダのみ**で、`Cookie` や `X-Forwarded-*` といった他のクライアントヘッダは転送しない。

### 4. `AUTH_MODE=disabled` では検証も転送も行わない

ローカル開発の経路（不変条件 9。デプロイ環境で使ってはならない）。

## 根拠

### MCP 仕様のトークン・パススルー禁止との関係（先に答えておく）

MCP の Security Best Practices は「**そのサーバー宛てに発行されていないトークンの転送**」を明示的に禁止している。この設計はそれに違反しない。**MCP と Core API は同一のオーディエンスであり、トークンはまさにこのリソース宛てに発行されている**からである。禁止されているのは「別のリソース向けに発行されたトークンを、検証せずに下流へ回して信頼させる」パターンであり、ここでは (a) オーディエンスが一致し、(b) MCP 自身が署名を検証し、(c) 下流の Core API も独立に検証する。

OSS として公開するため、この論点は必ず指摘される。先回りしてここに残す。

### マネージド ID（クライアント資格情報）では監査が壊れる

MCP コンテナの UAMI で Core API を呼ぶ案は、実装は最も簡単で、今すぐ動く。**しかし Core API から見た呼び出し元が常に MCP サーバになる。**

- 監査イベントの `actor` がすべて MCP になり、「誰の問い合わせに対してどのバージョンを返したか」が記録できない。これは ADR-0006 が中核価値として掲げている帰属そのものである
- 名前空間ごとの RBAC（`P2A-06`）を Core API で強制できない。設計原則「名前空間×ロールは PostgreSQL で管理し API で強制」が成立しなくなる

**機能が動くことと引き換えに、この製品の中核価値を捨てる交換になる**ため採らない。

### 同一オーディエンスにすると何を失うか

MCP に固有のスコープやアプリロールを定義できない。「MCP からは読み取りだけ、Web からは書き込みも」といった区別をトークン側で表現できず、区別が必要になったら Core API 側のロール（`roles` クレーム）と経路情報で行うことになる。Phase 1 では MCP が読み取り専用のツールしか公開していないため、実害がない。

## 検討した代替案

### On-Behalf-Of（OBO）フロー

MCP に独立したアプリ登録を作り、受け取ったトークンを Core API 向けのトークンへ交換する。MCP を独立したリソースとして扱えるので、固有のスコープを定義できる。

**却下する理由**: OBO には機密クライアント資格情報が必要になる。このリポジトリは**クライアントシークレットを持たない**方針を通してきた（`postdeploy` が `preAuthorizedApplications` を使うのも同じ理由）。Phase 1 で得られるものが「固有スコープを定義できる」だけであるのに対し、失うものが大きい。

将来 `P2A-06` で MCP に独立した識別子が必要になった場合の経路は、**別アプリ登録 + マネージド ID の Federated Identity Credential による OBO**（クライアントシークレット不要）である。今は作らない。

### MCP を無認証のままにして Core API を internal ingress に閉じる

MCP だけを外部公開し、Core API を内部に置けば、Core API 側の認証を省ける。**却下**: 認可判定と監査記録を Core API の一箇所に集める設計（ADR-0006）が崩れる。認可の判定材料である呼び出し元の識別子が Core API に届かない。ネットワーク境界を認可の代わりにする設計そのものが誤りである。

### MCP 認可仕様のフルセットを実装する

Protected Resource Metadata、`WWW-Authenticate` によるディスカバリ、OAuth のメタデータ公開まで実装する。**Phase 1 では行わない**。Phase 1 の要求は「Bearer を受けて検証して転送する」ことに尽きる。仕様準拠の残りは下記の未解決事項に置く。

## 結果（トレードオフ・影響）

### 得られるもの

- **エージェント経路がデプロイ環境で実際に動く。** Phase 1 の完了条件が満たされる
- **監査の `actor` が実際の呼び出し元になる。** ADR-0006 の帰属が MCP 経路でも成立する
- `P2A-06`（名前空間 RBAC）を Core API 側だけで実装できる。MCP 側に認可ロジックを重複させない

### 受け入れるコスト

- MCP に固有のスコープを持たせられない（上記）
- エージェントは Core API のオーディエンスを知る必要がある。MCP を「独立したリソース」として抽象化できていない
- MCP 側の検証と Core API 側の検証が二重になる（JWKS の取得も両方で行う）。境界での早期拒否という利点と引き換えである

### 影響を受ける他の決定

- **[ADR-0006](0006-ontology-versioning-and-audit.md)**: エージェント経路のアクセスログ（§4）が、この決定によって初めて実装可能になる
- バックログ `P2A-06`（名前空間 RBAC の強制）: Core API 側だけで完結できる前提が確定する

### 未解決のまま残す問い

- MCP 認可仕様のフルセット（Protected Resource Metadata、`WWW-Authenticate` によるディスカバリ）への準拠。Phase 1 では扱わない
- MCP に固有のスコープが必要になったときの移行手順（別アプリ登録 + Federated Identity Credential による OBO を想定しているが、詳細は未検討）
- エージェントがトークンを取得する具体的な経路のドキュメント（Foundry Agent Service から接続する場合の設定）
