# ADR-0046: 仮想グラフ(Ontop VKG)— 実データを実体化せずに SPARQL で引く

- **状態**: 採択
- **日付**: 2026-09-13
- **関連タスク**: `P3-01`
- **関連 ADR**: [ADR-0001](0001-rdf-store-selection.md)(ストア選定)、
  [ADR-0002](0002-triple-store-as-rebuildable-projection.md)(射影)、
  [ADR-0022](0022-competency-question-sets.md)(不変改訂の形)、
  [ADR-0041](0041-source-schema-scan.md)(スキャン)、
  [ADR-0030](0030-mapping-target-lifecycle.md)(生死の 4 状態)

## コンテキスト

`P3-01` は Phase 3 の最初の項目で、**顧客のリレーショナル DB を RDF として
読めるようにする**ものである。Ontop は R2RML マッピングを介して SPARQL を
SQL に書き換え、**実データを実体化しない**。

これは飾りではなく、[ADR-0002](0002-triple-store-as-rebuildable-projection.md)
が成立する前提である。あの ADR は「EmptyDir の 4〜8 GiB で足りる」を
**トリプルストアに載るのが語彙だけだから**という理由で正当化しており、
実データをグラフに載せるならその判断はやり直しになる。

### 実測した Ontop の性質(5.3.0)

設計の前に実物を測った。**推測で決めた項目は 1 つも無い。**

| 測ったこと | 結果 |
|---|---|
| 公式イメージの JDBC ドライバ | **1 つも入っていない。** `/opt/ontop/jdbc` ディレクトリすら無いが、起動スクリプトはクラスパスに `/opt/ontop/jdbc/*` を含める |
| 資格情報の渡し方 | `ONTOP_DB_PASSWORD_FILE`(ファイルで渡す)が**実在する**。プロパティファイルにも argv にも載らない |
| TBox の推論 | **効く。** `Customer ⊑ Party` を渡して `?x a ex:Party` を問うと、顧客のインスタンスが返る |
| TBox のトリプル自体 | **返らない。** `?s a owl:Class` は 0 件、`rdfs:label` も 0 件 |
| SPARQL Update | **受け付けない。** `/sparql` は 415、`/update` `/sparql/update` `/statements` はいずれも 404 |
| 不正なマッピング(即時初期化) | **コンテナが起動しない** |
| 不正なマッピングのエラー本文 | **接続ユーザから見える全関係を列挙する**(こちらの制御平面の表も入っていた) |
| 遅延初期化(`--lazy`) | 起動はする。最初のクエリで 500。**失敗を覚えず、関係が後から現れれば通る** |
| ポータルページ | `ONTOP_DISABLE_PORTAL_PAGE=true` で `/` と `/index.html` が 404。`/ontology` は既定で 404。**`/actuator/health` は残る** |
| CA 証書 | **1 枚も無い**(`/etc/ssl/certs` が空)。イメージの中からは TLS を検証できない |
| 同梱物のライセンス | `/opt/ontop/copyright/` に 27 件。Apache-2.0 / MPL-2.0(H2)/ BSD(Protege)/ EPL-1.0+LGPL 二重(Logback)。**GPL 単独は無い** |

**`P1-S3`(Ontop 配布物のライセンス確認)の結論を 5.3.0 で再確認した。**
あのときの結論「公式イメージには JDBC ドライバが一切同梱されていない」は
今も正しい。

## 決定

### 決定1: Ontop は「連邦のパートナー」ではなく「2 つ目の射影先」である。跨ぐ結合はしない

**宛先を URL で分ける。**

| 何を問うか | 宛先 |
|---|---|
| 語彙(クラス、述語、ラベル、廃止、SHACL) | `/namespaces/{ns}/sparql`(Fuseki) |
| 実データ(インスタンス) | `/namespaces/{ns}/scan-sources/{source}/sparql`(Ontop) |

**1 つのクエリが両方に跨ることはない。**

跨ぐ結合を実装するには分散クエリのエンジンが必要で、
[ADR-0001](0001-rdf-store-selection.md) は SPARQL の実装を自作しないと
決めている。`SERVICE` 句で繋ぐ選択は SSRF 対策として封じてある
(`sparql/guards.py`、`containers/fuseki/config.ttl`)。

**跨げないことの実害は小さい。** 実測のとおり Ontop は `--ontology` で
渡した TBox を使って推論するので、**語彙の意味は仮想グラフ側でも効く**。
効かないのは `rdfs:label` や `owl:deprecated` のような**語彙そのものに
ついての主張**だけで、それは Fuseki 側の担当である。

**却下した代替案: Fuseki の `SERVICE` 句で Ontop を呼ぶ。** 1 つのクエリで
両方を引けるが、`SERVICE` を有効にすると**任意の URL へ到達できる**
(Azure IMDS を含む)。allowlist を作る道もあるが、**「allowlist があるから
安全」と「SERVICE を無効にしてあるから安全」では強度が違う**。
Phase 1 から守ってきた線を Phase 3 の便利さで崩さない。

### 決定2: マッピングは**ソースごとの不変改訂**で、正本は PostgreSQL(Blob には置かない)

`competency_question_sets`([ADR-0022](0022-competency-question-sets.md) 決定1)と
同じ形にする。`reason` は必須である。

**Blob に置かない。** マッピングは Fuseki へ射影されないので、
不変条件2(Blob → PostgreSQL → Fuseki)を挟む理由が無い。挟むと**孤児 Blob
という故障モードを新しく作る**(`P2B-12` / `P2B-20` と同じ形)。PostgreSQL
だけなら、改訂と監査記録を同一トランザクションで書ける。

**改訂を書き換える口も、マッピングだけを消す口も作らない。**
マッピングは**実データへの入口の定義**なので、「いつから何が見えていたか」
を後から書き換えられてはいけない。止めたいならソースを消す
(`ON DELETE CASCADE` で一緒に消え、消したという事実は監査に残る)。

**Ontop へ渡す経路は API である。** `GET .../vkg-mapping.ttl` が
`text/turtle` で返す。JSON に包まないのは、取り出す側が毎回ほどくことになり
`jq -r` を挟んだ経路で**改行やエスケープが壊れる**ためである(このリポジトリで
何度も踏んだ形)。デプロイ環境での配線(init コンテナ)は `P3-07`。

### 決定3: 仮想グラフの抽象を `SparqlStore` と別にする

`ontology_core.vkg.VirtualGraphClient` を新しく作る。`SparqlStore` を
実装しない。

`SparqlStore` は**射影先**の抽象である(データセットを作り、名前付きグラフを
置き換え、更新を流す)。仮想グラフはそのどれもしない — **書き込む先が無い**。

押し込めると `update` / `put_graph` / `create_dataset` を「例外を投げる実装」で
埋めることになり、**契約に嘘を書く**。[ADR-0034](0034-construct-describe.md) が
`construct` を抽象メソッドにした理由(既定実装で例外を投げると持ち込みストアで
黙って 500 になる)の裏返しである。

実測で Ontop 自身が SPARQL Update を持たないことを確かめたうえで、
**こちら側にも経路を置かない**(テストが `update` 等の属性が無いことを固定する)。

### 決定4: `rr:sqlQuery` を受け付けない

R2RML の論理表は `rr:tableName`(表名)か `rr:sqlQuery`(任意の SQL)で
書ける。**後者を受け付けない。**

理由は**パーサが無いこと**である。`ontology_core.scan.referenced_relations` は
正規表現で、自身の docstring が「完全な SQL パーサではない。`CATALOG_QUERIES`
という固定の集合に対して確かめるためだけのもの」と書いている。それを任意の
SQL に向けると、**境界があるように見えて無い**状態を作る。それは
不変条件11 が最も避けたい形である。

**実データに対する本当の境界は、接続する DB ユーザの権限である。** 実測の
とおり Ontop はそのユーザに見える関係をすべて見る。だから運用の手順として
最小権限のユーザを使う(`P1-11` と同じ向き)。ここでできるのは**取り違えを
入口で捕まえる**ことだけで、それを「安全性の判定」と呼ばない。

**この制限は後から緩められる。** 逆(受け付けてから禁止する)はできない
(既に登録されたマッピングが動かなくなる)。

### 決定5: 主語の IRI を名前空間のデータ接頭辞の下に閉じ込める

データ接頭辞は `base_iri` から導く(`data_iri_prefix`)。
`https://e.example/retail#` → `https://e.example/retail/data/`。

**新しい列を作らない。** `base_iri` から決まるようにしておけば、
「データの接頭辞だけ別の名前空間を指している」状態を作れない。

**不変条件5 に直接触る。** 名前空間 A のマッピングが名前空間 B の IRI を
主語にできるなら、**A は B の用語について B が宣言していない事実を作れる**。

`base_iri` がスラッシュ区切りのとき、`.../data` という名前の**用語**を作れば
空間が重なりうる。**重なっても境界は破れない** — どちらも同じ名前空間の
下である。

### 決定6: クラスと述語は「自分の語彙」だけ実在を検査する

| 出所 | 扱い |
|---|---|
| 自分の `base_iri` の下 | **承認済み版に実在しなければ拒否。廃止済みも拒否**(後継を示す) |
| 他の名前空間の `base_iri` の下 | **拒否**(不変条件5) |
| 外部語彙 | **検査しない** |

**外部語彙を検査しない**のは、`rdfs:label` や schema.org への写像が正当な
主用途だからである([ADR-0023](0023-cross-domain-mappings.md) 決定6 /
[ADR-0015](0015-term-owners.md) 決定4 と同じ判断)。

**実在しない用語を拒否する**のは、通すと**その用語で問い合わせる
エージェントからは何も見えない**からである。実データは流れているのに
照会が 0 件を返す — 最も気づきにくい壊れ方である。

**廃止済みも拒否する。** 廃止した用語に新しく実データを流すと、**廃止の
宣言が意味を失う**(不変条件8)。後継を示すのは、直す先が分からない拒否は
直せないからである([ADR-0030](0030-mapping-target-lifecycle.md) の
`successor` と同じ理由)。

**述語をデータから作らせない。** `rr:predicateMap` の `rr:template` を
受け付けない — 列の値が述語になると**どの述語が現れるかが実データ次第**に
なり、この検査が原理的にできなくなる。

### 決定7: 空白ノードの主語を受け付けない

**行を引き直したときに同じ主語になる保証が無い。** エージェントは
「顧客 X の注文」を引いたあとにその注文を参照できなければならない。
参照を持ち回せない主語は、仮想グラフの用途に合わない。

### 決定8: `rr:graph` / `rr:graphMap` を受け付けない。仮想グラフは既定グラフに置く

書き手が名前付きグラフの IRI を決められると、**版のグラフ IRI
(`urn:ontology:graph/<ns>/<version>`)を名乗るマッピング**を作れる。
[ADR-0010](0010-approval-and-projection.md) 決定6 の「エージェントが読むのは
既定グラフ」と揃える。

### 決定9: `rr:parentTriplesMap` を受け付けない

参照結合はもう 1 つの TriplesMap の主語を借りる形なので、**借りた先の
検査結果に依存する**。段階を増やさず、`rr:template` で相手の IRI を
組み立てる形に寄せる(実測でその形が動いている)。

### 決定10: Ontop のエラー本文を呼び出し元へ渡さない

実測のとおり、Ontop は参照する関係が無いとき
`Cannot find relation ... (available choices: [...])` を返し、**接続ユーザから
見える全関係を列挙する**。これは顧客 DB のスキーマの開示であり、照会者が
知ってよい情報ではない。

`VirtualGraphClient` は**本文をログにだけ出し、応答にはステータスコードまでを
載せる**。

**`FusekiStore._raise_for_status` は本文を 500 文字まで含める。** あちらを
直さないのは、**相手が違う**からである — 漏れるのは自分が書いた内容と
呼び出し元自身のクエリである。ここは顧客の DB が相手である。

**この判断の根拠は実測に依存している。** だから
`containers/ontop/ontop-check.test.sh` が**「本文が全関係を列挙すること」を
検査する**。Ontop が列挙をやめたらそのテストが落ちて、根拠が変わったことに
気づける。

### 決定11: 「設定されていない」「マッピングが無い」を空の結果にしない

| 状態 | 応答 |
|---|---|
| `VKG_ENDPOINT_TEMPLATE` が未設定 | **503**(設定を指し示す) |
| マッピングが未登録 | **404** |
| 名前空間が退役済み | **409** |

**空の結果を返さない。** 実測のとおり、Ontop は問える範囲の外を**例外では
なく 0 件**で返す(TBox のトリプルがそうだった)。0 件は「該当する行が無い」と
区別できないので、**設定漏れがデータの不在として通る**。

この製品でいちばん避けたい形の 1 つであり、ADR-0016 決定5(計算できなかった)、
ADR-0025 決定3(切り詰めた)、ADR-0030 決定2(調べられなかった)、
ADR-0032 決定5(退役した名前空間へのクエリ)と同じ判断である。

### 決定12: マッピングをオントロジーの版に紐づけない。照合した版を記録する

版に紐づけると、**承認のたびに実データへの入口が止まる**(新しい版に対して
マッピングを書き直すまで動かない)。

代わりに、登録時点で承認済みだった版を `validated_against_version` に
記録する。**`NULL` は「承認済み版が無かった」であって「検査していない」
ではない。** 監査の本文にも `(承認済み版なし)` と書く。

**承認済み版が無い状態での登録を拒否しない。** この製品は Scan → Model の
順で進むので、版がまだ無い段階でマッピングを書くのは異常ではない。

**一方、スキャンが一度も成功していないソースでは拒否する。** そちらは
「検査できなかった」を「検査した」と書くことになるからである
(不変条件11 と同じ向き — 分からないなら許可しない)。しかも実測のとおり
**Ontop は不正なマッピングでは起動しない**ので、通すと仮想グラフが
丸ごと落ちる。

### 決定13: 仮想グラフの照会をアクセスログに記録しない(`P3-08` で埋める)

**この経路が返すのは顧客の実データである。** それでも
`access_events`([ADR-0018](0018-context-access-log.md))には記録しない。

理由は**あの表の形が合わないこと**である。`access_events` は「どの**版**の
何を返したか」を持ち、仮想グラフには版が無い。`default_graph_version` を
`NULL` で埋めると、**「承認済み版が無かった」と混ざる**(決定11 と同じ
種類の誤りを、自分で作ることになる)。

**アプリのログには出す**(actor / 名前空間 / ソース / 改訂 / 行数 /
切り詰め)。監査証跡ではないが、無記録でもない。

**これは受け入れたコストであり、`P3-08` として記録した。** 列を足す変更は
健全性指標・監査 API・`term_access` の更新に波及するので、`P3-01` の範囲に
入れない。

### 決定14: 仮想グラフの `CONSTRUCT` にトリプル数の上限を当てない

`sparql.py` は `CONSTRUCT` を解析してトリプル数の上限を当て、超えたら 413 で
断る([ADR-0034](0034-construct-describe.md) 決定4)。**仮想グラフでは当てない。**

仮想グラフの `CONSTRUCT` は顧客 DB の行数だけ膨らむので、**上限を当てるため
に全部を解析する**のが一番重い経路になる。エージェント向けの主経路は
`SELECT` であり、そこには行数の上限(`SPARQL_MAX_RESULTS`)が効いている。

**これも受け入れたコストである。** 大きな `CONSTRUCT` は
`VKG_QUERY_TIMEOUT_SECONDS` で止まる(止まり方は 502 で、切り詰めた
グラフを完全なものとして返すことはない)。

### 決定15: JDBC ドライバは pgjdbc と mssql-jdbc だけを同梱する

| ドライバ | ライセンス(一次情報で確認) | 扱い |
|---|---|---|
| pgjdbc 42.7.7 | BSD-2-Clause(jar 内 `META-INF/LICENSE` と POM) | **同梱** |
| mssql-jdbc 12.10.0.jre11 | MIT(POM) | **同梱** |
| MySQL Connector/J | GPL-2.0 with FOSS exception | **同梱しない** |
| Oracle JDBC | 独自条項(再配布の許諾が無い) | **同梱しない** |

**「私たちが再配布しないこと」と「利用者が使えないこと」は別である。**
`/opt/ontop/jdbc` はマウント可能なまま残す。

**ドライバは TLS を検証できる段で落とす。** 実測のとおり
`ontop/ontop:5.3.0` には CA 証書が 1 枚も無い。`--no-check-certificate` で
逃げない — SHA-256 で固定してあるので内容の完全性は保てるが、**「検証を
切った」という設定がイメージに残ると、次にここを触る人が別の
ダウンロードにもそれを流用する**。

### 決定16: イメージの既定を遅延初期化にする

即時初期化だと、マッピングが参照する関係が無いときに**コンテナが起動しない**。
起動しないと運用者に届くのは「Ontop が落ちている」だけで、原因(表名の誤り)は
コンテナのログの中に埋まる。

遅延なら起動はして、最初のクエリで 500 を返す — **そのとき Core API が
本文を捨ててログに出す**(決定10)。実測のとおり**遅延は失敗を覚えない**ので、
関係が後から現れれば次のクエリで通る。

**入口の検査(決定12)があるので、遅延で通るのは「登録後にスキーマが変わった」
場合に限られる。** その場合は、コンテナを落とすより 500 を返すほうがよい。

## 帰結

### 得られるもの

- **実データをコピーせずに SPARQL で引ける。** ADR-0002 の前提が実物で成立した
- **語彙の意味が仮想グラフ側でも効く**(TBox の推論)
- **マッピングの履歴が監査になる。** いつ・誰が・なぜ実データへの入口を
  変えたかが残る
- **スキャン(`P2A-01`)とマッピングが噛み合う。** 観測していない表は
  マッピングできない

### 受け入れるコスト

- **1 ソース = 1 Ontop インスタンス。** Ontop は 1 つの DB しか見ない
  (`--db-url` が 1 つ)。ソースが増えるとコンテナが増える。デプロイ時の
  構成は `P3-07` で決める
- **Entra トークン認証のソースでは仮想グラフを立てられない(未検証)。**
  Ontop は起動時に資格情報を 1 度読む形で、トークンの期限切れに追従する
  仕組みが無い。**`ONTOP_DB_PASSWORD_FILE` を読み直すかは確かめていない** —
  読み直したとしても、プール内の既存接続は古い資格情報で作られたままである。
  `P3-07` で実機に当てて確かめる
- **仮想グラフの照会がアクセスログに残らない**(決定13、`P3-08`)
- **仮想グラフの `CONSTRUCT` にトリプル数の上限が無い**(決定14)
- **`/actuator/health` が残る。** 内部 ingress にしか出さない前提だが、
  切る設定を入れていない(Ontop に切る口が無い)

### 確かめていないこと

- **デプロイ環境での動作は `P3-07`。** Container Apps 上での内部 ingress、
  マッピングの配線(init コンテナ)、Entra トークン認証の可否
- **SQL Server に対する動作。** ドライバは同梱したが、実機で確かめたのは
  PostgreSQL だけである
