# ADR-0047: 定義と実データの乖離検出 — 探りを投げる。データを取らない

- **状態**: 採択
- **日付**: 2026-09-13
- **関連タスク**: `P3-05`
- **関連 ADR**: [ADR-0046](0046-virtual-knowledge-graph.md)(仮想グラフ)、
  [ADR-0002](0002-triple-store-as-rebuildable-projection.md)(射影)、
  [ADR-0005](0005-reasoner-boundary.md)(SHACL の担当範囲)、
  [ADR-0030](0030-mapping-target-lifecycle.md)(生死の 4 状態)、
  [ADR-0022](0022-competency-question-sets.md)(想定質問)

## コンテキスト

承認したオントロジーは「こういう形のデータがある」という主張である。
**その主張が実データと食い違っていても、今は誰も気づかない。**

- クラスを定義したが、実データに 1 件も無い(定義が現実より広い)
- 必須(`sh:minCount ≥ 1`)にしたプロパティが、実データでは欠けている
  (定義が現実より厳しい)

SHACL 検証(`P2A-05`)では見つからない。あちらが検証するのは**投入された
TTL 自身**であり、スキーマだけの TTL には対象ノードが無いので「適合」を
返す(`ontology_core.shacl` の冒頭がそう書いている)。ADR-0009 の未解決事項に
「定義と実データの乖離検出は Ontop 経由が前提なので Phase 3 以降」とあり、
`P3-01`(ADR-0046)でその前提が揃った。

### 実測した Ontop の制約

**設計の途中で 1 つ、推測が外れた。**

| 書き方 | Ontop 5.3.0 |
|---|---|
| `FILTER NOT EXISTS { ?s p ?v }` | **拒否される。** `OntopUnsupportedKGQueryException: The expression Exists ... is not supported yet!` で HTTP 500 |
| `OPTIONAL { ?s p ?v } FILTER(!BOUND(?v))` | **動く**(3 件中 1 件欠けを正しく返した) |
| `MINUS { ?s p ?v }` | **動く**(同じ答え) |

最初は `FILTER NOT EXISTS` で書いた。**実物に当てて初めて分かった** —
Python 側のテストは探りの文字列を固定するだけなので、全部通っていた。

## 決定

### 決定1: pyshacl を実データに当てない。形から SPARQL の探りを組み立てる

**当てるにはデータをメモリに載せる必要がある。** それは ADR-0002 と
ADR-0046 が守っているもの(実データを実体化しない)を、**検査のために
壊す**ことになる。検査が設計の前提を壊すのは本末転倒である。

代わりに、`sh:NodeShape` から SPARQL の探り(probe)を作って仮想グラフに問う。
返るのは `ASK` の真偽と `COUNT` の 1 行だけで、**実データはこちらに来ない**。

**これは SHACL 検証ではない。** 見るのは 2 つだけである。

- **クラスに実データがあるか**: `ASK { ?s a C }`
- **必須プロパティが欠けている件数**:
  `SELECT (COUNT(DISTINCT ?s)) WHERE { ?s a C OPTIONAL { ?s p ?v } FILTER(!BOUND(?v)) }`

`sh:pattern` / `sh:datatype` / `sh:maxCount` / `sh:class` は**見ない**。
見ないことを名前(`divergence`、`ShaclReport` ではない)と応答
(`conclusive`)に書いておく — **「乖離が無い」を「SHACL に適合した」と
読まれてはいけない。**

**却下した代替案: 実データを取ってきて pyshacl に渡す。** 完全な SHACL
検証ができるが、(a) 上記のとおり設計の前提を壊し、(b) 顧客 DB の全行を
こちらのプロセスに載せることになる。**「検査のためなら実データを持って
きてよい」は、この製品では通らない。**

### 決定2: 0 件を 4 状態に分ける

これがこの ADR の中心である。

| 何が起きたか | 状態 | 意味 |
|---|---|---|
| 実データが 1 件以上あった | `matched` | — |
| マッピングはあるのに 0 件 | `empty` | **これが乖離である** |
| マッピングがそのクラス(述語)を作っていない | `unmapped` | **乖離ではない。** 入口が無い |
| 照会できなかった | `unknown` | **何も言えない。** 理由を `note` に入れる |

**3 つを 1 つの `0` に潰すと、マッピングの書き忘れも Ontop の停止も
「実データが無い」として報告される。** 運用者が取るべき対処が
まったく違う(マッピングを書く / Ontop を直す / 定義を狭める)のに、
見分けがつかなくなる。

ADR-0030 決定2 の 4 状態と同じ形にしてある。

### 決定3: マッピングが作っていないクラス・述語には探りを投げない

投げても 0 件が返るだけで、それは「乖離」ではない。**顧客 DB への
無駄なクエリになる**うえ、結果の解釈を誤らせる。

判定は**マッピングを解析して**決める(`R2rmlMapping.classes` /
`.predicates`)。登録時に検査しているので、解析は必ず通る。

### 決定4: `sh:targetClass` を持つ、IRI で名前の付いた形だけを見る

- **`sh:targetNode` / `sh:targetSubjectsOf` は扱わない。** 探りに使える
  「クラス」を与えない
- **空白ノードの形は取らない。** 報告に出す識別子が無く、運用者が
  「どの形の話か」を辿れない
- **`sh:targetClass` がリテラルの形も取らない。** どのノードにも
  当たらない形で、**SHACL-SHACL が段階 1 で報告する**(`shacl.py`)。
  ここで二重に報告しない
- **`sh:minCount` が型違いのときは必須と見ない。** これも段階 1 の担当で、
  **乖離の測定が SHACL の構文検査を兼ねると、どちらの問題なのかが
  分からなくなる**

### 決定5: 探りの本数に上限を置き、超えた分を `unknown` として報告に入れる

形の数と必須プロパティの数の積だけ探りが増え、**その 1 本ずつが顧客 DB への
クエリになる**。上界が無いものに上限を置く(`MAX_PROBES = 100`)。

**超えた分を欠落させない。** 報告に `unknown` + 理由「上限」として入れ、
`skipped_probes` に本数を出す。欠落させると**呼び出し側が「載っていない
ものは問題なし」と読む**(ADR-0016 決定5 / ADR-0030 決定4 と同じ形)。

**クラスに実データが無ければプロパティの探りを投げない。** 投げても
意味のある答えにならない。**投げなかった分は `issued_probes` から引く** —
「何本投げたか」が実際と合っていないと、コストの見積もりに使えない。

### 決定6: 測れないときは空の報告を返さない

| 状態 | 応答 |
|---|---|
| 承認済みの版が無い | **404**(測る基準が無い) |
| マッピングが無い | **404**(実データへの入口が無い) |
| 正本(Blob)が読めない | **404**(読めなかったことを言う) |
| `VKG_ENDPOINT_TEMPLATE` が未設定 | **503** |
| 名前空間が退役済み | **409** |
| SHACL の形が 1 つも無い | **200 + `no_shapes: true`** |

**最後の行だけ 200 である。** 形が無いのは異常ではない(スキーマだけの版が
そうなる)。ただし **`no_shapes` を立てて「乖離が無い」と区別する** —
形が無いから何も見つからなかったのであって、見て何も無かったのではない。

### 決定7: 読めなかった応答を `False` / `0` にしない

- `ASK` の応答が読めない → `unknown`(**`empty` にしない**)
- `COUNT` の応答が読めない → `missing_count = None`(**`0` にしない**)

「答えが偽だった」と「応答を読めなかった」、「0 件だった」と
「数えられなかった」は違う(ADR-0041 決定2 と同じ扱い)。

### 決定8: `FILTER NOT EXISTS` を使わない。`OPTIONAL` + `!BOUND` で書く

実測のとおり Ontop 5.3.0 が `NOT EXISTS` を拒否する。`MINUS` も動いたが、
**`OPTIONAL` + `!BOUND` を選ぶ** — SPARQL 1.0 の時代からある形で、
持ち込みストア(ADR-0001 設計原則3)でも通る可能性がいちばん高い。

**`NOT EXISTS` のほうが素直に読める。** だから「読みやすくする」変更で
戻されうる。**そうならないように 2 か所で固定した。**

- `packages/core/tests/test_divergence.py` が `"NOT EXISTS" not in query` を検査する
- `containers/ontop/ontop-check.test.sh` が**実物が 500 を返すこと**を検査する

後者が本体である。Ontop が対応したら**そのテストが落ちて、前提が
変わったことに気づける。**

### 決定9: 状態を変えない。定期実行もしない

`GET` で読むだけである(SHACL の `.../validate` や想定質問の `.../run` と
同じ位置づけ)。

**バックログの「定期的に実データへ当てる」は今回入れない。** 定期実行を
足すなら `scan_job`(ADR-0042)と同じ判断(既定で動かない、Manual トリガ)が
必要で、**通知の宛先も決まっていない**。報告を返す口を先に作り、
定期実行は分けた(`P3-09`)。

### 決定10: 乖離を承認のゲートにしない

`approve` は止めない。理由は 2 つある。

1. **乖離は「定義が悪い」とは限らない。** 実データがまだ入っていない
   新しいクラスは、正当な `empty` である
2. **不変条件15 に触る。** 承認時の検査でトリプルストアに問い合わせては
   ならない。仮想グラフはストアよりさらに外(顧客 DB)であり、
   **承認の可否を顧客 DB の可用性に依存させる**のは、あの不変条件が
   守ろうとしているものの逆向きである

**止めない代わりに、見えるようにする。** ADR-0022 決定6 の
「防止ではなく可視化」と同じ判断である。

## 帰結

### 得られるもの

- **定義と現実の食い違いが見えるようになった。** 「クラスを定義したのに
  実データが無い」「必須にしたプロパティが実データで欠けている」
- **実データは 1 行もこちらに来ない。** ADR-0002 / ADR-0046 の前提を
  壊していない
- **`unmapped` と `empty` が分かれる。** マッピングの書き忘れと定義の
  乖離を、運用者が取り違えない

### 受け入れるコスト

- **SHACL の制約のほとんどを見ていない**(`sh:pattern` / `sh:datatype` /
  `sh:maxCount` / `sh:class`)。**「乖離なし」は「SHACL に適合」ではない**
- **定期実行が無い**(決定9、`P3-09`)。今は運用者が叩くまで測らない
- **探りの本数だけ顧客 DB にクエリが飛ぶ。** 上限はあるが、
  **重いテーブルに対する実測をしていない**(題材は 5 行である)
- **`sh:path` が単一の IRI でない形(プロパティパス)を見ていない。**
  `sh:path [ sh:inversePath ... ]` のような形は必須プロパティとして拾わない

### 確かめていないこと

- **大きなテーブルに対する探りのコスト。** `ASK` は 1 行で止まるが、
  `COUNT` は全件を走る。**インデックスの無い列で重くなるはずだが、
  測っていない**
- **SQL Server に対する動作**(ADR-0046 と同じ)
