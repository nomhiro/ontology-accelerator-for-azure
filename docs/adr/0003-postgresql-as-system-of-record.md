# ADR-0003: PostgreSQL と Blob を正本(system of record)とする

- ステータス: 承認済み
- 日付: 2026-08-28

## コンテキスト

[ADR-0002](0002-triple-store-as-rebuildable-projection.md) でトリプルストアを「再構築可能な射影」として扱うと決めた。その前提として、**正本(system of record)をどこに置くか**を決める必要がある。

本プロジェクトが永続化すべきデータは、性質の異なる 2 種類に分かれる。

**(A) グラフとして表現されるデータ**
- 承認済みオントロジー本体(OWL クラス・プロパティ、SHACL シェイプ)
- 不変リビジョンとして保存され、バージョン間の差分を取りたい

**(B) リレーショナルなメタデータ**
- 名前空間の定義、名前空間 × ロールの権限(RBAC)
- 承認履歴と監査証跡(誰が提案・誰が承認・いつ・差分・理由)
- R2RML マッピング(Ontop VKG 用、Phase 3)
- メトリクス定義
- スキャンで得られたカタログ(ソース DB のスキーマ・統計)
- エージェントへ提供したコンテキストのアクセスログ

これらは要求される性質が異なる。(A) は不変で追記のみ、大きなテキストブロブとして扱える。(B) はトランザクション、外部キー制約、インデックス付きの検索、更新が必要である。

加えて、OSS として配布する以上、**ローカル開発でクラウドリソースを必要としない**ことが望ましい。

## 決定

**正本を 2 つに分けて配置する。**

| データ | 保存先 | 形式 |
|---|---|---|
| **オントロジー本体** | **Blob Storage** | バージョン付き TTL(不変リビジョン。コンテンツハッシュ + semver) |
| **取り込んだ文書** | **Blob Storage** | 原形のまま |
| **リレーショナルなメタデータ** | **PostgreSQL Flexible Server** (B1ms) | テーブル |

- PostgreSQL への接続は **Entra 認証によるパスワードレス**とする(Managed Identity)
- **ローカル開発のみ SQLite** を使い、差異は SQLAlchemy で吸収する
- トリプルストア(Fuseki)には**正本を置かない**。Fuseki のデータは常に Blob から再構築できる派生物である
- 書き込みの順序は **「正本に書く → ストアへ射影」** に固定する(Core API のみが実行)

## 根拠

### データの性質に保存先を合わせる

オントロジー本体をリレーショナルなテーブルに分解して格納するのは、意味がない上に有害である。TTL は既にテキストのシリアライゼーションであり、**不変のリビジョンとして丸ごと保存する**のが自然な形である。Blob のバージョニング機能がそのまま「不変リビジョン」の要件に合致する。

逆に、承認履歴や RBAC を Blob 上の JSON で管理するのは無理がある。「この名前空間のこのロールを持つユーザーの一覧」「直近 30 日の承認待ち一覧」といった問い合わせに、トランザクションとインデックスが必要である。

### 監査可能性が中核機能である

AWS 版の訴求は「説明可能・監査可能な意思決定」であり、本プロジェクトでも中核機能として設計する([ADR-0006](0006-ontology-versioning-and-audit.md))。監査証跡には次が要求される。

- **追記のみで改変されない**こと
- **時系列で検索できる**こと
- **外部キーで整合性が保たれる**こと(存在しないリビジョンへの承認記録が作られない)

これはリレーショナルデータベースが最も得意とする領域である。「監査ログを表計算やオブジェクトストレージで管理していた」という状態は、監査可能性を売りにする製品としては説得力を欠く。

### PostgreSQL Flexible Server B1ms を選ぶ理由

- **コストが低い** — `$0.026/時 × 730 = $18.98`。32 GiB ストレージを含めて月 $23([`../cost-estimate.md`](../cost-estimate.md))。オントロジーのメタデータ規模では B1ms で十分である
- **Entra 認証に対応する** — Managed Identity によるパスワードレス接続ができる。接続文字列にパスワードを持たない構成は、Key Vault の運用負担とシークレット漏洩リスクを同時に下げる
- **将来の昇格パスがある** — General Purpose へのスケールアップは `production` プロファイルで対応できる(設計原則 5)

### ローカル開発を SQLite で完結させる

OSS 利用者が最初に試すとき、Azure サブスクリプションを要求しないほうがよい。SQLAlchemy を通せば、開発時は SQLite、デプロイ時は PostgreSQL という構成が現実的なコストで維持できる。

ただしこれは**無条件の利点ではない**。両者の差異(型、同時実行、`ON CONFLICT` の挙動、JSON 型のサポート)はテストで担保する必要がある。この負担を受け入れる判断である(トレードオフ参照)。

### Blob のバージョニングを不変リビジョンの土台にする

コンテンツハッシュ + semver によるリビジョン識別は、Blob のバージョニングと自然に対応する。「あるバージョンのオントロジーを取得する」という操作が、Blob の 1 回の読み取りで済む。エージェントがバージョンを固定して参照する要件([ADR-0006](0006-ontology-versioning-and-audit.md))は、この構造の上に素直に載る。

## 検討した代替案

### Fuseki(トリプルストア)を正本にする

**却下。** これは [ADR-0002](0002-triple-store-as-rebuildable-projection.md) で却下した設計と表裏である。却下理由は 2 点。

1. ストアの永続化の正しさが不可欠になる。ACA の制約下(Azure Files のみ、TDB2 は mmap 依存)ではこれを保証できない
2. **リレーショナルなメタデータの置き場所が別途必要になる。** 承認履歴や RBAC を RDF で表現することは可能だが(実際 PROV-O で監査を表現する)、それを**トランザクショナルに更新し、インデックス付きで検索する**要求に対して、トリプルストアは適した道具ではない。結局 PostgreSQL が必要になり、正本が 2 箱に分かれる。ならば最初から役割を分けたほうが明快である

なお、**監査証跡の表現形式として PROV-O を使うこと**と、**その保存先を PostgreSQL にすること**は矛盾しない。PROV-O は表現の語彙であり、保存媒体の指定ではない([ADR-0006](0006-ontology-versioning-and-audit.md))。

### すべてを PostgreSQL に置く(オントロジー本体も含む)

**却下。** オントロジー本体を `TEXT` カラムや `bytea` として PostgreSQL に入れる案。正本が 1 箱で済むため運用が単純になる利点がある。

却下理由:
- **B1ms + 32 GiB という小さなインスタンスに、リビジョン履歴の全量を溜め込むことになる。** オントロジーは不変リビジョンとして蓄積するため単調増加する。ストレージ拡張はコスト増に直結する
- Blob のバージョニング、ライフサイクル管理、アクセス階層(Cool / Archive)といった、まさにこの用途向けの機能を捨てることになる
- 大きなテキストの読み書きが DB の接続とメモリを占有する

### すべてを Blob に置く(メタデータも JSON で)

**却下。** DB を排してコストを月 $23 削減できる魅力はある。実際、Phase 1 の機能範囲だけを見れば成立しないわけではない。

却下理由:
- **Phase 2 の核心機能(承認フロー、RBAC 強制、監査証跡)が成立しない。** 同時更新の競合、一覧の検索、参照整合性を Blob 上の JSON で実装することになり、実質的にデータベースを自作する
- 「監査可能」を訴求する製品として、監査ログの整合性を保証できない構造は取れない
- Phase 1 で通っても Phase 2 で必ず作り直しになる。**先送りしたコストが利息付きで返ってくる**種類の判断である

### Cosmos DB (NoSQL API) をメタデータストアにする

**却下。** サーバーレス課金でアイドル時のコストを下げられる可能性がある。

却下理由:
- 承認フローと RBAC は**関係を持つデータ**である(名前空間 — ロール — ユーザー — リビジョン — 承認記録)。結合と参照整合性が必要な領域で、ドキュメント指向を選ぶと整合性の維持がアプリコードの責務になる
- RU 課金はクエリパターンによってコストが予測しづらい。月額の見積りを提示する設計目標([`../cost-estimate.md`](../cost-estimate.md))と相性が悪い
- Entra 認証によるパスワードレス接続、SQLAlchemy によるローカル SQLite への切り替えといった利点も失う

### Azure SQL Database をメタデータストアにする

**却下(消極的)。** 技術的には妥当な選択肢である。却下理由は消極的なもので、(a)PostgreSQL のほうが OSS エコシステムでの馴染みがあり、コントリビューターの参入障壁が低い、(b)SQLAlchemy + PostgreSQL / SQLite の組み合わせのほうが、ローカル開発とデプロイの差異が小さい、という判断である。強い技術的な優劣を主張するものではない。

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **正本が 2 箱に分かれる。** PostgreSQL と Blob の間の整合性(オントロジーのリビジョンが Blob にあり、そのメタデータが PostgreSQL にある)を Core API が維持する責任を負う。片方だけ成功した場合の扱い(孤児 Blob、参照先のないメタデータ)を設計する必要がある。**Blob を先に書き、PostgreSQL のコミットを後にする**ことで、失敗時に残るのが「参照されない Blob」(無害、後処理で回収可能)になるようにする
- **PostgreSQL が月 $23 の固定費になる。** minimal 構成の月 $39〜61 のうち、最大の単一項目である
- **SQLite と PostgreSQL の差異がテストの負担になる。** 型、同時実行、`ON CONFLICT`、JSON 型の扱いが異なる。CI では PostgreSQL に対しても実行する構成が必要になる(SQLite だけで通るテストは信頼できない)
- **Blob のバージョニングと PostgreSQL のバックアップという、2 系統のバックアップ設計が必要になる**

### 得られるもの

- **[ADR-0002](0002-triple-store-as-rebuildable-projection.md) の射影設計が成立する。** 正本がストアの外にあることで、トリプルストアの永続化リスクが設計から消える
- **監査可能性を実装できる基盤が整う。** トランザクション、外部キー、時系列検索が使える
- **ストア選定の可逆性が高まる。** Fuseki を Oxigraph に、あるいは利用者持ち込みのストアに替えても、正本は動かない
- **バックアップがマネージドサービスの機能で完結する。** Blob のバージョニングと PostgreSQL の自動バックアップであり、自前のダンプスクリプトを運用しない
- **ローカル開発が Azure サブスクリプションなしで成立する**(SQLite + docker compose の Fuseki + PostgreSQL)
- **シークレットを持たない構成が可能になる**(Entra 認証によるパスワードレス接続)

### 影響を受ける他の決定

- [ADR-0002](0002-triple-store-as-rebuildable-projection.md) — 本決定は ADR-0002 の前提であり、両者は一体の設計である
- [ADR-0006](0006-ontology-versioning-and-audit.md) — 不変リビジョンを Blob に、監査証跡を PostgreSQL に置く配置は本決定に従う
- [ADR-0007](0007-no-purview-dependency.md) — カタログの正本を自前の PostgreSQL に持つことで、Purview への依存が不要になる
