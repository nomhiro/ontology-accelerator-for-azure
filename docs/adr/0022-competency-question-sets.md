# ADR-0022: 想定質問をデプロイ済みの名前空間に紐づける — 受け入れ基準を書き換えられるなら、通ったことは保証にならない

- ステータス: 承認済み
- 日付: 2026-09-11

## コンテキスト

[ADR-0009](0009-ontology-operations.md) 決定6 は「このオントロジーは○○に答えられなければならない」を SPARQL として書き、CI で回すと決めた。`P2B-07`(2026-09-09)はそこまでを実装した — リポジトリ内の YAML(`samples/<ns>.questions.yaml`)を読み、実 Fuseki に対して CI で実行する。

**デプロイ済みの名前空間に質問を紐づける仕組みは、意図的に未決のまま残した**(`P2B-07` の「storage を勝手に発明しない」)。決めるべきことが 3 つあった。

1. **どこに置くか。** TTL と同じ Blob が素直だが、質問は版ごとなのか名前空間ごとなのかが決まっていない
2. **`approve` をブロックするか。** ADR-0009 決定1 は「合意済みの規約はテストとして機械が実行」とし、形式的に決定可能なものはブロッキングとしている。想定質問は「合意済みの規約」に当たるので、落ちたら承認を止めるのが筋である。**ただし承認経路に SPARQL 実行を挟むと、Fuseki が落ちているときに承認できなくなる**(不変条件3 との関係)
3. **誰が書くか。** 名前空間の責任者([ADR-0015](0015-term-owners.md))と同じ主体だと思われるが、当時 `P2B-04` が未着手だった

3 は解けた(`P2B-04` は 2026-09-10 に完了し、名前空間単位の責任者は `namespace_roles` の `owner` である)。残る 1 と 2 を決める。

### 実測して分かったこと

**想定質問は rdflib で評価できる。** 同梱サンプル(`samples/retail-core.ttl`、トリプル 60 件)に対して同梱の質問 11 件を rdflib で評価し、**Fuseki と同じ 11/11** になることを確認した。所要時間は次のとおり。

| 測ったもの | 結果 |
|---|---|
| TTL の解析(トリプル 60 件) | 0.021 秒 |
| 質問 11 件の評価(合計) | 0.63 秒(初回クエリの 0.48 秒を含む) |
| 質問 **200 件**の評価(サンプルの質問を複製) | **1.24 秒** |
| 3 重の直積 `?a ?b ?c . ?d ?e ?f . ?g ?h ?i` を**全行取得** | 216,000 行 / **9.68 秒** |
| 同じクエリの**先頭 1 行だけ**を取得 | **0.000 秒** |
| 0 行になる直積(全走査が必要)`… FILTER(?a = <urn:nope>)` | 0 行 / **7.69 秒** |

**読み取れることが 2 つある。**

1. **行数を数えず「1 行以上あるか」だけを見れば、コストが桁で変わる。** 判定に必要なのは存在の有無だけである(`ask_true` は真偽、`non_empty` / `empty` は 0 行かどうか)。全行を materialize する理由が無い
2. **それでも 1 件のクエリを打ち切ることはできない。** rdflib にクエリタイムアウトは無く、「全部走査して 0 行」になる質問は最後まで走る。トリプル 60 件で 7.69 秒なので、実用規模では実質的に無限になりうる

## 決定

### 1. 想定質問は名前空間に紐づく不変改訂とし、PostgreSQL に置く

`competency_question_sets` テーブルを追加する。1 行 = 1 改訂。

| 列 | 意味 |
|---|---|
| `namespace` | 名前空間(`namespaces` への外部キー、`ON DELETE CASCADE`) |
| `revision` | 名前空間ごとに 1 から増える連番。**有効なのは最大の改訂** |
| `content` | 質問ファイル(YAML)の本文そのまま |
| `content_hash` | 本文の SHA-256 |
| `question_count` | 質問の件数(一覧を返すときに本文を解析しないため) |
| `created_by` / `created_at` / `reason` | 誰が・いつ・**なぜ**。`reason` は必須 |

**改訂は書き換えない**(不変条件7 と同じ形)。**Blob には置かない。**

Blob に置かない理由:

- **想定質問は射影されない。** Blob は「ローダが読んでストアへ載せる中身」の置き場である。TTL がそこにあるのはエージェントに渡す中身だからで、受け入れ基準はそうではない
- **Blob → PostgreSQL の順序を挟むと、孤児 Blob という新しい故障モードを作る**(`P2B-12` と同じ形の TOCTOU)。PostgreSQL だけなら改訂と監査記録を**同一トランザクション**で書ける
- 本文が小さい(同梱サンプルの質問ファイルは 6.5 KB)。上限は 256 KiB とする

### 2. 版ごとではなく名前空間ごとに 1 つ

**版ごとにすると、新しい版が自分の合格条件を自分で書き換えられる。** 受け入れ基準を提案者が書き換えられるなら、**テストが通ったことは何の保証にもならない**。これは四眼原則([ADR-0014](0014-namespace-rbac.md) 決定4)と同じ論点である。

「この版だけ特別な質問を足したい」という要求は、**質問集合の改訂**として全体に足すべきものである(そうすれば以降の版もその基準で検査される)。1 つの版だけを通すために基準を緩めるのは、まさに防ぎたいことである。

### 3. 承認時に評価して落ちたら 422 でブロックする。評価は正本の TTL に対してインメモリで行い、ストアには問い合わせない

**これがこの ADR の技術的な核心である。** ストアに問い合わせると 3 つ壊れる。

1. **順序が壊れる。** `approve` の時点でその版はまだ射影されていない。射影の後に検査すると「既定グラフに載った後の検査」になり、SHACL 検証を状態遷移の**前**に置いた理由(`P2A-05`)がそのまま当てはまって意味が無くなる
2. **可用性の向きが逆になる。** 不変条件3 は「射影の失敗は正本への書き込みを失敗させない」である。承認をストアの可用性に依存させるのは、この不変条件が守ろうとしているものの逆である
3. **評価対象が広がる。** ストアは複数の版を名前付きグラフで持つ。検査したいのは**いま承認しようとしている版**である

rdflib で評価できることは実測した(上記)。評価環境は**射影後の姿を写す** — その版の TTL を、既定グラフと**その版自身の名前付きグラフ**(`<graphBase>/<ns>/<version>`)の両方に読み込む。ADR-0010 決定5・6 が「承認済み現行版は既定グラフと名前付きグラフの両方に載る」と決めているので、これが忠実な写しになる。

**「評価できなかった」を合格にしない。** 予算超過・rdflib の例外は **502** で返す(SHACL の「検証できなかった」と同じ形)。落ちた質問があるのは **422** である。この 2 つを混ぜない — 運用者が取るべき対処が違う。

### 4. 判定は「1 行以上あるか」で行い、行数を数えない

実測(上記)により、全行の materialize は避ける。`non_empty` / `empty` の判定に必要なのは存在の有無だけである。216,000 行の直積でも先頭 1 行は 0.000 秒で取れる。

**報告の文言も「1 行以上」「0 行」にする。** 「3 行」と書けるふりをしない(数えていないので)。ストア経由の実行(`run_questions`、CI とローカルの CLI)は Fuseki が全件返すので従来どおり件数を出す。

### 5. 評価には壁時計の予算を設け、超えた質問は「評価していない」として報告する

`EVALUATION_BUDGET_SECONDS = 30`。質問の**間**で予算を確認し、超えたら残りを `not_evaluated` として返す。`approve` は `not_evaluated` が空でなければ 502 にする(**「評価していない」を合格にしない**)。

**1 件のクエリの途中では打ち切れない。** 実測のとおり rdflib にタイムアウトは無い。そのため呼び出し側は `asyncio.wait_for` で待つのをやめる(**リクエストはハングしない**)。ただしスレッドはそのクエリが終わるまで走り続ける。これは受け入れるコストとして明記する(下記)。

### 6. 質問集合を書けるのは `owner` のみ。読めるのは `data-analyst`

| 操作 | 必要なロール |
|---|---|
| 質問集合を読む / 改訂の一覧 / 版に対して試す | `data-analyst` |
| 新しい改訂を足す | **`owner`** |

`approve` は `maintainer` 以上である。**承認する主体が合格条件も書き換えられると検査が意味を失う**ので、書き込みは 1 段上に置く。

**ただしこれは「書き換えを防ぐ」仕組みではなく「書き換えが見える」仕組みである。** ロールは階層なので(`data-analyst` < `data-steward` < `maintainer` < `owner`)、**`owner` は基準を書き換えて自分で承認できる。** その代わりに:

- 改訂は不変で、履歴が残る
- `reason` が必須である
- すべての改訂が**追記専用の監査証跡**に残る(`action="questions-revised"`)
- 改訂で**減った質問の id** を監査の記録に残す。基準を緩めたことが一覧できる

**防止ではなく可視化であることを、ここに明記しておく。** 質問集合にも四眼原則を掛けるべきかは未解決として残す(ADR-0014 決定4 は承認について四眼原則を決めたが、基準の変更については決めていない)。

### 7. 質問集合が無い名前空間は承認をブロックしない

**不変条件11(権限の既定は拒否)はここには適用しない。** これは権限ではない。

「質問を書いていない」は「**基準を定めていない**」であって「基準を満たしていない」ではない。定めていない名前空間の承認を止めると、**この機能を入れた瞬間に既存のすべての名前空間が承認不能になる**。マイグレーションで既定の質問集合を発明することもできない(何を要求すべきかはその名前空間の持ち主しか知らない)。

**その代わり、定めていないことを健全性指標に出す。** `GET /namespaces/{ns}/health` に `competency_question_count` を足す([ADR-0020](0020-health-metrics.md) の枠組み)。同 ADR の言葉で言えば「測っていないものは、致命的になるまで見えない」。

### 8. どの改訂で合格したかを監査に記録する

`approved` の監査イベントの `reason` に、評価に使った改訂番号と結果を追記する。**後から「この版はどの基準で通ったのか」を辿れなければ、監査証跡として不完全である**(基準が変わりうるので、版だけでは復元できない)。

### 9. 状態を変えずに試せる口を用意する

`POST /namespaces/{ns}/versions/{v}/questions/run` は評価して報告だけを返す(SHACL の `.../validate` と同じ形)。レビュー中に「この版はいま基準を満たすか」を確認できる。**これが無いと、承認を試して 422 を食らうまで分からない。**

## 検討した代替案

### 質問集合を Blob に、TTL と並べて置く(`versions/<ns>/<version>.questions.yaml`)

**却下。** `P2B-07` が最初に想定した形で、TTL と同じ場所にあるのは素直である。

却下理由は 2 つ。**(a) 版ごとになる**ので決定2 に反する(提案者が自分の合格条件を書ける)。**(b) 射影されない中身のために Blob → PostgreSQL の順序を導入する**ことになり、Blob だけが残る孤児という故障モードを新しく作る。名前空間ごとに 1 つ(`versions/<ns>/_questions.yaml`)なら (a) は避けられるが、(b) と「改訂の履歴と監査を同一トランザクションで書けない」が残る。

### 承認をブロックせず、報告に留める(意味的差分と同じ扱い)

**却下。** 実装が単純になり、ストアの可用性とも切り離せる。

却下理由: **ADR-0009 決定1 が「合意済みの規約はテストとして機械が実行する」と決めている。** 想定質問はまさにそれである。落ちても通るなら、それは「合意済みの規約」ではなく「参考情報」である。意味的差分をブロックしないのは**差分に合否が無い**からで(ADR-0016 決定6)、想定質問には合否がある。

### 承認時に Fuseki へ射影してから評価する(一時的なグラフやデータセットを使う)

**却下。** ストアと同じエンジンで評価できるので、**判定が実行環境で食い違わない**という強い利点がある。

却下理由: 決定3 の 3 点がそのまま当てはまる。加えて、**一時データセットを作る操作は名前空間名の境界(不変条件5)に新しい入口を作る**。承認のために一時的なデータセット名を組み立てるコードは、そこを間違えると名前空間の分離を破る。得られるものに対して払う代償が大きい。

### 質問集合の SPARQL に `GRAPH` 句を禁じる

**却下。** インメモリ評価とストア評価の食い違いを構造的に消せる。

却下理由: **ストア経由の実行(CI とローカル CLI)との仕様が分岐する。** 同じ質問ファイルが場所によって受理されたり拒否されたりするのは、この製品がいちばん避けたい「静かな食い違い」の温床である。決定3 のとおり**評価環境を射影後の姿に合わせる**ことで、実用上の食い違いを小さくする方を採る。

**残る食い違いは明記する** — 質問が**別の版**のグラフ IRI を直書きしていると、インメモリ評価では 0 行になる(その版はそこに無い)。想定質問は「いま承認しようとしている版が基準を満たすか」を問うものなので、他の版のグラフ IRI を直書きする使い方は支持しない。

### 評価を別プロセスで行い、タイムアウトで殺す

**却下(今は)。** これだけが**本当に打ち切れる**唯一の方法である。

却下理由: プロセス起動のコスト(実測で 0.5〜1 秒)と実装の複雑さ(TTL と質問の受け渡し、結果の直列化、`uv run` の前提)を、**質問集合を書けるのが `owner` に限られている**という前提に対して払う理由が今は無い。承認のリクエスト自体はハングしない(決定5)ので、症状は「その承認が 502 になる」と「スレッドが 1 本しばらく走り続ける」に留まる。

**この判断は、質問集合をより広い主体が書けるようにしたら見直す。** バックログに記録する。

### 質問集合を MCP でエージェントに見せる

**却下(スコープ外)。** 受け入れ基準はオントロジーの持ち主とレビュー担当のためのものである。エージェントに「このオントロジーはこういう問いに答えられる」と伝える価値はありうるが、それは**質問文の一覧**であって SPARQL ではない。要求が出てから決める。

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **`approve` に SPARQL の評価が入る。** 実測で質問 200 件が 1.24 秒。承認は低頻度なので許容するが、**承認の応答時間が質問集合の書き方に依存する**ようになった
- **1 件の病的なクエリを打ち切れない。** 「全走査して 0 行」になる質問はトリプル 60 件で 7.69 秒(実測)。実用規模では実質的に無限になりうる。リクエストはハングしないが、**スレッドが 1 本走り続ける**。書けるのが `owner` に限られていることが唯一の緩和である
- **同じ質問を 2 つのエンジンで評価する。** 承認時は rdflib、CI とローカル CLI は Fuseki である。**判定が食い違う余地が構造的に残る**。同梱サンプルは両方で 11/11 を確認しているが、これは一般の保証ではない
- **`empty` の質問は空振りでも通る。** 何にも当たらないクエリは 0 行なので合格になる。SHACL の「制約名のタイプミスは検出できない」(`P2A-05`)と同じ family の既知の限界である。`expect` と応答の形が噛み合わないこと(ASK と SELECT の混同)は検出できるが、意図した対象に当たっているかは検出できない
- **`owner` は基準を書き換えて自分で承認できる**(決定6)。防止ではなく可視化である
- **質問集合が無い名前空間は素通りする**(決定7)。健全性指標で見えるだけである

### 得られるもの

- **受け入れ基準が名前空間の資産になった。** リポジトリの中のファイルではなく、デプロイ済みの名前空間に紐づいて、改訂の履歴と理由を持つ
- **基準を提案者が書き換えられない**(決定2・6 の範囲で)。「テストが通った」に意味がある
- **承認がストアの可用性に依存しない**(決定3)。不変条件3 の向きと整合する
- **「評価できなかった」を合格にしない**(決定5)。ADR-0016 決定5 / ADR-0020 決定3 / [ADR-0021](0021-owl-reasoning-in-ci.md) 決定1 に続く 4 例目である
- **どの基準で通ったかが監査から辿れる**(決定8)

### 影響を受ける他の決定

- [ADR-0009](0009-ontology-operations.md) 決定6 — 「CI で回す」を「デプロイ済みの名前空間にも紐づけ、承認をブロックする」まで進めた
- [ADR-0010](0010-approval-and-projection.md) — `approve` の処理順序に想定質問の評価が入った(SHACL → 廃止 → **想定質問** → 状態遷移)
- [ADR-0014](0014-namespace-rbac.md) 決定4 — 四眼原則は承認について決めているが、**基準の変更については決めていない**。決定6 でそのことを明記した
- [ADR-0020](0020-health-metrics.md) — 健全性指標に `competency_question_count` を足した(7 項目目)
- [ADR-0015](0015-term-owners.md) — 名前空間単位の責任者(`owner` ロール)が、基準を定める主体でもあることを確定させた

## 補記: 「防止ではなく可視化」から、特定の経路だけ防止するへ (2026-09-12、`P2B-16`)

決定6 は「質問集合にも四眼原則を掛けるべきかは未解決」として終わっていた。
[ADR-0029](0029-criteria-authorship.md) で決着を付けた。

**四眼原則を質問集合そのものには掛けない**(publish → submit → approve の
ライフサイクルを付けない)。機構が 2 倍になるうえ、最初の改訂を誰が承認するか
が決まらず、**そして塞ぐべき経路を塞がない**。

**代わりに `approve` が「審査される側が基準を書き換えた」ことを拒否する。**
条件は「有効な改訂の `created_by` == その版の `created_by` かつ その改訂の
`created_at` >= その版の `created_at`」である(422)。

四眼原則(ADR-0014 決定4)は「publish した主体は approve できない」なので、
**残っていた穴は「著者が基準を緩め、同僚が承認する」**だった。一人が全部やる
形ではないため四眼原則の考え方では捉えられない — 問題は
**「審査される成果物の著者が、その合格条件を書いた」**ことにある。

一方で**「基準を先に定めた責任者が、他人の版を承認する」は止めてはいけない**。
それは統制のあるべき姿である。時刻の境界がこの 2 つを分ける。

決定6 の「可視化」は**防止が入った後も残す**。`require_two_person_approval` が
無効な名前空間では止まらないが、レビュー用の口
(`POST .../versions/{v}/questions/run`)は `criteria_self_revised` として
事実を返す(ADR-0029 決定6)。
