# ADR-0023: 領域間マッピング — 「統合しない」を、論理的帰結を持たない述語で担保する

- ステータス: 承認済み
- 日付: 2026-09-11

## コンテキスト

[ADR-0009](0009-ontology-operations.md) 決定8 はこう決めた。

> 営業の「優良顧客」と経理の「優良顧客」が違うとき、**一つに統合しない**。名前空間を分けたまま、**マッピングを明示的な成果物として管理**する(SKOS の `closeMatch` / `exactMatch`、または `owl:equivalentClass`)。マッピング自体がレビュー対象になるので、意見の相違が消されずに記録される。

方針だけが決まっており、次が未決だった。

1. **どの述語を許すか**(決定8 は `owl:equivalentClass` も候補に挙げている)
2. **どこに置くか**(TTL に書くのか、PostgreSQL に構造化して持つのか)
3. **どちらの名前空間に属するか**
4. **逆向きを自動で作るか**
5. **トリプルストアに射影するか**

[ADR-0015](0015-term-owners.md) は用語の責任者を `base_iri` 配下に限定せず、外部 IRI にも置けるようにした。その理由がまさにこの決定8 である —「自分の名前空間から外部語彙への `skos:closeMatch` を張るとき、そのマッピングの妥当性について説明責任を負うのは**張った側**である」。器の一部は既に入っている。

### 実測: `owl:equivalentClass` は「統合」そのものである

決定8 が挙げた 2 つの選択肢が同じものかを、`P2B-01` で入れた ELK で確かめた。営業(`a:`)と経理(`b:`)の「優良顧客」を、**互いに素なクラスの下に置いたまま**結ぶ。

```turtle
b:Wholesale owl:disjointWith a:Retail .
a:GoodCustomer rdfs:subClassOf a:Retail .
b:GoodCustomer rdfs:subClassOf b:Wholesale .
# ここだけを差し替えて比較した
a:GoodCustomer owl:equivalentClass b:GoodCustomer .   # 案 1
a:GoodCustomer skos:exactMatch     b:GoodCustomer .   # 案 2
```

| 結んだ述語 | ELK の結論 |
|---|---|
| `owl:equivalentClass` | **充足不能クラス 2 件**: `a:GoodCustomer` と `b:GoodCustomer` |
| `skos:exactMatch` | 充足不能クラスなし |

**`owl:equivalentClass` で結んだ瞬間に、両方のクラスがインスタンスを持てなくなった。** 片方が壊れるのではなく**両方**である。「統合しない」という決定8 の趣旨に反するだけでなく、**壊れ方として最悪の形**(どちらの領域も自分の用語を使えなくなる)をとる。

さらに悪いことに、**この壊れ方は承認では止まらない。** [ADR-0021](0021-owl-reasoning-in-ci.md) 決定5 により推論器は CI にしか居らず、CI が検査するのはこのリポジトリの同梱物だけである。つまり `owl:equivalentClass` をマッピングの述語として提供すると、**承認は通るのに両方のクラスが使えなくなる**版を作れてしまう。

## 決定

### 1. マッピングの述語は SKOS の 5 つに限る。`owl:equivalentClass` と `owl:sameAs` は提供しない

これがこの ADR の中心である。**ADR-0009 決定8 が挙げていた `owl:equivalentClass` を却下する。**

| 述語 | 意味 | 性質 |
|---|---|---|
| `skos:exactMatch` | 高い信頼度で交換可能 | 対称・**推移的** |
| `skos:closeMatch` | 近いが交換可能とは限らない | 対称・**推移的でない** |
| `skos:broadMatch` | 相手の方が広い | `narrowMatch` の逆 |
| `skos:narrowMatch` | 相手の方が狭い | `broadMatch` の逆 |
| `skos:relatedMatch` | 関連がある | 対称 |

**`owl:equivalentClass` を却下する理由**は上記の実測である。**`skos:exactMatch` との違いは「強さ」ではなく「論理的帰結を持つかどうか」である** — `owl:equivalentClass` はクラスの外延の同一性を主張するので、推論器が一方の制約を他方へ流し込む。SKOS のマッピング述語は概念の間の関係であって外延の同一性ではないため、この流し込みが起きない。

**`skos:exactMatch` は `owl:sameAs` ではない。** SKOS が両者を分けているのは、まさに意図しない帰結を避けるためである。この区別がこの製品の設計の核(領域をまたぐ相違を消さない)と一致する。

**`owl:equivalentClass` を書きたい利用者を止めはしない** — 自分のオントロジーの TTL に書くのは自由である(それはその名前空間の内容であって、マッピングの仕組みの話ではない)。提供しないのは**マッピングの述語として**である。

### 2. PostgreSQL に構造化して持つ。TTL には書かない

`term_mappings` テーブルを追加する。理由が 3 つある。

1. **TTL に書くとマッピングが不変リビジョンに閉じ込められる。** マッピングは「2 つの名前空間の関係」であり、片方の版が上がるたびに書き直すものではない(ADR-0006 の不変リビジョンは**オントロジーの内容**についての決定である)
2. **ライフサイクルが違う。** 決定8 は「マッピング自体がレビュー対象になる」と言う。オントロジーの承認フロー(`draft` → `in-review` → `approved`)とは別の軸である
3. **決定1 の壊れ方を構造的に防ぐ。** マッピングが TTL に入らなければ**推論器の視界に入らない**。述語の検査を一箇所(API)で守れば、論理的帰結を持つマッピングは物理的に作れない

### 3. マッピングは「張った側」の名前空間に属する。逆向きは自動で作らない

これが 2 番目に重要である。

**「A が B に `exactMatch` と言っている」と「B が A に `exactMatch` と言っている」は別の事実である。** 逆向きを自動生成すると、**相手の名前空間に、相手が宣言していない主張が現れる**。決定8 の「意見の相違が消されずに記録される」に正面から反する。

代わりに**両方向から見えるようにする**。

- `GET /namespaces/{ns}/mappings` — その名前空間が**張った**マッピング(outgoing)
- `?direction=incoming` — 他の名前空間から**その名前空間へ張られた**マッピング
- 各マッピングに `reciprocal`(相手側も同じ用語ペアを宣言しているか)を添える

**片側だけの主張は異常ではない。** 相手がまだ宣言していないだけである。だからブロックも警告もしない。

### 4. 両側が違う述語を宣言したら「争われている」として報告する。消さない

A→B が `exactMatch` で B→A が `closeMatch` なら不整合である。しかし**どちらかを消してはいけない**(決定8)。

- 両方をそのまま保持し、`disputed: true` を添える
- 健全性指標に `disputed_mapping_count` を出す([ADR-0020](0020-health-metrics.md) の枠組み)

**これが決定8 の「意見の相違が消されずに記録される」の実装である。** 自動で片方に寄せる実装は、相違を消す実装である。

### 5. 宣言は `owner`、参照は `data-analyst`。理由は必須

| 操作 | 必要なロール |
|---|---|
| マッピングの一覧(outgoing / incoming) | `data-analyst` |
| マッピングの宣言・取り消し | **`owner`** |

**`maintainer` ではなく `owner` にする。** マッピングは**相手の領域の意味について何かを主張する**行為であり、ADR-0015 が「マッピングの妥当性について説明責任を負うのは張った側」と書いた責任がここに発生する。名前空間単位の説明責任は `owner` ロールが担う(ADR-0015)。

`reason` は必須である。「なぜこれが同じ(近い)と言えるのか」が無いマッピングは、レビュー対象になりえない。

### 6. ターゲット用語の実在は検査しない

[ADR-0015](0015-term-owners.md) 決定4 と同じ理由である。ストアは再構築可能な射影であって正本ではないので、存在確認は正本への書き込みを射影の可用性に依存させる(不変条件2・3 が禁じている向き)。

**加えて、外部語彙へのマッピングが正当な主用途である。** SKOS や schema.org の用語は、このシステムのどの名前空間にも存在しない。実在を要求すると、いちばん使いたい形が使えなくなる。

### 7. トリプルストアには射影しない。API と MCP で提供する

- **マッピングはどの版にも属さない**ので、版の名前付きグラフに混ぜられない
- 既定グラフは常に単一の承認済み版である([ADR-0010](0010-approval-and-projection.md) 決定6)。マッピングを既定グラフに混ぜると、その決定が崩れる
- 専用グラフ(`urn:ontology:mapping/...`)に載せる案は、**エージェントに `GRAPH` 句を書かせることになる**。「マッピングはこのグラフにある」という知識をエージェントに要求するのは、MCP ツールで渡すより悪い

MCP の `term_mappings` ツールで渡す。射影するかは要求が出てから決める(`P2B-17` として記録)。

**追記(2026-09-12、`P2B-17`)**: [ADR-0031](0031-mapping-export.md) で決着した。**射影しない。** 代わりに `GET /namespaces/{ns}/mappings/export` が **SKOS のトリプルと記述ノードを含む Turtle** を返す(ADR-0026 の PROV-O 書き出しと同じ形)。射影しない理由は 4 つあり、うち 2 つは `P2B-18` を実装した後に見えたもの — **終点の生死(`target_status`)が射影したグラフでは伝わらない**こと、そして**権限の粒度がデータセット単位でしか持てない**ことである。

## 検討した代替案

### `owl:equivalentClass` も許す(ADR-0009 決定8 が挙げていた案)

**却下。** 決定1 の実測が理由である。`equivalentClass` は論理的帰結を持ち、互いに素なクラスの下にある 2 つの用語を結ぶと**両方が充足不能になる**。しかも承認はそれを止めない(推論器は CI にしかいない)。

**「利用者が正しく使えばよい」という反論は成立しない。** マッピングは**領域が違う**から張るものであり、領域が違えば制約が食い違うのが普通である。「食い違っている 2 つを結ぶ」がこの機能の主用途なので、論理的帰結を持つ述語は構造的に危ない。

### マッピングを TTL に書く(オントロジーの一部として管理する)

**却下。** W3C 標準忠実という路線には合っており、SPARQL でそのまま引けるという強い利点がある。

却下理由: **不変リビジョンに閉じ込められる**(決定2)。マッピングは片方の版が上がるたびに書き直すものではない。加えて、TTL に入れると推論器の視界に入るので、決定1 の壊れ方が復活する。

### 逆向きのマッピングを自動生成する(`exactMatch` は対称なので)

**却下。** SKOS の定義上 `exactMatch` は対称なので、形式的には正しい。

却下理由: **相手が宣言していない主張を相手の名前空間に作る**(決定3)。決定8 の趣旨は相違を残すことである。「営業は同じだと言っているが経理はまだ何も言っていない」という状態は、**記録されるべき事実**である。

### 両側の `owner` の承認を要求する(合意を強制する)

**却下。** マッピングが「両者の合意」になるので、意味としては強い。

却下理由: **合意を強制すると、合意できない相違が記録されなくなる。** 決定8 が守ろうとしているのは相違の記録であり、合意の強制はその逆である。

**この案は魅力的で、将来 `agreed` フラグとして足す価値がある**(相互に宣言され、かつ述語が一致している状態を「合意」と呼べる)。決定3 の `reciprocal` は既にその材料である。

### マッピング専用の名前空間を作る

**却下。** マッピングがどちらにも属さないという性質を素直に表せる。

却下理由: **名前空間は RBAC とデータセットの境界である**(不変条件5、ADR-0014)。マッピングのために名前空間を 1 つ作ると、「そのマッピング名前空間の `owner` は誰か」という権限の設計が二重になる。決定3 の「張った側に属する」なら既存の権限がそのまま効く。

### 推移的閉包を計算して返す

**却下(スコープ外)。** 「A→B→C」から「A→C」を導ければ便利である。

却下理由: **`exactMatch` は推移的だが `closeMatch` は推移的でない**(決定1 の表)。混ぜて閉包を取ると、**近いだけの用語を交換可能として扱う**誤った同一視を作る。述語ごとに閉包の規則が違うので、素朴な実装は静かに間違う。要求が出てから、述語ごとの規則を明示して設計する。

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **`owl:equivalentClass` を使いたい利用者には応えない。** 論理的な同一視が本当に必要な場合(同じ組織の中で用語を統合すると決めた場合)は、マッピングではなく**オントロジー本体で表現する**ことになる。それはこの機能の対象外である
- **マッピングが SPARQL で引けない**(決定7)。エージェントは MCP ツール経由でしか見えない。**書き出し(`P2B-17`、[ADR-0031](0031-mapping-export.md))で自分のストアへ読み込めるようにしたが、このシステムのストアからは引けないままである**
- **片側だけの主張が大量に溜まりうる。** `reciprocal` で見えるが、集計はしていない(初期状態では片側だけが正常なので、集計すると雑音になる)
- ~~**マッピングの先が廃止されても気づけない。**~~ **解決した**(2026-09-12、`P2B-18`、[ADR-0030](0030-mapping-target-lifecycle.md))。一覧の各件に終点の生死(`target_status`)が付く。権限の論点は「**相手の名前空間を読む権限が無ければ `unknown` を返す**」で決着した(`active` とは言わない)
- **推移的閉包が無い。** 多段のマッピングは呼び出し側が辿る

### 得られるもの

- **「統合しない」が構造的に担保される。** 述語の制限(決定1)とマッピングを TTL に入れないこと(決定2)の二重で、論理的帰結を持つマッピングが作れない
- **相違が消えない。** 逆向きを自動生成せず(決定3)、争いを両方保持する(決定4)
- **説明責任が記録される。** `owner` が `reason` 付きで宣言する(決定5)。ADR-0015 が用語の責任者を外部 IRI にも置けるようにした理由がここで回収される
- **実測で判断した。** 決定8 が並列に挙げていた 2 つの選択肢が**同じものではない**ことを、推論器で確かめた

### 影響を受ける他の決定

- [ADR-0009](0009-ontology-operations.md) 決定8 — **補記を追加した。** `owl:equivalentClass` を候補から外す
- [ADR-0015](0015-term-owners.md) — 用語の責任者を `base_iri` 配下に限定しなかった理由がここで回収された
- [ADR-0020](0020-health-metrics.md) — 健全性指標に `disputed_mapping_count` を足した(8 項目目)
- [ADR-0030](0030-mapping-target-lifecycle.md) — 決定6(実在を検査しない)は**維持**したまま、**読むときに終点の生死を返す**ようにした
- [ADR-0021](0021-owl-reasoning-in-ci.md) — 推論器が CI にしかいないことが、決定1 の却下理由の一部になっている
