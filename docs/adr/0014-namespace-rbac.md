# ADR-0014: 名前空間 RBAC と四眼原則

- 状態: 採用
- 日付: 2026-09-09
- 関連: [ADR-0006](0006-ontology-versioning-and-audit.md)（監査可能性）、[ADR-0009](0009-ontology-operations.md) 決定4（責任者）、[ADR-0010](0010-approval-and-projection.md)（承認の権限を Phase 1 では強制できない）、[ADR-0012](0012-mcp-to-core-api-authentication.md)（呼び出し元の識別子が Core API まで届く）、バックログ `P2A-06`

## コンテキスト

Phase 1 は**認証済みの呼び出し元が誰でも何でもできる**状態である。ADR-0010 は「機構を先に作り、権限を後から締めるのは順序として妥当（逆はできない）」としてこれを意図的に受け入れ、README に「記録は正しく、強制が無い」と明記した。

締める前提は揃った。

- `NamespaceRole`（`owner` / `maintainer` / `data-steward` / `data-analyst`）と `PlatformRole`（`platform-admin` / `platform-viewer`）は語彙として定義済み
- [ADR-0012](0012-mcp-to-core-api-authentication.md) により、**エージェント経路でも呼び出し元の識別子が Core API まで届く**。MCP のマネージド ID で呼ぶ設計にしていたら、この ADR は成立しなかった
- 設計原則「名前空間×ロールは PostgreSQL で管理し API で強制する」

決めるべきことは 4 つある。

1. **どのロールが何をできるか**（権限マトリクス）
2. **四眼原則をどう強制するか。** 提案者と承認者を別人にする要求（ADR-0010）と、**運用者 1 人のデプロイで同梱サンプルを承認する**必要（Phase 1 の完了条件）が正面から衝突する
3. **付与が 1 件も無い既存のデプロイをどうするか。** 素朴に強制すると、更新した瞬間に誰も何もできなくなる
4. **`platform-admin` は名前空間の権限を飛び越えられるか**

## 決定

### 1. 権限は「名前空間ごとの付与」で決める。テーブルは 1 つ

`namespace_roles`（`namespace`, `principal_id`, `role`, `granted_by`, `granted_at`）。`(namespace, principal_id)` を一意にする。1 人が 1 つの名前空間に持つロールは 1 つである（複数ロールの合成は考えない。順序付きなので上位が下位を含む）。

`principal_id` は Entra の**オブジェクト ID**（`Principal.object_id`）である。UPN や表示名ではない。UPN は変わりうるし、ゲストの `#EXT#` 形式は書き換えの罠がある（`P1-11` で実際に踏んだ）。

### 2. 権限マトリクス（上位は下位のすべてを含む）

| 操作 | 必要なロール |
|---|---|
| SPARQL 読み取り / 版の一覧 / 決定記録の参照 | `data-analyst` |
| SHACL 検証（`validate`）| `data-analyst` |
| `publish` / `submit` | `data-steward` |
| `reject` | `maintainer` |
| `approve` | `maintainer` |
| 名前空間の削除 | `owner` |
| ロールの付与・取り消し | `owner` |
| 名前空間の作成 | （名前空間がまだ無いので）`platform-admin` か、後述の自己奉仕 |
| `POST /admin/reconcile` | `platform-admin` |

順序は `data-analyst` < `data-steward` < `maintainer` < `owner`。

**`reject` を `maintainer` にしたのは意図的である。** 却下は「この提案を現行にしない」という決定であり、承認と同じ重みの判断である。提案者が自分の提案を取り下げる操作とは別物なので、`data-steward` には与えない（取り下げが必要なら新しい版を出せばよい。オントロジーは不変リビジョンである）。

### 3. 名前空間を作った主体は自動的に `owner` になる

作成と同じトランザクションで付与する。そうしないと**作った本人が何もできない名前空間**ができる。

名前空間の作成そのものは `platform-admin` を要求する。ただし `AUTH_MODE=disabled`（ローカル開発）では `Principal.local_dev()` が `platform-admin` を持つので開発は止まらない。

### 4. 四眼原則は**名前空間ごとの設定**にする。既定は「有効」

`namespaces` に `require_two_person_approval`（既定 `true`）を持たせる。有効なら、**その版を `publish` した主体は `approve` できない**。

**なぜ設定にするか。** 四眼原則を無条件に強制すると、運用者 1 人のデプロイ（`azd up` の `postdeploy` が同梱サンプルを publish → submit → approve する経路）が動かなくなる。これは Phase 1 の完了条件そのものなので壊せない。

**なぜ既定を「有効」にするか。** 規制産業での採用可否を左右する要件（ADR-0006 のコンテキスト）であり、**安全側を既定にする**。緩めるのは明示的な選択であるべきで、逆（既定で緩く、締めるのを忘れる）は事故になる。

**同梱サンプルの名前空間は `require_two_person_approval: false` で作る。** `postdeploy` が明示的にそう指定する。**「デモのために既定を緩める」のではなく「デモの名前空間だけを緩める」**。README に、実運用の名前空間では有効のままにすることを書く。

### 5. `platform-admin` は名前空間の権限を飛び越えられる。ただし四眼原則は飛び越えられない

`platform-admin` はすべての名前空間で `owner` として扱う。運用者がロックアウトから回復する経路が必要である（`owner` が退職した名前空間など）。

**しかし四眼原則は飛び越えられない。** `platform-admin` が自分で publish したものを自分で approve できてしまうと、四眼原則は「管理者以外への制約」に成り下がる。規制対応の文脈では意味を失う。

### 6. 付与が 1 件も無い名前空間は「誰も権限を持たない」として扱う。移行は明示的に行う

**暗黙のフォールバック（付与が無ければ全員に許可する等）を作らない。** それは「強制していない」を「強制している」と誤認させる、この製品で最も避けたい形である。

既存のデプロイのために、`namespaces.created_by` から `owner` を 1 件付与する**マイグレーション**を書く。`created_by` は Phase 1 から記録されているので、作成者が owner になる。作成者が不明な行があれば、そこは付与されないまま残り、`platform-admin` が回復させる。

## 根拠

### なぜ Entra のアプリロールだけで済ませないのか

Entra のアプリロールはテナント全体に対する粗粒度の属性であり、**「名前空間 × ロール」の組み合わせを表現できない**（名前空間は動的に増える）。アプリロールを名前空間ごとに作る運用は、名前空間の作成に Entra への書き込み権限を要求することになり、`R5`（OSS 利用者にアプリ登録権限が無い場合の障壁）を悪化させる。

そのため粗粒度（`platform-admin` か否か）は Entra、細粒度（名前空間 × ロール）は PostgreSQL に置く。これは設計原則として最初から宣言していた方針である。

### なぜ四眼原則を `publish` 主体との比較で判定するのか

「提案者」を誰と見るかには選択肢がある。`created_by`（publish した主体）か、`submitted` を行った主体か。

**`created_by` を採る。** 版の内容を作った主体が提案者であり、`submit` は「レビューに出す」という事務的な操作でありうる（他人の draft を代わりに submit することは自然に起こる）。内容の責任は publish 側にある。

なお `audit_events` には両方が記録されているので、後から別の解釈で監査することは可能である。

### なぜ役割を 4 つに保つのか

`NamespaceRole` は既に 4 つ定義されている。増やしたくなる誘惑（`reviewer` を別に作る等）はあるが、**ロールが増えるほど「誰が何をできるか」を人が把握できなくなる**。4 段の順序付きロールなら「上位は下位を含む」の一言で説明できる。

## 検討した代替案

### 四眼原則を常に強制する（設定にしない）

規制対応としては最も強い。**却下**: 運用者 1 人のデプロイで同梱サンプルを承認できなくなり、Phase 1 の完了条件（エージェントが承認済みサンプルを参照できる）が壊れる。「デモのために原則を曲げる」のではなく「原則を名前空間ごとに選べるようにし、デモの名前空間だけ緩める」方が、実運用の既定を安全側に保てる。

### 承認権限を持つ主体が 2 人以上いるときだけ四眼原則を効かせる

設定を増やさずに済み、単独運用でも動く。**却下**: 「人数によって静かに強制が切り替わる」ため、運用者が「四眼原則が効いている」と思っている状態と実際が食い違う。この製品が最も避けたい形である。設定として明示させる。

### `platform-admin` に四眼原則も飛び越えさせる

運用は楽になる。**却下**: 四眼原則が「管理者以外への制約」になり、規制対応の文脈で意味を失う。管理者がどうしても承認したいなら、もう 1 人に `maintainer` を付与すればよい（そのための `owner` 権限は持っている）。

### 付与が無い名前空間を「全員に許可」とする（後方互換のため）

更新しても既存の運用が止まらない。**却下**: 「強制していない」を「強制している」と誤認させる。マイグレーションで `created_by` から明示的に付与する方が、状態が説明可能である。

### 用語単位（クラス・プロパティ単位）の権限

ADR-0009 決定4 は「名前空間と**用語**に責任者を持たせる」としている。**この ADR では名前空間単位に限る**。用語単位の責任者は `P2B-04` で扱う。権限（何ができるか）と責任者（誰が説明責任を負うか）は別の概念であり、後者は健全性指標とルーティングのためのものである。

## 結果（トレードオフ・影響）

### 得られるもの

- **承認に説明責任が伴う。** 「記録は正しいが強制が無い」状態が終わる
- **四眼原則が既定で有効になる。** 規制産業での採用可否を左右する要件に応えられる
- ADR-0012 で呼び出し元の識別子を Core API まで届けた投資が、ここで効く

### 受け入れるコスト

- **既存のデプロイはマイグレーションが必要。** `created_by` から `owner` を付与する。作成者が不明な名前空間は `platform-admin` が回復させる
- **`postdeploy` は名前空間の作成時に四眼原則を無効にする。** 同梱サンプルは 1 人で承認される。README に「実運用の名前空間では有効のままにする」ことを書く
- **ロールを付与する UI が無い。** Phase 2 の Web 画面（`P2A-03`）まで API 直叩きになる
- `platform-admin` は Entra のアプリロールに依存する。アプリ登録に手が届かない利用者は `AUTH_MODE=disabled` のローカル開発か、マイグレーションで付与された `owner` で運用することになる

### 影響を受ける他の決定

- **[ADR-0010](0010-approval-and-projection.md)**: 「承認の権限を Phase 1 では強制できない」を解消する。README の「記録は正しく、強制が無い」の記述を書き換える
- **[ADR-0009](0009-ontology-operations.md) 決定4**: 責任者（owner）の置き場所がこの ADR の `namespace_roles` で決まる。用語単位は `P2B-04`
