# ADR-0050: 用語のベクトル検索を Azure AI Search ではなく PostgreSQL(pgvector)で行う

- 状態: 採択
- 日付: 2026-09-13
- 関連: `P3-02`、[ADR-0003](0003-postgresql-as-system-of-record.md)、[ADR-0008](0008-independent-implementation.md)、[ADR-0010](0010-approval-and-projection.md)、[ADR-0017](0017-deprecation-lifecycle.md)、[ADR-0025](0025-result-limits.md)、[ADR-0043](0043-ontology-proposal.md)

## 文脈

AWS 版は OpenSearch Serverless でベクトル検索を提供している。当初の計画([設計計画](../../README.md)と [ADR-0008](0008-independent-implementation.md))はその対応物として **Azure AI Search** を Phase 3 で追加する前提だった。

実装に入る前に、その前提を一次情報で確かめた。

### 測ったこと(2026-09-12〜13)

| 測ったこと | 結果 |
|---|---|
| AI Search Free tier の容量 | 50 MB / 索引 3 つ |
| **Free tier のマネージド ID による Entra 認証** | **非対応**(API キー運用に戻る) |
| Free tier のセマンティックランカー | 非対応 |
| Free tier の休止 | **使われないと削除されうる** |
| AI Search Basic の単価 | **月 $97 の固定費。スケールゼロが無い** |
| Serverless Developer | プレビュー |
| Azure PG 16 の対応拡張に `vector` があるか | **ある(0.8.2)** |
| ローカルの `pgvector/pgvector:pg16` | 0.8.6 |
| `pg_trgm` | **ある(1.6)** |
| `pg_bigm` / `pgroonga`(日本語の形態素解析) | **無い** |
| pgvector の `hnsw` 索引の次元の上限 | **2000**(2001 以上で `column cannot have more than 2000 dimensions for hnsw index`) |
| `halfvec(3072)` + `hnsw` | 動く |
| Japan East の `text-embedding-3-small` v1 | 利用可。`OpenAI.GlobalStandard` の割り当ては上限 4,000 / 使用 0 |
| Japan East の `text-embedding-3-large` の GlobalStandard | **既に 3,002 / 6,000 使用中**(別用途) |

### 何が問題か

この製品は「**minimal で評価でき、`azd down` で完全に消える**」を掲げている([README](../../README.md)、[ADR-0002](0002-triple-store-as-rebuildable-projection.md) がストアの永続化リスクを消したのも同じ理由である)。

- **Basic の月 $97 は、minimal の総額($39〜49)の 2 倍以上**である。ベクトル検索を足すためだけに評価の敷居が 3 倍になる
- **Free tier は API キー運用に戻す。** [ADR-0043 決定9](0043-ontology-proposal.md) は「キーが存在しなければ、キーが漏れることもない」として推論のローカル認証を無効にした。検索のためにキーを 1 本増やすのは、その判断の逆である
- **用語は 1 名前空間あたり数百〜数千である。** [ADR-0025](0025-result-limits.md) が結果に上限を置いているのと同じ規模感で、専用の検索サービスを要求する量ではない

## 決定

### 決定1: 用語のベクトル検索は PostgreSQL(pgvector)で行う。Azure AI Search を導入しない

**既に払っているリソースに載せる。** PostgreSQL Flexible Server B1ms は正本として必ず存在する([ADR-0003](0003-postgresql-as-system-of-record.md))。`vector` と `pg_trgm` は Azure の対応拡張一覧にあるので、**追加費用は $0** である。

**却下した案:**

| 案 | 却下の理由 |
|---|---|
| AI Search Basic | **月 $97 の固定費でスケールゼロが無い。** minimal の総額を 3 倍にする |
| AI Search Free | **マネージド ID による Entra 認証に非対応**(実測)。API キー運用に戻る。加えて容量 50 MB・索引 3 つでは名前空間を増やせず、**使われないと削除されうる** |
| AI Search Serverless Developer | プレビュー。**`azd up` の唯一性を掲げる製品の既定にプレビューを置けない** |
| Cosmos DB for MongoDB vCore のベクトル検索 | 正本を増やす。**この製品で PostgreSQL を正本にした判断(ADR-0003)を薄める** |
| `azure_ai` 拡張(SQL の中から Azure OpenAI を呼ぶ) | **Azure Database for PostgreSQL 固有で、ローカルの docker では再現できない。** この製品は「ローカルで検証できることを増やす」を優先してきた(決定3 で扱う) |

### 決定2: 2 つの経路を持つ。ベクトルだけにしない

| 経路 | 何に強いか | 実装 |
|---|---|---|
| **ベクトル** | 言い換え・概念の近さ | pgvector の `<=>`(cosine) |
| **3-gram** | 表記の一致・部分一致 | `pg_trgm` の `word_similarity()` |

**両方が必要だと実測で確かめた**(PostgreSQL 16 + pgvector 0.8.6、`source_text` は `customerId / 顧客ID / 顧客を一意に識別する番号` の形)。

| 問い | `similarity`(既定閾値 0.3) | `word_similarity` | 結論 |
|---|---|---|---|
| 「顧客ID」 | **0 件** | `customerId` に 1.000 | 表記は 3-gram で当たる |
| 「お客様」 | 0.000 | **0.000** | **3-gram では絶対に当たらない** |
| 「注文日」 | 0 件 | `orderedAt` に 0.750 | — |

つまり

- **「お客様」→ `Customer` はベクトルの経路でしか当たらない。** 3-gram は 1 つも共有しないので、閾値を 0 にしても当たらない
- **「顧客ID」→ `customerId` は 3-gram の方が確実である。** 識別子の部分一致は埋め込みが苦手な形である

**日本語の形態素解析は使えない。** `pg_bigm` / `pgroonga` は Azure の対応拡張一覧に無い(PG 16 の一覧で確認)。つまり **BM25 相当のキーワード検索は作れない**。3-gram で代用する。

**これは Azure AI Search との唯一の実質的な差である**(あちらには `ja.microsoft` / `ja.lucene` のアナライザがある)。用語のラベルは短い文字列なので 3-gram で実用上足りると見ているが、**長文の文書検索には弱い**ことを記録しておく。文書の検索が必要になったら、この判断を測り直す。

### 決定3: 埋め込みの生成はアプリ側で行う。`azure_ai` 拡張を使わない

`azure_ai` 拡張は SQL の中から Azure OpenAI を呼べる(`azure_openai.create_embeddings`)。1 文で索引を作れるので魅力的だが、**Azure Database for PostgreSQL 固有であり、ローカルの docker では再現できない**。

この製品は一貫して「ローカルで検証できることを増やす」を選んできた(`docker-compose` で Fuseki + PostgreSQL + Azurite を揃え、[ADR-0005](0005-reasoner-boundary.md) は SHACL を pyshacl で完結させた)。**デプロイしないと動かない経路を増やさない。**

**API キーを使わない**([ADR-0043 決定9](0043-ontology-proposal.md) と同じ)。アカウント側でローカル認証を無効にしてあるので、マネージド ID でしか呼べない。

### 決定4: 埋め込みは射影である。承認の経路から呼ばない

**不変条件1・3 と同じ形である。** 正本は Blob の TTL で、埋め込みはそこから作り直せる。だから

- **`approve` の中で作らない。** 独立した口(`POST /namespaces/{ns}/search/rebuild`)にしてある。承認の中で呼ぶと、**埋め込みモデルの停止が承認を止める**
- **どの版・どのモデルから作ったかを行に持つ**(`built_from_version` / `model`)。モデルを変えたときに作り直す判断ができる
- **名前空間の行を丸ごと入れ替える**(差分更新にしない)。縮めた版(用語を廃止して消した版。不変条件8)を反映したときに、**検索に出るが版には無い用語**を作らない

**却下した案: `approve` の成功後に非同期で作る。** 「作り終わったか」を運用者が知る手段が別に必要になり、失敗したときに**検索が黙って古い版を指す**。射影の回収は [ADR-0013](0013-reconcile-repairs-observed-divergence.md) が `reconcile` で扱っている形であり、検索の索引にも同じ仕組みを作るのは `P3-02` の範囲を越える。**当面は明示的な作り直しだけを持つ**(バックログに追記した)。

### 決定5: 埋め込みは `text-embedding-3-small`(1536 次元)に固定する

**pgvector の `hnsw` 索引は 2000 次元までである**(実測)。`text-embedding-3-large`(3072)を使うには `halfvec` へのキャストが要る(動くことは確かめた)。

**採らない理由は 2 つ。**

1. **キャストを挟むと、列の型と埋め込みの次元の関係が読みにくくなる。** `vector(3072)` の列に `hnsw` を張れないので、索引は `halfvec(3072)` への式索引になる。式索引はクエリ側の書き方が索引と一致しないと黙って使われない
2. **Japan East の `text-embedding-3-large` の GlobalStandard の割り当ては既に 3,002/6,000 使用中**である(実測)。他の用途と競合する

**次元は 4 か所に書かれている**(コードの定数・`Settings` の既定・マイグレーション・Bicep の出力)。**どこも import で繋げられない**ので、`packages/api/tests/test_embedding_contract.py` が機械的に突き合わせる。

- マイグレーションは import しない。**過去の履歴が現在のコードに依存すると、定数を変えた瞬間に履歴の意味が変わる**
- `Settings` は import しない。`ontology_core/__init__.py` が config を読むので、**`import ontology_core` のたびに rdflib が読み込まれる**

### 決定6: 3-gram は `word_similarity` を使い、閾値の既定は 0.6 にする

**`similarity` では日本語の短い問いが当たらない**(決定2 の表)。`source_text` は局所名・ラベル・説明をつないだ長い文字列なので、短い問いは全体の類似度を上げない。

**既定は 0.6 — PostgreSQL 自身が `<%` 演算子に対して選んだ値である**(実測: `pg_trgm.word_similarity_threshold` = 0.6、`similarity_threshold` = 0.3、`strict_word_similarity_threshold` = 0.5)。

**緩めない。** 0.3 にすると「顧客ID」で `Customer` と `customerName` まで当たる(実測 0.400)。それは**概念の隣**であって表記の一致ではなく、ベクトルの経路の担当である。**2 つの経路の役割を混ぜると、`route` を返している意味が薄れる。**

**演算子(`<%`)ではなく明示的な比較で絞る。** `<%` はセッション変数を見るので、**設定した閾値が効いているかを応答から確かめられない**。

### 決定7: 融合は RRF(順位だけを使う)。言語タグで絞らない

**RRF は順位だけを使う。** cosine 距離と 3-gram の類似度は尺度が違うので、正規化して足し合わせる案は「どちらをどれだけ重視するか」という**測っていない判断**を含む。定数 `k = 60` は原論文(Cormack ら 2009)の値で、**調整していない** — 調整するなら「何に対して良くなったか」を測る必要がある。

**`both`(両方の経路で当たった)を別の値として返す。** 片方より強い根拠であり、潰すとその情報が消える。

**埋め込みの材料は言語タグで絞らない。** 日本語と英語のラベルが両方あるオントロジーで片方だけを埋め込むと、**もう片方の言葉で聞いたときに出てこない**。両方つないで 1 本のテキストにする。局所名を先頭に置くのは、**ラベルが無い用語**(実際にある)でも `GoldCustomer` のような名前で当てられるようにするためである。

### 決定8: 「ベクトルが使えない」を「該当なし」にしない

埋め込みが 0 件、またはモデルが未設定でも **3-gram だけで検索は成立する**。そのとき

- `vector_available: false` と `vector_note`(理由)を必ず返す。**`vector_note` を空にしない**
- `embedded_term_count` を返す。**`0` は「作っていない」であって「用語が無い」ではない**
- `conclusive: false` を返す。**偽のときに「これが全部です」と言ってはいけない**

**モデルの呼び出しが失敗しても検索を失敗させない。** 3-gram の結果は正しいので、返せるものを返して**落ちたことを見せる**(不変条件3 と同じ向き)。ただし**問いを応答に載せない** — 利用者の入力である。

これはこのリポジトリで繰り返し出てくる形である(ADR-0016 決定5 の「計算できなかった」、ADR-0030 の `unknown`、ADR-0047 決定6 の `conclusive`)。**「測れなかった」を「問題なし」にしない。**

### 決定9: 廃止済みの用語も検索の結果に返す

**除外しない**([ADR-0017 決定3](0017-deprecation-lifecycle.md) と同じ向き)。廃止された用語を検索で見つけられないと、**「なぜその用語が使えないのか」に答えられない**。`deprecated` の印と `deprecated_hits` の一覧で警告として見せ、MCP のツールの説明に「**廃止済みを根拠に回答を作ってはいけない**」と書いてある。

### 決定10: 権限は検索が `data-analyst`、作り直しが `maintainer`

- **検索は読み取りである。** `/sparql` と同じ最小のロールにした — 「どの用語があるか」を知る行為は SPARQL で引けることと同じ範囲である
- **作り直しは `maintainer`。** 射影なのでデータは壊れないが、**モデルの呼び出しに費用が発生する**。`data-analyst` に開けない

**退役した名前空間では作り直さない**([ADR-0032](0032-namespace-retirement.md) 決定5 と同じ形)。版を作れない名前空間の索引を作る意味が無く、費用だけが発生する。

### 決定11: MCP に `search_context` を出す。埋め込みの作り直しは出さない

**エージェントが「どの用語を使えばよいか分からない」状態を解けるようにする。** `sparql_query` は IRI を知っている前提である。

**作り直しは出さない。** MCP は読み取り専用である(設計原則4)。加えて**費用が発生する行為をエージェントに開けない**。

**承認済み版から作った埋め込みしか引かない**ので、[ADR-0010](0010-approval-and-projection.md) の「エージェントに出すのは `approved` の版だけ」は保たれる。

## 帰結

### 得たもの

- **ベクトル検索の追加費用が $0 になった。** Phase 3 の見積りが月 $136〜158 から**月 $39〜49 のまま**になる(LLM の従量は別)
- **API キーが 1 本も増えない。** マネージド ID だけで完結する
- **ローカルで全部検証できる。** `pgvector/pgvector:pg16` と `pg_trgm` は docker で動く。埋め込みの生成だけがモデルを要求し、そこは差し替えられる
- **`azd down` で消えるものが増えない。** AI Search の索引という「消し忘れる先」が無い

### 失ったもの / 引き受けたリスク

- **日本語の形態素解析が無い。** `pg_bigm` / `pgroonga` が Azure に無いので、BM25 相当は作れない。**用語のラベルでは 3-gram で足りると見ているが、長文の文書検索には弱い**
- **セマンティックランカーが無い。** AI Search の再ランキングに相当するものは持たない。RRF で融合するだけである
- **hnsw の索引は挿入が重い。** 用語数が 1 名前空間あたり数万に達すると、作り直しの所要時間が問題になりうる。**測っていない**(バックログに追記した)
- **B1ms の 1 vCPU / 2 GiB を検索と正本で共有する。** 検索が重いと正本への書き込みが遅くなる。**用語数が数千の規模では問題にならないと見ているが、測っていない**
- **索引が選ばれるかを実測で固定できていない。** 212 行では planner が `hnsw` も `gin` も選ばず Seq Scan になる(実測)。**索引が「ある」ことは固定したが、「使われる」ことは固定していない**

### この判断を測り直す条件

次のどれかが起きたら、AI Search を再検討する。

1. **文書(Blob)の全文検索が要件になったとき。** 長文に対する 3-gram は弱い
2. **1 名前空間の用語数が数万に達したとき。** hnsw の作り直しと B1ms の共有が効く
3. **`pg_bigm` か `pgroonga` が Azure の対応拡張に入ったとき。** そのときは pgvector 側が強くなる(この判断を補強する向き)
4. **AI Search にスケールゼロの層ができたとき。** 固定費という最大の却下理由が消える

## ADR-0008 への影響

[ADR-0008](0008-independent-implementation.md) の対応表にある「OpenSearch Serverless → Azure AI Search」は、**この ADR で覆された**。同 ADR に補記を追加した。

**独立実装を選んだ判断そのものは変わらない** — むしろ「AWS 版の構成をそのまま写さない」ことがここで実益になった。フォークしていれば OpenSearch に相当するものを探し続けることになっていた。
