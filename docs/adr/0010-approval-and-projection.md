# ADR-0010: 承認の実行方法と、状態に応じた射影

- ステータス: 承認済み
- 日付: 2026-09-05

## コンテキスト

[ADR-0009](0009-ontology-operations.md) は「権限を要する判断は人間が決める」と方針を定めた。しかし**その承認を実際にどう実行するのか**は決めていない。

実装を調べると、承認の器はあるが遷移が存在しなかった。

```
OntologyVersionStatus: draft / in-review / approved / superseded  （4 状態）
実際に使われる箇所:      draft のみ（他は 0 箇所）
approved_by / approved_at: 列はあるが、どこからも書かれない
```

2026-09-03 に `publish` が `approved` をハードコードしていた問題を修正し、`draft` を記録するようにした（[`backlog.md`](../backlog.md) の履歴を参照）。**誰も承認していないのに「承認済み」と記録される**状態は解消したが、これは新しい食い違いを生んだ。

- **射影の挙動は変えていない。** 未承認の版がそのまま Fuseki に載り、エージェントが未承認の定義を受け取りえる
- **Blob のプレフィックスが `approved/`** のまま、未承認の版を含んでいる
- **承認する手段が無い。** `approved` に到達する経路が存在せず、`publish` は書き込み専用の操作になった

さらに ADR-0009 が Critical として記録した問題が未解決である。`tdb2:unionDefaultGraph = true` のため**既定グラフが全バージョンの和集合になり**、`GRAPH` 句なしのクエリで矛盾する定義が同時に返る（実測済み）。

この 2 つは同じ問いに帰着する。**どの版を、どこに射影するのか。** 承認の設計と射影の設計は分離できない。

### 二つの要求が衝突する

- **エージェントは承認済みの定義だけを見なければならない。** これが製品の中核価値（[ADR-0006](0006-ontology-versioning-and-audit.md)）
- **レビュアは承認前に SPARQL で検証できなければならない。** 「このオントロジーは想定質問に答えられるか」（ADR-0009 決定 6）を確かめずに承認するのは、目を閉じて承認することと同じ

「承認前は射影しない」とレビューが盲目になり、「未承認も既定グラフに載せる」とエージェントに未承認が届く。どちらも採れない。

### ローダは PostgreSQL を見ない

`containers/fuseki/load-snapshot.sh` は Blob の一覧だけを見て TDB2 を再構築する。承認状態は PostgreSQL にあるため、**現状のローダは「どの版が承認済みか」を知る手段を持たない**。

## 決定

### 1. 承認を publish から分離する

`publish` は版を `draft` として作るだけにする。承認は別の操作とする。

```
POST /namespaces/{ns}/versions                    → draft を作る
POST /namespaces/{ns}/versions/{v}/submit         → draft を in-review にする
POST /namespaces/{ns}/versions/{v}/approve        → in-review を approved にする
POST /namespaces/{ns}/versions/{v}/reject         → in-review を draft に戻す（理由必須）
```

### 2. 承認の実体は API に置く

状態遷移と監査記録を API が担う。Web UI・外部の承認システム（Teams 承認、ITSM 等）は**いずれもこの API を叩く**。承認のロジックを UI に埋め込まない。

理由は企業の現実である。オントロジーをレビューするのは業務の専門家であり、その組織には既に承認の仕組みがある場合が多い。API を境界にしておけば、UI を差し替えても、既存の承認フローに乗せても、記録の形が変わらない。

### 3. 状態遷移

| 遷移 | 実行できる者 | 記録 |
|---|---|---|
| （新規）→ `draft` | 認証済みの呼び出し元 | `created_by` |
| `draft` → `in-review` | 提案者または責任者 | `audit_events`（`action=submitted`） |
| `in-review` → `approved` | **責任者のみ。既定では提案者と同一人物を許さない（四眼原則）** | `approved_by` / `approved_at` + `audit_events` |
| `in-review` → `draft`（却下） | 責任者 | `audit_events`（`action=rejected`、`reason` 必須） |
| `approved` → `superseded` | **自動。** 同じ名前空間の別の版が `approved` になった時点で、それまでの `approved` を `superseded` にする | `audit_events`（`action=superseded`） |

四眼原則は設定で無効化できる。OSS として一人で使う利用者を排除しないためである。既定は有効。

`superseded` を自動にするのは、[ADR-0009](0009-ontology-operations.md) が「旧版を印付ける主体がいない」ことを問題としたためである。人手に委ねると必ず漏れる。

### 4. 承認の粒度は版単位とする

用語単位の承認は採らない。オントロジーが不変リビジョンである以上（[ADR-0006](0006-ontology-versioning-and-audit.md)）、承認も版に対して行うのが整合する。

「1 箇所直したいのに全体を再承認になる」という負担は認める。これは**意味的差分レビュー**（[`backlog.md`](../backlog.md) の `P2B-09`）で軽減する。レビュアが見るのは版全体ではなく、前の承認済み版からの差分である。

用語単位の承認は Phase 3 以降の課題として残す。

### 5. 射影は状態で決める

上記の衝突を、**射影先を分けることで解く**。

| 状態 | 既定グラフ | 名前付きグラフ | 誰が見えるか |
|---|---|---|---|
| `approved`（現行の 1 版のみ） | **載せる** | 載せる | エージェント・全員 |
| `in-review` | 載せない | **載せる** | `GRAPH` 句を書いたレビュア |
| `draft` | 載せない | 載せない | 誰にも見えない（Blob と PostgreSQL にのみ存在） |
| `superseded` | 載せない | 保持ポリシーの範囲で載せる | `GRAPH` 句を書いた監査 |

これで両方の要求が満たされる。**エージェントは `GRAPH` 句を書かなければ承認済みの現行版だけを見る。レビュアは `GRAPH` 句で審査中の版を検証できる。**

### 6. 既定グラフは常に単一の版を指す

`tdb2:unionDefaultGraph` の使用をやめる。承認済み現行版を、名前付きグラフに加えて**既定グラフにも読み込む**（`tdb2.tdbloader` を `--graph` 無しでもう一度呼ぶ）。

現行版のトリプルを二重に保持することになるが、オントロジー規模では無視できる。ADR-0009 が Critical とした問題への対処である。

### 7. ローダへは Blob 上のマニフェストで状態を渡す

**ローダに PostgreSQL の資格情報を持たせない。** Fuseki コンテナの権限を広げないためである。

代わりに、名前空間ごとにマニフェストを Blob へ置く。

```
versions/<namespace>/_state.json
{
  "schema": 1,
  "namespace": "retail-core",
  "current": "2.0.0",
  "versions": [
    {"version": "2.0.0", "status": "approved"},
    {"version": "2.1.0", "status": "in-review"},
    {"version": "1.0.0", "status": "superseded"}
  ],
  "generated_at": "2026-09-05T00:00:00Z"
}
```

**`_state.json` が版ファイルと衝突しないことは、既存の検証規則から保証される。** `_VERSION_PATTERN` は `[A-Za-z0-9][A-Za-z0-9.+-]{0,63}` であり、`_` で始まる名前は版として不正である。同様に `_NAMESPACE_PATTERN` は `[a-z0-9][a-z0-9-]{1,62}` なので、`_` で始まるディレクトリ名は名前空間として不正である。したがって `_` 始まりの名前は安全に予約できる。

**マニフェストは PostgreSQL の状態の射影であり、正本ではない。** [ADR-0002](0002-triple-store-as-rebuildable-projection.md) の「トリプルストアは再構築可能な射影」と同じ位置づけである。書き込み順序も同じ規律に従う。

```
Blob(TTL) → PostgreSQL(状態) → Blob(マニフェスト) → Fuseki(射影)
```

`POST /admin/reconcile` はマニフェストを PostgreSQL から再生成できる。マニフェストが壊れても、正本から作り直せる。

マニフェストが存在しない名前空間について、ローダは**失敗を明示する**（黙って全件を承認済みとして扱わない）。推測は Critical を再来させる。

### 8. Blob のプレフィックスを `versions/` に改名する

`approved/` は全ての公開済み版（`draft` を含む）を格納するため、名前が実態と食い違っている。`versions/` にする。

未リリースであり、`azd down` で完全削除できる設計なので、破壊的変更を今のうちに済ませる。

## 根拠

### 射影先を分けるのが、衝突の唯一の解

「エージェントは承認済みのみ」と「レビュアは承認前に検証」は、**同じ場所に載せる限り両立しない**。分ける軸は 3 つ考えられた。

- **データセットを分ける**（`<ns>` と `<ns>_draft`）— 名前空間名がセキュリティ境界であり（[ADR-0001](0001-rdf-store-selection.md)）、派生した名前を増やすと境界の検証対象が増える
- **グラフを分ける**（既定グラフと名前付きグラフ）— **採用。** 既に版ごとに名前付きグラフへ射影しており（ADR-0006）、追加の概念を導入しない
- **エンドポイントを分ける** — 認可で分ける発想だが、Phase 1 に名前空間 RBAC が無く、実現できない

2 つめが最も安い。既定グラフと `GRAPH` 句の違いは SPARQL の標準機能であり、独自の仕組みを発明しない。

### `draft` を射影しないのは、レビューの単位を明確にするため

`draft` は「まだ人に見せる段階でないもの」である。射影すると、審査に出していない版が `GRAPH` 句で読めてしまい、`in-review` との区別が意味を失う。

**提出（submit）という明示的な行為をレビューの開始点にする。**これによりレビュアは「何を見ればよいか」が一意に決まる。

### マニフェストを Blob に置くのは、ローダの権限を広げないため

ローダに PostgreSQL を読ませれば、マニフェストは不要になる。しかし Fuseki コンテナに DB 資格情報を持たせることになり、侵害時の影響範囲が広がる。

Fuseki は internal ingress のみで外部に出ていないが、それは多層防御の 1 層であって、権限を最小に保つ理由を打ち消さない。マニフェストは JSON 1 ファイルであり、この対価は安い。

### 承認の権限を Phase 1 では強制できない

四眼原則と「責任者のみ」の判定には、名前空間 RBAC（`P2A-06`）と責任者（`P2B-04`）が必要で、どちらも Phase 2 である。

したがって **Phase 1 では認証済みの呼び出し元が誰でも承認できる。** ただし `approved_by` に誰が承認したかは記録される。**記録は正しく、強制が無い**状態である。これを README に明記する。機構を先に作り、権限を後から締めるのは順序として妥当である（逆はできない）。

## 検討した代替案

### Git / Pull Request ベースのレビュー

**却下。** [ADR-0006](0006-ontology-versioning-and-audit.md) が既に却下している理由を継承する（専門家が Git を使えるとは限らない / RBAC の二重管理 / テキスト差分は RDF の差分ではない）。

この ADR の観点で理由をもう 1 つ加える。**射影の状態管理が Git のブランチモデルと噛み合わない。** どのブランチのどのコミットが「現行の承認済み版」なのかを Fuseki に伝える仕組みは、結局マニフェスト相当のものになる。Git を使う利点が消える。

### 承認前は一切射影しない

**却下。** レビュアが「このオントロジーは想定質問に答えられるか」を確かめられなくなる。ADR-0009 決定 6 が「想定質問を実行可能なテストにする」と決めたのに、承認前にそのテストを回せないのでは意味がない。

### 未承認も既定グラフに載せる（現状維持）

**却下。** これが現状であり、ADR-0009 が Critical とした問題そのものである。エージェントが未承認・矛盾する定義を受け取る。

### ローダに PostgreSQL の資格情報を持たせる

**却下。** 上記「根拠」のとおり、Fuseki コンテナの権限を広げる。マニフェストで足りる。

### 用語単位の承認を今から実装する

**却下（Phase 3 以降へ）。** 不変リビジョンとの整合が難しく、「どの用語がどの版で承認されたか」を追う構造が必要になる。版単位 + 意味的差分レビューで実務上の負担は下げられる。

### 承認のロジックを Web UI に持たせる

**却下。** 外部の承認システムに乗せられなくなる。企業には既に承認の仕組みがあることが多く、そこへ繋げられないと採用の障壁になる。

## 結果（トレードオフ・影響）

### 受け入れるコスト

- **最小の承認 API を Phase 1 で実装する必要がある。** この ADR の決定 1・5 を実装すると `publish` は `draft` しか作らないため、承認する手段が無ければ `publish` が書き込み専用の操作になる。`submit` / `approve` / `reject` の最小実装を Phase 1 の欠陥修正に含める
- **権限が Phase 1 では強制されない。** 認証済みの誰でも承認できる。記録は残る。README に明記する
- **現行版のトリプルを二重に持つ。** 既定グラフと名前付きグラフの両方に載せる
- **Blob のプレフィックス改名は破壊的変更。** 未リリースなので許容する
- **postprovision がマニフェストを書く必要がある。** サンプルは API を経由せず Blob へ直接書くため

### 得られるもの

- **エージェントは承認済みの現行版だけを見る。** `GRAPH` 句を書かないクエリが単一の版を返す（ADR-0009 の Critical が閉じる）
- **レビュアは承認前に SPARQL で検証できる。** 想定質問テストを承認前に回せる
- **旧版が自動で `superseded` になる。** 印付けの漏れが構造的に起きない
- **承認の記録が信用できる。** `approved_by` が実際の承認者を指す

### 影響を受ける他の決定

- **[ADR-0002](0002-triple-store-as-rebuildable-projection.md)**: 射影の対象が「全ての版」から「状態に応じた版」に変わる。マニフェストという新しい射影が加わる（正本は PostgreSQL）
- **[ADR-0006](0006-ontology-versioning-and-audit.md)**: 保持ポリシーの実装がマニフェストに乗る。`superseded` の自動付与を追加する
- **[ADR-0009](0009-ontology-operations.md)**: 決定 2（既定グラフは最新の承認済み版のみ）の具体的な実現方法を、この ADR が定める

### 未解決のまま残す問い

- 保持ポリシーの具体的な値（`superseded` を何版まで載せるか）。マニフェストに持たせる形は決めたが、既定値は運用実績が無いと決められない
- 却下された `draft` の扱い（残し続けるか、一定期間で消すか）
- 廃止（`owl:deprecated`、ADR-0009 決定 3）と `superseded` の関係。前者は用語単位、後者は版単位であり、両立させる設計は未検討
- 外部の承認システムとの連携の具体形（Webhook か、ポーリングか、双方向か）
