# ADR-0042: スキャンの定期実行は既定で動かない — 顧客 DB へ手を伸ばす処理をオプトインにする

- ステータス: 承認済み
- 日付: 2026-09-12

## コンテキスト

[ADR-0041](0041-source-schema-scan.md)(`P2A-01`)でソース DB のスキャンを
実装したが、**決定10 で ACA Job を意図的に範囲外にした** — Bicep は
`az bicep build` で構文までしか確かめられず、課金なしに動作を検証できない
ためである。「書いたが動かしていない IaC」を残さないために `P2A-19` として
記録した。

デプロイ窓が取れたのでここで書く。窓の中で実機確認する。

### 決めるべきこと

1. **いつ走るのか**(定期実行なのか、呼ばれたときなのか)
2. **何を対象にするのか**(どのソースを、誰の権限で)
3. **1 つのソースが落ちたとき、ジョブは失敗なのか**
4. **ジョブのイメージを誰が更新するのか**
5. **ジョブに何を渡すのか**
6. **`SCAN_ALLOWED_HOSTS` と `SCAN_VAULT_URL` をデプロイ環境でどう与えるのか**

## 決定

### 1. 既定は `Manual` トリガである。cron を設定したときだけ `Schedule` になる

`SCAN_JOB_CRON` が空なら `triggerType: 'Manual'`、値があれば
`triggerType: 'Schedule'` でその cron を使う。

**既定で顧客 DB へ手を伸ばし始めない。** これは不変条件11(権限の既定は拒否)
と同じ向きの判断である。定期実行は

- **他人の DB に対して**繰り返し接続を試み
- 実行ごとに課金され
- 運用者が気づかないうちに始まる

ものなので、**設定したときだけ動く**のが安全側である。`SCAN_ALLOWED_HOSTS`
を既定で空にした(ADR-0041 決定5)のと同じ理由で、**設定するまで何も起きない**
状態を既定にする。

**オンデマンドの口は既に API にある**(`POST .../scan`)。定期実行が無いことは
機能の欠落ではなく、**運用者が頻度を決めるまで頻度を決めない**という態度で
ある。

> **副作用として、既定のデプロイでジョブは一度も実行されない。** 実機確認は
> `az containerapp job start` で明示的に起動して行う。**「毎晩動いている
> はずだが確かめていない」より、「明示的に起動して確かめた」のほうが強い。**

### 2. 対象は登録済みの全ソースである。名前空間をまたぐ

ジョブは `scan_sources` を名前空間で絞らずに読む。

**不変条件5(名前空間名はセキュリティ境界)に反しない。** 境界が守るのは
**外部入力が別の名前空間へ届かないこと**である。このジョブは外部入力を
受け取らない — トリガに引数が無く、対象は DB にある登録の全体である。
`POST /admin/reconcile`(`platform-admin`)が全名前空間を見るのと同じ位置に
ある、**システムの保守処理**である。

**引数を受け取らないのは意図である。** 実行ごとに対象を渡せる形にすると、

- ジョブを起動できる主体が**対象を選べる**ようになり
- 「誰がどの DB をスキャンできるか」が名前空間の権限の外に出る
  (ADR-0041 決定8 が避けたこと)

**主体はジョブのマネージド ID である。** `scan_runs.started_by` に
`AZURE_CLIENT_ID` を書く。人間が起動していないことが記録から読める。

### 3. 1 つのソースが落ちてもジョブは成功で終わる

**区別するのは「掃引が走ったか」と「全ソースに届いたか」である。**

| 何が起きたか | 終了コード |
|---|---|
| 掃引が走った(一部のソースが `failed` でも) | **0** |
| 掃引そのものが走れなかった(PostgreSQL に繋がらない、設定が無い) | **1** |

1 つの顧客 DB が落ちていることをジョブの失敗にすると、**ACA の再試行が
健全なソースを何度も叩く**。届かなかったことは
**`scan_runs` に `failed` として残る**(ADR-0041 決定7)ので、情報は失われない。

**ただし「終了コード 0」を「全部うまくいった」と読ませない。** 失敗が 1 件でも
あれば WARNING で件数と理由を出し、最後に必ず要約を出す。
**読むべき場所は `scan_runs` である**ことをログに書く。

> これは「測れなかったことを、問題が無かったことにしない」の系である。
> 終了コードは**掃引の実行**についてしか語れない。

### 4. 1 つのソースの失敗が残りを止めない。セッションは巻き戻して続ける

想定外の例外(`SourceConnectionError` ではないもの)が出たときは、
**セッションを `rollback` してから次のソースへ進む**。巻き戻さないと、
半端なトランザクションが残って**残り全部が「失敗」になる**(症状が原因を
指さなくなる)。

### 5. ジョブは Core API と同じイメージを使い、`postdeploy` が更新して副作用で確かめる

**別のイメージを作らない。** ジョブが呼ぶのは `ontology_api.services.scan`
そのもので、依存も同じである。2 つ目のイメージはビルド時間を倍にし、
**ずれる余地を作る**(スキャンの本体が 2 つの版で動く)。

**イメージの更新は `postdeploy` が行う。** azd の `provision` の時点では
`SERVICE_API_IMAGE_NAME` がまだ空で、ジョブはプレースホルダのイメージを
指す。azd がコンテナアプリのイメージを差し替えるのは `azd-service-name`
タグが付いたリソースだけで、**ジョブは対象外である**(azd 1.28.0 が
`host: containerapp-job` を扱えるかは確認できなかった — `azd show` は
**不正な host 値も黙って受け付けるので、この検査では何も分からない**。
実測した)。

そこで `postdeploy` が `az containerapp job update --image` で差し替え、
**読み戻して一致を確認する**。CLAUDE.md の規律どおり、
**終了コードを見るだけでは足りない**。

**プレースホルダのまま実行されたらどうなるか**: 既定は `Manual` トリガ
(決定1)なので**自動では実行されない**。明示的に起動すれば、
プレースホルダは終了しないプロセスなので実行はタイムアウトで `Failed` に
なる — **静かに成功したことにはならない**。

### 6. ジョブに Fuseki と Blob の資格情報を渡さない

スキャンが触るのは PostgreSQL(カタログ)とソース DB だけである。
**必要のないものを渡さない。** 具体的には

| 渡すもの | なぜ |
|---|---|
| PostgreSQL の接続先 | カタログの書き込み先 |
| `SCAN_ALLOWED_HOSTS` | 接続先の allowlist(ADR-0041 決定5) |
| `SCAN_VAULT_URL` | 秘密の在り処(値は入らない。決定4) |
| `AZURE_CLIENT_ID` | マネージド ID。`started_by` にも使う |
| App Insights / `LOG_LEVEL` | 観測 |

| 渡さないもの | なぜ |
|---|---|
| `FUSEKI_ADMIN_PASSWORD` | スキャンは Fuseki を触らない |
| Blob のエンドポイント | スキャンは正本 TTL を触らない |
| `ENTRA_API_AUDIENCE` 等 | ジョブは HTTP を受け付けない |

**渡さないことが security property である。** ジョブのイメージは API と
同じなので、**渡せば使えてしまう**。

### 7. `SCAN_VAULT_URL` の既定はこのプロジェクトの Key Vault である

マネージド ID は既に `Key Vault Secrets User` を持っている
(`shared.bicep`)。運用者は**追加のロール付与なしに**ソース DB の
パスワードを置ける。

**別の Key Vault を指すこともできる**(`SCAN_VAULT_URL` パラメータ)。その
場合は**その Vault に対して `Key Vault Secrets User` を手で付与する必要が
ある** — Bicep は自分が作っていないリソースにロールを付けない。README に
書く。

> **同じ Vault にプラットフォーム自身の秘密(PostgreSQL 管理者・Fuseki
> 管理者)と顧客 DB の秘密が同居する。** 分けたい運用者のために
> パラメータを用意したうえで、既定は「動く」を採った。

### 8. ジョブのリソースは 0.5 vCPU / 1Gi、実行のタイムアウトは 30 分

スキャンは 5 本のクエリを 1 接続で流すだけで CPU を使わない。大きな
スキーマでも `information_schema` の読み取りが支配的である。

**タイムアウトは 30 分。** 届かないソースが多数あると、接続のタイムアウトが
積み上がる。`replicaTimeout` を無制限にすると**掃引が終わらないまま課金が
続く**。

**再試行は 0 回。** 決定3 のとおり、届かなかったことは `scan_runs` に残る。
再試行は**健全なソースを再度叩くだけ**である。

## 検討した代替案

### 既定で毎晩走らせる

**却下(決定1)。** 「定期実行」と書いてあるのだから既定で定期実行する。

却下理由: **他人の DB に対する繰り返しの接続を、運用者の明示なしに始める
ことになる。** 頻度は「そのソースがどれだけ変わるか」と「そのソースに
どれだけ負荷をかけてよいか」で決まる — **こちらが知らないこと**である。
`SCAN_ALLOWED_HOSTS` が空なら接続はできないので害は無いという主張は成り立つが、
**allowlist を設定した瞬間に毎晩の接続が始まる**のは驚きである。

### 実行ごとに対象のソースを引数で渡す

**却下(決定2)。** ジョブの `start` に環境変数の上書きを添えれば対象を選べる。

却下理由が 2 つある。**(1) API がジョブを起動できるようにすると新しい権限が
要る**(ARM への書き込み)。API のマネージド ID にジョブの実行権限を与える
ことは、**API の侵害の影響範囲を広げる**。**(2) 対象を選べる口は、名前空間の
権限の外に「どの DB をスキャンできるか」を作る**(ADR-0041 決定8 が避けたこと)。

オンデマンドが必要なら**既にある API の同期エンドポイント**を使う。そこでは
名前空間の `owner` が要求される。

### 1 つでも失敗したらジョブを失敗させる

**却下(決定3)。** 「失敗を隠さない」に見える。

却下理由: **ACA の再試行が健全なソースを何度も叩く。** また、顧客 DB の
1 つが計画停止しているだけで毎回赤くなり、**アラートが意味を失う**。
失敗は `scan_runs` に**ソース単位で**残る — そちらが読むべき場所である。

### ジョブ専用のイメージを作る

**却下(決定5)。** 依存が最小になる。

却下理由: **スキャンの本体が 2 つの版で動く余地ができる。** ジョブが呼ぶのは
`ScanService` そのものなので、**同じイメージであることが「API で検証した
挙動がジョブでも成り立つ」の根拠になる**。

### azd の `host: containerapp-job` に任せる

**却下(決定5)。** azd がイメージの差し替えをやってくれるなら `postdeploy`
は不要になる。

却下理由: **azd 1.28.0 が対応しているかを確認できなかった。** `azd show` は
`host: not-a-real-host` すら黙って受け付ける(実測)ので、**受け付けたことは
対応の証拠にならない**。**未確認の挙動に依存しない** — `az containerapp job
update` で明示的に差し替え、読み戻して確かめる。

> azd を上げて対応が確認できたら、この決定は見直してよい。そのときは
> `postdeploy` の差し替えを外せる。

### `replicaTimeout` を無制限にする

**却下(決定8)。** 大きなスキーマでも途中で切られない。

却下理由: **終わらない掃引に課金が続く。** 届かないソースが多数あると
接続のタイムアウトが積み上がる。30 分で切り、**どこまで読めたかは
`scan_runs` に残る**。

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **既定のデプロイでジョブは一度も走らない**(決定1)。`SCAN_JOB_CRON` を
  設定するか、手で起動する必要がある
- **`postdeploy` がイメージを差し替える**(決定5)。`azd provision` だけを
  走らせるとジョブはプレースホルダを指したままになる。**`azd up` は
  provision → deploy → postdeploy の順なので通常は問題にならない**
- **掃引の粒度が「全ソース」しかない**(決定2)。1 つのソースだけを定期的に
  スキャンしたい要求には応えられない
- **終了コードが「全ソースに届いた」を意味しない**(決定3)。読むべきは
  `scan_runs`
- **別の Key Vault を使うならロール付与が手作業になる**(決定7)

### 得られるもの

- **定期実行の口ができた。** 頻度は運用者が決める
- **API で検証した挙動がそのままジョブで動く**(同じイメージ・同じ
  `ScanService`。決定5)
- **ジョブが持つ資格情報が最小になった**(決定6)
- **`SCAN_ALLOWED_HOSTS` / `SCAN_VAULT_URL` がデプロイ環境に届くようになった。**
  `P2A-01` はローカルでしか設定できていなかった(この ADR で気づいた)

### 影響を受ける他の決定

- [ADR-0041](0041-source-schema-scan.md) 決定10 — 「ACA Job はこの ADR では
  作らない」を、この ADR が引き取って閉じた
- ADR-0041 決定5 — allowlist はジョブにも効く(`ScanService` を通るため)。
  **ジョブは allowlist を迂回しない**
- ADR-0041 決定7 — `running` のまま残った run を**ジョブはスキップしない**。
  片付けられていない記録が機能を止めてはいけない
- [ADR-0013](0013-reconcile-repairs-observed-divergence.md) — 名前空間をまたぐ
  保守処理という位置づけが `reconcile` と同じである
