# ADR-0025: 結果件数の上限を境界で強制する — 「効いている」と誤認させる設定をやめる

- ステータス: 承認済み
- 日付: 2026-09-11

## コンテキスト

`SPARQL_MAX_RESULTS`(既定 10,000)は `ontology_core.config.Settings` が保持し、
`infra/modules/api.bicep` が注入している。**しかしどこも強制していない**
(`P2A-08`)。結果件数を制限する実装は `ontology_core.sparql.guards` を含め
どこにも無い。

**これは不変条件11 が名指しした形そのものである** — 「強制していない」を
「強制している」と誤認させる。設定が存在し、Bicep が注入しているという事実が、
効いていることの証拠のように読める。README の「動作を確認済み」節と
`config.py` のコメントは正直にそう書いてあるが、**正直な注記は強制の代わりに
ならない**。

### ストア側では止められない(実測)

Fuseki に行数の上限を持たせられるなら、そこで止めるのが最善である
(ストアが無駄な仕事をしない)。Fuseki 6.2.0 / Jena ARQ 6.2.0 を調べた。

| 調べたもの | 結果 |
|---|---|
| ARQ のコンテキスト記号(`arq:*`) | `queryTimeout` / `updateTimeout` / `httpQueryTimeout` のみ。**行数の上限は無い** |
| `fuseki:queryLimit`(語彙に**存在する**) | **効かない。** サーバ階層とサービス階層の両方、`xsd:integer` と `xsd:long` の両方で `queryLimit 5` を設定し、12 行のデータに `SELECT` を投げて **12 行返った** |
| `fuseki:queryLimit` の読み手 | `fuseki-server.jar` 内で `pQueryLimit` を参照するのは `FusekiVocab` / `FusekiVocabG`(語彙の定義)**だけ**。実装に読み手がいない |

**Fuseki 自身の語彙にも「定義はあるが効かない設定」があった。** 皮肉だが、
この ADR が直そうとしている問題とまったく同じ形である。

`arq:queryTimeout` は実際に効いており、既に `containers/fuseki/config.ttl` で
使っている(10 秒 / 30 秒)。**時間は止められるが行数は止められない。**
30 秒で 1,000 万行返るクエリは通る。

### `CONSTRUCT` / `DESCRIBE` はこの経路では動いていない(実測)

行数の上限を設計するうえで「何が返るのか」を確かめたところ、別の問題が出た。

| クエリの形 | `FusekiStore.query` の結果 |
|---|---|
| `SELECT` | `{head, results}` |
| `ASK` | `{head, boolean}` |
| `CONSTRUCT` | **`SparqlStoreError`**: 「クエリの応答が JSON として解釈できません」 |
| `DESCRIBE` | 同上 |

`FusekiStore.query` は `Accept: application/sparql-results+json` を送るが、
Fuseki はクエリの形に従って RDF(Turtle)を返すため JSON の解析に失敗する。

**`ensure_agent_safe_query` はこの 2 つを許している。** つまり
**ガードが通したクエリが 502 で落ちる。** エージェントから見ると「クエリが
悪い」のか「サーバが壊れている」のか区別がつかない。

## 決定

### 1. SPARQL のテキストを書き換えない

`LIMIT` を後付けする実装は採らない。

- 既存の `LIMIT` / `OFFSET`、副問い合わせ、`GROUP BY` / `ORDER BY` との
  相互作用で**意味が変わる**(外側に `LIMIT` を付けると集約の結果が変わる)
- **`CONSTRUCT` の `LIMIT` は解の数であってトリプル数ではない。**
  `DESCRIBE` は実装依存である
- **クエリを書き換える実装は、[ADR-0001](0001-rdf-store-selection.md) が
  名前空間の隔離で避けた「任意 SPARQL の書き換え」と同じ形**である。
  あちらはデータセット分離で回避した。ここも書き換えずに済ませる

### 2. 応答の行数を API の境界で数え、上限を超えたら切り詰める

`ontology_core.sparql.limits.cap_bindings(payload, limit)` が `SELECT` の
`results.bindings` を `limit` 件に切る。**元の払い出しを破壊しない**
(新しい辞書を返す)。

`ASK` は行の概念が無いので対象外である。**対象外であることをコードで明示する**
(`boolean` を持つ応答はそのまま返し、`truncated` は偽)。

### 3. 切り詰めたことを必ず見せる。黙って切らない

[ADR-0016](0016-semantic-diff.md) 決定5(空白ノードが多すぎて差分を計算
できなかった)、[ADR-0020](0020-health-metrics.md) 決定3(測れなかった指標)、
[ADR-0021](0021-owl-reasoning-in-ci.md) 決定1(推論の結論が不完全)、
[ADR-0022](0022-competency-question-sets.md) 決定5(評価しきれなかった質問)と
**同じ原則である。** 5 例目。

**切り詰めた結果を「全部です」として返すのは、この製品でいちばん避けたい形**
である — エージェントは「該当は 10,000 件で全部見た」と信じて回答を作る。

### 4. 伝え方は層で分ける([ADR-0017](0017-deprecation-lifecycle.md) 決定3 の再利用)

| 層 | 伝え方 | 理由 |
|---|---|---|
| Core API | **ヘッダ** `X-Ontology-Result-Truncated: true` と `X-Ontology-Result-Limit: <N>` | 本文は標準の SPARQL Results JSON のままにする(ADR-0001 の「SPARQL 1.1 Protocol をハード境界にする」) |
| MCP | **本文** の `result_truncated` / `result_limit` / `result_total_rows` | **エージェントはヘッダを見ない** |

ADR-0017 決定3 が廃止済み用語の警告でこの分岐を決めている。**同じ理由が同じ形で
当てはまるので、同じ形にする**(新しい流儀を増やさない)。

### 5. 上限を超えてもエラーにしない

413 や 422 で拒否する案は採らない。**エージェントは「全部は取れなかった」ことを
知ったうえで続けられるべき**である。拒否すると回答が作れない。

**上限は防御であって仕様の宣言ではない。** ただし決定3 のとおり、切り詰めたことを
知らせずに成功を返してはいけない。

### 6. アクセスログには切り詰める前の行数を記録する

`access_events.returned_row_count` には**ストアが返した行数**(切り詰め前)を
入れる。「エージェントに何行渡したか」ではなく「**何行返ろうとしたか**」を
記録する。

**上限に張り付いているクエリを見つけられるのは後者だけである。** 切り詰めたか
どうかは「行数 > 上限」で判定できるので、列は足さない(マイグレーションを
増やさない)。

### 7. `SPARQL_MAX_RESULTS` は 1 以上に限る

`Field(ge=1)` で検証する。0 や負の値は**設定の誤りとして起動時に落とす**。

「0 なら上限なし」という解釈を作らない — **この設定の目的は上限をかけること**
なので、0 を「無制限」と読む余地を残すのは、この ADR が直している問題
(効いていない設定)の別の形である。

### 8. `CONSTRUCT` / `DESCRIBE` はガードで拒否する

**502 ではなく 400 で、理由を添えて拒否する。** ガードが通したクエリが 502 で
落ちる状態は、エージェントに「サーバが壊れている」と誤解させる。

対応するには `FusekiStore.query` の内容交渉と戻り値の型(いまは `dict`)を
変える必要があり、トリプル数の上限という別の設計も要る。**`P2A-14` として
分離する。** それまでは「この経路は `SELECT` と `ASK` だけを受け付ける」と
明示的に言う。

## 検討した代替案

### `LIMIT` を注入する

**却下。** 決定1 の通り。**「上限 + 1 件だけ取ってくる」実装にすれば境界で
切るより安い**という利点は本物だが、意味を変えずに注入する方法が無い。

### 上限超過を 413 / 422 で拒否する

**却下。** 決定5。防御として単純で、「全部取れなかったのに気づかない」事故も
起きない。しかし**エージェントが回答を作れなくなる**。上限は「大きすぎる結果で
システムを壊さない」ためのもので、利用者の問いを否定するためのものではない。

### ストア側で止める

**できない**(実測)。将来 Fuseki が行数の上限に対応したら、**多層防御として
足す**(`arq:httpServiceAllowed` と `guards` の関係と同じ形で、権威ある制御を
ストア側に置く)。バックログに記録する。

### 応答をストリーミングして途中で切る

**却下(今は)。** ストアの応答全体を一度も受け取らずに済むので、**API の
メモリも守れる**唯一の案である。

却下理由: `SparqlStore.query` の契約が `dict` を返すことなので、ストリーミングに
するには抽象の契約(不変条件4)を変える必要がある。**上限の主目的は
「エージェントに渡す量」を抑えることで、それは境界の切り詰めで達成できる。**
API のメモリは守れないままである — これは受け入れるコストとして明記する。

### `CONSTRUCT` / `DESCRIBE` に対応する

**却下(`P2A-14` に分離)。** 内容交渉、戻り値の型、トリプル数の上限という
3 つの設計が要る。この ADR の範囲は「行数の上限を強制する」ことである。

## 結果(トレードオフ・影響)

### 受け入れるコスト

- **ストアの応答全体は一度受け取る。** 上限は「エージェントに渡す量」を抑える
  が、**API のメモリは守らない**。1,000 万行返すクエリは、切り詰める前に
  一度メモリに載る。時間の上限(`arq:queryTimeout` 30 秒)が事実上の防波堤で
  あり続ける
- **ストアの仕事は減らない。** ストア側に上限が無いので、無駄な計算は起きる
- **`CONSTRUCT` / `DESCRIBE` が使えないことが明示的になった**(決定8)。
  今までも動いていなかったが、エラーが 502 から 400 に変わる。**「使えるように
  見えて 502」よりはよいが、使えるようになったわけではない**
- **`SPARQL_MAX_RESULTS=0` を設定していた環境は起動しなくなる**(決定7)。
  そんな設定に意味は無いので、黙って無視するより落ちる方がよい

### 得られるもの

- **設定が実際に効く。** 「強制していない」を「強制している」と誤認させる状態が
  消えた(不変条件11 と同じ向きの判断)
- **切り詰めたことがエージェントに届く**(決定4)。ADR-0017 決定3 の形を
  再利用したので、流儀が増えていない
- **アクセスログで「上限に張り付いているクエリ」を見つけられる**(決定6)
- **ガードが通したクエリが 502 で落ちる状態が消えた**(決定8)

### 影響を受ける他の決定

- **不変条件11**(「強制していない」を「強制している」と誤認させない)—
  権限の話として書かれていたが、**設定全般に当てはまる**ことがここで確認された
- [ADR-0017](0017-deprecation-lifecycle.md) 決定3 — 層ごとに伝え方を分ける形を
  再利用した
- [ADR-0018](0018-context-access-log.md) — `returned_row_count` の意味を
  「ストアが返した行数」と確定させた(決定6)
- [ADR-0001](0001-rdf-store-selection.md) — 「任意 SPARQL を書き換えない」
  という方針をここでも守った
